패킷
HTTP 요청은 문자열 전송이 아니다

우리는 매일 requests.get(url) 한 줄을 쓴다. 그 한 줄 아래에서 문자열은 잘게 쪼개지고, 세 겹으로 포장되고, 각자 다른 길로 여행한 뒤 반대편에서 다시 조립된다. 그 단위가 패킷이다. 그리고 이 포장 방식의 한계가, 결국 HTTP를 TCP에서 UDP 위로 옮기게 만들었다(HTTP/3, 2022).

💬 "HTTP 요청은 단순한 문자열 전송이 아님. TCP vs UDP, QUIC은 왜 UDP 위에서 HTTP/3를 만들었을까?"

00requests.get() 한 줄의 착각

문자열이 "그대로" 날아간다고 생각하면 설명되지 않는 것들

Django 코드에서 외부 API를 부르는 흔한 한 줄이 있다.

resp = requests.get("https://api.example.com/v1/users")

겉보기에 이 코드는 GET /v1/users HTTP/1.1...이라는 문자열을 서버에 보내고 문자열을 돌려받는 일처럼 보인다. 하지만 문자열이 통째로 날아간다는 모델로는 설명할 수 없는 일들이 실무에서 매일 일어난다:

  • 왜 같은 요청인데 첫 요청만 유독 느린가? (연결 수립 비용)
  • 왜 응답 JSON이 중간에 잘려서 도착하는 법이 없는가? 네트워크는 분명 유실이 있는데?
  • 왜 VPN을 켜면 멀쩡하던 업로드가 특정 크기에서만 멈추는가? (MTU 문제)
  • 왜 구글은 잘 돌아가던 HTTP를 굳이 UDP 위에 다시 만들었는가?

네 가지 질문의 답은 전부 한 단어로 수렴한다. 패킷(packet) — 데이터가 네트워크를 여행하는 실제 단위다.

이 문서가 답하는 것

① HTTP "문자열"은 실제로 어떤 모습으로 전선을 타는가 ② TCP와 UDP는 무엇을 맞바꾼 선택지인가 ③ QUIC은 왜 TCP를 고치지 않고 UDP 위에 새로 지었는가. 다 읽으면 curl이 느린 이유를 계층 단위로 짚을 수 있게 된다.

01전화망을 버린 발명 — 패킷 교환

패킷은 기술이기 전에, 회선을 독점하지 않겠다는 설계 사상이다

1960년대까지 장거리 통신의 유일한 모델은 회선 교환(circuit switching)이었다. 전화를 걸면 나와 상대 사이에 물리적 경로 하나가 통화가 끝날 때까지 독점된다. 품질은 보장되지만, 침묵하는 순간에도 회선은 낭비되고, 경로 중 한 곳이 끊기면 통화 전체가 죽는다.

이를 뒤집은 것이 패킷 교환(packet switching)이다. 데이터를 작은 조각으로 잘라 각 조각에 목적지 주소를 붙이고, 조각마다 그때그때 가능한 경로로 독립적으로 보낸 뒤, 도착지에서 재조립한다. 회선을 독점하는 대신 모두가 같은 회선을 잘게 나눠 쓰는 방식이다.

  1. 1961–64폴 바란(Paul Baran), RAND 연구소공격에도 살아남는 분산 통신망 연구(On Distributed Communications). 메시지를 블록으로 나눠 여러 경로로 보내는 개념 제안
  2. 1965–66도널드 데이비스(Donald Davies), 영국 NPL같은 개념을 독립적으로 고안하고 "패킷"이라는 이름을 붙임
  3. 1969ARPANET 첫 메시지UCLA→스탠퍼드연구소(SRI). 패킷 교환 네트워크의 첫 실증 — 오늘날 인터넷의 직계 조상
  4. 1980–81UDP(RFC 768) · TCP(RFC 793) 표준화패킷 위에서 "어떤 약속으로 주고받을지"를 정한 두 전송 규약
  5. 2021–22QUIC(RFC 9000) · HTTP/3(RFC 9114)40년 만의 전송 계층 세대교체 — 이 문서의 종착지
📦 비유 — 전화 vs 택배

회선 교환은 전용 전화선이다: 통화 중엔 그 선이 온전히 내 것. 패킷 교환은 택배다: 이삿짐을 상자 여러 개에 나눠 담고 각 상자에 주소를 붙이면, 상자마다 다른 트럭·다른 고속도로를 타고 가도 결국 같은 집에 도착한다. 트럭 하나가 막혀도 이사 전체가 멈추지 않는다.

✅ 실무 감각

이 사상 덕분에 순서 뒤바뀜과 유실은 버그가 아니라 전제다. 패킷들은 서로 다른 경로로 여행하므로 늦게 출발한 놈이 먼저 도착할 수 있고, 중간 라우터가 혼잡하면 조용히 버려진다(drop). "네트워크는 원래 불안정하다"가 아니라, 불안정을 허용하는 대신 값싸고 튼튼해지는 쪽을 선택한 것이다. 그 위에 신뢰성을 다시 쌓는 일은 다음 계층(TCP)의 몫이 된다.

02패킷 해부 — 세 겹의 포장지

HTTP 문자열은 잘리고, 세 번 포장되어 전선을 탄다

이제 requests.get()의 문자열이 실제로 어떤 모습이 되는지 보자. 애플리케이션이 쓴 데이터는 아래로 내려가며 계층마다 헤더(header) — 그 계층이 일하는 데 필요한 메타데이터 — 를 앞에 덧붙인다. 이 과정을 캡슐화(encapsulation)라 부른다.

애플리케이션 "GET /v1/users HTTP/1.1\r\nHost: ..." ← HTTP 메시지 (문자열) │ 잘라서 ▼ 전송 계층 ┌─────────┬──────────────┐ (TCP/UDP) │ TCP 헤더 │ 데이터 조각 │ ← 세그먼트 (포트·순서번호) └─────────┴──────────────┘ ▼ 인터넷 계층 ┌────────┬─────────┬──────────────┐ (IP) │ IP 헤더 │ TCP 헤더 │ 데이터 조각 │ ← IP 패킷 (IP 주소) └────────┴─────────┴──────────────┘ ▼ 링크 계층 ┌──────────┬────────┬─────────┬──────────┐ (Ethernet) │ ETH 헤더 │ IP 헤더 │ TCP 헤더 │ 데이터 │ ← 프레임 (MAC 주소 = 바로 다음 장비까지의 주소) └──────────┴────────┴─────────┴──────────┘ ▼ 010110... 전기 신호 / 전파 / 빛
📎 용어: 세그먼트 · 패킷 · 프레임

엄밀히는 계층마다 이름이 다르다 — TCP 조각은 세그먼트(segment), IP 조각은 패킷(packet), 이더넷 조각은 프레임(frame). 일상 대화에선 전부 뭉뚱그려 "패킷"이라 부르며, 이 문서도 구분이 필요한 곳 외엔 그렇게 쓴다.

왜 자르는가 — MTU 1,500바이트

포장 한 상자에 담을 수 있는 크기엔 상한이 있다. 이더넷 표준에서 프레임 하나에 실을 수 있는 IP 패킷의 최대 크기, 즉 MTU(Maximum Transmission Unit)는 관례적으로 1,500바이트다. 여기서 IP 헤더 20바이트와 TCP 헤더 20바이트(옵션 없을 때 기준)를 빼면, 패킷 하나에 실리는 실제 데이터는 최대 1,460바이트(MSS, Maximum Segment Size)다.

즉 100KB짜리 JSON 응답은 약 70개의 패킷으로 잘려 도착한다. "응답을 받았다"는 한 문장 뒤에는 70번의 독립적인 배달이 숨어 있는 것이다.

⚠️ 흔한 오해 — "패킷은 네트워크가 알아서 해주는 것"

대체로 맞지만, 경계가 새는 순간이 있다. VPN·터널은 패킷을 한 번 더 포장하므로 실효 MTU가 1,500보다 작아진다(예: 1,400대). 이때 큰 패킷이 조용히 버려지면 "작은 요청은 되는데 큰 업로드만 멈추는" 괴상한 증상이 된다. ping은 되는데 파일 업로드만 안 되면 MTU를 의심하라 — 애플리케이션 로그엔 아무것도 남지 않는 계층의 문제다.

03UDP — 최소한의 약속

"IP 패킷에 포트 번호만 얹었습니다"

패킷을 받았다 치자. 이 컴퓨터에서 돌아가는 수십 개 프로세스 중 누구에게 전달할 것인가? IP 주소는 컴퓨터까지만 데려다준다. 프로세스를 구분하는 번호가 포트(port)이고, 이걸 붙여주는 최소한의 규약이 UDP(User Datagram Protocol, RFC 768 · 1980)다.

UDP의 헤더는 8바이트가 전부다: 출발 포트, 도착 포트, 길이, 체크섬(전송 중 깨졌는지 검산하는 값). 끝. 연결 개념도, 도착 확인도, 순서 보장도, 재전송도 없다. 패킷 교환망의 성질(유실·순서 뒤바뀜)이 그대로 애플리케이션에 노출된다.

# UDP 전송의 전부 — 연결 수립 없이 즉시 발사
import socket
sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)   # DGRAM = UDP
sock.sendto(b"ping", ("10.0.0.5", 9999))
# 도착했는지는 아무도 모른다. 그게 사양이다.

이 "무책임함"은 결함이 아니라 용도에 맞는 선택지다. 화상통화에서 0.5초 전 프레임이 유실됐다면, 재전송받아 늦게 보여주는 것보다 버리고 다음 프레임을 보여주는 게 낫다. DNS 질의처럼 한 패킷에 담기는 요청-응답이라면 연결 수립 자체가 낭비다. 게임·화상통화(WebRTC)·DNS가 UDP를 쓰는 이유다.

📎 용어: 데이터그램(datagram)

UDP가 보내는 독립적인 메시지 한 덩어리. TCP가 데이터를 경계 없는 바이트 스트림으로 다루는 것과 달리, UDP는 sendto() 한 번 = 데이터그램 한 개 = (충분히 작다면) 패킷 한 개로, 메시지 경계가 보존된다.

04TCP — 신뢰성의 가격표

불안정한 패킷망 위에 "믿을 수 있는 바이트 스트림"이라는 환상을 짓는다

반면 HTTP·데이터베이스·이메일은 단 1바이트도 잃어버리면 안 된다. JSON 중간이 유실된 채 파싱할 수는 없다. TCP(Transmission Control Protocol, RFC 793 · 1981)는 유실되고 뒤섞이는 패킷망 위에, 다음 세 가지 장치로 "빠짐없고 순서 맞는 바이트 스트림"을 지어 올린다:

  1. 연결 수립 — 3-way 핸드셰이크보내기 전에 SYN(synchronize, 접속 개시 신호) → SYN-ACK → ACK 세 번의 메시지를 주고받는(왕복 1회) 절차로 서로의 존재와 시작 순서번호를 합의한다. 이 비용이 "첫 요청만 느린" 이유의 절반이다 — 나머지 절반은 TLS(HTTPS의 's'를 담당하는 암호화 규약. 암호화 키를 합의하는 자체 핸드셰이크가 TCP 핸드셰이크 뒤에 한 번 더 필요하다) 핸드셰이크다.
  2. 순서번호 + 확인응답(ACK) + 재전송모든 바이트에 일련번호를 붙이고, 받는 쪽은 어디까지 받았는지 응답(ACK)한다. 응답이 없으면 유실로 판단하고 다시 보낸다. 우리가 "응답이 중간에 잘린 걸 본 적 없는" 이유다.
  3. 흐름·혼잡 제어상대와 네트워크가 소화할 수 있는 만큼만 보내도록 전송 속도를 조절한다. 유실이 감지되면 "네트워크가 혼잡하다"는 신호로 읽고 스스로 속도를 줄인다.

⚙️ TCP — 등기 소포

연결 지향 · 신뢰성 보장 · 바이트 스트림

  • 순서 보장, 유실 시 재전송
  • 연결 수립 비용(핸드셰이크) 선불
  • HTTP/1.1·HTTP/2, DB, SSH, 이메일
  • 커널(OS의 핵심부)이 구현 — 앱은 소켓을 SOCK_STREAM(TCP)으로 여는 것까지만 관여

🔍 UDP — 엽서

비연결 · 무보장 · 메시지(데이터그램) 단위

  • 즉시 발사, 도착·순서 보장 없음
  • 헤더 8바이트, 오버헤드 최소
  • DNS, 화상통화, 게임, 그리고 QUIC
  • 신뢰성이 필요하면 앱이 직접 만든다
⚠️ 핵심 통찰 — TCP와 UDP는 우열이 아니라 트레이드오프다

TCP는 신뢰성을 지연(latency)으로 지불한다: 핸드셰이크 왕복, ACK 대기, 유실 시 재전송 대기. UDP는 지연을 아끼는 대신 신뢰성을 애플리케이션의 숙제로 떠넘긴다. "TCP가 더 좋은 프로토콜"이 아니라, 무엇을 포기할지 고른 두 선택지다. 이 관점이 서야 "QUIC이 UDP 위"라는 문장이 이상하게 들리지 않는다.

05HTTP는 그 위에 산다

HTTP의 역사는 "TCP 연결을 어떻게 아껴 쓸까"의 역사였다

HTTP는 스스로 패킷을 다루지 않는다. TCP가 제공하는 "믿을 수 있는 바이트 스트림"이라는 배관 위에 요청-응답이라는 대화 형식만 얹은 규약이다. 그래서 HTTP의 진화사는 곧 비싼 TCP 연결을 아껴 쓰는 기법의 진화사다:

세대연결 사용 방식남은 문제
HTTP/1.0 (1996)요청 1개마다 TCP 연결을 새로 맺고 끊음핸드셰이크 비용 × 요청 수
HTTP/1.1 (1997)keep-alive — 연결 하나를 재사용, 단 요청은 한 번에 하나씩 순서대로앞 응답이 끝나야 다음 요청 (HTTP 계층 줄서기)
HTTP/2 (2015)멀티플렉싱 — 연결 하나에 여러 요청·응답 스트림을 동시에 섞어 보냄TCP 계층의 줄서기가 남는다 → 다음 섹션

브라우저가 페이지 하나를 그리는 데 요청 수십 개가 필요해지자, HTTP/2는 연결 하나에 스트림 여러 개를 겹쳐 보내는 멀티플렉싱(multiplexing)으로 대응했다. HTML·CSS·이미지 요청이 한 TCP 연결 위에서 동시에 흐른다. HTTP 계층의 줄서기는 이걸로 풀렸다 — 그런데 여기서 더 깊은 계층의 문제가 드러난다.

✅ 실무 감각 — 핸드셰이크 비용은 코드 한 줄 차이다

외부 API를 반복 호출하는 Django 서비스에서 requests.get()을 매번 새로 부르면 호출마다 TCP+TLS 핸드셰이크를 다시 지불한다. requests.Session()을 재사용하면 keep-alive로 연결이 유지된다:

# ❌ 호출마다 TCP+TLS 핸드셰이크 (왕복 2~3회씩 낭비)
for user_id in user_ids:
    requests.get(f"https://api.example.com/users/{user_id}")

# ✅ 연결 재사용 — 핸드셰이크는 처음 한 번만
session = requests.Session()
for user_id in user_ids:
    session.get(f"https://api.example.com/users/{user_id}")

06TCP의 유리천장 — HOL 블로킹

HTTP/2가 아무리 영리해도 뚫을 수 없는 한 층 아래의 벽

HOL 블로킹(Head-of-Line blocking, 줄 맨 앞 막힘) = 줄 맨 앞의 하나가 막히면 뒤 전체가 기다리는 현상. 문제는 TCP의 가장 큰 장점이 이 현상을 만든다는 것이다.

TCP는 "빠짐없이, 순서대로"를 약속했다. 그래서 패킷 하나가 유실되면, 그 뒤에 이미 도착해 있는 패킷들도 커널 버퍼에서 대기한다. 재전송된 패킷이 도착해 구멍이 메워지기 전까지, 커널은 애플리케이션에 한 바이트도 올려보내지 않는다 — 순서를 어길 수 없기 때문이다.

HTTP/2에서 이게 치명적인 이유: 멀티플렉싱으로 여러 스트림이 한 TCP 연결에 타고 있는데, TCP는 스트림 개념을 모른다. TCP가 보기엔 전부 하나의 바이트 스트림이다. 그래서 CSS 스트림의 패킷 하나가 유실되면, 멀쩡히 도착한 이미지·HTML 스트림까지 전부 함께 멈춘다.

한 TCP 연결에 스트림 3개 (HTTP/2 멀티플렉싱) 전송: [CSS#1] [IMG#1] [HTML#1] [CSS#2] [IMG#2] ... ✕ 유실! 수신 버퍼: [CSS#1] [ 구멍 ] [HTML#1] [CSS#2] [IMG#2] ▲ TCP: "IMG#1이 올 때까지 아무것도 못 올려보냄" → 이미 도착한 HTML#1, CSS#2 도 전부 대기 → 스트림 3개가 전부 멈춤 (연대책임)
⚠️ 핵심 통찰 — 문제는 HTTP가 아니라 TCP에 있었다

HTTP/2는 HTTP 계층의 줄서기를 없앴지만, TCP 계층의 줄서기는 HTTP가 어떻게 해볼 수 없다. 순서 보장은 TCP의 정체성이고, 그 구현은 커널 안에 있다. 실제로 패킷 유실이 잦은 환경에서는 HTTP/2 연결 하나가 HTTP/1.1 연결 여러 개(브라우저는 보통 도메인당 최대 6개를 병렬로 연다)보다 느려지는 역전이 관측된다 — 유실 하나의 피해 범위가 연결 전체이기 때문이다. 이 벽을 넘으려면 HTTP가 아니라 전송 계층을 갈아야 한다.

07QUIC — 왜 하필 UDP 위인가

관통 질문의 답 — 40년 묵은 전송 계층을 교체하는 유일하게 가능한 경로

2012년 구글의 짐 로스킨드(Jim Roskind)가 설계한 QUIC은 2013년 공개되고 2015년 IETF(인터넷 표준화 기구)에 제출되어, 2021년 5월 RFC 9000으로 표준이 됐다. 그리고 2022년 6월, QUIC 위에서 동작하는 HTTP가 HTTP/3(RFC 9114)로 표준화됐다. 그런데 왜 TCP를 개선하지 않고 UDP 위에 새로 만들었을까? 이유는 두 겹이다.

이유 1 — TCP는 사실상 수정 불가능하다 (경화, ossification)

TCP를 고치는 게 정공법 아닌가? 시도는 있었다. 그러나 두 개의 벽이 있다:

  • TCP는 커널 안에 산다. TCP 동작을 바꾸려면 전 세계 서버·PC·폰의 OS 커널이 업데이트되어야 한다. 수년~수십 년 단위의 일이다.
  • 중간 장비들이 TCP를 뜯어본다. 인터넷 곳곳의 방화벽·NAT(사설 IP↔공인 IP를 바꿔치기하는 공유기·게이트웨이 장비)·로드밸런서(통칭 미들박스)는 TCP 헤더를 읽고 참견하도록 만들어져 있어, TCP에 새 기능을 넣으면 낯선 패킷을 버리거나 망가뜨린다. 실제로 TCP도 UDP도 아닌 새 전송 프로토콜(SCTP 등)은 미들박스들이 통과시켜주지 않아 보급에 실패했다. 프로토콜이 굳어 바꿀 수 없게 된 이 상태를 경화(ossification)라 부른다.

남은 선택지가 UDP다. UDP는 (거의) 모든 미들박스가 통과시켜 주고, 아무 약속도 하지 않는 빈 종이라서 그 위에 무엇이든 새로 지을 수 있다. QUIC은 TCP가 커널에서 하던 일 — 연결, 순서, 재전송, 혼잡 제어 — 을 전부 유저스페이스(애플리케이션/라이브러리 레벨)에서 다시 구현했다. 커널 업데이트 없이 브라우저 배포만으로 프로토콜을 진화시킬 수 있게 된 것이다. 나아가 QUIC은 헤더 대부분을 암호화해 미들박스가 아예 뜯어볼 수 없게 만들었다 — 미래의 경화까지 차단한 설계다.

🏗️ 비유 — 리모델링 불가 건물

TCP는 세입자(미들박스)들이 벽 구조에 맞춰 살림을 짜놓은 40년 된 건물이라 기둥 하나 옮길 수 없다. UDP는 옆의 빈 땅이다. QUIC은 그 빈 땅에 새 건물을 짓고 창문을 전부 불투명하게(암호화) 만들어, 앞으로는 누구도 벽 구조에 의존하지 못하게 했다.

이유 2 — 새로 짓는 김에 TCP의 구조적 한계를 해결

TCP + TLS의 문제QUIC의 해법
HOL 블로킹 — 유실 하나에 모든 스트림 연대책임스트림을 전송 계층이 직접 안다. 스트림별로 독립 전달 — CSS 패킷이 유실돼도 그 스트림만 기다리고 이미지·HTML은 계속 흐른다
연결 비용 — TCP 핸드셰이크 1왕복 + TLS 1.3 핸드셰이크 1왕복 = 첫 데이터까지 2왕복 (TLS 1.3의 재방문 단축을 써도 TCP의 1왕복은 남는다)전송과 암호화(TLS 1.3 내장) 핸드셰이크를 한 번에 — 1왕복. 한 번 만난 서버엔 0-RTT(왕복 없이 첫 패킷에 요청 동봉 — 재전송 공격(replay) 위험이 있어 GET 같은 멱등 요청에만 허용)도 가능
연결 = 양끝의 (IP, 포트) 네 값(4-튜플) — Wi-Fi에서 LTE로 바뀌면 내 IP가 바뀌므로 연결이 끊기고 처음부터 다시연결을 연결 ID(Connection ID)로 식별 — 네트워크가 바뀌어도 같은 연결이 이어진다 (connection migration)
첫 데이터를 보내기까지의 왕복 (RTT) TCP+TLS1.3 : [TCP 핸드셰이크]──▶ [TLS 핸드셰이크]──▶ [HTTP 요청] = 2 RTT QUIC : [QUIC 핸드셰이크(TLS 내장)]──▶ [HTTP 요청] = 1 RTT QUIC 재방문: [핸드셰이크 + HTTP 요청 동봉] = 0 RTT RTT 100ms 환경이면 첫 바이트까지 200ms → 100ms → ~0ms
⚠️ 흔한 오해 — "QUIC = UDP니까 신뢰성이 없다"

반대다. QUIC은 UDP를 배달 트럭으로만 쓰고, 그 위에서 순서·재전송·혼잡 제어·암호화를 전부 자체 구현한다. 신뢰성은 TCP와 동급이고, 스트림 독립성·핸드셰이크·연결 이동성은 그 이상이다. "UDP 위"는 무책임함의 계승이 아니라 배포 가능한 유일한 통로였을 뿐이다.

08우리 스택에서 패킷 보기

추상적 계층 이야기를 nginx·Django·디버깅 현장으로 내리기

지금 우리 요청은 어느 세대인가

브라우저 개발자도구 Network 탭에서 Protocol 열을 켜보면 (h2 = HTTP/2, h3 = HTTP/3) 지금도 확인할 수 있다. 전형적인 Django 서비스라면:

  • 브라우저 ↔ CDN/로드밸런서 — CDN(Cloudflare, CloudFront 등)이 HTTP/3를 지원하면 이 구간은 이미 QUIC일 수 있다. nginx도 1.25부터 HTTP/3를 지원한다.
  • nginx ↔ gunicorn ↔ Django — 이 구간은 여전히 HTTP/1.1 over TCP(또는 유닉스 소켓)다. HTTP/3의 이득은 유실·지연이 많은 사용자 쪽 마지막 구간에서 크므로, 내부 구간까지 바꿀 실익은 적다 — 사용자 구간은 무선(Wi-Fi·LTE)이라 유실이 잦고 이동 중 네트워크가 바뀌지만, 내부 구간은 같은 데이터센터의 안정된 유선이라 TCP의 약점이 드러날 일이 거의 없기 때문이다.

즉 "우리 서비스에 HTTP/3 적용"은 대부분 엣지(CDN/nginx) 설정 문제지 Django 코드의 문제가 아니다 — HTTP는 어느 배관 위에서든 같은 대화 형식이기 때문이다.

계층 이야기가 실감나지 않으면 한 번쯤 직접 잡아보라. 서버에서 tcpdump로 80/443 포트를 캡처하면 이 문서의 그림이 그대로 보인다:

✅ 실무 감각 — 계층으로 나눠서 의심하라

"API가 느리다/안 된다"는 제보를 받으면 계층 사다리를 위에서부터 내려가라: ① HTTP 계층(상태코드·앱 로그·gunicorn 타임아웃) → ② 전송 계층(핸드셰이크는 되나? curl -v로 connect 시간과 TLS 시간 분리) → ③ 그 아래(DNS, MTU, 방화벽이 특정 포트를 버리는가). 대부분은 ①에서 끝나지만, ①의 로그에 아무것도 없는 미스터리는 거의 항상 ②·③의 문제다.

09한 장 요약 치트시트

Q. HTTP 요청은 단순한 문자열 전송이 아니다?

맞다 — 문자열은 최대 1,460바이트 조각으로 잘리고, TCP·IP·이더넷 세 겹 헤더로 포장되어, 각자 독립적으로 여행한 뒤 반대편에서 재조립된다. 유실·순서 뒤바뀜은 패킷 교환망의 전제이고, 이를 숨겨 "온전한 문자열이 도착한 것처럼" 보이게 만드는 장치(순서번호·ACK·재전송)가 TCP다. 그 편의는 핸드셰이크 왕복과 대기라는 지연으로 지불한다.

Q. TCP vs UDP — 무엇의 트레이드오프인가?

TCP는 신뢰성을 지연으로 지불하고, UDP는 지연을 아끼는 대신 신뢰성을 애플리케이션의 숙제로 떠넘긴다. 우열이 아니라 무엇을 포기할지 고른 두 선택지다. QUIC은 UDP 쪽을 골라 그 숙제를 직접 푼 경우다.

Q. QUIC은 왜 UDP 위에서 HTTP/3를 만들었나?

TCP는 커널과 미들박스에 박혀 굳어버려(경화) 사실상 수정이 불가능했고, UDP는 어디서나 통과되는 빈 종이였기 때문이다. QUIC은 UDP를 배달 트럭으로만 쓰고 그 위에 신뢰성·TLS 1.3·스트림을 유저스페이스에서 새로 구현했다. 덕분에 TCP의 구조적 한계였던 HOL 블로킹(유실 하나에 전체 스트림 연대책임)을 스트림별 독립 전달로 풀고, 첫 데이터까지의 왕복을 2 RTT → 1 RTT(재방문 0 RTT)로 줄였다.
