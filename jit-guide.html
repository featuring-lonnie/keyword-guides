00질문의 전제부터 뒤집기

"인터프리터 언어"라는 말은 반쯤 틀렸다

질문에는 숨은 전제가 두 개 있다. 하나는 "언어는 인터프리터 방식이거나 컴파일 방식이다", 다른 하나는 "컴파일하면 기계어가 나온다". 둘 다 정확하지 않다.

파이썬은 언어, 즉 문법과 의미 규칙이다. 그 규칙대로 코드를 실제로 돌리는 프로그램을 구현(implementation)이라고 부른다. 우리가 python이라고 치면 뜨는 것은 C로 짠 구현인 CPython이고, 같은 파이썬 코드를 전혀 다른 방식으로 돌리는 PyPy 같은 구현도 있다. 인터프리트할지 컴파일할지는 언어가 아니라 구현이 고르는 전략이다.

짧은 답부터 말하면, CPython은 소스를 실행하기 좋은 일렬 명령인 바이트코드로 한 번 컴파일해 두고(결과는 .pyc로 재사용), 그 바이트코드를 인터프리트한다. 기계어까지는 만들지 않기 때문에 여전히 "인터프리터"라고 불린다.

이 문서가 답하는 것

① CPython은 기계어 대신 바이트코드를 택하면서 무엇을 얻고 무엇을 버렸나 ② 그 대가를 줄이려고 3.11 특화 인터프리터와 3.13 JIT는 각각 무엇을 우선했고, 그 결과 어떤 개념이 생겼나 ③ Django 서비스에서는 실제로 무엇이 달라지나. 다 읽으면 __pycache__와 PYTHON_JIT=1이 한 줄기 이야기의 양 끝이라는 게 보인다.

01실행 전략 세 가지와 그 대가

어떤 전략이든 무언가를 우선하고 무언가를 버린다

📎 용어: 컴파일(compile)

컴파일 = 코드를 실행하는 일과는 분리된 번역 작업으로 다른 표현으로 바꾸는 것. 번역을 실행 전에 끝내 두는 게 보통이지만, 실행 도중에 틈틈이 번역하는 방식(JIT)도 있다. 목적지가 꼭 기계어일 필요도 없다. TypeScript → JavaScript도 컴파일이다.

📎 용어: 인터프리트(interpret)

인터프리트 = 명령을 기계어로 바꾸지 않고, 이미 기계어로 만들어진 프로그램(인터프리터)이 명령을 하나씩 읽어 그 자리에서 대신 실행하는 것. 인터프리터가 읽는 명령은 소스 텍스트일 수도, 미리 번역해 둔 중간 형태일 수도 있다.

📎 용어: 기계어 · 바이트코드 · 가상 머신

기계어는 CPU가 직접 실행하는 명령이다. CPU 계열마다 다르다 — 대부분의 인텔 · AMD 서버는 x86-64, 애플 M 칩과 AWS Graviton은 AArch64(ARM 64비트)다. 바이트코드는 실제 CPU가 아니라 소프트웨어로 만든 가상의 CPU를 위한 명령이고, 그 가상 CPU를 가상 머신(VM)이라고 부른다. CPython 안에는 파이썬 바이트코드용 VM이 들어 있다. Java의 JVM(Java 가상 머신)도 같은 구조다.

전략우선한 것버린 것
AOT 컴파일
(Ahead-Of-Time)
C, Go, Rust		실행 속도 — 실행 전에 기계어를 전부 만들어 둔다실행 중에만 알 수 있는 정보 활용, CPU · OS별 빌드, 고칠 때마다 빌드 대기
인터프리트이식성 · 즉시 실행 — 인터프리터만 있으면 어디서나 바로 돈다실행 속도 — 명령마다 해석하는 비용을 낸다
JIT 컴파일

V8은 Chrome과 Node.js의 JavaScript 엔진이다. 표의 세 줄은 뒤에서 하나씩 풀어 간다. CPython의 출발점은 두 번째 줄이다.

02선택 ① 바이트코드 VM — 기계어 대신 얻은 것

import 한 줄 안에서 일어나는 네 단계

import shop 한 줄이 실행될 때 CPython 안에서 일어나는 일을 따라가 보자.

shop.py (텍스트) │ ① 토큰화: 글자를 단어(토큰) 단위로 자른다 │ ② 파싱: 토큰을 문법 구조로 조립한다 ▼ AST (추상 구문 트리) ← 코드 구조를 나무 모양으로 표현 │ ③ 컴파일: 나무를 일렬로 놓인 명령으로 편다 ▼ code object (바이트코드) ──▶ __pycache__/shop.cpython-314.pyc 로 저장 │ ④ 실행 ▼ 평가 루프 (ceval) ← C로 짠 반복문 (개념상) 반복: 명령 하나 꺼내기 → 무슨 명령인지 확인 → 해당 C 코드 실행
📎 용어: code object · ceval

code object는 함수나 모듈 하나를 컴파일한 결과물이다. 바이트코드와, 그 바이트코드가 쓰는 상수 · 변수 이름을 함께 담는다. 함수라면 total.__code__로 직접 볼 수 있다. ceval은 이 평가 루프가 들어 있는 CPython 소스 파일 ceval.c에서 온 이름이다.

왜 AST에서 멈추지 않고 한 번 더 펴나

AST를 그대로 따라가며 실행하는 인터프리터도 만들 수 있고, 만들기는 오히려 그쪽이 더 단순하다. 하지만 실행할 때마다 노드마다 자식을 찾아 내려갔다가 결과를 들고 올라오는 일을 반복해야 한다. 바이트코드는 같은 일을 일렬로 놓인 작은 명령으로 펴 둔 것이라, 인터프리터 루프는 "다음 명령을 꺼내 실행한다"만 반복하면 되고 일반적으로 더 빠르다. 대신 나무를 명령으로 펴는 컴파일 단계가 하나 더 생긴다.

그 컴파일 결과를 .pyc로 저장해 두면, 다음 import 때는 ①~③을 통째로 건너뛴다. 공식 튜토리얼도 .pyc는 더 빨리 실행되는 게 아니라 더 빨리 로드될 뿐이라고 설명한다(의역).

🎯 우선한 것

  • 루프 속도 — 나무를 오르내리는 대신 일렬 명령을 차례로 꺼낸다 (AST를 바로 실행하는 것보다)
  • 이식성 — CPU별 기계어 생성기가 없다. C 컴파일러만 있으면 어느 CPU에서나 같은 인터프리터가 돈다 (기계어로 컴파일하는 것보다)
  • 내부를 바꿀 자유 — 바이트코드는 공개 약속이 아니라 CPython 내부 구현이다

🗑️ 버린 것

  • 명령 사이를 오가는 비용 — CPU가 아니라 C로 짠 루프가 명령을 하나씩 꺼내 실행한다 (03장 1번)
  • 컴파일 단계 하나 — 나무를 명령으로 펴는 시간. .pyc로 만회한다
  • 버전 간 호환 — 버전이 다르면 바이트코드도, .pyc도 다르다

이 선택에서 생긴 개념이 바이트코드, code object, VM 스택, .pyc다. 하나씩 눈으로 확인해 보자.

바이트코드를 눈으로 보기

📎 용어: VM 스택

바이트코드 VM이 계산 중간값을 쌓아 두는 임시 선반. 명령은 선반 맨 위에서 값을 꺼내 쓰고, 결과를 다시 맨 위에 올린다. 덧셈 명령은 맨 위 두 값을 꺼내 더하고 결과 하나를 올린다. 함수 호출 기록을 쌓는 콜 스택과는 다른 것이다.

shop.py

def total(prices):
    s = 0
    for p in prices:
        s = s + p
    return s

dis.dis(total) — CPython 3.14 출력 (함수 시작 · 반복 종료부 생략)

  2   LOAD_SMALL_INT      0
      STORE_FAST          1 (s)
  3   LOAD_FAST_BORROW    0 (prices)
      GET_ITER
  L1: FOR_ITER           11 (to L2)
      STORE_FAST          2 (p)
  4   LOAD_FAST_BORROW_LOAD_FAST_BORROW 18 (s, p)
      BINARY_OP           0 (+)
      STORE_FAST          1 (s)
      JUMP_BACKWARD      13 (to L1)
📎 dis 출력 읽는 법

dis(disassembler)는 code object 안의 바이트코드를 사람이 읽을 수 있게 풀어 주는 표준 라이브러리다. 왼쪽 숫자는 소스 줄 번호, 가운데는 명령 이름, 오른쪽 숫자는 명령에 붙는 인자, 괄호는 그 인자를 사람이 읽기 좋게 풀어 쓴 것(변수 이름, 점프할 위치)이다. L1:은 점프 목적지 표시이고, L2는 생략한 반복 종료부에 있다.

이름의 _BORROW는 3.14에서 생긴 내부 최적화 변형이라 "변수 값을 올린다"로 읽으면 된다. LOAD_FAST_BORROW_LOAD_FAST_BORROW 18은 변수 두 개를 올리는 명령 둘을 하나로 합친 것(슈퍼명령어)이고, 18은 변수 번호 1(s)과 2(p)를 한 숫자에 담은 값이다.

소스바이트코드하는 일
s = 0LOAD_SMALL_INT → STORE_FAST0을 스택에 올리고, 꺼내서 s에 저장
for p in prices:GET_ITER → FOR_ITER → STORE_FAST리스트에서 반복자를 만들고, 다음 값을 꺼내 p에 저장. 값이 없으면 루프 끝(L2)으로
s = s + pLOAD_FAST… → BINARY_OP → STORE_FASTs와 p를 스택에 올리고, 두 값을 꺼내 더한 결과를 올린 뒤, 그 결과를 s에 저장
(루프 한 바퀴 끝)JUMP_BACKWARDL1로 돌아가 다음 값을 꺼낸다

CPython이 만든 "컴파일 결과"는 이 명령들이다. CPU는 이 명령을 모른다. ceval 루프가 하나씩 읽어서 해당하는 C 코드를 대신 실행한다. 컴파일을 하는데도 인터프리터라고 불리는 이유가 이것이다.

⚠️ 바이트코드는 버전마다 다르다

같은 함수를 3.12에서 보면 0을 LOAD_CONST로 올리고, s와 p도 LOAD_FAST 두 번으로 따로 올린다. 바이트코드는 CPython 내부 구현이라 버전 사이 호환을 약속하지 않는다. 그 자유 덕분에 06장의 특화 같은 개선을 버전마다 넣을 수 있었다.

.pyc와 __pycache__ — 컴파일 결과를 버리지 않기

import한 모듈의 code object는 소스 옆 __pycache__/ 폴더에 모듈명.구현-버전.pyc 형태로 캐시된다. 파일 이름에 cpython-314 같은 버전 태그가 붙는 이유가 바로 위의 호환 문제다.

.pyc 앞부분 헤더에는 바이트코드 형식 번호(magic number) · 플래그 · 원본 소스의 수정 시각 · 원본 소스의 크기가 기록된다. 기본 방식에서는 다음 import 때 형식 번호 · 수정 시각 · 크기 중 하나라도 다르면 캐시를 버리고 다시 컴파일한다. 코드를 고치면 자동으로 반영되는 이유다. (소스 내용의 해시로 검사하는 방식을 고를 수도 있는데, 그때는 규칙이 다르다.)

✅ 직접 확인해볼 것

python main.py로 실행하면 main.py의 .pyc는 생기지 않고, main.py가 import한 모듈의 것만 생긴다. 캐시를 확인하고 저장하는 일은 import가 맡는데, 명령줄에서 직접 실행한 파일은 import되는 게 아니라 __main__으로 바로 실행되기 때문이다. 공식 튜토리얼도 명령줄에서 직접 불러온 모듈은 항상 다시 컴파일하고 결과를 저장하지 않는다고 적는다(의역). Django에서 manage.py의 .pyc가 없는 이유다.

03대가 — 인터프리터는 어디서 시간을 쓰나

덧셈 한 번에 인터프리터가 하는 네 가지 일

02장에서 버린 것의 청구서가 여기서 나온다. 다만 비용 전부가 바이트코드 탓은 아니다. 먼저 파이썬 언어 자체의 성질 하나를 짚자.

📎 용어: 동적 타입(dynamic typing)

변수의 타입이 코드에 고정되지 않고 실행 중 값에 따라 정해지는 방식. x = 1 다음 줄에 x = "a"를 써도 된다. 이건 실행 전략이 아니라 파이썬 언어의 성질이라, 어떤 구현이든 "지금 이 값이 뭐지?"를 알아내는 문제를 풀어야 한다.

타입을 가리지 않는 일반 덧셈 명령 BINARY_OP (+) 하나를 실행할 때 인터프리터 루프가 하는 일은 이렇다. 3.10까지는 int 덧셈도 늘 이런 일반 경로를 탔다.

  1. 디스패치 ← 바이트코드 VM을 택한 대가다음 명령을 꺼내 무슨 명령인지 보고, 해당 C 코드로 점프한다. 덧셈 하나처럼 명령이 하는 실제 일이 작을수록, 이 오가는 비용의 비중이 커진다.
  2. 타입 확인 ← 동적 타입s와 p가 int인지, float인지, str인지 실행 시점에 확인한다.
  3. 연산 찾기 ← 동적 타입그 타입에 맞는 덧셈 구현(int라면 int의 덧셈 C 함수, 사용자 클래스라면 __add__)을 찾아 호출한다.
  4. 객체 관리 ← 모든 값이 객체인 설계결과 int는 (−5 ~ 256의 미리 만들어 둔 작은 정수를 벗어나면) 힙에 새로 만들고, 참조 카운트를 올리고 내린다.
📎 용어: 힙 · 참조 카운트

힙 = 프로그램이 실행 중 필요할 때 떼어 쓰는 메모리 영역. 참조 카운트 = 이 객체를 가리키는 곳의 수. CPython은 이 숫자가 0이 되는 순간 객체를 해제하기 때문에, 값을 옮기고 버릴 때마다 이 숫자를 부지런히 고친다.

C 컴파일러가 int 두 개의 덧셈을 만나면 CPU 명령 몇 개로 끝낸다. C는 타입이 코드에 고정된 언어라 2 · 3번이 필요 없고, 값이 객체가 아니라 4번도 없고, 명령들이 이미 이어진 기계어라 1번도 없다.

⚠️ 핵심 통찰

네 가지 중 1번만 바이트코드를 택한 대가이고, 2~4번은 파이썬이 동적 타입이고 모든 값이 객체라서 생긴다. 그래서 병목의 핵심은 "기계어가 아니라서"보다 "매번 처음 보는 것처럼 확인해서"다. 루프가 만 번 도는 동안 p가 늘 int였어도 확인도 만 번 한다. 이후 CPython의 속도 개선은 이 네 가지를 하나씩 줄여 가는 이야기다 — 3.11 특화 인터프리터는 2 · 3번을, JIT는 남은 1 · 4번 쪽을 노린다.

04JIT — 실행해 보고 나서 컴파일한다

AOT도 인터프리터도 못 하는 것: 관찰한 사실로 기계어 만들기

JIT 컴파일은 프로그램이 실행되는 도중에 코드 일부를 기계어로 컴파일하는 방식이다. 흐름은 보통 이렇다.

바이트코드 실행 (인터프리터) │ 실행 횟수를 센다 ▼ "이 루프 벌써 수천 번 돌았다" ── 뜨거운(hot) 코드로 판정 │ 지금까지 관찰한 사실을 전제로 ▼ 기계어 생성: "p는 항상 int였다"를 전제로 한 빠른 버전 │ ├─ 전제가 맞으면 → 이어 붙은 기계어로 실행 └─ 전제가 깨지면 (p에 float 등장) → 인터프리터로 되돌아간다

소스만 봐서는 p가 int일지 모르지만, 실행해 보면 안다.

📎 용어: guard · deoptimization

guard는 전제를 쓰는 연산 앞마다 둔 "전제가 아직 맞나?" 검사다. 검사가 실패해 인터프리터의 일반 경로로 돌아가는 것을 deoptimization(역최적화)이라고 한다.

🎧 비유 — 외국어 강연

AOT는 강연 원고 전체를 미리 번역해 책으로 나눠주는 것이다. CPython 인터프리터는 통역사가 원고를 자기만 알아보는 약식 메모(바이트코드)로 옮겨 두고, 강연 중에는 메모를 보며 한 문장씩 통역하는 것이다. 원문을 다시 해독하지는 않지만, 문장마다 통역은 한다. JIT는 자주 반복되는 문장이 나오면 번역 자막을 청중 화면에 바로 띄워 통역사를 건너뛰는 것이다.

🎯 JIT가 우선한 것

  • 명령 사이 오가기 제거 — 명령들이 이어 붙은 기계어가 된다
  • 실행 중에만 아는 정보 — 실제 타입, 자주 가는 분기를 전제로 흔한 경우를 빠르게 만든다

🗑️ JIT가 버린 것

  • 단순함 — 인터프리터와 컴파일러를 함께 유지해야 한다
  • 기동 직후 속도 — 뜨거워질 때까지는 인터프리터 속도고, 컴파일 자체도 시간을 쓴다
  • 메모리 — 만든 기계어를 올려 둘 공간
  • 단순한 메모리 권한 — 실행 중 만든 코드를 메모리에 써넣고 실행해야 해서, 쓰는 동안만 쓰기를 허용하고 다 쓰면 읽기 · 실행으로 바꾸는 절차가 따라온다(W^X: 쓰기와 실행을 동시에 허용하지 않아, 써넣은 데이터가 곧바로 코드로 실행되는 공격을 막는 규칙)

이 선택에서 생긴 개념이 뜨거운(hot) 코드 판정, guard, deoptimization이다.

이런 흐름이 있었다

JIT 자체는 LISP와 Java 시절부터 있던 아이디어다. 1999년 공개된 Java HotSpot은 이름 그대로 "자주 도는 곳(hot spot)만 컴파일"하는 방식을 택했고, Java 1.3부터 기본 JVM이 됐다.

V8은 2008년 공개 때 반대 길을 택해, 인터프리터 없이 모든 JavaScript를 일단 기계어로 만들었다. 그렇게 기준 컴파일러(baseline compiler)가 만든 기계어가 결국 Chrome의 JavaScript 메모리에서 3분의 1 가까이를 차지하게 됐고, V8은 인터프리터(Ignition)를 들여 메모리와 기동 시간을 줄였다. V8도 HotSpot처럼 인터프리터로 시작하는 구조로 돌아온 것이다 — 기동 속도와 메모리를 우선하면 인터프리터를 버리기 어렵다.

05갈림길 — PyPy는 속도를, CPython은 호환을

같은 문제를 두고 반대 우선순위를 골랐다

03장의 비용을 줄이는 가장 직접적인 방법은 JIT다. 파이썬에서 이 길을 먼저 간 구현이 PyPy다. PyPy는 루프가 실제로 지나간 경로를 기록해 기계어로 만드는 tracing JIT를 쓰고, 공식 사이트는 벤치마크 기하평균 기준으로 CPython 3.11보다 약 3배 빠르다고 밝힌다.

📎 용어: 기하평균 · C 확장 모듈 · PyPI

기하평균은 벤치마크별 속도 비율을 모두 곱한 뒤 개수만큼 제곱근을 취한 평균으로, 극단적인 결과 한두 개에 덜 휘둘린다. C 확장 모듈은 C로 작성해 CPython에 붙이는 모듈이다. psycopg2나 NumPy의 핵심 연산이 여기에 해당하고, CPython의 객체 구조와 참조 카운트 방식을 그대로 전제하고 짜여 있다. PyPI는 pip install이 패키지를 받아 오는 공개 저장소다.

🏎️ PyPy

우선한 것: 속도

  • 처음부터 JIT를 중심에 두고 설계했다. 메모리 관리도 참조 카운트를 쓰지 않고 가비지 컬렉터(GC)로 한다. (CPython에도 gc 모듈이 있지만, 참조 카운트로 못 치우는 순환 참조를 보조로 치우는 역할이다)
  • 버린 것: C 확장과의 직접 호환 — 호환 계층으로 NumPy 등을 돌리지만, 경계를 넘나드는 비용과 호환 확인이 따라온다
  • 생긴 개념: tracing JIT, 호환 계층

🐍 CPython

우선한 것: 기존 생태계와의 호환

  • C 확장이 기대는 C API와 객체 구조(참조 카운트 포함)는 바꿀 수 없다. JIT 공식 지원 로드맵(PEP 836)도 인기 PyPI 패키지와의 호환 검토를 목표에 넣었다
  • 버린 것: 대담한 재설계 — 대신 바꿀 수 있는 쪽, 즉 바이트코드와 인터프리터 내부에서 한 단계씩 빨라지는 길을 택했다
  • 생긴 개념: 06 · 07장에서

PEP는 파이썬 변경 제안 문서다. CPython의 그 "한 단계씩"은 두 번의 선택으로 나타났다. 기계어 없이 인터프리터를 똑똑하게 만든 3.11, 그리고 그래도 남는 비용을 기계어로 줄이려는 3.13 이후의 JIT다.

06선택 ② 3.11 특화 인터프리터 — 기계어 없이 guard부터

인터프리터를 버리지 않고, 실행 중에 명령을 바꿔 끼운다

3.11의 특화 적응형 인터프리터(PEP 659)는 기계어를 만들지 않는다. 대신 실행해 본 결과를 보고, 일반 명령을 그 타입 전용 명령으로 바꿔 끼운다. PEP 659는 느린 명령을 빠른 변형으로 교체하는 이 과정을 quickening이라고 부른다.

dis.dis(total, adaptive=True) — total([1, 2, 3]) 한 번 호출 후, 바뀐 명령만 발췌 (3.14)

FOR_ITER          ──▶  FOR_ITER_LIST        # 리스트 전용 반복
BINARY_OP (+)     ──▶  BINARY_OP_ADD_INT    # int + int 전용 덧셈

adaptive=True는 "실행 중에 바뀐 명령을 보여 달라"는 옵션이다. 옵션 없이 보면 원래 명령이 나온다. 3.14에서는 명령이 두 번째 실행될 때 특화되기 때문에, 원소 셋짜리 리스트로 한 번만 불러도 루프 안의 명령은 이미 바뀌어 있다. 실제 출력에 함께 보이는 JUMP_BACKWARD_NO_JIT는 07장에서 다룬다.

BINARY_OP_ADD_INT는 입구에서 두 값이 모두 int인지 확인하는 guard를 거친 뒤 int 덧셈 C 코드로 바로 간다. 03장의 2번(타입 확인)과 3번(연산 찾기)이 이 확인으로 줄어든다. 전제에 안 맞는 값이 오면 그 자리에서 일반 경로로 처리하고, 계속 틀리면 다시 특화를 시도한다 — 들어오는 타입에 맞는 전용 명령으로 바꾸거나, 맞는 것이 없으면 일반 명령으로 둔다.

🎯 우선한 것

  • 수습 범위가 작다 — 명령 하나 단위로만 특화하니 전제가 깨져도 그 명령만 다시 처리하면 된다. PEP 659는 여러 명령을 묶어 특화하면 구간 한가운데서 되돌리는 코드가 필요해진다고 설명한다(의역). 앞 명령들이 실행된 상태를 인터프리터용으로 되살려야 하기 때문이다
  • 이식성 유지 — 기계어를 만들지 않으니 CPU별 코드가 필요 없다

🗑️ 버린 것

  • 바이트코드는 고정이라는 전제 — 명령이 실행 중에 제자리에서 바뀐다. dis에 adaptive 옵션이 따로 있는 이유다
  • 약간의 메모리 — 명령 뒤에 캐시 칸을 붙인다

그리고 남은 것이 있다. 1번(명령 사이 오가기)과 4번(객체 관리)은 대부분 그대로다. 명령 둘을 합친 슈퍼명령어나 3.14의 _BORROW 변형이 일부를 줄이긴 하지만, 명령마다 C 루프를 거친다는 구조는 바뀌지 않는다. 이 남은 몫이 07장 JIT의 과녁이다.

이 선택에서 생긴 개념은 세 가지다. 특화(quickening), 명령 바로 뒤에 붙은 16비트 칸들에 타입 · 위치 정보를 저장하는 인라인 캐시, 그리고 인터프리터 안에서 쓰는 guard. 여기서 쌓은 타입 관찰과 guard가 그대로 JIT의 재료가 된다.

결과는 컸다. What's New 3.11은 3.10 대비 워크로드에 따라 10~60%, 표준 벤치마크 평균 약 1.25배 빨라졌다고 적는다. 특화 인터프리터를 포함한 3.11 전체 개선의 합이다.

07선택 ③ 3.13~3.15 JIT — 남은 비용을 기계어로

무거운 컴파일러 대신, 미리 구워 둔 기계어 조각을 이어 붙인다

micro-op와 trace

3.13에 들어온 JIT(PEP 744)는 바이트코드를 바로 기계어로 바꾸지 않는다. 먼저 뜨거운 구간의 명령을 micro-op로 쪼갠다.

📎 용어: micro-op (uop)

바이트코드 명령 하나를 더 작은 내부 명령으로 나눈 것. 예를 들어 BINARY_OP_ADD_INT는 "맨 위 값이 int인지 확인", "그 아래 값이 int인지 확인", "int 덧셈"의 세 조각이다. 이렇게 나눠 두면 같은 확인이 연달아 나올 때 뒤쪽을 지울 수 있고, 조각마다 기계어 틀을 미리 만들어 둘 수 있다.

어느 구간이 뜨거운지는 루프 끝의 "뒤로 점프" 명령이 센다. PYTHON_JIT=1로 JIT를 켜고 함수를 한 번 실행한 뒤 dis.dis(total, adaptive=True)로 보면, JUMP_BACKWARD가 JUMP_BACKWARD_JIT로 바뀌어 있다. 이 명령이 반복 횟수를 세다가 기준을 넘으면, 그 루프가 앞으로 돌 경로를 micro-op 목록으로 만든다. 이것이 trace다. JIT가 꺼져 있으면 같은 자리에 JUMP_BACKWARD_NO_JIT가 나온다.

만든 micro-op 목록은 기계어로 가기 전에 최적화 단계를 거친다. 3.13부터 연달아 나오는 같은 guard를 지우고, 결과가 상수로 정해지는 계산을 미리 접는다.

Copy-and-patch

PEP 744는 LLVM(clang · Rust 등이 공유하는 최적화 · 기계어 생성 엔진) 같은 기존 컴파일러 프레임워크를 쓰면 구현은 쉽지만, 무거운 런타임 의존성과 훨씬 큰 JIT 컴파일 비용을 치러야 한다는 취지로 설명한다(의역). 그래서 CPython은 2021년 논문에서 제안된 copy-and-patch를 택했다.

[CPython을 빌드할 때 — 한 번] micro-op 하나하나의 C 구현 ──(LLVM)──▶ 기계어 조각 = "stencil" 빈칸이 뚫려 있음: [상수] [점프 주소] [파이썬 프로그램이 돌 때 — 매번] 뜨거운 구간의 micro-op 목록 │ 최적화: 중복 guard 제거 · 상수 접기 ▼ stencil 복사 ─▶ 빈칸에 실제 값 기입 ─▶ 이어 붙이기 ─▶ 실행 가능한 기계어

🎯 우선한 것

  • 실행 중 코드 생성 속도 — 논문 기준 LLVM -O0보다 약 100배 빠르게 코드를 만든다(논문의 SQL 쿼리 컴파일러 사례)
  • 배포 단순함 — LLVM은 JIT를 넣어 CPython을 빌드할 때만 필요하고, 파이썬을 쓰는 사람은 설치하지 않아도 된다

🗑️ 버린 것

  • 무거운 최적화 — 실행 중에는 stencil을 이어 붙일 뿐 깊은 분석을 하지 않는다. 논문 기준 만든 코드는 -O0 코드보다 14% 빠른 수준으로, 높은 최적화 단계와 겨루는 방식이 아니다

이 선택에서 생긴 개념이 micro-op, trace, stencil이다.

그 결과 3.13 JIT는 특화 인터프리터와 비슷한 속도였다(PEP 744). 조각을 이어 붙여 명령 사이 오가기는 줄였지만, 값은 여전히 VM 스택 메모리를 오갔고 참조 카운트 갱신도 조각마다 남아 있었다. 이 두 가지를 줄이는 최적화는 3.15에 들어왔다.

3.14 → 3.15 — 남아 있던 비용을 줄이는 중

3.13은 기본 빌드에 JIT가 없어서, 파이썬을 소스에서 직접 빌드하며 옵션을 켜야 했다. 3.14부터는 python.org의 macOS · Windows 공식 설치 파일에 JIT가 들어 있고, 기본으로는 꺼져 있다. 환경 변수 PYTHON_JIT=1로 켠다.

3.14에는 기계어 없이 1번(디스패치)을 줄이는 다른 시도도 들어왔다. tail-calling 인터프리터는 거대한 C 분기문 대신, 명령별 작은 C 함수가 다음 함수로 꼬리 호출(호출 기록을 쌓지 않고 바로 넘어가는 호출)해 이어지는 방식이다. 빌드 옵션(--with-tail-call-interp)으로 켜고 Clang 19 이상(x86-64 · AArch64)에서만 되며, pyperformance(파이썬 공식 벤치마크 모음) 기하평균 3~5% 빨랐다. 3.15에서는 Windows 64비트 공식 설치 파일이 이 방식을 쓴다.

3.15는 JIT의 앞단과 최적화 단계를 크게 넓혔다.

3.15에서 바뀐 것줄이는 비용
tracing frontend 개편
(frontend = 어떤 경로를 micro-op 목록으로 만들지 정하는 JIT 앞단)		3.14까지는 바이트코드와 특화 정보로 경로를 추정했지만, 이제 실제 실행을 기록한다. 객체 생성 · 제너레이터 일부까지 JIT가 다룰 수 있는 코드가 넓어졌다
레지스터 할당값을 레지스터(CPU 안의 초고속 저장 칸)에 둔 채 연산을 이어 가, VM 스택 메모리를 읽고 쓰는 일을 건너뛴다
최적화 확대안전할 때 참조 카운트 갱신을 생략하고(03장 4번), 상수 전파도 더 넓게 한다

결과는 pyperformance 기하평균으로 x86-64 Linux에서 모든 최적화를 켜고 빌드한 표준 인터프리터 대비 8~9%, AArch64 macOS에서 tail-calling 인터프리터 대비 12~13% 개선이다. 3.15 문서의 수치이고, 아직 최종이 아니라고 명시돼 있다.

⚠️ 평균의 함정

같은 문서는 JIT를 넣은 빌드와 넣지 않은 빌드를 벤치마크별로 비교하면 약 15% 느려지는 경우부터 100% 넘게 빨라지는 경우까지 있다고 적는다(unpack_sequence 마이크로벤치마크 제외). 기하평균은 "내 코드가 이만큼 빨라진다"는 약속이 아니다.

지금의 위치는 이렇다. 3.15에서도 JIT는 실험적 기능이고, 켜야 동작한다. 실험 기능에서 정식 기능으로 올리는 조건과 일정은 PEP 836(Draft)이 제안하고 있고, 기본값으로 켜는 것은 그 뒤 릴리스 매니저가 따로 승인할 일이다.

# JIT가 포함된 빌드인지, 켜져 있는지 확인 (3.14+)
$ PYTHON_JIT=1 python3.14 -c "import sys; print(sys._jit.is_available(), sys._jit.is_enabled())"
True True
# 첫 값이 False면 JIT 없이 빌드된 파이썬이다. Linux 배포판 · Docker 이미지는 빌드마다 다를 수 있으니 이것부터 본다
# _로 시작하는 이름은 내부용 API라는 표시다

08우리 스택에서 달라지는 것

nginx → gunicorn → Django → PostgreSQL 위에서 다시 보기

JIT가 줄이는 건 "파이썬 코드를 실행하는 시간"뿐

Django 요청 하나의 시간은 대략 세 덩어리로 나뉜다. ① 파이썬 코드 실행(뷰 로직, 시리얼라이저, ORM이 SQL을 조립하는 부분) ② 대기(PostgreSQL 쿼리 결과, 외부 API, Redis 응답) ③ C 코드(05장의 C 확장 — DB 드라이버 등). 03장의 네 가지 비용은 전부 ①에서만 생기므로, 특화 인터프리터도 JIT도 ①만 줄인다.

🔥 이득 볼 가능성이 큰 코드

  • 순수 파이썬 루프로 대량 데이터를 가공하는 배치 · Celery 작업
  • 파이썬으로 짠 점수 계산 · 정렬 · 매칭 로직
  • 같은 타입으로 오래 반복되는 코드

🧊 이득이 거의 없는 코드

  • DB · 네트워크 응답을 기다리는 시간이 대부분인 API
  • 무거운 연산을 이미 NumPy · pandas(C 코드)가 하는 작업
  • 한 번만 도는 기동 · 설정 코드
⚠️ 가장 싼 성능 개선은 JIT가 아니라 버전

06장의 특화 인터프리터는 3.11부터 설정 없이 기본으로 동작한다. 3.11 이전 버전에서 도는 서비스는 JIT를 논하기 전에 이 이득 자체를 받지 못하고 있다. 실험 플래그를 켜는 것보다 지원되는 최신 버전으로 올리는 쪽이 위험 대비 효과가 크다. JIT를 운영에서 켜려면, 내 워크로드로 벤치마크한 뒤에 결정한다.

JIT가 만든 기계어는 디스크에 남지 않는다

.pyc와 달리 JIT 기계어는 프로세스 메모리에만 있다. gunicorn 워커(요청을 처리하는 파이썬 프로세스 하나하나)가 재시작될 때마다 — max_requests 설정에 따른 주기적 재시작이나 배포 때 — 워밍업을 처음부터 다시 한다. 워커를 자주 갈아 끼우는 설정일수록 JIT가 뜨거워질 기회도 줄어든다.

Dockerfile의 PYTHONDONTWRITEBYTECODE=1

Dockerfile에 흔히 넣는 이 설정은 .pyc를 새로 쓰지 말라는 뜻이다. 이미 있는 .pyc는 그대로 읽는다. 따라서 이미지 안에 .pyc가 없는 모듈은 프로세스가 뜰 때마다 메모리에서 다시 컴파일된다.

어떤 모듈에 .pyc가 없는지는 설치 방식에 따라 다르다. 우리 앱 코드는 보통 없다. 라이브러리는 pip로 설치하면 기본으로 .pyc가 만들어지지만, uv는 --compile-bytecode(또는 UV_COMPILE_BYTECODE)를 줘야 만든다. gunicorn의 preload_app(마스터 프로세스가 앱을 먼저 import한 뒤 워커를 복제하는 설정)이 꺼진 기본 상태라면 이 import와 컴파일이 워커마다 반복된다.

# 기동 시간이 문제가 될 때 — 빌드 단계에서 바이트코드를 미리 굽는다
ENV UV_COMPILE_BYTECODE=1          # uv로 설치하는 라이브러리
RUN python -m compileall -q .       # 앱 코드
✅ 실무 감각

둘 다 "컴파일"이지만 줄이는 비용이 다르다. .pyc는 기동(import) 비용을, JIT는 오래 도는 코드의 실행 비용을 줄인다. 배포 직후 첫 요청이 느리면 앞쪽을, 오래 도는 배치가 느리면 뒤쪽을 의심한다.

09한 장 요약 치트시트

파이썬은 인터프리터 언어라면서 왜 컴파일을 해요?

인터프리터냐 컴파일러냐는 언어가 아니라 구현이 고르는 전략이고, CPython은 둘 다 한다. 소스를 실행하기 좋은 일렬 명령(바이트코드)으로 한 번 펴 두려고 컴파일하고(.pyc로 캐시), 이식성과 내부를 바꿀 자유를 위해 기계어까지는 가지 않는다 — 그래서 "인터프리터"다. 그 대가인 "명령마다 매번 확인하는 비용"을, C 확장 호환을 깨지 않는 선에서 3.11은 명령 특화로, 3.13부터는 뜨거운 구간을 실행 중에 기계어로 바꾸는 JIT로 줄여 가고 있다.
