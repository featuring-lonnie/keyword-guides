MVCC
읽는 쪽과 쓰는 쪽이 서로 기다리지 않는 법

결제 트랜잭션이 잔액을 50으로 바꾸고 아직 커밋하지 않았습니다. 그 순간 다른 요청이 같은 잔액을 읽으면 무엇을 받을까요? 기다리지도 않고 0.3ms 만에 100이 돌아옵니다. 데이터베이스는 그 행을 두 벌 들고 있었기 때문입니다. 그렇다면 두 요청이 동시에 잔액을 고치면, 그때도 서로 방해하지 않을까요?

💬 "트랜잭션은 어떻게 서로의 작업을 방해하지 않고 데이터를 읽고 쓸까? 데이터베이스가 하나의 데이터에 여러 버전을 가지고 있는 것을 아는가? 각 벤더사마다 이것을 푸는 방법도 다르다."

00방해하지 않는 것은 절반뿐이다

질문의 전제부터 짚고, 짧은 답을 먼저 둡니다

질문에는 전제가 하나 숨어 있습니다. "트랜잭션은 서로 방해하지 않는다." 이 말은 절반만 맞습니다. 읽는 쪽과 쓰는 쪽은 서로를 기다리지 않습니다. 하지만 같은 행을 고치려는 두 쓰기는 지금도 줄을 섭니다. 둘 중 하나는 기다리거나, 에러를 받고 처음부터 다시 해야 합니다.

읽기와 쓰기가 서로 기다리지 않는 비결이 질문의 두 번째 줄입니다. 데이터베이스는 한 행의 여러 버전을 함께 들고 있습니다. 누가 행을 고치는 동안에도 읽는 쪽은 고치기 전 버전을 봅니다. 이 방식을 MVCC(Multi-Version Concurrency Control, 다중 버전 동시성 제어)라고 부릅니다.

세 번째 줄, 벤더마다 푸는 방법이 다르다는 것도 맞습니다. 가장 먼저 부딪히는 차이는 기본 격리 수준입니다. PostgreSQL 은 기본으로 문장마다 새 기준 시점을 잡고, MySQL 의 기본 저장 엔진(테이블을 실제로 저장하고 읽고 쓰는 부품)인 InnoDB 는 트랜잭션에 한 번 잡습니다. 그 밖에 쓰기가 부딪혔을 때 에러를 낼지 최신 값에 쓸지, 옛 버전을 어디에 두고 언제 치울지가 갈립니다. 다만 Django 는 두 DB 를 모두 READ COMMITTED 로 연결하므로, Django 에서는 격리 수준을 올렸을 때와 옛 버전을 치울 때 이 차이를 만납니다.

읽기 위주 작업과 쓰기 위주 작업이 다른 구성을 고르는 이유도 첫 문단에 있습니다. 버전 덕분에 사라진 기다림은 읽기와 쓰기 사이뿐이라, 조회가 대부분인 작업은 MVCC 덕을 크게 보고 같은 행에 쓰기가 몰리는 작업은 거의 못 봅니다. 그래서 둘은 격리 수준, 쓰는 방식, 테이블 배치를 다르게 고릅니다(08장 3번).

이 문서가 답하는 것

① 읽기는 왜 쓰기를 기다리지 않게 됐나 ② 같은 SELECT 를 두 번 했는데 값이 다른 것은 정상인가 ③ 동시에 잔액을 고치면 무엇이 사라지고, PostgreSQL 과 MySQL 은 그때 왜 다르게 행동하나 ④ Django 에서 이것을 어떻게 다루나 ⑤ 읽기 위주와 쓰기 위주 작업에서 고르는 구성이 왜 달라지나. 다 읽으면 "격리 수준" 설정 한 줄이 실제로 무엇을 바꾸는지 설명할 수 있습니다.

01트랜잭션과 격리 수준

뒤에서 계속 쓰는 말

📎 용어: 트랜잭션 · 커밋 · 롤백

트랜잭션은 "전부 반영되거나 전부 없던 일이 되거나" 둘 중 하나로 끝나는 SQL 묶음입니다. 계좌 이체의 출금과 입금이 대표적입니다. 커밋(COMMIT)은 묶음의 변경을 확정해 다른 트랜잭션에도 보이게 하는 것이고, 롤백(ROLLBACK)은 묶음 전체를 취소하는 것입니다. Django 에서는 가장 바깥의 transaction.atomic() 블록 하나가 트랜잭션 하나입니다. 그 안에 겹쳐 쓴 atomic 은 트랜잭션이 아니라 저장점(savepoint, 그 지점까지만 되돌릴 수 있게 찍어 두는 표시)이 됩니다.

트랜잭션 하나만 돌 때는 문제가 없습니다. 문제는 웹 서버가 요청을 동시에 처리하면서 생깁니다. 여러 트랜잭션이 같은 행을 동시에 만지면, 혼자 돌았다면 나오지 않았을 결과가 나옵니다. 대표적인 것은 다음과 같습니다.

이상 현상무슨 일이 생기나
더티 리드남이 아직 커밋하지 않은 값을 읽는다. 그 트랜잭션이 롤백하면 존재한 적 없는 값을 본 셈이 된다
반복 불가능한 읽기한 트랜잭션 안에서 같은 행을 두 번 읽었는데, 사이에 남이 커밋해서 값이 다르다
팬텀(phantom)같은 조건으로 두 번 조회했는데, 사이에 남이 넣은 행이 새로 나타난다
갱신 분실(lost update)둘이 같은 값을 읽고 각자 계산해 저장하면, 먼저 저장한 쪽의 변경이 사라진다

앞의 셋은 SQL 표준이 격리 수준을 정의할 때 쓰는 현상입니다. 갱신 분실은 표준 목록에는 없지만 실무에서 가장 자주 만나는 문제라 함께 둡니다.

📎 용어: 격리 수준

격리 수준은 "이 트랜잭션이 남의 동시 작업에서 얼마나 떨어져 있을지"를 고르는 설정입니다. SQL 표준은 약한 순서로 READ UNCOMMITTED · READ COMMITTED · REPEATABLE READ · SERIALIZABLE 넷을 정의합니다. 강할수록 위 이상 현상을 더 많이 막고, 그 대신 기다림이나 실패가 늘어납니다. 가장 강한 SERIALIZABLE 은 "트랜잭션을 하나씩 차례로 돌린 것과 같은 결과"를 보장합니다.

표준은 "어떤 현상을 막아야 하는가"만 정하고 "어떻게 막을지"는 정하지 않습니다. 그래서 같은 이름의 격리 수준이 벤더마다 다르게 동작합니다. 지금부터 볼 선택들은 전부 "어떻게 막을까"에 대한 답입니다.

02선택 ① 잠금으로 줄을 세운다

가장 먼저 떠오르는 방법 — 한 행에는 한 버전만 둔다

가장 단순한 해법은 행마다 자물쇠를 다는 것입니다. 행의 버전은 하나뿐이니, 누가 쓰는 동안 다른 사람이 읽으면 반쯤 바뀐 값이나 롤백될 값을 볼 수 있습니다. 그러니 쓰는 동안에는 아무도 못 읽게, 읽는 동안에는 아무도 못 쓰게 막습니다.

📎 용어: 공유 잠금 · 배타 잠금

공유 잠금(shared lock)은 읽을 때 거는 잠금입니다. 여러 트랜잭션이 함께 걸 수 있지만, 걸려 있는 동안 아무도 그 행을 고치지 못합니다. 배타 잠금(exclusive lock)은 쓸 때 거는 잠금입니다. 걸려 있는 동안 다른 트랜잭션은 그 행에 공유 잠금도 배타 잠금도 걸지 못하고 기다립니다.

잠금을 아무 때나 풀면 결과가 꼬입니다. x 를 읽고 잠금을 바로 풀었다고 해 봅시다. 그사이 남이 x 와 y 를 함께 고쳐 커밋하고, 나는 y 를 새 값으로 읽습니다. 내가 본 x 는 옛 시점, y 는 새 시점이라 두 값이 맞지 않습니다. 그래서 규칙이 하나 생겼습니다. 트랜잭션은 필요한 잠금을 모으기만 하다가, 하나라도 풀기 시작한 뒤에는 새 잠금을 얻지 않습니다. 이것이 2단계 잠금(2PL, Two-Phase Locking)이고, 실무에서는 잠금을 커밋할 때까지 쥐었다가 한꺼번에 푸는 형태로 씁니다.

2PL 만으로 끝나지는 않습니다. 행만 잠그면, 내가 조건으로 조회한 범위에 남이 새 행을 INSERT 하는 팬텀은 막지 못합니다. 잠그는 대상에 "조건에 맞는 범위"까지 넣어야(InnoDB 의 next-key lock 같은 범위 잠금) 결과가 트랜잭션을 하나씩 돌린 것과 같아집니다.

읽기가 쓰기를 실제로 얼마나 기다리는지 PostgreSQL 에서 흉내 내 봤습니다. SELECT ... FOR SHARE 는 읽으면서 공유 잠금을 거는 문장입니다. 한 세션이 행을 고치고 커밋하지 않은 채 두고, 다른 세션이 공유 잠금으로 읽습니다.

실측 — PostgreSQL 14, 로컬 테스트용 DB 서버, 두 세션 (발췌)

A: UPDATE account SET balance = 50 WHERE id = 1   -- 커밋 전
B: SELECT balance ... FOR SHARE   -- 1초 뒤에도 대기 중
A: COMMIT
B: -> 50   -- A 가 커밋한 뒤에야, 약 1.1초 기다려서 받음

B 는 A 가 끝날 때까지 아무것도 못 했습니다. A 가 1초 걸렸으니 1초를 기다렸고, A 가 외부 API 를 부르느라 10초 걸렸다면 10초를 기다렸을 것입니다. 이 방식에서는 매출 집계 같은 긴 읽기 쿼리가 결제 같은 짧은 쓰기를 붙잡고, 그 반대도 일어납니다.

이 방식은 옛날이야기가 아닙니다. Microsoft 문서에 따르면 직접 설치한 SQL Server 는 별도 설정이 없으면 READ COMMITTED 를 공유 잠금으로 구현합니다(Azure SQL Database 는 기본이 버전 읽기입니다). 다만 행을 읽은 직후 공유 잠금을 풀기 때문에 2PL 은 아니고, 그래서 01장의 반복 불가능한 읽기가 생깁니다.

📎 용어: 데드락

데드락(교착 상태)은 A 가 B 의 잠금을, B 가 A 의 잠금을 서로 기다리는 상태입니다. 둘 다 영원히 기다리게 되므로, 데이터베이스는 이를 감지하면 한쪽 트랜잭션을 에러로 끝내 풀어 줍니다. 잠금을 많이 오래 쥘수록 잘 생깁니다.

✅ 우선한 것

단순한 정확성

  • 행마다 버전이 하나라 "지금 값"이 무엇인지 모호하지 않다
  • 2단계 잠금에 범위 잠금까지 더하면 하나씩 돌린 것과 같은 결과가 나온다

🗑️ 버린 것

읽기와 쓰기 사이의 동시성

  • 버전이 하나뿐이라 쓰는 중인 행은 읽을 수 없다. 읽기가 쓰기를, 쓰기가 읽기를 기다린다
  • 잠금을 오래 쥘수록 기다림이 길어지고 데드락이 잦아진다

이 선택에서 생긴 개념: 공유 잠금과 배타 잠금, 2단계 잠금과 범위 잠금, 데드락과 그 감지.

03선택 ② 옛 버전을 남겨 둔다

읽는 사람에게는 고치기 전 사본을 보여 주면 된다

선택 ①에서 읽기가 막힌 이유는 버전이 하나뿐이어서였습니다. 그렇다면 버전을 여러 개 두면 됩니다. 쓰는 쪽은 새 버전을 만들고, 그 버전이 커밋되기 전까지 다른 트랜잭션에는 옛 버전을 보여 줍니다. 읽는 쪽은 잠금을 걸 필요가 없습니다. 이것이 MVCC 이고, 이 아이디어는 1978년 MIT 박사 논문에서 처음 정리됐습니다.

PostgreSQL 공식 문서는 MVCC 의 핵심을 이렇게 요약합니다(의역). 읽기는 쓰기를 막지 않고, 쓰기도 읽기를 막지 않는다. 선택 ①과 같은 상황을 이번에는 잠금 없는 보통 SELECT 로 다시 돌렸습니다.

실측 — 같은 상황, 보통 SELECT, READ COMMITTED(PostgreSQL 기본) (발췌)

A: UPDATE account SET balance = 50 WHERE id = 1   -- 커밋 전
B: SELECT balance ...   -- -> 100, 0.3ms, 기다리지 않음
A: COMMIT
B: SELECT balance ...   -- -> 50 (같은 B 트랜잭션 안의 다음 문장)

B 는 기다리지 않고, 아직 커밋되지 않은 50 대신 커밋된 마지막 값 100 을 받았습니다. 더티 리드도 생기지 않았습니다. 같은 트랜잭션 안의 두 번째 SELECT 가 50 으로 바뀐 이유는 04장에서 봅니다. 그러면 데이터베이스는 어느 버전을 누구에게 보여 줄지 어떻게 정할까요?

버전마다 붙은 두 개의 꼬리표

PostgreSQL 은 트랜잭션이 처음 쓰기를 할 때 계속 늘어나는 번호(트랜잭션 ID)를 붙입니다. 읽기만 하는 트랜잭션은 번호를 받지 않습니다. 다만 SELECT ... FOR UPDATE · FOR SHARE 처럼 행을 잠그는 읽기는 쓰기로 쳐서 번호를 받습니다. 그리고 행의 버전마다 이 번호 두 개를 숨은 컬럼으로 적어 둡니다. xmin 은 이 버전을 만든 트랜잭션, xmax 는 이 버전을 지우거나 새 버전으로 바꾼 트랜잭션입니다(0 이면 아직 아무도 바꾸지 않음). FOR UPDATE 같은 행 잠금도 잠근 트랜잭션 번호를 여기에 적는데, 이때는 버전이 지워진 것이 아닙니다. 둘 다 SELECT xmin, xmax, * 로 볼 수 있습니다.

실측 — xmin · xmax (발췌)

-- 754번 트랜잭션이 넣은 행. A 의 트랜잭션 ID 는 756
A: UPDATE account SET balance = 50 WHERE id = 1   -- 커밋 전
A 가 보는 행 ->  xmin=756  xmax=0    balance=50    -- 자기가 만든 새 버전
B 가 보는 행 ->  xmin=754  xmax=756  balance=100   -- 756이 바꾸는 중인 옛 버전
A: COMMIT
새 트랜잭션  ->  xmin=756  xmax=0    balance=50

같은 순간에 A 와 B 는 서로 다른 버전을 봤습니다. B 가 본 옛 버전에는 "756번이 이 버전을 끝냈다"는 표시가 붙어 있지만, 756번은 아직 커밋하지 않았습니다. 그래서 B 에게 이 옛 버전은 아직 살아 있는 버전입니다. 판단 규칙을 줄이면 이렇습니다.

이 버전이 나에게 보이는가? 내가 만든 버전이고, 내가 다시 지우지 않았다 ── 예 ─▶ 보임 (커밋 전이어도) │ 아니오 ▼ xmin 트랜잭션이 커밋됐고, 내 기준 시점 전에 커밋됐다 ── 아니면 ─▶ 안 보임 │ 예 ▼ xmax 가 비었거나 잠금 표시뿐이거나, xmax 가 남의 트랜잭션이고 커밋 전(또는 롤백)이거나, 내 기준 시점 뒤에 커밋됐다 ── 아니면 ─▶ 안 보임 (이미 지워진 버전) │ 예 ▼ 보임

규칙에 나온 "내 기준 시점"이 다음 장의 주제입니다. 옛 버전이 실제로 어디에 놓이는지는 엔진마다 다릅니다. PostgreSQL 은 새 버전을 테이블 안에 옛 버전과 나란히 씁니다. MySQL 의 InnoDB 는 행을 제자리에서 고치면서 옛 값을 undo log 에 옮겨 둡니다. undo log 는 이름대로 롤백할 때 변경을 되돌리는 데 쓰는 기록이고, 옛 버전을 봐야 하는 트랜잭션도 이 기록을 거슬러 가 옛 값을 되살립니다. 두 방식 모두 MVCC 입니다. 어느 쪽이든 옛 버전은 볼 사람이 남아 있는 동안 지울 수 없고, 나중에 누군가 치워야 합니다(07장).

📚 비유

공유 문서의 버전 기록을 떠올려 보세요. 누가 문서를 고치는 동안에도 다른 사람은 마지막으로 저장된 판을 읽을 수 있습니다. 고치는 사람이 저장을 눌러야(커밋) 새 판이 모두에게 보입니다. 다만 데이터베이스는 문서 하나가 아니라 행마다 이 기록을 따로 둡니다.

✅ 우선한 것

읽기와 쓰기 사이의 동시성

  • 보통 SELECT 는 잠금을 걸지 않고, 쓰는 중인 행도 옛 버전으로 바로 읽는다
  • 긴 읽기 쿼리가 짧은 쓰기를 붙잡지 않는다

🗑️ 버린 것

"값은 하나"라는 단순함

  • 한 행의 버전이 여럿이 되어 공간을 더 쓰고, 다 쓴 버전을 치우는 작업이 따로 필요하다
  • 트랜잭션마다 보이는 값이 다를 수 있어, 어느 시점의 값을 볼지 따로 정해야 한다

이 선택에서 생긴 개념: 행 버전, 트랜잭션 ID, 가시성 규칙(xmin · xmax), undo log, 잠그지 않는 읽기.

04선택 ③ 어느 시점을 기준으로 볼 것인가

기준 시점을 문장마다 잡느냐, 트랜잭션에 한 번 잡느냐

📎 용어: 스냅샷

스냅샷은 "이 순간까지 커밋된 트랜잭션은 어디까지인가"를 적은 메모입니다. 데이터를 복사하는 것이 아닙니다. 앞 장의 가시성 규칙에서 "내 기준 시점"이 이 메모입니다. 스냅샷에 들어 있는 트랜잭션이 만든 버전만 보입니다.

선택 ②가 남긴 숙제는 "어느 시점의 값을 보여 줄까"였습니다. 답은 두 가지로 갈립니다. PostgreSQL 과 InnoDB 는 문장(SQL 한 줄)을 실행할 때마다 새 스냅샷을 잡는 것으로 READ COMMITTED 를, 트랜잭션에서 한 번 잡은 스냅샷을 끝까지 쓰는 것으로 REPEATABLE READ 를 구현합니다. 잠금 방식 엔진은 같은 이름의 수준을 02장처럼 잠금으로 구현합니다. 같은 SELECT 를 두 번 하고 그 사이에 다른 세션이 값을 바꿔 커밋했습니다.

실측 — 같은 SELECT 두 번, 사이에 다른 세션이 70 으로 바꾸고 커밋 (발췌)

READ COMMITTED    1회차 -> 100   2회차 -> 70    -- 문장마다 새 스냅샷
REPEATABLE READ   1회차 -> 100   2회차 -> 100   -- 첫 문장의 스냅샷을 계속 씀

READ COMMITTED 의 2회차가 70 이 된 것은 버그가 아닙니다. 01장의 "반복 불가능한 읽기"가 이 수준에서는 허용된다는 뜻입니다. 매 문장이 최신 커밋을 보니 대부분의 웹 요청에는 이쪽이 자연스럽습니다. PostgreSQL 의 기본 격리 수준이 READ COMMITTED 입니다.

REPEATABLE READ 는 트랜잭션 전체가 한 시점의 데이터를 봅니다. 월말 정산처럼 여러 테이블을 차례로 읽어 합계를 맞춰야 할 때, 중간에 들어온 결제 때문에 앞뒤 합계가 어긋나는 일이 없습니다. MySQL InnoDB 의 기본 격리 수준이 이쪽입니다.

⚠️ 흔한 오해: "트랜잭션을 시작한 순간의 데이터"

스냅샷은 BEGIN 하는 순간에 잡히지 않습니다. PostgreSQL 은 트랜잭션 제어문이 아닌 첫 문장에서 잡고, InnoDB 는 첫 일관된 읽기, 곧 잠그지 않는 보통 SELECT 에서 잡습니다(두 문서 모두 의역). BEGIN 과 첫 SELECT 사이에 들어온 커밋은 보입니다.

✅ 우선한 것 (REPEATABLE READ 쪽)

트랜잭션 안의 일관된 읽기

  • 같은 것을 여러 번 읽어도 값이 같다
  • 여러 테이블을 읽어도 한 시점의 상태로 맞아떨어진다

🗑️ 버린 것

지금 값과의 일치

  • 트랜잭션이 길수록 내가 보는 값이 실제 최신 값에서 멀어진다
  • 스냅샷이 오래 살아 있는 동안 옛 버전을 치우지 못한다
  • 옛 스냅샷을 근거로 쓰기를 하면, 그사이 바뀐 실제 값과 부딪힌다

이 선택에서 생긴 개념: 스냅샷, 문장 단위 스냅샷과 트랜잭션 단위 스냅샷.

05선택 ④ 쓰기끼리는 다시 줄을 선다

MVCC 가 풀지 않은 나머지 절반

버전을 여러 개 두는 것은 읽기를 위한 해법입니다. 같은 행에 두 트랜잭션이 동시에 새 버전을 만들려 하면, 어느 쪽을 다음 버전으로 삼을지 정해야 합니다. 그래서 MVCC 데이터베이스도 쓰기에는 선택 ①의 배타 잠금을 그대로 씁니다. 먼저 고친 트랜잭션이 행 잠금을 쥐고, 나중에 온 쪽은 앞의 트랜잭션이 커밋이나 롤백할 때까지 기다립니다.

기다림만으로는 막히지 않는 갱신 분실

잔액 100 에서 A 는 30, B 는 20 을 빼려 합니다. 둘 다 먼저 잔액을 읽고, 애플리케이션에서 뺄셈을 한 다음, 그 결과를 저장합니다. 기대값은 50 입니다.

실측 — 읽고 → 파이썬에서 계산 → 저장, READ COMMITTED (발췌)

A 읽음 100, B 읽음 100
A: UPDATE ... SET balance = 70; COMMIT
B: UPDATE ... SET balance = 80; COMMIT
최종 balance -> 80   -- 기대값 50. A 가 뺀 30 이 사라졌다

A 가 먼저 커밋한 뒤에 B 가 썼으니 두 UPDATE 는 부딪히지도 않았습니다. 문제는 B 가 저장한 80 이 이미 낡은 값 100 에서 계산한 결과라는 점입니다. 데이터베이스는 80 이 낡은 100 에서 나온 줄 모르니 막지 못합니다. 이것이 01장의 갱신 분실입니다.

엔진은 부딪힌 쓰기를 어떻게 처리하나

이번에는 뺄셈을 데이터베이스에 맡겨 SET balance = balance - 20 처럼 썼습니다. A 가 먼저 고치고 커밋하기 전에 B 가 같은 행을 고칩니다. 이때 B 의 UPDATE 는 기다리다가, A 가 커밋하면 다음 둘 중 하나가 됩니다.

실측 — 같은 행을 동시에 UPDATE, A 커밋 뒤 B 의 결과 (발췌)

READ COMMITTED    B: 성공           최종 50
REPEATABLE READ   B: ERROR: could not serialize access due to concurrent update
                                     최종 70   -- B 는 롤백, 재시도해야 한다

READ COMMITTED 의 B 는 기다린 뒤 A 가 만든 최신 버전을 다시 읽고, WHERE 조건이 여전히 맞는지 확인한 다음 그 위에 뺄셈을 했습니다. 문장마다 최신 커밋을 보기로 한 수준이니 자연스러운 동작입니다.

REPEATABLE READ 의 B 앞에는 두 길이 있습니다. 스냅샷에서 본 옛 버전을 기준으로 쓰면 A 의 변경이 사라집니다. 최신 버전을 기준으로 쓰면 B 가 트랜잭션 내내 본 값과 실제로 쓴 근거가 달라집니다. PostgreSQL 은 둘 다 택하지 않고 B 를 에러로 끝냅니다. 같은 이유로, 위의 "읽고 → 계산 → 저장" 실험도 REPEATABLE READ 에서 돌리면 B 의 저장이 같은 에러로 거부되고 A 의 변경이 남습니다.

MySQL InnoDB 는 같은 REPEATABLE READ 라는 이름으로 뒤의 길을 택합니다. 공식 문서에 따르면 InnoDB 의 스냅샷은 보통 SELECT 에 적용되고, UPDATE · DELETE 와 잠금 읽기(SELECT ... FOR UPDATE)는 스냅샷을 따르지 않고 가장 최신의 커밋된 값을 대상으로 할 수 있습니다(MySQL 8.4 공식 문서 기준). 그래서 에러 없이 기다렸다가 최신 값에 씁니다.

대신 보통 SELECT 로 읽어 둔 값(스냅샷)과 UPDATE · 잠금 읽기가 보는 값(최신)이 어긋날 수 있습니다. 예를 들어 get_or_create() 가 "이미 있다"며 IntegrityError 를 냈는데, 바로 뒤의 get() 으로는 그 행이 안 보입니다. 유니크 검사는 최신 값을, get() 은 옛 스냅샷을 보기 때문입니다. 그리고 "읽고 → 계산 → 저장"의 갱신 분실은 InnoDB 의 READ COMMITTED 와 REPEATABLE READ 모두 막아 주지 않습니다.

같은 행을 동시에 UPDATE 했을 때 뒤에 온 쪽의 결과를 엔진별로 모으면 이렇습니다.

격리 수준PostgreSQLInnoDB
READ COMMITTED기다린 뒤 최신 버전에 적용기다린 뒤 최신 버전에 적용
REPEATABLE READ기다린 뒤 에러, 재시도 필요기다린 뒤 최신 버전에 적용, 에러 없음

✅ 우선한 것

같은 행의 다음 버전은 하나

  • 두 쓰기가 한 행에 섞이지 않는다
  • PostgreSQL 의 REPEATABLE READ 는 스냅샷과 어긋난 쓰기를 거부한다

🗑️ 버린 것

쓰기의 동시성과 단순한 코드

  • 같은 행을 고치는 쓰기는 MVCC 에서도 여전히 기다리고, 데드락도 남는다
  • 거부를 택한 쪽은 애플리케이션이 재시도를 짜야 하고, 거부하지 않는 쪽은 애플리케이션이 갱신 분실을 막아야 한다

이 선택에서 생긴 개념: 쓰기용 행 잠금, 갱신 분실, 직렬화 실패(serialization failure)와 재시도, "최신 값 읽기"인 잠금 읽기.

06선택 ⑤ 스냅샷으로도 못 막는 어긋남

서로 다른 행을 고쳤는데 규칙이 깨지는 경우

선택 ④는 같은 행을 두 번 고치는 충돌만 잡습니다. 그런데 서로 다른 행을 고쳤는데도 규칙이 깨지는 경우가 있습니다. "당직 의사는 최소 한 명" 규칙이 있고 지금 두 명이 당직입니다. 두 의사가 동시에 "나 말고 한 명이 더 있으니 빠져도 된다"고 확인한 뒤, 각자 자기 행만 고칩니다.

실측 — 두 세션이 각자 당직 수를 세고(2명), 각자 자기 행만 off 로 고침 (발췌)

REPEATABLE READ   A: COMMIT 성공   B: COMMIT 성공            최종 당직 0명
SERIALIZABLE      A: COMMIT 성공   B: ERROR: could not serialize access due to
                                      read/write dependencies among transactions
                                                               최종 당직 1명

REPEATABLE READ 에서 두 트랜잭션은 서로 다른 행을 고쳤으니 행 잠금으로는 부딪히지 않았습니다. 둘 다 같은 스냅샷(2명)을 근거로 판단했고, 결과는 아무도 하나씩 돌렸다면 나올 수 없는 0명입니다. 이 현상을 write skew 라고 부르고, 스냅샷 하나로 트랜잭션을 돌리는 방식(스냅샷 격리)의 알려진 한계입니다.

PostgreSQL 의 SERIALIZABLE 은 이 경우를 잡습니다. 트랜잭션들이 무엇을 읽었고 누가 그것을 고쳤는지를 추적합니다. 당직 예에서 A 는 B 의 행을 B 가 고치기 전 값으로 읽었습니다. 하나씩 돌렸다면 A 가 B 보다 먼저 돈 경우에만 나올 수 있는 값입니다. B 도 A 의 행을 A 가 고치기 전 값으로 읽었으니, B 가 A 보다 먼저여야 합니다. 이런 고리는 하나씩 돌린 어떤 순서로도 설명할 수 없습니다. PostgreSQL 은 고리가 생길 수 있는 모양(한 트랜잭션이 읽은 것을 다른 트랜잭션이 고친 관계가 연달아 두 번 이어진 모양)을 보면, 실제로 고리가 완성되지 않았더라도 안전하게 한쪽을 에러로 끝냅니다. 이 기법을 SSI(Serializable Snapshot Isolation)라고 합니다.

✅ 우선한 것

하나씩 돌린 것과 같은 결과

  • write skew 까지 막아, 애플리케이션 규칙을 데이터베이스가 지켜 준다
  • 읽기를 잠그지 않는 것은 그대로다

🗑️ 버린 것

실패하지 않는 커밋

  • 같은 행을 건드리지 않아도 에러가 날 수 있어, 모든 트랜잭션에 재시도가 필요하다
  • 읽은 범위를 추적하는 비용이 들고, 안전하게 잡느라 실제 충돌이 아닌 경우에도 실패한다

이 선택에서 생긴 개념: 스냅샷 격리와 그 한계인 write skew, SSI.

07선택 ⑥ 옛 버전은 어디에 두고 언제 치우나

벤더마다 다른 마지막 갈림길

선택 ②는 옛 버전을 치우는 일을 남겼고, 선택 ③은 스냅샷이 살아 있는 동안 그 일을 미루게 만들었습니다. ④ · ⑤를 거치는 동안에도 이 비용은 그대로 쌓입니다. 벤더가 가장 크게 갈리는 곳이 이 비용을 어디에 두고 언제 치르느냐이고, 이 차이가 운영에서 겪는 증상의 차이로 이어집니다.

엔진옛 버전의 자리치우는 방식
PostgreSQL테이블 안. 새 버전을 옛 버전 옆에 쓴다VACUUM 이 더는 아무도 볼 수 없는 버전의 자리를 재사용 가능으로 표시한다
MySQL InnoDB행 본체는 제자리에서 고치고 옛 값은 undo log 로 옮긴다백그라운드 purge 가 필요 없어진 undo 기록과, 지운 행 · 보조 인덱스의 옛 항목을 지운다
Oracleundo 영역보존 기간(undo_retention)은 보장이 아닌 목표다. 공간이 바닥나면 기간 안의 undo 도 덮어쓰고, retention guarantee 를 켜면 덮어쓰지 않는 대신 쓰기가 실패한다

옛 버전을 어디에 두느냐가 곧 무엇을 우선했느냐입니다.

엔진✅ 우선한 것🗑️ 버린 것
PostgreSQL옛 값을 옮기지 않아 갱신과 롤백이 단순하다. 롤백은 그 트랜잭션을 "취소됨"으로 표시하면 끝난다테이블이 부풀고, VACUUM 이 갱신 속도를 따라가야 한다
InnoDB행 본체를 제자리에서 고쳐 테이블이 덜 부푼다. 보조 인덱스의 옛 항목과 지운 행은 purge 전까지 남는다옛 버전을 읽으려면 undo 를 거슬러 가야 하고, 롤백도 undo 를 되돌려 적용해야 한다
Oracle옛 버전이 쓰는 공간의 상한긴 조회가 필요한 옛 값을 잃고 실패할 수 있다

그렇다면 언제 치울 수 있을까요? 한 세션이 트랜잭션을 연 채 멈춰 있는 동안, 다른 세션이 1,000행을 고쳐 커밋하고 VACUUM 을 돌렸습니다. 고치기 전 버전은 이제 새로 볼 트랜잭션이 없으면 죽은 버전입니다. VACUUM 은 열려 있는 트랜잭션 중 가장 오래된 것의 번호나 스냅샷을 기준선으로 삼고, 그 뒤에 지워진 버전은 남겨 둡니다. 멈춘 세션이 무엇을 했느냐에 따라 기준선이 달라졌습니다.

실측 — 멈춘 세션의 상태별, VACUUM 뒤 남은 죽은 버전 수 (PostgreSQL, 발췌)

READ COMMITTED,  SELECT 만 하고 멈춤                  -> 0      -- 정리를 막지 않음
READ COMMITTED,  먼저 다른 테이블에 INSERT 하고 멈춤  -> 1000   -- 트랜잭션 ID 를 받아서
READ COMMITTED,  다른 테이블 행을 FOR UPDATE 하고 멈춤 -> 1000   -- 행 잠금도 쓰기라 ID 를 받아서
REPEATABLE READ, SELECT 만 하고 멈춤                  -> 1000   -- 스냅샷을 쥐고 있어서
⚠️ 핵심 통찰: 오래 열린 트랜잭션이 옛 버전을 붙잡는다

옛 버전은 그것을 볼 수 있는 트랜잭션이 하나라도 남아 있으면 지울 수 없습니다. PostgreSQL 에서 정리를 막는 것은 REPEATABLE READ 이상에서 스냅샷을 쥐고 있거나, 이미 쓰기(행 잠금 포함)를 한 채 열려 있거나, 한 문장이 오래 도는 트랜잭션입니다. READ COMMITTED 에서 읽기만 하고 멈춰 있는 트랜잭션은 문장이 끝날 때 스냅샷을 놓으므로 막지 않습니다. 증상은 정리 방식을 따라 갈립니다. PostgreSQL 과 InnoDB 는 치우지 못한 버전이 쌓여 테이블이나 undo 가 부풉니다. Oracle 은 공간이 모자라면 아직 필요한 undo 도 덮어쓰고, 그 옛 값이 필요한 긴 조회가 ORA-01555: snapshot too old 로 끝납니다.

이 선택에서 생긴 개념: VACUUM, purge, undo 보존 기간, snapshot too old.

08실무 — Django에서

1. 기본 격리 수준을 알고 시작한다

Django 는 PostgreSQL 에서 데이터베이스와 같은 READ COMMITTED 를 씁니다. MySQL 에서는 MySQL 기본값(REPEATABLE READ)을 따르지 않고 READ COMMITTED 로 연결합니다. 문서는 그 이유로 05장의 get_or_create() 사례를 들어, REPEATABLE READ 에서는 데이터 손실이 가능하다고 경고합니다(의역). 바꾸려면 DATABASES 의 OPTIONS 에 적습니다.

from django.db.backends.postgresql.psycopg_any import IsolationLevel

DATABASES = {
    "default": {
        # ...
        "OPTIONS": {"isolation_level": IsolationLevel.SERIALIZABLE},  # PostgreSQL
    },
}

올리면 05 · 06장의 직렬화 실패가 생기므로, 재시도 코드 없이 설정만 올리면 에러만 늘어납니다.

2. 갱신 분실과 write skew 는 세 가지 중 하나로 막는다

❌ 나쁜 예 — 읽어서 파이썬에서 계산하고 저장 (05장의 최종 80)

with transaction.atomic():
    account = Account.objects.get(pk=account_id)
    account.balance -= amount          # 다른 요청이 그사이 바꾼 값을 모른다
    account.save()

✅ 좋은 예 ① — 계산을 데이터베이스에 맡긴다 (단일 UPDATE)

Account.objects.filter(pk=account_id).update(balance=F("balance") - amount)
# UPDATE ... SET balance = balance - %s  → 같은 시나리오에서 최종 50

F("balance") 는 파이썬으로 읽어 온 값이 아니라 컬럼 자체를 가리킵니다. 그래서 뺄셈이 SQL 안에서 행 잠금을 쥔 채 일어납니다. READ COMMITTED 에서는 기다린 뒤 최신 값에 적용되고, PostgreSQL REPEATABLE READ 이상에서는 스냅샷 뒤에 바뀐 행이면 직렬화 실패(40001)가 납니다(05장).

✅ 좋은 예 ② — 읽을 때 잠근다 (잔액 검사처럼 계산 전에 판단이 필요할 때)

with transaction.atomic():
    account = Account.objects.select_for_update().get(pk=account_id)
    if account.balance < amount:
        raise InsufficientBalance
    account.balance -= amount
    account.save()
# 실측: 뒤에 온 쪽은 앞 트랜잭션이 커밋할 때까지 약 0.6초 기다린 뒤 70 을 읽어 50 을 저장

select_for_update() 는 05장의 잠금 읽기(SELECT ... FOR UPDATE)를 만듭니다. READ COMMITTED 에서는 앞 트랜잭션을 기다린 뒤 최신 값을 읽고, 커밋할 때까지 그 행을 잠급니다. PostgreSQL REPEATABLE READ 이상에서는 스냅샷 뒤에 바뀐 행이면 최신 값을 읽지 않고 직렬화 실패를 냅니다.

세 번째 방법은 격리 수준을 올리고 실패하면 다시 하는 것입니다. 06장 같은 여러 행에 걸친 규칙은 이 방법이 아니면 잠글 대상을 정하기 어렵습니다. 1번의 설정은 연결 전체에 걸리므로, 그렇게 올리면 이 루프가 모든 쓰기 트랜잭션에 필요해집니다. 한 곳만 올리려면 같은 DB 를 가리키는 별도 DATABASES 별칭에 SERIALIZABLE 을 주고, 그 트랜잭션과 안의 쿼리를 모두 using 으로 그 별칭에 보냅니다.

from django.db import OperationalError, transaction

for attempt in range(3):
    try:
        with transaction.atomic():
            leave_oncall(doctor_id)
        break
    except OperationalError as e:
        cause = e.__cause__
        code = getattr(cause, "sqlstate", None) or getattr(cause, "pgcode", None)
        if code != "40001":   # 직렬화 실패만 재시도
            raise
else:
    raise RetryExhausted   # for 가 break 없이 끝나면, 곧 세 번 다 실패하면 실행

직렬화 실패는 SQLSTATE(에러 종류를 나타내는 표준 다섯 자리 코드)가 40001 이고, Django 에서는 OperationalError 로 감싸져 올라옵니다. 원래 드라이버 예외는 __cause__ 에 있습니다. PostgreSQL 드라이버 psycopg 3 은 이 코드를 sqlstate 에, psycopg2 는 pgcode 에 담으므로 코드에서 둘 다 봅니다. 재시도는 반드시 트랜잭션 전체를 처음부터 다시 해야 합니다. 실패한 트랜잭션 안의 값은 이미 낡았기 때문입니다. 그래서 이 루프는 바깥에 다른 atomic 이 없을 때만 맞습니다. ATOMIC_REQUESTS(요청 하나를 트랜잭션 하나로 감싸는 설정)를 켰다면 안쪽 atomic 은 저장점이 되어 처음부터 다시 하지 못합니다.

⚠️ 흔한 실수: atomic 안에서 오래 머문다

transaction.atomic() 안에서 외부 API 를 부르거나 대용량 파일을 처리하면, 그동안 트랜잭션이 열려 있습니다. select_for_update 를 썼다면 다른 요청이 그만큼 줄을 서고, 행 잠금도 쓰기로 쳐서 07장처럼 옛 버전 정리까지 밀립니다. 다른 쓰기를 했거나 REPEATABLE READ 이상이어도 밀립니다. 트랜잭션 안에는 데이터베이스 작업만 두고 나머지는 밖으로 뺍니다.

3. 읽기 위주인가, 쓰기 위주인가

00장의 짧은 답대로 MVCC 의 덕은 읽기 쪽에 갑니다. 그래서 고르는 것이 달라집니다. 조회가 대부분이면 기본 READ COMMITTED 와 보통 SELECT 로 충분하고, 여러 테이블을 한 시점으로 맞춰야 하는 집계만 REPEATABLE READ 로 묶습니다.

조회수 · 재고처럼 같은 행에 쓰기가 몰리면 격리 수준보다 쓰는 방식이 중요합니다. 그 행은 05장처럼 한 줄로 처리되므로 F() 한 문장 UPDATE 나 짧은 select_for_update 로 줄을 짧게 합니다. 갱신마다 옛 버전도 생기므로 PostgreSQL 은 VACUUM 이, InnoDB 는 purge 가 그 속도를 따라가야 합니다(PostgreSQL 은 인덱스 컬럼을 고치지 않는 갱신이면 페이지에 다시 접근할 때 일부를 미리 정리합니다). 오래 도는 집계 조회는 이 정리를 붙잡으므로 그런 데이터와 떼어 둡니다(07장).

09한 장 요약 치트시트

트랜잭션은 어떻게 서로 방해하지 않고 읽고 쓸까?

행의 옛 버전을 남겨 두고, 읽는 쪽에게는 자기 스냅샷 시점의 버전을 보여 주기 때문이다. 그래서 보통 읽기는 잠금이 필요 없고 쓰기를 기다리지 않는다. 하지만 같은 행을 고치는 쓰기끼리는 여전히 행 잠금으로 줄을 서고, 부딪히면 엔진에 따라 기다렸다가 최신 값에 쓰거나(InnoDB, PostgreSQL READ COMMITTED) 에러를 내고 재시도를 요구한다(PostgreSQL REPEATABLE READ · SERIALIZABLE). 벤더 차이는 기본 격리 수준, 이 쓰기 충돌의 처리, 옛 버전을 어디에 두고 언제 치우는지에서 난다.

읽기 위주와 쓰기 위주는 왜 다르게 고르나?

MVCC 가 없앤 기다림은 읽기와 쓰기 사이뿐이기 때문이다. 조회가 대부분이면 기본 READ COMMITTED 와 보통 SELECT 로 충분하다. 같은 행에 쓰기가 몰리면 그 쓰기는 여전히 줄을 서고 옛 버전 정리 비용만 늘어나므로, 격리 수준보다 F() · 짧은 잠금 같은 쓰는 방식과 긴 집계 조회를 떼어 두는 배치를 먼저 고른다.

단계우선한 것 / 버린 것생긴 개념

② 옛 버전 남기기읽기와 쓰기 사이의 동시성 / 값은 하나라는 단순함행 버전, xmin · xmax, 가시성 규칙, undo log
③ 기준 시점 정하기일관된 읽기 / 최신 값과의 일치스냅샷, 문장 단위 · 트랜잭션 단위 스냅샷
④ 쓰기는 다시 잠그기같은 행의 다음 버전은 하나 / 쓰기 동시성과 단순한 코드갱신 분실, 직렬화 실패, 잠금 읽기

READ UNCOMMITTED 를 고르면 PostgreSQL 은 READ COMMITTED 와 같게 동작합니다.
