00태초의 웹 — 파일 배달부

1991년의 웹 서버는 하는 일이 딱 하나였습니다. 디스크에 있는 HTML 파일을 찾아서 그대로 보내주기. 요청 URL이 /about.html이면 about.html 파일을 읽어 응답으로 던집니다. 끝.

브라우저 ──"/about.html 주세요"──▶ 웹서버 ──▶ 디스크에서 about.html 읽음 브라우저 ◀────── 파일 내용 그대로 ◀──┘ 누가 언제 요청해도 같은 내용. 웹 전체가 "읽기 전용"이었다.

문제는 곧 나타났습니다. 사람들은 움직이는 웹을 원했습니다. 검색 결과, 방명록, 접속 카운터, 폼 제출 — 요청한 사람과 내용에 따라 매번 다른 응답을 만들어야 하는 것들. 그런데 웹 서버는 파일 배달부일 뿐, 프로그램을 실행할 줄은 몰랐습니다.

이 문서가 답하는 것

① "프로그램을 실행하는 웹"이 어떻게 시작됐나(CGI) ② 그 방식의 비용이 어떻게 WAS를 만들었나 ③ 왜 웹서버와 WAS가 합쳐지지 않고 두 겹으로 남았나. 끝까지 읽으면 nginx→gunicorn→Django 구조가 "관습"이 아니라 "필연"으로 보입니다.

01CGI의 발명 (1993)

해법은 단순하고 대담했습니다. "웹서버야, 네가 직접 계산하지 말고, 외부 프로그램을 실행해서 그 출력을 응답으로 보내라."

1993년, NCSA(미국 국립슈퍼컴퓨팅응용연구소)의 Rob McCool이 이 규약을 정리했습니다. 그가 만들던 NCSA HTTPd는 세계 최초급 웹서버이자 Apache의 직계 조상입니다. 이 규약이 CGI(Common Gateway Interface) — "웹서버와 외부 프로그램 사이의 공통 관문 규약"입니다. 훗날 RFC 3875로 표준화됩니다.

🍽️ 비유

파일 배달부(웹서버)가 손님의 특별 주문을 받았습니다. 배달부는 요리를 못 하니, 주문서를 들고 요리사(외부 프로그램)에게 달려가 요리를 받아다 배달합니다. CGI는 그 "주문서 양식"입니다 — 배달부와 요리사가 서로 말이 통하게 하는 약속.

이 발명의 의미는 큽니다. 웹서버를 고치지 않고도, 어떤 언어로든(Perl, C, 셸 스크립트...) 동적 웹을 만들 수 있게 됐습니다. 동적 웹, 즉 오늘날 "웹 애플리케이션"이라 부르는 모든 것의 출발점입니다.

02CGI는 어떻게 동작하나

규약 자체는 놀랄 만큼 소박합니다. 웹서버는 요청이 오면:

  1. 요청 정보를 환경변수에 담는다 — 메서드는 REQUEST_METHOD, 쿼리는 QUERY_STRING, 경로는 PATH_INFO...
  2. 지정된 프로그램을 새 프로세스로 실행한다
  3. 요청 본문(body)은 프로그램의 표준 입력(stdin)으로 넣어준다
  4. 프로그램이 표준 출력(stdout)에 찍은 내용을 그대로 HTTP 응답으로 보낸다

1990년대의 실제 모습 — Perl CGI 스크립트

#!/usr/bin/perl
# 웹서버가 요청마다 이 스크립트를 "새 프로세스로" 실행한다

my $name = $ENV{'QUERY_STRING'};   # 요청 정보는 환경변수로 들어옴

print "Content-Type: text/html\n\n";  # stdout에 찍으면 = HTTP 응답
print "<h1>Hello, $name!</h1>";

프로그램 입장에선 웹을 몰라도 됩니다. 환경변수를 읽고 stdout에 찍는다 — 그게 전부. 이 단순함 덕에 CGI는 모든 웹서버가 채택하는 표준이 됐고, 웹은 폭발적으로 동적화됐습니다.

✅ 지금도 남아 있는 흔적

Django에서 request.META['REQUEST_METHOD'], QUERY_STRING 같은 키를 본 적 있다면 — 그게 CGI의 환경변수 이름 그대로입니다. WSGI의 environ 딕셔너리도 CGI 환경변수 규약을 계승한 것입니다. 30년 전 규약이 여러분 코드 안에 살아 있습니다.

03CGI의 비용 — 요청마다 프로세스

단순함의 청구서가 도착합니다.

CGI의 치명적 설계가 하나 있습니다. 요청이 올 때마다 프로세스를 새로 만들고, 응답을 보내면 죽입니다. 초당 100 요청이면 초당 100번의 프로세스 생성·소멸.

요청 1 ──▶ [프로세스 생성 → 인터프리터 로딩 → 실행 → 응답 → 종료] 요청 2 ──▶ [프로세스 생성 → 인터프리터 로딩 → 실행 → 응답 → 종료] 요청 3 ──▶ [프로세스 생성 → 인터프리터 로딩 → 실행 → 응답 → 종료] └── 매번 처음부터. 아무것도 재사용 못 함 ──┘

프로세스를 새로 만드는 건 OS 입장에서 꽤 비싼 작업입니다. 실행 파일/인터프리터를 메모리에 올리고, 런타임을 초기화하고, 실행 환경을 차리고... 언어에 따라 요청당 수백 ms까지 갑니다. 그런데 진짜 문제는 따로 있습니다:

  • 매번 처음부터 — Perl/Python 인터프리터, 라이브러리 로딩을 요청마다 반복
  • DB 커넥션도 매번 — 프로세스가 죽으니 커넥션 풀 같은 건 존재할 수 없음. 요청마다 DB에 새로 접속
  • 상태를 못 가짐 — 캐시, 세션, 준비된 데이터... 전부 프로세스와 함께 증발
⚠️ 핵심 통찰

웹이 커지자 CGI는 자기 발명이 만든 트래픽을 감당하지 못하게 됐습니다. 병목은 여러분의 코드가 아니라 "실행 환경을 매번 새로 차리는 비용"이었습니다. 이후 30년의 진화는 전부 이 한 문장을 해결하는 역사입니다: "어떻게 하면 프로그램을 죽이지 않고 계속 살려둘까?"

04진화 1: 프로세스를 살려두자

1990년대 중반, 두 갈래의 해법이 나옵니다.

🔌 FastCGI — 밖에서 살려두기

프로그램을 상주 프로세스로 계속 띄워두고, 웹서버가 소켓으로 요청을 전달. 한 프로세스가 여러 요청을 연달아 처리.

  • 생성·로딩 비용을 한 번만 지불
  • CGI의 프로그래밍 모델은 거의 유지
  • PHP-FPM이 이 계보의 현역

🧩 mod_php/mod_perl — 안에 넣기

아예 인터프리터를 웹서버(Apache) 안에 내장. 별도 프로세스 없이 웹서버가 직접 코드 실행.

  • 가장 빠른 경로 (프로세스 경계 없음)
  • 대신 앱이 죽으면 웹서버도 같이 위험
  • 웹서버와 앱의 운명이 묶임 → 뒷날의 교훈

둘 다 "매번 새로 차리는 비용"은 없앴습니다. 그런데 내장 방식(mod_php)의 부작용이 중요한 교훈을 남깁니다. 앱 코드의 메모리 누수·크래시가 웹서버 전체를 흔들고, 앱을 재배포하려면 웹서버를 건드려야 하고, 웹서버 설정과 앱 로직이 뒤엉킵니다. "정적 파일 나르기"와 "비즈니스 로직 실행"은 성격이 너무 다른 일이라는 게 드러난 겁니다. 이 긴장이 다음 진화를 부릅니다.

05진화 2: WAS의 탄생

그래서 방향이 정해집니다. 애플리케이션을 실행하는 전용 서버를 따로 두자.

📎 용어: WAS

WAS(Web Application Server) = 애플리케이션 코드를 상주 상태로 실행·관리하는 서버. 참고로 WAS는 한국 업계에서 주로 쓰는 명칭이고, 해외에선 application server라 부릅니다. Java 진영의 Tomcat이 대표적이고, Python 세계에선 gunicorn/uvicorn이 사실상 같은 역할입니다.

WAS가 CGI 시대의 문제를 어떻게 해결하는지 보면 존재 이유가 선명해집니다:

CGI의 문제WAS의 해법
요청마다 프로세스 생성·소멸앱을 미리 로딩해 상주. worker 프로세스/스레드가 요청을 돌려가며 처리
DB 접속을 매번 새로프로세스가 살아 있으니 커넥션 풀 유지 가능
상태·캐시를 못 가짐메모리 캐시, 세션, 준비된 설정을 재사용
동시 요청 = 프로세스 수만큼 폭증정해진 worker 수만 미리 만들어 돌려쓰는 풀(pool) 방식으로 동시성 관리

즉 WAS의 본질은 "비싼 준비(로딩·커넥션·초기화)를 한 번만 하고, 요청은 준비된 환경에서 처리한다"입니다. 여기에 앱 생명주기 관리(시작·재시작·죽은 worker 교체)까지 얹은 것이 현대의 WAS입니다.

✅ 우리 스택으로 번역하면

gunicorn이 Django 앱을 worker 프로세스 여러 개로 미리 띄워두고(상주), 요청이 오면 노는 worker에게 배분합니다. Django의 DB 커넥션 재사용(CONN_MAX_AGE)도 프로세스가 살아 있기에 가능한 것. gunicorn = 파이썬의 WAS라고 이해하면 정확합니다. 그리고 WAS와 앱이 대화하는 규약이 WSGI — CGI의 직계 후손입니다(환경변수 딕셔너리 environ을 넘겨주는 것까지 닮았죠).

06웹서버와 WAS, 갈라진 진화

그럼 WAS가 다 하면 되지, 왜 웹서버(nginx)를 앞에 또 둘까?

두 서버가 마주하는 문제의 성격이 정반대이기 때문입니다. 각자 자기 문제에 최적화하다 보니 서로 다른 생물로 진화했습니다.

🌐 웹서버 (nginx, Apache)

문제: "수만 개의 커넥션을 어떻게 싸게 붙들고 있나"

  • 정적 파일 서빙, SSL 종료, 압축
  • 느린 클라이언트 상대 (모바일, 저속망)
  • 해법: 이벤트 루프 — 스레드 몇 개로 수만 커넥션 담당
  • 요청당 일은 얕고, 커넥션은 많고 오래감

⚙️ WAS (gunicorn, Tomcat)

문제: "무겁고 복잡한 앱 코드를 어떻게 안전하게 실행하나"

  • 비즈니스 로직, DB 접근, 템플릿 렌더링
  • 블로킹·CPU 소모·크래시 가능성이 있는 코드
  • 해법: worker 프로세스 풀 — 격리하고 죽으면 교체
  • 요청당 일은 깊고, 동시 처리 수는 제한적

1990년대 말~2000년대의 C10K 문제("서버 한 대로 커넥션 1만 개를 어떻게 버티나")가 이 분화를 결정지었습니다. 커넥션마다 스레드를 하나씩 붙이면 스레드 1만 개가 필요한데, 스레드는 각자 메모리(스택)를 차지하고 OS가 이들을 번갈아 실행하느라 전환 비용이 폭증해 서버가 일보다 전환에 더 바빠집니다. 그래서 웹서버는 이벤트 루프 — 적은 수의 스레드가 수만 개 커넥션의 "이벤트(데이터 도착 등)"만 골라 처리하는 방식 — 로 진화했고(nginx가 그 대표), 무거운 앱 실행은 WAS의 worker 풀에 맡기는 분업이 자리잡았습니다.

🏨 비유

호텔로 치면 웹서버는 로비의 컨시어지입니다. 수백 명의 손님을 동시에 응대하고, 간단한 질문(정적 파일)은 즉답하고, 수상한 손님은 걸러냅니다(보안·rate limit). WAS는 주방입니다. 주문(동적 요청)만 받아서 요리사 몇 명(worker)이 깊은 작업을 합니다. 컨시어지에게 요리를 시키거나 요리사에게 로비를 맡기면 둘 다 망합니다. 일의 성격이 다르면 서버도 달라야 합니다.

⚠️ 그래서 nginx를 앞에 두는 실전 이유

느린 클라이언트가 응답을 1분 동안 받아가는 상황을 상상해 보세요. nginx가 없으면 그 1분 동안 귀한 gunicorn worker 하나가 통째로 붙들립니다(worker는 몇 개 안 됨!). nginx가 앞에서 응답을 버퍼링해주면 worker는 응답을 nginx에 던지고 즉시 다음 요청으로. 이것 하나만으로도 두 겹 구조의 값어치가 있습니다. 정적 파일, SSL, 트래픽 스파이크 방어는 덤입니다.

07현대 아키텍처 한 바퀴

이제 전체 그림을 그릴 수 있습니다. 요청 하나의 여정:

브라우저 │ HTTPS ▼ [웹서버: nginx] ← 커넥션 수만 개 담당 (이벤트 루프) │ ├─ 정적 파일(/static)이면 → 여기서 바로 응답, 끝 │ ├─ SSL 종료, 압축, 버퍼링, rate limit │ ▼ 동적 요청만 뒤로 전달 (리버스 프록시) [WAS: gunicorn] ← worker 프로세스 N개 상주 (프로세스 풀) │ ▼ WSGI 규약 (CGI의 후손: environ 딕셔너리) [앱: Django] ← 비즈니스 로직, ORM, 템플릿 │ ▼ [DB: PostgreSQL] ← 커넥션 풀로 재사용
📎 용어: 리버스 프록시

리버스 프록시(reverse proxy) = 클라이언트 요청을 대신 받아 뒤의 서버로 전달해주는 중개자. "프록시"가 클라이언트 쪽 대리인이라면, "리버스"는 서버 쪽 대리인입니다. nginx가 gunicorn 앞에서 하는 역할이 바로 이것.

각 층이 CGI 시대의 어떤 고통을 해결했는지 대응시켜 보면:

층물려받은 숙제진화의 결과
nginx커넥션 폭증 (C10K)이벤트 루프로 수만 커넥션을 싸게
gunicorn요청마다 프로세스 생성 (CGI)worker 상주 + 풀로 재사용
WSGI서버↔앱 규약 (CGI 인터페이스)환경변수 → environ 딕셔너리로 계승
Django매 요청 초기화앱·설정·커넥션을 한 번만 준비
✅ 한 걸음 더: ASGI

WSGI는 "요청 하나 → 응답 하나"의 동기 모델이라 WebSocket이나 async 뷰를 못 다룹니다. 그래서 async 버전 규약인 ASGI(uvicorn이 대표 서버)가 나왔습니다. DB·API 응답을 기다리는 동안 다른 요청을 처리하는 비동기 방식을 서버 규약 레벨로 끌어올린 것. 진화는 지금도 진행 중입니다.

08CGI는 죽었나 — 서버리스라는 환생

CGI 방식 자체는 성능 문제로 사실상 은퇴했습니다. 그런데 재미있는 반전이 있습니다.

AWS Lambda 같은 서버리스를 보세요. "요청이 오면 실행 환경을 띄워 코드를 실행하고, 끝나면 정리한다. 상태는 유지하지 않는다." — 어디서 본 모델이죠? CGI의 사상과 정확히 같습니다. 그리고 앓는 문제도 같습니다. 실행 환경을 새로 차리는 비용, 서버리스 세계에선 이걸 콜드 스타트(cold start)라고 부릅니다. CGI의 fork 비용이 이름만 바꿔 돌아온 겁니다.

  • CGI: 요청마다 프로세스 생성 → 느려서 WAS(상주)로 진화
  • 서버리스: 요청마다 실행환경 기동 → 콜드 스타트가 아프니 warm 인스턴스 유지, provisioned concurrency... 결국 또 "살려두기"로 회귀
🔄 역사는 반복된다

"매번 새로 차릴 것인가(단순함·격리·확장 용이) vs 살려둘 것인가(빠름·상태 유지)"는 웹 30년의 영원한 시소입니다. CGI → WAS로 기울었다가, 서버리스로 다시 반대편을 시도했다가, 콜드 스타트 때문에 또 가운데로. 트레이드오프는 사라지지 않고 자리만 옮깁니다. 이걸 알면 다음에 어떤 새 패러다임이 와도 "무엇을 얻고 무엇을 내주는 거지?"를 먼저 물을 수 있습니다.

09한 장 요약 치트시트

  1. 1991정적 웹웹서버 = 파일 배달부. HTML을 그대로 서빙
  2. 1993CGI요청마다 외부 프로그램을 새 프로세스로 실행 → 동적 웹의 시작 (NCSA, Rob McCool)
  3. 1996~FastCGI / mod_php프로세스 생성 비용 제거 — 상주시키거나 웹서버에 내장
  4. 2000sWAS 정착 + C10K앱 전용 서버(worker 풀) / 웹서버는 이벤트 루프로 커넥션 특화 → 분업 확정
  5. 현재nginx → gunicorn → Django웹서버(커넥션·정적·버퍼링) + WAS(앱 상주 실행) + WSGI(CGI의 후손 규약)
WAS는 왜 필요해졌나

CGI가 요청마다 프로세스를 새로 만들던 비용(인터프리터 로딩·DB 재접속·상태 증발)을 없애기 위해. WAS의 본질 = "비싼 준비는 한 번만, 요청은 상주 worker가 처리."

웹서버와 WAS는 왜 갈라졌나

푸는 문제가 정반대라서. 웹서버는 "얕은 일 × 수만 커넥션" → 이벤트 루프로, WAS는 "깊은 일 × 제한된 동시성" → worker 프로세스 풀로 각자 최적화. 앞뒤로 세우면(리버스 프록시) 서로의 약점을 가려준다.

기억할 것내용
CGI웹서버↔외부 프로그램 규약. 요청마다 새 프로세스 (환경변수 in, stdout out)
CGI의 병실행 환경을 매번 새로 차리는 비용 — 코드가 아니라 준비가 병목
WAS앱을 상주 실행. 커넥션 풀·캐시·worker 관리 (gunicorn = 파이썬의 WAS)
WSGIWAS↔파이썬 앱 규약. CGI 환경변수의 직계 후손 (environ)
nginx를 앞에 두는 이유정적·SSL·버퍼링·스파이크 방어 — 귀한 worker를 느린 클라이언트에서 보호
서버리스 콜드 스타트CGI의 fork 비용의 환생 — 트레이드오프는 자리만 옮긴다
