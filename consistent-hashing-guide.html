안정 해싱
Consistent Hashing Ring

캐시 서버가 3대에서 4대가 되는 순간, 기존 키의 75%가 엉뚱한 서버를 가리키게 된다면? 서버 한 대를 늘렸을 뿐인데 캐시 전체가 무효화되는 사고 — 안정 해싱은 이 문제를 풀기 위해 태어났습니다.

💬 "결정론적 알고리즘을 이용한 라우팅과 클러스터 환경에서의 수평확장성 확보"
— 이번 주 키워드를 제안하며 붙은 한 줄. 이 문서는 이 문장을 풀어내는 것이 목표입니다.

00서버가 한 대 늘어나는 순간 생기는 일

트래픽이 늘어서 서버를 추가했더니, 오히려 장애가 났다

서비스가 커지면 데이터를 한 대의 서버에 다 담을 수 없게 됩니다. 그래서 캐시든 DB든 여러 대에 나눠 담기 시작하는데, 이때 즉시 부딪히는 질문이 있습니다.

"이 키(key)는 몇 번 서버에 저장하고, 읽을 때는 어떻게 같은 서버를 다시 찾아가지?"

📎 용어: 샤딩(sharding) / 파티셔닝(partitioning)

샤딩 = 데이터를 여러 서버(노드)에 쪼개어 나눠 저장하는 것. 각 조각을 샤드(shard) 또는 파티션(partition)이라 부릅니다. "user:1~100만은 A서버, 100만~200만은 B서버"처럼 범위로 나눌 수도 있고, 이 문서의 주제처럼 해시로 나눌 수도 있습니다.

가장 먼저 떠오르는 답은 hash(key) % 서버수입니다. 간단하고, 빠르고, 균등하게 퍼집니다.

📎 용어: 해시 함수 — 이 문서 전체의 전제

해시 함수 = 임의의 문자열을 정해진 범위의 큰 정수로 바꿔주는 함수(예: md5("user:42") → 어떤 128비트 숫자). 우리가 기대는 성질은 딱 두 가지입니다. ① 같은 입력이면 언제나 같은 출력 — 그래서 저장할 때와 읽을 때 같은 서버를 찾아갈 수 있습니다. ② 출력이 범위 전체에 고르게 흩어짐 — 그래서 키가 특정 서버에 쏠리지 않습니다. 앞으로 나오는 모든 이야기는 이 두 성질 위에 서 있습니다.

그런데 % 서버수 방식에는 치명적인 약점이 하나 있습니다 — 서버 수가 변하는 순간 거의 모든 키의 답이 바뀐다는 것. 그리고 클러스터(같은 일을 나눠 맡는 서버 묶음)에서 서버 수는 반드시 변합니다. 트래픽이 늘면 증설하고, 장비는 언젠가 죽으니까요.

이 문서가 답하는 것

① hash % N은 왜 확장에 취약한가 ② "해시 링"은 어떤 구조이고 왜 노드가 변해도 일부 키만 움직이는가 ③ 중앙 조회 서버 없이 모든 클라이언트가 같은 노드를 찾아가는 "결정론적 라우팅"은 어떻게 성립하는가. 다 읽으면 맨 위에 인용한 한 줄 — "결정론적 알고리즘을 이용한 라우팅과 수평확장성 확보" — 를 남에게 설명할 수 있게 됩니다.

01hash(key) % N은 왜 무너지는가

나머지 연산의 배신 — 재배치 폭풍(rebalancing storm)

캐시 서버 3대(N=3)에 hash(key) % 3으로 키를 분배하고 있다고 합시다. 어느 날 트래픽이 늘어 4대로 늘렸습니다(N=4). 이제 모든 키는 % 4로 다시 계산됩니다.

키의 해시값 % 3 (서버 3대) % 4 (서버 4대) 결과 ────────────────────────────────────────────────────────── hash = 12 ──▶ 서버 0 ──▶ 서버 0 그대로 ✓ hash = 13 ──▶ 서버 1 ──▶ 서버 1 그대로 ✓ hash = 14 ──▶ 서버 2 ──▶ 서버 2 그대로 ✓ hash = 15 ──▶ 서버 0 ──▶ 서버 3 이동! ✗ hash = 16 ──▶ 서버 1 ──▶ 서버 0 이동! ✗ hash = 17 ──▶ 서버 2 ──▶ 서버 1 이동! ✗ hash = 18 ──▶ 서버 0 ──▶ 서버 2 이동! ✗ ⋮ 12개 중 3개만 생존

이유는 이렇습니다. N+1대가 된 뒤 키가 갈 수 있는 서버는 N+1곳이고, 그중 우연히 예전과 같은 곳일 확률은 대략 1/(N+1)입니다. 즉 서버를 N대에서 N+1대로 늘리면 제자리에 남는 키는 평균 1/(N+1)뿐입니다. 3대→4대면 75%가 이동하고, 10대→11대면 약 91%가 이동합니다. 서버를 많이 가진 큰 클러스터일수록 피해가 더 커지는, 확장에 정확히 역행하는 구조입니다.

⚠️ 핵심 통찰 — 문제는 해시가 아니라 "나머지"다

해시 함수 자체는 죄가 없습니다. 죄인은 % N입니다. 나머지 연산은 결과가 N에 종속되기 때문에, N이 1만 변해도 거의 모든 키의 목적지가 재추첨됩니다. 캐시라면 대량 캐시 미스(cache miss — 캐시에 없어서 원본 DB까지 가는 것)가 터져 DB가 트래픽을 정통으로 맞고, 데이터 저장소라면 노드 사이에 대규모 데이터 이사가 벌어집니다. 안정 해싱의 목표는 단 하나 — 키의 목적지를 서버 "수"로부터 독립시키는 것입니다.

1/(N+1)
N대→N+1대 증설 후 제자리에 남는 키 비율
75%
3대→4대 증설 시 이동하는 키 비율 (1 − 1/4)
~91%
10대→11대 증설 시 이동하는 키 비율 — 클러스터가 클수록 피해가 커진다

02해시 링 — 안정 해싱의 핵심 아이디어

서버 수로 나누지 말고, 서버와 키를 같은 공간에 놓아라

안정 해싱(consistent hashing)은 1997년 MIT의 David Karger 연구진이 논문 「Consistent Hashing and Random Trees」에서 제안했습니다. 웹 캐시 서버가 수시로 추가/제거되는 환경에서 재배치를 최소화하는 것이 목적이었고, 공저자 중 Daniel Lewin과 Tom Leighton은 이듬해(1998년) 이 기술을 상용화한 CDN 회사 Akamai를 공동 창업했습니다. (CDN = 사용자와 가까운 곳곳에 캐시 서버 — 엣지 서버 — 를 두고 콘텐츠를 대신 전달해 주는 서비스.) 아이디어는 두 단계입니다.

  1. 1단계 — 해시 공간을 원(ring)으로 만든다해시 함수의 출력 범위(예: 0 ~ 2³²−1)를 시계처럼 둥글게 이어 붙입니다. 최댓값 다음은 다시 0입니다. 이 원 위의 "위치"는 서버 수와 아무 관계가 없습니다.
  2. 2단계 — 서버도, 키도 같은 원 위에 올린다서버는 이름(예: "10.0.1.5:6379")을 해시해 원 위의 한 점에 앉힙니다. 키도 해시해서 원 위의 한 점을 얻습니다. 키의 담당 서버는 키 위치에서 시계 방향으로 돌다가 처음 만나는 서버입니다.
0 (= 2³²) — 12시 방향 ● 노드 A ┌──────┴──────┐ ┌────┘ └────┐ ┌─┘ ✕ key "cart:77" │ ┐ │ 시계 방향 ↻ ● 노드 B │ ┘ └─┐ ✕ key "user:42" └────┐ ┌────┘ └──── ● ──────┘ 노드 C 규칙: 키 위치에서 시계 방향(↻)으로 이동 → 처음 만나는 노드가 담당 · "cart:77" 은 A를 막 지난 자리 → 시계 방향 첫 노드는 B ⇒ B 담당 · "user:42" 는 B를 막 지난 자리 → 시계 방향 첫 노드는 C ⇒ C 담당 · 노드 B가 죽으면? B가 맡던 구간(A~B)의 키만 다음 노드 C로 넘어간다. user:42 를 비롯한 나머지 구간의 키는 담당이 그대로다.

이 구조에서 노드 하나가 사라지면 어떻게 될까요? 그 노드가 맡던 구간(호, arc)의 키들만 시계 방향 다음 노드로 넘어갑니다. 다른 구간의 키들은 자기 담당 노드가 그대로이므로 아무 영향이 없습니다. 노드가 추가될 때도 마찬가지로, 새 노드는 자기 앞 구간의 키만 이전 담당자에게서 가져옵니다. 변화의 영향 반경이 "전체"에서 "이웃 구간 하나"로 줄어드는 것 — 이것이 % N과의 결정적 차이입니다.

🍕 비유 — 원탁의 피자 나누기

원탁에 사람들이 띄엄띄엄 앉아 있고, 피자 조각(키)은 테이블 가장자리를 따라 놓여 있습니다. 규칙은 "각 조각은 시계 방향으로 가장 가까운 사람이 먹는다". 한 사람이 자리를 뜨면 그 사람 몫이던 조각만 옆 사람에게 넘어갈 뿐, 테이블 전체가 조각을 재분배하지는 않습니다. 새 사람이 끼어 앉으면 옆 사람 몫의 일부만 가져갑니다. (실제 구현은 이 직관에 더해, 다음 절의 "가상 노드"로 몫의 크기까지 고르게 맞춥니다.)

📎 용어: "consistent(안정/일관)"의 의미

여기서 consistent는 트랜잭션의 일관성(consistency — DB에서 커밋 전후로 데이터 규칙이 깨지지 않는다는 그 성질)과는 다른 뜻입니다. 노드 집합이 조금 변해도 해시 결과(키→노드 매핑)가 거의 그대로 유지된다, 즉 매핑이 변화에 안정적이라는 의미입니다. 그래서 한국어로는 "안정 해시" 또는 "일관된 해싱"으로 옮깁니다.

03결정론적 라우팅 — 조회 없이 길을 찾는 법

관통 질문 전반부: "결정론적 알고리즘을 이용한 라우팅"

📎 용어: 결정론적(deterministic)

결정론적 알고리즘 = 같은 입력을 넣으면 언제, 어디서, 누가 실행해도 항상 같은 출력이 나오는 알고리즘. 반대는 실행할 때마다 결과가 달라질 수 있는 비결정론적(예: 난수 기반 무작위 선택)입니다.

키가 어느 서버에 있는지 알아내는 방법은 크게 두 갈래입니다.

⚙️ 조회 방식 (디렉터리)

"키→서버" 매핑표를 중앙 저장소에 두고 매번 물어본다

  • 매핑을 자유롭게 바꿀 수 있음 (유연)
  • 대신 조회 서버가 병목이자 단일 장애점(SPOF — 이것 하나가 죽으면 전체가 마비되는 지점)
  • 모든 요청에 조회 왕복 비용 추가

🔍 계산 방식 (결정론적 해싱)

키만 보고 수식으로 계산해서 서버를 알아낸다

  • 중앙 서버 불필요, 조회 왕복 0회
  • 같은 해시 함수 + 같은 노드 목록만 공유하면 누가 계산해도 같은 답
  • 안정 해싱이 여기에 속함

안정 해싱의 라우팅이 성립하는 조건은 단 두 가지입니다: ① 모두가 같은 해시 함수를 쓸 것 ② 모두가 같은 노드 목록(링 구성)을 알 것. 이 둘만 맞으면 애플리케이션 서버가 100대여도, 각자가 독립적으로 ring.get_node("user:42")를 계산해서 전원이 같은 서버에 도착합니다. 서로 합의하는 통신도, 중앙 코디네이터도 필요 없습니다. 이것이 "결정론적 알고리즘을 이용한 라우팅"의 실체입니다.

⚠️ 흔한 오해 — "그럼 노드 목록은 누가 알려주나?"

키→노드 계산은 결정론적이지만, 노드 목록 자체는 어딘가에서 관리되어야 합니다. 실무에서는 (a) 설정 파일에 박아두거나(nginx upstream), (b) 클라이언트 라이브러리에 서버 목록을 주거나(memcached), (c) 노드끼리 가십(gossip) 프로토콜 — 각 노드가 주기적으로 이웃과 "내가 아는 클러스터 상태"를 교환해 전체에 퍼뜨리는 방식 — 으로 동기화합니다(Dynamo·Cassandra·Redis Cluster — 각 제품은 뒤 절에서 다룹니다). 안정 해싱이 없애주는 것은 "키마다 물어보는 조회"이지, "클러스터 멤버십 관리"가 아닙니다.

✅ 실무 감각 — 왜 하필 해시인가

결정론만 필요하면 "user_id 범위로 나누기"도 결정론적입니다. 하지만 범위 분할은 인기 유저가 몰린 범위에 부하가 쏠립니다. 해시 함수는 입력을 출력 공간에 고르게 흩뿌리는 성질이 있어서, 결정론과 균등 분산을 동시에 얻습니다. 참고로 여기 쓰는 해시는 보안 목적이 아니라 분배 목적이라 암호학적 강도가 필요 없습니다. 이미 충돌 저항성이 깨졌지만 빠른 MD5나, 처음부터 비암호학적으로 설계된 MurmurHash·CRC 계열이면 충분합니다.

04가상 노드 — 불균형을 잡는 기술

노드 3개를 링에 그냥 올리면, 한 놈이 절반을 먹는다

02절의 링에는 함정이 있습니다. 노드를 해시해서 링에 앉히면 위치가 운에 따라 정해지므로, 어떤 노드는 넓은 구간을, 어떤 노드는 좁은 구간을 맡게 됩니다. 노드가 몇 개 없을수록 이 불균형은 심해지고, 특정 노드에 부하가 쏠리는 핫스팟(hot spot)이 생깁니다. 게다가 노드 하나가 죽으면 그 노드의 부하 전부가 시계 방향 다음 노드 한 대에 얹히는 것도 문제입니다.

해결책은 의외로 단순합니다. 물리 노드 하나를 링 위의 여러 점으로 쪼개서 올리는 것 — 이 점들을 가상 노드(virtual node, vnode) 또는 토큰(token)이라 부릅니다.

가상 노드 없이 (물리 노드 3개) 가상 노드 적용 (노드당 4개씩 배치) ●A ●A ●B ┌────┴────┐ ┌────┴────┐ ┌─┘ └─┐ ●C┘ └●A │ │ │ │ │ ●B ●B ●C │ │ │ │ └─┐ ┌─┘ ●A┐ ┌●B └────●C───┘ └──●C ●A──┘ A가 링의 절반을 독식 😰 구간이 잘게 섞여 A·B·C 몫이 비슷 🙂 A 죽으면 → B가 전부 인수 A 죽으면 → A의 조각들이 B와 C에 분산 인수

가상 노드는 세 가지를 한꺼번에 해결합니다.

  • 균등화 — 점을 많이 찍을수록, 운 좋게 넓은 구간과 운 나쁘게 좁은 구간이 한 노드 안에서 서로 상쇄되어 노드별 총합이 평균에 가까워집니다. 동전을 많이 던질수록 앞면 비율이 50%에 다가가는 것과 같은 원리입니다.
  • 장애 분산 — 죽은 노드의 조각난 구간들이 여러 생존 노드에 나눠서 흡수됩니다. 한 대가 부하를 독박 쓰지 않습니다.
  • 이기종 장비 대응 — 성능 좋은 서버에는 가상 노드를 더 많이 배정해 가중치를 줄 수 있습니다 (예: 신형 장비 200개, 구형 장비 100개).

이 기법을 대규모로 증명한 것이 2007년 Amazon의 Dynamo 논문입니다. Amazon 내부의 키-값 저장소(Redis처럼 key로 넣고 key로 꺼내는 단순한 구조의 DB) Dynamo는 안정 해싱 링에 가상 노드(논문 용어로는 토큰)를 결합해 장바구니 데이터를 분산했고, 이 설계는 이후 Cassandra·Riak 같은 분산 DB의 원형이 되었습니다.

✅ 실무 감각 — 가상 노드 개수도 공짜가 아니다

Cassandra는 노드당 가상 노드 수를 num_tokens 설정으로 조절하는데, 기본값이 한때 256이었다가 4.0부터 16으로 내려갔습니다. 가상 노드가 많을수록 분포는 고와지지만, 링 메타데이터가 커지고 노드 간 복구·스트리밍 연산이 느려지는 비용이 있기 때문입니다(개선된 토큰 배치 알고리즘 덕에 적은 수로도 균형이 좋아진 것도 이유). "많을수록 좋다"가 아니라 트레이드오프라는 감각을 기억하세요.

05수평 확장 시나리오 — 증설과 장애

관통 질문 후반부: "클러스터 환경에서의 수평확장성 확보"

📎 용어: 수평 확장(scale-out) vs 수직 확장(scale-up)

수직 확장 = 서버 한 대를 더 좋은 장비로 키우는 것. 한계가 빨리 오고 비쌉니다. 수평 확장 = 평범한 서버를 여러 대 추가해서 처리량을 늘리는 것. 클러스터(같은 일을 나눠 하는 서버 묶음) 운영의 기본 전략이지만, "추가한 만큼 순증"이 되려면 추가 비용(재배치)이 작아야 합니다. 안정 해싱이 바로 그 조건을 만들어 줍니다.

시나리오 A — 노드 증설

노드 n대가 키 K개를 나눠 들고 있을 때 새 노드 D를 투입하면, D는 자신의 가상 노드들이 앉은 구간의 키만 기존 담당자들에게서 넘겨받습니다. 이동량은 평균 K/(n+1)개(= 전체 키를 늘어난 노드 수로 나눈 몫) — 새 노드가 맡아야 할 딱 그만큼만 움직입니다. % N 방식의 "거의 전부"와 비교하면, 노드가 많을수록 격차는 극적으로 벌어집니다.

「노드 D 추가」 시 이동량 비교 (키 100만 개, 10대 → 11대) hash % N ██████████████████████████████████████████████ ~91만 개 이동 안정 해싱 █████ ~9만 개 이동 (K/11) 이동한 키 = 캐시라면 miss, 저장소라면 네트워크로 실어 나를 데이터

시나리오 B — 노드 장애

노드가 죽으면 그 노드의 구간들이 링에서 사라지고, 각 구간의 키는 자동으로 시계 방향 다음 생존 노드로 라우팅됩니다. 링 재구성 외에 별도의 재배치 계산이 필요 없고, 가상 노드 덕에 부하는 여러 노드로 분산 흡수됩니다. 죽은 노드가 복귀하면 다시 자기 구간만 되찾아 갑니다.

⚠️ 흔한 오해 — "안정 해싱이면 데이터 유실도 막아주나?"

아닙니다. 안정 해싱은 "누가 담당인가"를 정하는 라우팅 규칙일 뿐, 죽은 노드에 있던 데이터를 살려내지는 못합니다. 캐시라면 miss 후 원본에서 다시 채우면 그만이지만, 저장소라면 같은 데이터를 여러 노드에 복사해 두는 복제(replication)가 별도로 필요합니다. 다만 이때도 링은 쓸모가 있습니다 — Dynamo처럼 "담당 노드에서 시계 방향으로 이어지는 몇 개 노드에 복사본을 둔다"는 식으로, 링이 복제본 위치를 정하는 기준 역할까지 해주기 때문입니다.

⚠️ 핵심 통찰 — 수평확장성의 본질은 "변화 비용의 상한"

수평확장성은 "서버를 더 꽂을 수 있다"가 아니라 "서버를 꽂고 뽑는 비용이 클러스터 크기에 비례해 커지지 않는다"입니다. 안정 해싱은 노드 1대의 변화가 건드리는 키를 "전체 키 ÷ 노드 수"만큼으로 묶어두므로, 클러스터가 커질수록 오히려 변화 1회의 상대적 충격이 줄어듭니다. 그래서 수십~수백 대 규모에서도 무중단 증설·축소(elastic scaling)가 성립합니다.

06Python으로 60줄 구현

개념은 링, 자료구조는 "정렬된 리스트 + 이진 탐색"

"원"이라는 그림을 코드로 옮기면 의외로 평범합니다. 가상 노드들의 해시값을 정렬된 리스트로 들고, 키 해시보다 큰 첫 값을 찾으면 그것이 "시계 방향 첫 노드"입니다. 링을 0부터 시계 방향으로 쭉 펼쳐 일렬로 세운 것이 바로 이 정렬된 리스트이므로, 리스트에서 "오른쪽" = 링에서 "시계 방향"이 됩니다. 리스트 끝을 넘어가면 인덱스를 0으로 되돌리면(wrap-around) 원이 완성됩니다.

탐색에는 파이썬 표준 라이브러리 bisect를 씁니다. bisect_right(keys, h)는 정렬된 리스트에서 h보다 큰 첫 원소의 인덱스를 이진 탐색으로 돌려주는데, 이것이 정확히 우리가 원하는 "시계 방향으로 처음 만나는 가상 노드"입니다.

❌ 나쁜 예 — hash % N: 노드 목록이 변하면 매핑이 전면 재추첨

def get_node(key: str, nodes: list[str]) -> str:
    # len(nodes)가 3→4가 되는 순간 기존 키의 75%가 다른 노드를 가리킴
    # 주의: 파이썬 내장 hash()는 프로세스마다 달라질 수 있음(PYTHONHASHSEED)
    #       → 서버끼리 결과가 어긋나므로 md5처럼 고정된 해시를 써야 함
    idx = int(hashlib.md5(key.encode()).hexdigest(), 16) % len(nodes)
    return nodes[idx]

✅ 좋은 예 — 해시 링 + 가상 노드

import bisect, hashlib

def _hash(s: str) -> int:
    # 결정론적: 어떤 서버/프로세스에서 실행해도 같은 입력 → 같은 출력
    # md5는 128비트라 링 범위가 0~2¹²⁸이지만 원리는 동일 —
    # 범위가 얼마든 "정렬 + 끝에서 처음으로 감기"면 그게 링이다
    return int(hashlib.md5(s.encode()).hexdigest(), 16)

class HashRing:
    def __init__(self, nodes: list[str], vnodes: int = 100):
        self._vnodes = vnodes
        self._ring = sorted(
            (_hash(f"{node}#{i}"), node)      # 가상 노드: 노드당 vnodes개의 점
            for node in nodes
            for i in range(vnodes)
        )
        self._keys = [h for h, _ in self._ring]

    def get_node(self, key: str) -> str:
        # 키 위치에서 "시계 방향 첫 가상 노드"를 이진 탐색 — O(log V)
        idx = bisect.bisect_right(self._keys, _hash(key))
        if idx == len(self._ring):
            idx = 0                          # 링 끝을 넘으면 처음으로 (wrap-around)
        return self._ring[idx][1]

    def add_node(self, node: str) -> "HashRing":
        # 새 링을 만들어 반환 (기존 링은 불변) — 조회 중인 코드와의 경합 없음
        # 주의: 이 단순 구현은 모든 노드의 vnode 수가 같다고 가정한다.
        #      노드마다 가중치를 다르게 주려면 노드별 vnode 수를 따로 들고 있어야 한다
        current = sorted({n for _, n in self._ring} | {node})
        return HashRing(current, self._vnodes)


ring = HashRing(["cache-a", "cache-b", "cache-c"])
ring.get_node("user:42")     # 몇 번을 불러도, 어느 서버에서 불러도 같은 답

이진 탐색은 후보를 매번 절반으로 줄이므로, 조회 비용은 가상 노드 총 개수 V에 대해 O(log V)입니다. 노드 100대 × 가상 노드 100개 = 10,000개여도 10,000을 2로 몇 번 나눠야 1이 되는가, 즉 약 14회 비교면 끝납니다 — 사실상 공짜입니다.

✅ 실무 감각 — 직접 구현보다 검증된 구현을

위 코드는 원리 이해용입니다. 실무에서는 라이브러리·미들웨어에 이미 들어 있는 구현을 쓰는 것이 기본입니다: Python이면 uhashring, memcached 클라이언트의 ketama 옵션(ketama = 안정 해싱 구현의 사실상 표준이 된 라이브러리), nginx의 hash ... consistent 등. 특히 클라이언트마다 해시 구현이 다르면 결정론이 깨져서 같은 키가 서버마다 다른 노드로 가는 사고가 나므로, 한 시스템 안에서는 반드시 같은 구현을 공유해야 합니다.

07진화와 변형 — Ring 이후의 알고리즘들

링은 시작이었을 뿐, "적게 움직이는 결정론적 분배"는 하나의 계보가 되었다

  1. 1997안정 해싱 논문 (Karger 외, MIT)해시 링 개념 제안. 웹 캐시 서버가 수시로 추가·제거되는 환경의 핫스팟 문제가 동기였다.
  2. 2007libketama & Dynamo 논문last.fm이 memcached용 안정 해싱 라이브러리 ketama를 공개해 캐시 업계의 사실상 표준이 됨. 같은 해 Amazon이 Dynamo 논문으로 가상 노드와 복제를 결합한 저장소 설계를 공개.
  3. 이후변형 알고리즘들 — 같은 목표, 다른 트레이드오프링 없이 "키와 노드를 함께 해시한 점수가 가장 높은 노드"를 고르는 랑데부 해싱, 링 자료구조를 아예 없애고 계산만으로 답을 내는 Google의 Jump Hash(2014), 룩업 표를 미리 만들어 조회를 O(1)로 만든 Google의 Maglev(2016) 등. 메모리·조회 속도·유연성 중 무엇을 살릴지에 따라 갈립니다.
⚠️ 흔한 오해 — "Redis Cluster도 안정 해싱이겠지?"

아닙니다. Redis Cluster는 공식 문서가 명시하듯 안정 해싱을 쓰지 않고, 해시 슬롯(hash slot) 방식을 씁니다: 키를 CRC16(key) mod 16384로 16,384개 슬롯 중 하나에 결정론적으로 배정하고, "슬롯→노드" 할당표를 노드들이 관리합니다. 증설 시에는 슬롯 단위로 소유권을 옮기므로 재배치가 최소화됩니다. "% N이잖아?"라고 생각할 수 있지만, 나누는 수가 노드 수가 아니라 고정된 16384라서 노드가 변해도 키→슬롯 매핑은 절대 변하지 않습니다 — 움직이는 것은 슬롯의 소유권뿐. "고정된 중간 단위 + 소유권 이동"이라는, 같은 문제에 대한 또 다른 해법입니다.

지점어떻게 쓰이나
nginx 업스트림 upstream 블록에 hash $request_uri consistent;라고 쓰면 ketama 방식 안정 해싱으로 백엔드를 고릅니다. 같은 URI는 늘 같은 백엔드로 가므로 백엔드 로컬 캐시 적중률이 오르고, 백엔드가 죽어도 그 몫의 URI만 재배치됩니다.
memcached 클라이언트 여러 memcached 서버를 쓸 때 클라이언트 라이브러리가 ketama 링으로 키를 분배합니다. 서버 목록에 한 대를 추가해도 대량 캐시 미스가 나지 않는 이유입니다.
Redis Cluster 07절에서 본 해시 슬롯 방식입니다. 알고리즘은 링과 다르지만, 애플리케이션 입장에서 얻는 효용은 같습니다 — "노드를 늘려도 전면 재배치 없이 슬롯 단위로만 이사한다".
DB 샤딩 설계 PostgreSQL을 수평 분할할 때 "무엇으로 나눌 것인가"의 선택지가 바로 이 문서의 내용입니다. % N으로 시작하면 첫 증설 때 전체 재배치라는 청구서가 날아옵니다 — 처음부터 링 또는 고정 슬롯(예: 슬롯 1024개를 만들어 노드에 배정)으로 설계하는 것이 안전합니다.
CDN / 로드밸런서 Akamai 이래 CDN 엣지 캐시 선택, Google Maglev 같은 L4 로드밸런서(패킷의 IP·포트만 보고 서버를 고르는 로드밸런서)의 커넥션 분배가 모두 이 계보입니다. "같은 클라이언트/URL은 되도록 같은 곳으로"가 필요한 모든 곳에 있습니다.
✅ 실무 감각 — 언제 꺼내 들 카드인가

판단 기준은 간단합니다: "키로 노드를 고르는 구조인가?" + "노드 집합이 변할 수 있는가?" 둘 다 예라면 % N 대신 안정 해싱(또는 고정 슬롯)을 검토하세요. 반대로 노드(또는 파티션) 수가 처음부터 고정이라면 % N도 충분히 훌륭합니다 — 도구는 문제에 맞을 때만 씁니다.

09한 장 요약 치트시트

💬 "결정론적 알고리즘을 이용한 라우팅"이란?

중앙 조회 서버 없이, 키를 해시하는 계산만으로 담당 노드를 알아내는 것. 같은 해시 함수와 같은 링 구성을 공유하는 한, 어떤 클라이언트가 계산해도 같은 키는 같은 노드로 간다. 조회 왕복도, 단일 장애점도 없다.

💬 "클러스터 환경에서의 수평확장성 확보"란?

노드를 추가/제거할 때 이동하는 키를 "변화 후 노드 수로 나눈 몫"(키 K개·노드 n대면 대략 K/n)만큼으로 묶어두는 것. hash % N은 노드 1대 변화에 거의 모든 키가 재배치되어 클러스터가 클수록 증설 비용이 커지지만, 해시 링에서는 이웃 구간만 움직이므로 무중단 증설·축소가 성립한다. 이것이 링 구조가 수평확장성을 "확보"해 주는 메커니즘이다.

기억할 것내용
링의 규칙노드와 키를 같은 해시 공간(원) 위에 놓고, 키에서 시계 방향 첫 노드가 담당. 노드가 변해도 이웃 구간만 영향받는다
가상 노드물리 노드 1개를 링 위 여러 점으로 → 균등화 + 장애 시 부하 분산 + 가중치. 개수는 트레이드오프 (Cassandra 기본값 256→16)
결정론의 조건같은 해시 함수 + 같은 노드 목록. 멤버십 관리(설정/가십)는 별도로 필요
안정 해싱 ≠ 복제라우팅 규칙일 뿐, 데이터 보존은 복제(replication)가 담당
변형들랑데부(링 없이 점수 비교) · Jump(메모리 0, 고정 샤드용) · Maglev(O(1) 룩업) · Redis 해시 슬롯(고정 16384 + 소유권 이동)
실무 접점nginx hash ... consistent · memcached ketama · Redis Cluster · DB 샤딩 설계 · CDN
