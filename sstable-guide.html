데이터베이스는 수정할 때 덮어쓸까

00답은 엔진마다 다르다

"수정 = 덮어쓰기"라는 직관부터 짚기

엑셀 셀의 값을 고치면 그 칸의 숫자가 바뀝니다. 데이터베이스도 그럴 거라고 생각하기 쉽습니다. 하지만 "덮어쓴다"는 말에는 두 가지 전제가 숨어 있습니다. 하나는 옛 값이 더는 필요 없다는 것이고, 다른 하나는 그 자리에 다시 쓰는 일이 싸다는 것입니다. 데이터베이스에서는 둘 다 늘 참은 아닙니다. 다른 트랜잭션이 아직 옛 값을 읽고 있을 수 있고, 디스크의 아무 자리나 골라 다시 쓰는 일은 생각보다 비쌉니다.

그래서 저장 엔진(데이터베이스 안에서 실제로 데이터를 디스크에 놓고 꺼내는 부분)마다 답이 다릅니다. 짧은 답은 세 가지입니다.

  1. 그 자리를 덮어쓴다 — MySQL InnoDB대부분의 경우 행이 있던 자리에서 값을 바꾼다. 다만 옛 값은 버리지 않고 undo log라는 별도 공간에 복사해 둔다.
  2. 행은 새로 쓴다 — PostgreSQL옛 행은 그대로 두고 새 버전의 행을 하나 더 쓴다. 아무도 옛 행을 보지 않게 되면 나중에 VACUUM이 치운다.
  3. 파일을 절대 고치지 않는다 — LSM(Log-Structured Merge-tree) 계열RocksDB, Cassandra 같은 저장소다. 바뀐 값을 메모리에 모았다가 키 순으로 정렬한 새 파일로 통째로 쓴다. 이 정렬된, 한 번 쓰면 고치지 않는 파일이 SSTable이다. 옛 값은 뒤에서 여러 파일을 합칠 때(compaction) 사라진다.

셋 모두 "옛 값을 치우는 일"을 어딘가에서 따로 합니다. 다른 점은 그 일을 언제, 얼마나 몰아서 하느냐입니다. 이 문서는 1번에서 출발해, 앞 선택이 남긴 비용이 다음 선택을 부르는 흐름을 따라 SSTable까지 갑니다.

이 문서가 답하는 것

1. 엔진마다 "수정"이 디스크에서 실제로 무엇을 하는가 · 2. SSTable은 왜 "정렬"과 "불변"을 고집하고, 그 대가는 무엇인가 · 3. compaction과 tombstone은 왜 필요한가 · 4. PostgreSQL에서 대량 UPDATE가 테이블을 부풀리는 이유와 대처법.

01디스크는 어떻게 쓰이나

세 선택을 비교할 저울 세 개

페이지 단위로 읽고 쓴다

데이터베이스는 디스크를 바이트 단위로 다루지 않습니다. 일정한 크기의 덩어리인 페이지(블록이라고도 부릅니다) 단위로 읽고 씁니다. 기본 크기는 PostgreSQL이 8KB, MySQL InnoDB가 16KB입니다. 행 하나에서 숫자 하나를 바꾸더라도, 디스크에 반영할 때는 그 행이 든 페이지 한 장을 통째로 씁니다.

순차 쓰기가 랜덤 쓰기보다 싸다

파일 끝에 이어서 쓰는 것을 순차 쓰기, 파일 여기저기의 페이지를 골라 쓰는 것을 랜덤 쓰기라고 합니다. 회전하는 하드디스크에서는 랜덤 쓰기마다 헤드를 움직여야 해서 차이가 극단적이었습니다. SSD는 쓴 자리를 바로 덮어쓰지 못해 새 내용을 빈 자리에 쓰고, 나중에 큰 블록 단위로 지우면서 아직 살아 있는 데이터를 옮겨 씁니다(가비지 컬렉션). 흩어진 작은 쓰기는 이 옮겨 쓰기를 늘리므로, 몰아서 순서대로 쓰는 편이 SSD에서도 유리합니다.

📎 용어: WAL (Write-Ahead Log)과 체크포인트

데이터 파일을 고치기 전에 "무엇을 바꿀지"를 로그 파일 끝에 먼저 순차로 적어 두는 방식입니다. 데이터 파일 반영이 늦어져도 로그만 디스크에 안전하게 있으면 서버가 죽은 뒤 로그를 다시 읽어 복구할 수 있습니다. 로그가 끝없이 길어지지 않도록, 데이터베이스는 가끔 메모리에서 고친 페이지를 모두 데이터 파일에 내려 쓰고 "복구는 로그의 여기부터 읽으면 된다"고 표시합니다. 이 시점을 체크포인트라고 합니다. 이 문서의 세 방식은 모두 WAL을 씁니다. 차이는 그 뒤에 데이터 파일을 어떻게 다루느냐에 있습니다.

저울 세 개 — 읽기 · 쓰기 · 공간 증폭

저장 방식을 비교할 때는 "내가 원한 양에 비해 실제로 얼마나 더 했나"를 세 방향으로 잽니다.

이름뜻
읽기 증폭값 하나를 찾으려고 실제로 읽은 데이터의 양 ÷ 찾은 데이터의 양. 여러 파일을 뒤져야 하면 커진다
쓰기 증폭디스크에 실제로 쓴 양 ÷ 애플리케이션이 쓴 양. 숫자 하나 때문에 페이지 한 장을 쓰거나, 같은 데이터를 여러 번 다시 쓰면 커진다
공간 증폭디스크에 차지한 크기 ÷ 살아 있는 데이터의 크기. 옛 버전을 쌓아 두면 커진다

셋 중 둘을 얻으면 하나를 내준다는 경험칙을 RUM 추측(R 읽기 · U 갱신 · M 공간)이라고 부릅니다. 아래 선택들은 이 저울 위에서 무엇을 내줄지 고른 결과입니다.

02선택 ① 그 자리를 덮어쓴다

B-tree 제자리 갱신 — MySQL InnoDB

가장 직관적인 방식부터 봅시다. 데이터를 키 순으로 정리된 페이지들에 나눠 담고, 어떤 키가 어느 페이지에 있는지 찾아가는 길잡이 페이지를 위에 층층이 얹습니다. 이 나무 모양 구조가 B-tree입니다. 키 하나를 찾으려면 꼭대기에서부터 몇 장의 페이지만 따라 내려가면 됩니다.

InnoDB는 테이블 자체를 기본 키 순의 B-tree로 저장합니다. 이것을 클러스터드 인덱스라고 합니다. MySQL 공식 문서는 클러스터드 인덱스의 레코드가 그 자리에서(in-place) 갱신된다고 적고 있습니다. UPDATE가 오면 해당 행이 든 페이지를 메모리(버퍼 풀)로 읽어 와 값을 바꾸고, 나중에 그 페이지를 원래 위치에 다시 씁니다.

[ 루트 페이지 ] ┌──────┴──────┐ [ 중간 페이지 ] [ 중간 페이지 ] ┌────┴────┐ [ 잎 페이지 16KB ] ← id=42 의 행이 여기 있다 id=41 … id=42 view_count: 7 → 8 ← 같은 자리의 값을 바꾼다 id=43 … │ └─ 옛 값 7 은 undo log 에 복사해 둔다

덮어쓰는데도 옛 값을 따로 남기는 이유

📎 용어: 트랜잭션과 ROLLBACK

트랜잭션은 전부 반영되거나 전부 취소되는 SQL 묶음입니다. 취소하는 명령이 ROLLBACK입니다. 대부분의 데이터베이스는 진행 중인 트랜잭션이 다른 트랜잭션의 커밋 전 변경을 보지 않도록 약속합니다.

덮어쓰기 방식도 옛 값을 바로 버리지는 못합니다. 이유는 두 가지입니다. 트랜잭션이 ROLLBACK되면 원래 값으로 되돌려야 합니다. 그리고 이 갱신이 커밋되기 전에 다른 트랜잭션이 같은 행을 읽으면, 위 약속 때문에 바뀌기 전 값을 보여 줘야 합니다. 그래서 InnoDB는 행을 고치기 전에 옛 값을 undo log에 적어 두고, 행 안의 숨은 포인터가 그 기록을 가리키게 합니다. 옛 값이 필요한 트랜잭션이 모두 끝나면 백그라운드 작업(purge)이 undo 기록을 지웁니다.

페이지를 덮어쓰는 도중에 전원이 나가면 절반만 새 내용인 "찢어진 페이지"가 생길 수 있습니다. WAL에는 보통 "이 페이지의 이 부분을 이렇게 바꿔라"처럼 멀쩡한 페이지 위에 다시 적용할 변경만 적혀 있어서, 바탕 페이지가 깨지면 WAL로도 되살리지 못합니다. 덮어쓰기라 깨지기 전 모습도 남아 있지 않습니다. 그래서 InnoDB는 페이지를 제자리에 쓰기 전에 doublewrite buffer라는 별도 영역에 한 번 더 써 둡니다. 덮어쓰기를 택한 대가로 생긴 장치입니다.

✅ 우선한 것

읽기와 공간

  • 키마다 최신 값이 딱 한 자리에 있다. 찾을 곳이 하나다
  • 테이블 파일에 같은 행의 버전이 여러 개 쌓이지 않는다 (옛 값은 undo에 쌓이지만 purge가 곧 지운다)

🗑️ 버린 것

싼 쓰기

  • 바꾼 행들이 여러 페이지에 흩어져 있으면 그만큼 랜덤 쓰기가 된다
  • 숫자 하나에도 페이지 한 장(16KB)을 다시 쓴다
  • 갱신할 때마다 옛 값을 undo log로 옮기고, 찢어진 페이지에 대비해 한 번 더 써야 한다

이 선택에서 생긴 개념: 페이지와 버퍼 풀, 옛 값을 따로 담는 undo log와 그것을 치우는 purge, 찢어진 페이지에 대비하는 doublewrite.

03선택 ② 행은 새로 쓰고 옛것은 나중에 치운다

PostgreSQL — 옛 값을 다른 곳에 옮기지 않고 그 자리에 둔다

선택 ①에서 옛 값을 undo log로 옮기는 일은 갱신할 때마다 따라붙습니다. PostgreSQL은 반대로 갑니다. 옛 행은 손대지 않고, 새 버전의 행을 하나 더 씁니다. 옛 값을 남기는 이유는 선택 ①과 같습니다. 이 갱신보다 먼저 시작한 트랜잭션은 아직 옛 값을 읽어야 할 수 있습니다. 다른 점은 옛 값을 다른 곳으로 옮기지 않고 테이블 안 원래 자리에 그대로 둔다는 것입니다. 옛 버전을 남겨 아직 그것을 봐야 하는 트랜잭션에 보여 주는 방식을 MVCC(다중 버전 동시성 제어)라고 부릅니다. InnoDB가 undo log로 옛 값을 보여 주는 것도 MVCC이고, PostgreSQL과 다른 점은 옛 버전을 어디에 두느냐입니다.

📎 용어: 튜플과 ctid

PostgreSQL에서 행 하나의 한 버전을 튜플이라고 부릅니다. ctid는 그 튜플이 테이블 파일의 어디에 있는지를 나타내는 숨은 컬럼으로, (페이지 번호, 페이지 안의 순번) 꼴입니다. SELECT ctid, * FROM ...로 볼 수 있습니다. 인덱스는 키 값과 함께 그 행의 ctid를 적어 두고, 그것으로 테이블의 행을 찾아갑니다.

직접 확인해 봤습니다. 행 하나를 넣고 숫자만 두 번 올렸습니다.

실측 — PostgreSQL 14, 로컬 테스트용 DB 서버 (발췌)

INSERT INTO item VALUES (1, 'pen', 0);
--  ctid  | id | name | view_count
-- (0,1)  |  1 | pen  |          0

UPDATE item SET view_count = view_count + 1 WHERE id = 1;
-- (0,2)  |  1 | pen  |          1     ← 같은 행인데 위치가 바뀌었다

UPDATE item SET view_count = view_count + 1 WHERE id = 1;
-- (0,3)  |  1 | pen  |          2

-- pageinspect 확장으로 0번 페이지 안을 그대로 보면
--  lp | t_ctid | t_xmax
--   1 | (0,2)  |    736   ← 처음 버전. 736번 트랜잭션이 끝냈다
--   2 | (0,3)  |    737   ← 두 번째 버전
--   3 | (0,3)  |      0   ← 지금 살아 있는 버전

열의 뜻은 이렇습니다. lp는 페이지 안 순번, t_xmax는 이 버전을 끝낸 트랜잭션 번호(0이면 아직 살아 있음), t_ctid는 다음 버전의 위치입니다(마지막 버전은 자기 자신을 가리킵니다). 값을 두 번 바꿨더니 한 페이지 안에 버전이 세 개 있습니다. 앞의 두 개는 지워지지 않았고 t_xmax 표시만 붙었습니다. 아무도 볼 수 없게 된 옛 버전을 dead tuple이라고 합니다.

⚠️ 흔한 오해: "PostgreSQL은 디스크를 덮어쓰지 않는다"

덮어쓰지 않는 것은 행입니다. 페이지는 여전히 테이블 파일의 원래 자리에 다시 씁니다. 위 예에서 새 버전이 들어간 0번 페이지는 파일의 같은 위치에 다시 기록됩니다. 그래서 PostgreSQL도 선택 ①과 같은 랜덤 쓰기 비용과 찢어진 페이지 문제를 안고 있습니다. 찢어진 페이지는 체크포인트 뒤 처음 바뀌는 페이지의 전체 내용을 WAL에 적어 두는 방식(full page writes)으로 대비합니다.

치우는 사람 — VACUUM

dead tuple은 누군가 치워야 합니다. 그 일이 VACUUM입니다. VACUUM은 dead tuple이 차지하던 자리를 "재사용 가능"으로 표시합니다. 공식 문서에 따르면 일반 VACUUM은 그 공간을 운영체제에 돌려주지 않습니다(테이블 끝 페이지가 통째로 비는 특별한 경우만 예외). 대신 다음 INSERT와 UPDATE가 그 자리를 씁니다. 파일 크기를 실제로 줄이려면 테이블 전체를 새 파일로 다시 쓰는 VACUUM FULL이 필요한데, 그동안 테이블을 읽지도 쓰지도 못하게 잠급니다. PostgreSQL에는 이 일을 알아서 돌리는 백그라운드 작업 autovacuum이 있습니다.

실측 — 10만 행 테이블에 전 행 UPDATE 1회 (autovacuum을 끄고 측정, 발췌)

처음                       5096 kB
전 행 view_count + 1 후    10192 kB   ← 10만 개의 새 버전 + 10만 개의 dead tuple
VACUUM 후                 10192 kB   ← 파일은 그대로, 빈자리만 재사용 표시
한 번 더 전 행 UPDATE 후     10192 kB   ← 빈자리를 재사용해서 더 늘지 않음
VACUUM FULL 후             5096 kB   ← 새 파일로 다시 써서 줄어듦

lede에서 말한 "두 배"가 이것입니다.

인덱스까지 새로 쓰지 않으려는 장치 — HOT

새 버전이 생기면 위치(ctid)가 바뀝니다. 인덱스는 ctid로 행을 찾아가므로, 원칙적으로는 그 행을 가리키는 모든 인덱스에도 새 항목을 넣어야 합니다. 인덱스가 다섯 개면 값 하나 바꾸는 데 인덱스 다섯 곳을 고치는 셈입니다. 이 비용을 줄이려고 PostgreSQL은 HOT(Heap-Only Tuple) 갱신을 씁니다. 공식 문서가 밝힌 조건은 두 가지입니다.

  1. 인덱스에 걸린 컬럼의 값이 바뀌지 않았다. (PostgreSQL 16부터 BRIN 인덱스는 이 조건에서 빠집니다.)
  2. 옛 행이 있는 같은 페이지에 새 버전이 들어갈 빈자리가 있다.

두 조건이 맞으면 새 버전을 같은 페이지에 넣고 인덱스는 건드리지 않습니다. 인덱스는 계속 처음 버전을 가리키고, 읽는 쪽은 페이지 안에서 t_ctid를 따라 새 버전까지 갑니다. 조건이 둘인 이유도 여기서 나옵니다. 인덱스 키 값이 바뀌면 옛 키 자리의 항목으로는 새 값을 찾을 수 없으니 새 키 자리에 항목이 필요하고(조건 1), 이 따라가기는 같은 페이지 안에서만 하므로 새 버전도 같은 페이지에 있어야 합니다(조건 2).

t_ctid 사슬 자체는 HOT이 아니어도 모든 UPDATE에 생깁니다. HOT인지는 새 버전의 행 머리에 붙는 "인덱스가 직접 가리키지 않는 버전"(heap-only) 표시로 갈리고, 위 실측에서 view_count에 인덱스를 걸면 사슬은 같은데 이 표시가 사라졌습니다.

2번 조건을 돕는 설정이 fillfactor입니다. INSERT가 페이지를 몇 %까지만 채울지 정하는 값으로, 테이블의 기본값은 100(꽉 채움)입니다. 70으로 낮추면 페이지마다 30%를 갱신용으로 비워 둡니다.

실측 — 10만 행, 갱신마다 10%의 행만 view_count + 1, 3회 (n_tup_upd = 전체 갱신 수, n_tup_hot_upd = 그중 HOT 갱신 수, 발췌)

                   n_tup_upd   n_tup_hot_upd
fillfactor 100        30000          18090     ← 기본값. 일부만 HOT
fillfactor 70         30000          30000     ← 전부 HOT

꽉 채운 기본값에서도 일부가 HOT인 것은 회차마다 다른 행을 갱신해서, 앞 회차의 옛 버전이 정리된 빈자리를 다음 회차가 쓰기 때문으로 보입니다. 같은 실험을 "전 행을 한 번에 갱신"으로 바꾸면 fillfactor 70에서도 HOT은 약 44%였습니다. 비워 둔 30%로는 모든 행의 새 버전을 담지 못하기 때문입니다. fillfactor는 조금씩 자주 바뀌는 테이블에서 효과가 큽니다.

✅ 우선한 것

갱신 경로의 단순함 — 옛 값을 옮기지 않는다

  • 갱신은 새 버전을 하나 쓰고 옛 버전에 "끝났다" 표시만 붙이면 된다
  • ROLLBACK은 새 버전을 무효로 두면 끝이다. undo 기록을 거꾸로 적용할 필요가 없다

🗑️ 버린 것

공간과 인덱스 쓰기

  • dead tuple 만큼 테이블이 부푼다 (공간 증폭)
  • HOT이 아니면 인덱스마다 새 항목을 쓴다 (쓰기 증폭)
  • 옛 버전을 치우는 VACUUM이라는 일이 따로 생긴다

이 선택에서 생긴 개념: 튜플 버전과 dead tuple, 그것을 치우는 VACUUM과 autovacuum, 인덱스 쓰기를 아끼는 HOT, HOT을 돕는 fillfactor.

②도 풀지 못한 것: 페이지는 여전히 제자리에 쓰므로 랜덤 쓰기는 ①과 같습니다.

04선택 ③ 파일을 절대 고치지 않는다

memtable과 SSTable — 랜덤 쓰기를 없애려는 선택

선택 ①과 ② 모두 남긴 비용이 하나 있습니다. 바뀐 행이 흩어진 페이지들에 있으면 그 페이지들을 하나하나 제자리에 써야 한다는 것, 곧 랜덤 쓰기입니다. 쓰기가 아주 많은 서비스(로그, 이벤트, 시계열 데이터)에서는 이것이 병목이 됩니다.

이 문제를 겨냥한 구조가 LSM-tree(Log-Structured Merge-tree)입니다. 변경을 바로 디스크 곳곳에 반영하지 않고 메모리에 모아 두었다가, 묶어서 한 번에 순서대로 흘려보내자는 아이디어입니다. 이 구조에서 디스크에 쓰는 파일 형식으로 널리 알려진 것이 SSTable(Sorted String Table)입니다. 구글 내부에서 쓰던 형식을 Bigtable 논문이 바깥에 소개했고, 지금은 LevelDB, RocksDB, Cassandra 같은 저장소가 같은 뼈대를 씁니다.

쓰기 경로

  1. WAL에 순차로 적는다서버가 죽어도 잃지 않도록. 파일 끝에 붙이기만 한다.
  2. memtable에 넣는다memtable은 메모리 안에서 키 순서를 유지하는 자료구조다. 실제 저장소는 스킵 리스트 같은 정렬 구조를 쓴다. 넣는 순간 이미 정렬돼 있고, 디스크를 건드리지 않아 싸다.
  3. 가득 차면 SSTable로 내린다(flush)memtable을 얼리고 새 memtable을 연 뒤, 얼린 것을 키 순서 그대로 새 파일 하나에 처음부터 끝까지 순차로 쓴다. 그 파일은 다시는 고치지 않는다.

Bigtable 논문의 설명으로는 SSTable은 키에서 값으로의, 디스크에 있고 정렬된 불변(immutable) 맵입니다(의역). 한 번 쓰면 고치지 않으니 읽을 때 잠금이 필요 없고, 지운 데이터를 영구히 없애는 일은 쓸모없어진 파일을 지우는 일이 됩니다.

수정과 삭제는 "새 기록"이 된다

파일을 고치지 않으니 수정도 삭제도 새 기록을 더 쓰는 것으로 표현합니다. 수정은 같은 키에 새 값을 쓰는 것이고, 삭제는 "이 키는 지워졌다"는 표시를 쓰는 것입니다. 이 삭제 표시를 tombstone(묘비)이라고 부릅니다. 읽을 때는 가장 최근 것부터 찾아서 처음 만나는 기록을 답으로 씁니다. 그 기록이 tombstone이면 "없다"가 답입니다.

Python으로 100줄 남짓한 장난감을 만들어 확인했습니다. 장난감의 memtable은 그냥 dict이고 flush할 때 키 순으로 정렬합니다. SSTable은 그렇게 정렬해 쓴 텍스트 파일입니다. memtable에 3개가 차면 flush하고, 끝에 남은 것도 마지막에 flush합니다.

실측 — 장난감 LSM, Python 3.12 (발췌, 파일 확장자와 따옴표 표기는 줄임)

① 쓰기
  flush → sst_000: ['apple', 'banana', 'cherry']
② 같은 키를 수정·삭제 (기존 파일은 손대지 않음)
  flush → sst_001: ['apple', 'banana', 'date']
  flush → sst_002: ['apple']                      # 끝에 남은 1개
③ 디스크 상태
  sst_000: ["apple", 1]  ["banana", 1]  ["cherry", 1]
  sst_001: ["apple", 2]  ["banana", "__TOMBSTONE__"]  ["date", 1]
  sst_002: ["apple", 3]
  디스크의 줄 수 7 / 살아 있는 키 3개 (apple, cherry, date)
④ 읽기 — 최신 파일부터 찾는다
  get('apple')  = 3     ← sst_002, 연 파일 1개
  get('banana') = None  ← sst_001, 연 파일 2개   # tombstone 을 만났다
  get('cherry') = 1     ← sst_000, 연 파일 3개
  get('zebra')  = None  ← 없음,   연 파일 3개   # 없는 키가 제일 비싸다

쓰기는 늘 메모리와 파일 끝에서만 일어났습니다. 대신 ③과 ④에 비용이 보입니다. 살아 있는 키는 3개인데 디스크에는 7줄이 있고(공간 증폭), cherry와 없는 zebra는 파일 세 개를 다 열어야 했습니다(읽기 증폭).

📒 비유

가계부를 고쳐 쓰지 않고 정정 내역을 새 장에 덧붙이는 사람을 떠올려 보세요. 쓸 때는 지우개도 필요 없고 늘 마지막 장에만 쓰면 되니 빠릅니다. 하지만 "3월 식비가 최종적으로 얼마였지?"를 알려면 마지막 장부터 거꾸로 넘겨 봐야 하고, 공책은 계속 두꺼워집니다.

왜 굳이 "정렬"까지 하나

📎 용어: 이진 탐색과 병합

이진 탐색은 정렬된 목록의 가운데를 보고, 찾는 값이 앞쪽인지 뒤쪽인지 판단해 절반씩 버리며 찾는 방법입니다. 100만 개도 20번 안쪽으로 찾습니다. 병합은 정렬된 목록 여러 개를 앞에서부터 한 칸씩 비교해 가장 작은 것을 내보내는 일입니다. 이렇게 하면 각 목록을 한 번씩만 훑어 정렬된 목록 하나로 합칠 수 있습니다.

로그처럼 도착한 순서대로 쓰기만 해도 쓰기는 빠릅니다. 정렬은 그 다음 일을 위해서입니다. 파일 안이 키 순이면 ① 파일 안에서 이진 탐색으로 키를 찾을 수 있고, ② "user:100"부터 "user:200"까지 같은 범위 조회를 이어진 구간 하나로 읽을 수 있으며, ③ 여러 파일을 합칠 때 병합으로 각 파일을 앞에서부터 한 번씩만 훑으면 됩니다. 정렬은 memtable 안에서 이미 끝나 있으니 flush는 순서대로 쏟아 내기만 하면 됩니다.

✅ 우선한 것

쓰기 — 랜덤 쓰기를 순차 쓰기로

  • 디스크에는 WAL 끝과 새 파일만 쓴다
  • 파일이 불변이라 읽기에 잠금이 필요 없고, 찢어진 페이지 걱정이 없다

🗑️ 버린 것

읽기와 공간

  • 키 하나를 찾으려 여러 파일을 뒤진다. 없는 키가 가장 비싸다
  • 옛 값과 tombstone이 파일마다 쌓인다

이 선택에서 생긴 개념: memtable, flush, 정렬된 불변 파일 SSTable, 삭제 표시 tombstone, "최신 것부터 읽는다"는 규칙.

05SSTable 한 개 들여다보기

파일 하나 안에서 읽기 비용을 줄이는 장치들

선택 ③이 버린 것은 읽기였습니다. 그 비용은 두 겹입니다. 파일 하나 안에서 키를 찾는 비용, 그리고 여러 파일을 뒤지는 비용입니다. 앞의 것은 파일 구조로 줄이고, 뒤의 것은 다음 장의 compaction으로 줄입니다. LevelDB의 파일 형식 문서를 기준으로 SSTable 한 개의 모양을 보면 아래와 같습니다. 그림에 나오는 Bloom filter부터 정의해 둡니다.

📎 용어: Bloom filter

"이 키가 이 집합에 들어 있는가?"에 "확실히 없다" 또는 "있을 수도 있다"로 답하는 작은 자료구조입니다. "없다"는 틀리지 않지만 "있을 수도"는 가끔 틀립니다. 그 대신 키 전체를 저장하는 것보다 훨씬 적은 메모리로 답합니다.

┌─────────────────────────────┐ 파일 시작 │ data block 1 (약 4KB) │ apple … banana │ data block 2 │ cherry … grape │ … │ 키 순서대로, 블록마다 압축 가능 │ data block N │ ├─────────────────────────────┤ │ filter block (Bloom filter) │ 필터 정책을 켰을 때만 생긴다 │ metaindex block │ filter block 이 어디 있는지 │ index block │ 블록마다 "키의 상한 → 위치" ├─────────────────────────────┤ │ footer (고정 크기) │ index·metaindex 블록의 위치 └─────────────────────────────┘ 파일 끝
  • data block — 키·값 쌍을 정렬된 순서로 담은 덩어리입니다. LevelDB의 기본 크기는 압축 전 약 4KB입니다. 이웃한 키는 앞부분이 겹치는 경우가 많아서, 앞 키와 겹치는 부분은 생략하고 다른 부분만 적습니다. 그러면 가운데 키 하나를 읽으려 해도 블록 처음부터 풀어야 하므로, 일정 개수마다 키를 통째로 적는 지점(restart point)을 둡니다. 이 지점들을 대상으로 이진 탐색해 범위를 좁힌 뒤, 가까운 지점부터 읽으면 됩니다.
  • index block — data block마다 "이 블록에 든 키의 상한 → 블록의 위치"를 하나씩 적은 목록입니다. 파일을 열 때 메모리에 올려 두면, 키 하나를 찾을 때 index에서 이진 탐색으로 블록을 고르고 그 블록만 디스크에서 읽으면 됩니다.
  • footer — 파일 끝의 고정 크기 영역입니다. 읽는 쪽은 파일 끝에서 정해진 길이만큼 거꾸로 읽어 index block의 위치를 알아냅니다. 파일을 처음부터 끝까지 다 쓴 뒤에야 index를 알 수 있으니, index를 맨 뒤에 두는 것이 한 번에 순서대로 쓰기와 잘 맞습니다.

장난감 실측에서 가장 비쌌던 것은 없는 키 zebra였습니다. 파일마다 Bloom filter를 두면, 필터가 "확실히 없다"고 답한 파일은 열어 보지 않고 건너뜁니다. LevelDB는 필터 정책을 설정했을 때 filter block을 만들고, RocksDB의 필터 설정도 같은 역할을 합니다. 여기에 자주 읽는 data block을 메모리에 캐시하는 block cache까지 더하면, 선택 ③이 버린 읽기를 되사는 장치가 갖춰집니다.

06선택 ④ 치우는 일을 몰아서 한다

compaction — 공간과 읽기를 되찾는 대신 쓰기를 다시 한다

flush할 때마다 파일이 하나씩 늘어나니, 그대로 두면 읽기는 점점 더 많은 파일을 뒤지고 디스크에는 옛 값과 tombstone이 쌓입니다. 그래서 LSM 저장소는 백그라운드에서 여러 SSTable을 읽어 하나의 새 SSTable로 병합합니다. 같은 키가 여러 파일에 있으면 최신 값만 남기고, 더는 필요 없는 tombstone은 지웁니다. 다 쓰고 나면 입력 파일들을 삭제합니다. 이것이 compaction입니다. 기존 파일을 고치는 게 아니라 새 파일을 만들고 옛 파일을 버리므로 "불변" 원칙은 그대로 지켜집니다.

실측 — 앞의 장난감에서 이어서 compaction (발췌, 표기는 줄임)

⑤ compaction
  compaction → sst_003: ['apple', 'cherry', 'date']   # banana 와 그 tombstone 이 함께 사라졌다
  디스크의 줄 수 3                                     # 7 → 3
  compaction 이 다시 쓴 바이트 39 (flush 로 쓴 바이트 107)
  get('cherry') = 1 ← sst_003, 연 파일 1개             # 3개 → 1개

공간과 읽기가 돌아왔습니다. 대신 이미 디스크에 한 번 쓴 데이터를 다시 읽고 다시 썼습니다. 장난감에서는 flush 107바이트에 39바이트를 더 써서 쓰기 증폭이 (107 + 39) ÷ 107 ≈ 1.4배이고, 실제 저장소에서는 이 일이 층마다 되풀이됩니다. 실제 저장소는 SSTable을 여러 층(level)으로 나눠 둡니다. 막 flush된 파일은 맨 위 L0에 놓이고, 서로 키 범위가 겹칠 수 있습니다. compaction을 거칠 때마다 데이터는 더 크고 오래된 아래 층(L1, L2, …)으로 내려갑니다. 같은 키·값이 아래 층으로 내려갈 때마다 다시 쓰이니, 이것이 LSM의 쓰기 증폭입니다. 선택 ③은 랜덤 쓰기를 없앴지만, 순차 쓰기를 여러 번 하는 것으로 대가를 나눠 치르는 셈입니다.

얼마나 부지런히 합칠 것인가 — leveled와 tiered

compaction의 방식은 크게 두 갈래이고, 이것도 같은 저울 위의 선택입니다.

📐 leveled

층마다 크기 한도를 두고(아래로 갈수록 약 10배), 한도를 넘친 층의 파일을 바로 아래 층의 키 범위가 겹치는 파일들과 합친다

  • L1부터는 한 층 안에서 파일의 키 범위가 겹치지 않아, 층마다 많아야 파일 하나만 보면 된다
  • 읽기·공간 유리, 쓰기 증폭 큼. RocksDB의 기본값

🧱 tiered (size-tiered)

비슷한 크기의 파일이 여러 개 모이면 그때 한꺼번에 합친다

  • 같은 데이터를 다시 쓰는 횟수가 적다
  • 그 대신 키 범위가 겹치는 파일이 많이 남아 읽기가 무겁고, 합칠 때 디스크 사용량이 크게 출렁인다
  • 쓰기 유리, 읽기·공간 불리. RocksDB의 Universal이 이 계열

tombstone은 언제 사라지나

tombstone을 너무 일찍 지우면, 아래 층의 더 오래된 파일에 남은 같은 키의 옛 값이 다시 보입니다. 그래서 LevelDB는 더 아래 층에 그 키 범위와 겹치는 파일이 없을 때만 tombstone을 버립니다. 여러 서버에 복제하는 저장소는 꺼져 있던 서버가 돌아와 옛 값을 되살리지 않도록 유예 기간을 둔 뒤에야 지웁니다(Cassandra 기본 10일).

⚠️ 흔한 오해: "삭제하면 공간이 바로 준다"

LSM 저장소에서 삭제는 tombstone을 하나 더 쓰는 일입니다. 공간은 compaction이 옛 값과 tombstone을 함께 치울 때에야 돌아옵니다. 대량 삭제 직후에는 오히려 디스크 사용량이 늘 수 있고, tombstone이 많이 쌓인 구간은 읽을 때 "지워졌다"는 표시들을 하나하나 건너뛰느라 느려집니다.

✅ 우선한 것

읽기와 공간을 되찾기

  • 뒤져야 할 파일 수를 묶어 둔다
  • 옛 값과 tombstone을 실제로 지운다

🗑️ 버린 것

쓰기, 그리고 예측 가능성

  • 같은 데이터를 여러 번 다시 쓴다 (쓰기 증폭)
  • 합치는 동안 입력과 출력 파일이 함께 있어 디스크가 일시적으로 더 든다
  • 백그라운드 I/O(디스크 읽기·쓰기)가 몰리면 전경 요청이 느려질 수 있다

이 선택에서 생긴 개념: compaction, 층(level), leveled와 tiered 전략, tombstone의 유예 기간.

⚠️ 핵심 통찰

"덮어쓰지 않는 저장소"는 정리를 안 하는 게 아니라 나중으로 미룬 저장소입니다. InnoDB의 purge, PostgreSQL의 VACUUM, LSM의 compaction 순으로 옛 값 정리가 쓰기 순간에서 멀어지고, 그만큼 갱신 순간에 옛 값을 처리하는 일이 줄어듭니다. 다만 PostgreSQL은 HOT이 아니면 인덱스 쓰기를 따로 치르므로, 가벼워지는 것은 옛 값 처리에 한정됩니다. 대신 정리를 기다리는 동안 읽기와 공간이 값을 치릅니다. 미룬 정리가 쓰기 속도를 따라가지 못하면 공간이 부풀고 읽기가 느려지므로, 이런 시스템을 운영할 때는 "정리 작업이 쓰기를 따라가고 있는가"를 지켜봐야 합니다.

07실무 — Django와 PostgreSQL에서

1. 대량 UPDATE는 테이블을 키운다

Django의 QuerySet.update()는 SQL UPDATE 한 문장이 됩니다. 행마다 새 튜플이 생기고, 옛 튜플은 dead tuple이 됩니다.

# 전 행에 새 버전이 생긴다. 옛 버전 10만 개는 autovacuum 이 치울 때까지 남는다
Post.objects.update(is_featured=False)

# 바뀔 행만 고르면 새 버전도 dead tuple 도 그만큼만 생긴다
Post.objects.filter(is_featured=True).update(is_featured=False)

autovacuum은 기본 설정에서 대략 "죽은 행 수가 50개 + 테이블 행 수의 20%"를 넘으면 그 테이블을 청소합니다. 큰 배치 작업 직후에는 이 기준을 금세 넘기므로 그 테이블은 곧 autovacuum 대상이 됩니다.

다만 오래 열린 트랜잭션은 VACUUM을 막을 수 있습니다. 이미 쓰기를 한 트랜잭션, REPEATABLE READ 이상에서 시작 무렵의 화면을 쥔 트랜잭션, 오래 도는 쿼리는 그 뒤에 죽은 버전을 "아직 볼 수도 있는" 것으로 남겨, 다른 테이블의 것이라도 VACUUM이 치우지 못하게 합니다. PostgreSQL 기본값(READ COMMITTED)에서 읽기만 하고 멈춘 트랜잭션은 문장 사이에 화면을 쥐지 않아 막지 않습니다. Django에서는 transaction.atomic() 안에서 쓰기를 한 뒤 오래 걸리는 일을 할 때, ATOMIC_REQUESTS(요청 하나를 트랜잭션 하나로 감싸는 설정)로 쓰기를 한 요청이 오래 걸릴 때 이런 트랜잭션이 생깁니다.

2. 자주 바뀌는 카운터 컬럼

조회수, 좋아요 수처럼 한 행이 아주 자주 바뀌는 컬럼은 갱신할 때마다 새 튜플을 만듭니다. 이때 HOT이 되느냐가 차이를 만듭니다.

  • 카운터 컬럼에는 인덱스를 걸지 않는다. 인덱스에 걸린 컬럼의 값이 바뀌면 HOT 조건 1이 깨집니다. 정렬이 꼭 필요하면 다른 방법(주기적 집계 테이블 등)을 먼저 고려합니다.
  • 인덱스 걸린 auto_now 컬럼을 조심한다. updated_at = models.DateTimeField(auto_now=True, db_index=True)는 save()마다 인덱스 컬럼 값을 바꾸므로, 그 테이블의 save()는 HOT이 될 수 없습니다. 직접 확인해 보니 인덱스 컬럼을 같은 값으로 SET하면 HOT이 됐고, 다른 값으로 바꾸면 1,000건 중 0건이었습니다.
  • 갱신이 잦은 테이블은 fillfactor를 낮춘다. Django 모델의 Meta에는 테이블 fillfactor 옵션이 없어서 마이그레이션에 RunSQL("ALTER TABLE ... SET (fillfactor = 80)")처럼 넣습니다. 공식 문서대로 이 명령은 이미 채워진 페이지를 바로 바꾸지 않습니다. 새로 채워지는 페이지부터 적용되게 두거나, 점검 시간에 테이블을 다시 써서 전체에 적용합니다.

3. 부풀었는지 확인하는 법

SELECT relname, n_live_tup, n_dead_tup,
       n_tup_upd, n_tup_hot_upd,          -- HOT 비율 = hot_upd / upd
       last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 10;

n_dead_tup이 계속 크게 남아 있으면 VACUUM이 따라가지 못하거나, 쓰기를 한 채 오래 열린 트랜잭션이 막고 있다는 신호입니다. 갱신이 많은 테이블에서 n_tup_hot_upd가 n_tup_upd보다 한참 작으면 인덱스 구성이나 fillfactor를 다시 볼 차례입니다.

⚠️ VACUUM FULL은 마지막 수단

파일 크기를 줄이려고 운영 중에 VACUUM FULL을 돌리기 전에, 끝날 때까지 테이블 크기만큼의 디스크 공간이 잠시 더 든다는 점도 계산에 넣습니다.

4. LSM 계열 저장소를 고를 때

쓰기가 압도적으로 많고 대부분 최근 것을 읽는 데이터(이벤트 로그, 시계열 지표, 메시지 이력)는 LSM 계열이, 읽기가 쓰기만큼 많고 조인이 잦은 업무 데이터는 B-tree 기반 RDB가 잘 맞습니다. LSM 저장소를 쓴다면 삭제가 많은지(tombstone), 없는 키 조회가 많은지(Bloom filter)를 먼저 물어보세요.

08한 장 요약 치트시트

데이터베이스는 수정할 때 덮어쓸까?

엔진마다 다르다. InnoDB는 행을 제자리에서 고치되 옛 값을 undo log로 옮기고, PostgreSQL은 행의 새 버전을 옆에 쓰고 옛 버전을 VACUUM이 나중에 치우며, LSM 계열은 정렬된 불변 파일(SSTable)을 새로 쓰고 compaction이 몰아서 치운다. 덮어쓰지 않는 이유도 하나가 아니다. PostgreSQL이 행을 새로 쓰는 것은 옛 값을 아직 읽을 트랜잭션이 있을 수 있어서이고, LSM이 파일을 새로 쓰는 것은 랜덤 쓰기를 없애기 위해서다. 그 대가로 옛 값이 쌓이는 공간과 여러 곳을 뒤지는 읽기를 치르고, 미뤄 둔 정리 작업이 그것을 되갚는다.

SSTable이란

키 순으로 정렬해 한 번에 쓰고 다시는 고치지 않는 파일. 정렬 덕분에 파일 안 이진 탐색, 범위 조회, 파일끼리의 병합이 싸고, 불변 덕분에 읽기에 잠금이 필요 없다. 수정은 새 값, 삭제는 tombstone으로 표현되고, 읽기는 최신 파일부터 본다.
