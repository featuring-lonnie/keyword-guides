멱등성
같은 요청이 두 번 와도, 세상은 한 번만 바뀐다

결제 버튼을 눌렀는데 응답이 안 온다. 다시 누르면 두 번 결제될까, 아니면 한 번도 안 됐을까? 이 질문에 "알 수 없다"라고 답할 수밖에 없는 이유와, 그럼에도 시스템을 안전하게 만드는 방법.

💬 "'한 번만 실행될 것'이라는 가정은 분산 시스템에서 상당히 비싼 가정이다. At-most-once, At-least-once, Exactly-once까지 알아봅시다."

00어느 날의 타임아웃

모든 재시도 버튼 뒤에는 같은 딜레마가 있다

사용자가 10,000원 결제 버튼을 눌렀다. 프론트엔드는 POST /payments를 보냈고… 30초가 지나도록 응답이 없다. 타임아웃. 이제 코드는 선택해야 한다.

  • 재시도하지 않는다 → 사실은 서버까지 요청이 못 갔던 거라면, 결제가 유실된다. 사용자는 "눌렀는데 왜 안 돼요?"라고 문의한다.
  • 재시도한다 → 사실은 서버가 결제를 처리했는데 응답만 못 돌아온 거라면, 이중 결제가 된다. 사용자는 환불을 요구하고, 회사는 신뢰를 잃는다.

어느 쪽이 맞는지 클라이언트는 알 방법이 없다. 응답이 안 왔다는 사실은 "요청이 유실됐다"와 "처리됐는데 응답이 유실됐다"를 구분해 주지 않기 때문이다. 이 문서의 주제인 멱등성(idempotency)은 이 딜레마를 정면으로 푸는 대신 우회한다 — "몇 번 실행돼도 한 번 실행한 것과 같게" 만들어서, 재시도를 마음 놓고 할 수 있게 하는 것이다.

이 문서가 답하는 것

① 왜 "한 번만 실행될 것"은 보장할 수 없는 비싼 가정인가 ② at-most-once / at-least-once / exactly-once는 정확히 뭐가 다른가 ③ exactly-once가 불가능하다면 Kafka가 파는 "exactly-once"는 무엇인가 ④ 우리 Django·Celery 코드를 멱등하게 만드는 실전 레시피. 다 읽으면 "재시도해도 되나?"라는 질문에 스스로 답할 수 있다.

01멱등성이란 무엇인가

수학에서 빌려온 150년 넘은 단어

📎 용어: 멱등(idempotent)

멱등한 연산 = 한 번 적용하든 여러 번 적용하든 결과 상태가 같은 연산. 수학 기호로는 f(f(x)) = f(x). 한자로 '멱(冪)'은 거듭제곱이라는 뜻으로, "거듭해도(冪) 같다(等)"로 기억하면 된다. 영어 idempotent는 라틴어 idem(같은)과 potens(힘)에서 온 말로 — "몇 번을 거듭제곱해도 자기 자신과 같다"는 뜻을 담아 — 1870년 수학자 벤저민 퍼스(Benjamin Peirce)가 대수학에서 만든 용어다.

코드로 보면 바로 감이 온다.

abs(abs(-5)) == abs(-5)   # 절댓값: 멱등 ✅ 몇 번 씌워도 5

x = 5       # 대입: 멱등 ✅ 열 번 실행해도 x는 5
x += 1      # 증가: 비멱등 ❌ 실행 횟수만큼 결과가 달라진다
🛗 비유: 엘리베이터 버튼

엘리베이터 호출 버튼은 멱등하다 — 조급하게 다섯 번 눌러도 엘리베이터는 한 대만 온다. 반면 자판기 버튼은 비멱등하다 — 다섯 번 누르면(돈이 있다면) 콜라가 다섯 캔 나온다. 시스템 설계에서 우리가 원하는 것은 자판기가 아니라 엘리베이터다.

HTTP는 이 개념을 프로토콜에 새겨 놓았다

HTTP 표준(RFC 9110 §9.2.2)은 메서드별로 멱등성을 명시한다. "같은 요청을 여러 번 보냈을 때 서버에 의도된 효과가 한 번 보낸 것과 같으면 멱등"이라고 정의하고, 이렇게 분류한다.

메서드멱등?왜
GET / HEAD✅ (나아가 '안전(safe)' — 상태를 아예 안 바꾸는 더 강한 성질)읽기만 하고 상태를 바꾸지 않는다
PUT✅"이 값으로 교체하라" — 두 번 교체해도 같은 값
DELETE✅두 번 지워도 "없는 상태"는 같다 (두 번째는 404여도 서버 상태는 동일)
POST❌"새로 만들어라" — 두 번 보내면 두 개 생긴다
⚠️ 흔한 오해: 멱등 = 같은 응답

멱등성은 서버 상태에 대한 약속이지 응답에 대한 약속이 아니다. DELETE를 두 번 보내면 첫 번째는 200, 두 번째는 404를 받을 수 있다 — 그래도 멱등하다. 리소스가 없는 상태라는 결과가 같기 때문이다. 또 하나: 클라이언트·프록시가 GET·PUT을 자동 재시도할 수 있는 근거가 바로 이 명세다. 반대로 명세는 POST 같은 비멱등 메서드의 자동 재시도를 막지만, 현실에서는 프록시나 커넥션 재사용 실패 등으로 POST도 중복 도달할 수 있다 — 뒤에서 볼 멱등성 키가 필요한 또 하나의 이유다.

✅ 실무 감각

멱등성이 왜 중요한지는 한 문장으로 요약된다: 멱등해야 재시도가 안전하다. 그리고 다음 섹션에서 보겠지만, 분산 시스템에서 재시도는 선택이 아니라 필수다.

02네트워크가 숨기는 세 가지

왜 "한 번만 실행될 것"은 비싼 가정인가

단일 프로세스 안에서 함수를 호출하면 결과는 둘 중 하나다 — 성공하거나, 예외가 나거나. 그런데 분산 시스템(여러 컴퓨터가 네트워크로 통신하며 하나의 일을 하는 시스템 — 프론트↔백엔드, 백엔드↔결제사 API, 웹서버↔큐↔워커 전부 해당)에서 원격 호출의 결과는 셋이다. 성공, 실패, 그리고 모름.

클라이언트 서버 │ │ │── POST /payments (10,000원) ────▶│ ✅ 결제 처리 완료 │ │ │ ✗ ◀──────── 200 OK ────────────│ 응답이 도중에 유실 │ │ │ (타임아웃… 성공인지 실패인지 │ │ 클라이언트는 알 수 없다) │ │ │ │── POST /payments (재시도) ───────▶│ 💸 결제가 한 번 더!

타임아웃 순간 실제로 벌어졌을 수 있는 일은 — 00에서 본 두 경우에 하나를 더해 — 세 가지고, 클라이언트 입장에서는 전부 똑같이 보인다.

  1. 요청이 유실됐다 — 재시도해야 한다.
  2. 처리된 뒤 응답만 유실됐다 — 재시도하면 중복이다.
  3. 서버가 그냥 느리다 — 아직 처리 중인데 재시도가 도착하면 같은 요청이 동시에 두 번 처리될 수 있다.
⚠️ 핵심 통찰

"응답을 못 받았다"는 "처리되지 않았다"가 아니다. 요청의 전달 여부와 처리 여부를 클라이언트가 확정할 수 없다는 것 — 이것이 분산 시스템의 근본 조건이고, "한 번만 실행될 것"이라는 가정이 비싼 이유다. 이 가정 위에 지은 코드는 네트워크가 완벽할 때만 옳다. 그리고 네트워크는 완벽하지 않다.

✅ 실무 감각

이 "모름"은 우리 스택 모든 경계에서 발생한다. 브라우저→nginx, nginx→gunicorn(응답이 늦으면 gunicorn이 처리 중이던 자기 프로세스를 강제 종료한다 — 요청은 처리 중이었는데 응답은 영영 사라진다), Django→결제사 API, Django→SQS→Celery(레시피 ②에서 다룬다). 경계가 하나 늘 때마다 "모름"이 발생할 지점도 하나 는다.

03두 장군 문제 — 불가능성의 증명

이건 엔지니어링 부족이 아니라 수학이다

"그럼 확인 응답(ack)을 더 보내면 되지 않나?"라는 생각이 자연스럽게 든다. 이 직관이 왜 틀렸는지를 보여주는 것이 두 장군 문제(Two Generals Problem)다. 1975년 아코윤루(Akkoyunlu) 등의 논문에서 제기됐고, 1978년 짐 그레이(Jim Gray)가 데이터베이스 교과서적 노트에서 '두 장군 역설'이라는 이름을 붙였다.

두 장군이 계곡을 사이에 두고 각자의 언덕에 진을 쳤다. 동시에 공격해야만 이긴다. 연락 수단은 계곡(적진)을 통과하는 전령뿐인데, 전령은 붙잡힐 수 있다 — 즉 메시지가 유실될 수 있는 채널이다.

장군 A 장군 B │── "새벽에 공격" ─────────────────▶│ 받았다. 그런데… │ │ A는 내가 받은 걸 모른다. │◀──────────── "확인!" ────────────│ 나 혼자 공격하게 될지도? │ 받았다. 그런데 B는 │ │ 내 확인이 도착한 걸 모른다… │ │── "확인의 확인!" ────────────────▶│ (무한 반복…) │ │ 어느 쪽도 "상대가 확실히 안다"에 도달하지 못한다 — 마지막 전령은 언제나 유실됐을 수 있으므로

어떤 프로토콜을 쓰든 마지막으로 보낸 메시지는 유실됐을 수 있고, 보낸 쪽은 그 메시지가 도착했는지 알 수 없다. 확인을 아무리 겹쳐도 이 구조는 사라지지 않는다. 메시지 시스템에 대입하면: 보낸 쪽은 "도착했는가"를 알아야 재전송 여부를 정할 수 있는데, 그 "앎"이 바로 장군들이 끝내 도달하지 못한 합의다. 따라서 유실 가능한 채널 위에서 두 노드가 "정확히 한 번"에 대해 완전한 합의에 도달하는 것은 수학적으로 불가능하다는 것이 증명되어 있다.

⚠️ 핵심 통찰: exactly-once delivery는 불가능하다

메시지가 유실될 수 있는 네트워크에서, 유한한 횟수의 메시지로 "정확히 한 번 전달"을 보장하는 것은 불가능하다. 이것은 더 좋은 라이브러리나 더 큰 예산으로 해결되는 문제가 아니라 정리(theorem)다. 그렇다면 실전 시스템들은 이 불가능 앞에서 무엇을 골랐을까 — 다음 섹션에서 본다.

📎 그럼 TCP는 뭐지?

TCP도 재전송과 수신 측 중복 제거(패킷마다 붙는 순번)로 한 연결 안에서 신뢰성 있는 전달을 흉내 낸다 — 다음 두 섹션에서 배울 "재시도 + 중복 걸러내기" 조합의 원조 격이다. 하지만 연결이 끊기고 다시 맺어지면 순번이 처음부터 다시 시작되어, 서버는 새 요청이 "이전 연결에서 이미 받은 것"인지 알 길이 없다. 타임아웃 후 애플리케이션이 새 연결로 재시도하는 상황이 바로 그 지점이고, 그래서 애플리케이션 레벨의 멱등성이 따로 필요하다.

04세 가지 전달 보장

유실과 중복, 둘 중 하나는 골라야 한다

exactly-once delivery가 불가능하다면, 현실의 메시지 시스템이 고를 수 있는 선택지는 두 개다. 재시도를 안 하거나(유실 감수), 재시도를 하거나(중복 감수).

📤 At-most-once — 최대 한 번

보내고 확인하지 않는다(fire-and-forget). 실패해도 재시도 없음.

  • 중복 없음 ✅ / 유실 가능 ❌
  • 구현이 가장 단순하고 빠르다
  • 예: 접속 로그, 실시간 지표처럼 하나쯤 빠져도 되는 데이터

📬 At-least-once — 최소 한 번

확인 응답(ack)이 올 때까지 재시도한다.

  • 유실 없음 ✅ / 중복 가능 ❌ (ack만 유실된 경우)
  • 업무 데이터의 사실상 표준 선택
  • 예: 결제, 주문, DM 발송 — 단, 받는 쪽이 멱등해야 안전

세 번째인 exactly-once(정확히 한 번)는 "전달" 수준에서는 불가능하므로, 시스템 전체를 설계해서 효과가 정확히 한 번인 것처럼 만드는 목표 상태를 가리키는 말로 쓰인다. 공식은 이미 나왔다:

분산 시스템의 기본 공식

at-least-once 전달 + 멱등한 처리 = 사실상의 exactly-once. 유실은 재시도로 막고, 재시도가 만드는 중복은 멱등성으로 무해하게 만든다. 어려운 보장(정확히 한 번 전달)을 포기하는 대신, 달성 가능한 두 가지를 조합하는 것이다.

보장유실중복
at-most-once가능 ❌없음 ✅
at-least-once없음 ✅가능 ❌
exactly-once (효과 기준)없음 ✅발생하되 무해화 ✅
📮 비유: 등기 우편

일반 우편은 at-most-once다 — 부치고 잊는다, 가끔 사라진다. 등기처럼 수취 확인(ack)이 돌아올 때까지 다시 부치기는 at-least-once다 — 반드시 도착하지만 같은 편지가 두 통 올 수 있다. exactly-once처럼 보이게 하려면? 받는 사람이 편지 봉투의 일련번호를 보고 이미 읽은 편지는 버리면 된다. 그 "일련번호 확인"이 다음 섹션부터 나오는 멱등성 장치들이다.

05그런데 Kafka는 "exactly-once"를 판다?

불가능하다더니 — delivery와 processing은 다른 말이다

Kafka(카프카)는 대용량 메시지를 디스크 로그에 쌓아두고 여러 소비자(컨슈머)가 읽어가게 하는 메시지 브로커다. 메시지는 토픽(topic)이라는 이름 붙은 로그에 쌓이고, 각 토픽은 병렬 처리를 위해 여러 파티션(partition)으로 쪼개진다 — 순서(그리고 곧 나올 순번)는 파티션 안에서만 보장된다. 2017년 Kafka 0.11이 "exactly-once semantics(EOS)"를 발표했을 때 "불가능하다는 걸 해냈다고?"라는 논쟁이 벌어졌다. 답은: Kafka가 보장하는 것은 정확히 한 번의 전달(delivery)이 아니라 정확히 한 번의 처리 효과(processing)다. 내부를 보면 방금 배운 공식 그대로다.

부품 ① 멱등 프로듀서 — 시퀀스 번호로 중복 제거

프로듀서(메시지를 보내는 쪽)는 브로커로부터 고유한 프로듀서 ID(PID)를 받고, 파티션마다 메시지에 0, 1, 2, … 순번을 붙여 보낸다. 브로커는 "마지막으로 저장한 순번 + 1"인 메시지만 받아들인다.

Producer(PID=7) Broker │── msg(seq=41) ────────────▶│ 41 = 40+1 → 저장 ✅ │ ✗ ◀── ack 유실 │ │── msg(seq=41) 재전송 ──────▶│ 41 ≤ 마지막(41) │◀───────── ack ─────────────│ → 중복, 버리고 ack만 🗑

재전송(at-least-once)은 그대로 두고, 받는 쪽에서 순번으로 중복을 판별해 버리는 것 — 등기 우편 비유의 일련번호가 정확히 이것이다. Kafka 3.0부터는 이 동작(enable.idempotence=true, acks=all)이 기본값이다.

부품 ② 트랜잭션 — "읽고-처리하고-쓰기"를 원자적으로

"A 토픽에서 읽어서 → 가공해서 → B 토픽에 쓰고 → 어디까지 읽었는지(오프셋 — 파티션 안에서 내가 읽은 위치) 기록"하는 파이프라인을 생각하자. 오프셋 기록도 사실은 Kafka 내부 토픽에 쓰는 것이라, B 토픽 쓰기와 오프셋 기록을 하나의 트랜잭션 — 원자적(atomic) 단위, 즉 전부 반영되거나 전부 취소되거나 둘 중 하나 — 으로 묶을 수 있다. 중간에 죽으면 쓰기와 오프셋이 함께 취소되고, 재시작한 컨슈머는 이전 위치부터 다시 읽어 다시 처리한다 — 미완성 쓰기는 버려지므로 결과는 한 번 처리한 것과 같다. 이것이 KIP-98(Kafka Improvement Proposal 98)이 정의한 EOS의 전체 그림이다.

⚠️ 흔한 오해: "Kafka 쓰면 exactly-once 자동 해결"

Kafka의 EOS는 Kafka 토픽 사이의 파이프라인 안에서만 성립한다. 컨슈머가 메시지를 읽어 외부 세계(DB 업데이트, 이메일 발송, 결제 API 호출)에 부수효과를 일으키는 순간, 그 부분의 멱등성은 다시 여러분의 숙제가 된다. 마법의 스위치가 아니라 "우리 공식이 아주 잘 구현된 사례"로 이해해야 한다.

06레시피 ① HTTP API — 멱등성 키

POST를 안전하게 재시도하는 업계 표준 패턴

POST는 본질적으로 비멱등하다. 이걸 멱등하게 만드는 표준 관행이 멱등성 키(idempotency key)다. 결제 업계의 Stripe가 대중화했고, 현재 IETF에서 Idempotency-Key HTTP 헤더로 표준화가 진행 중이다. 동작 원리는 세 줄로 요약된다.

  1. 클라이언트가 요청마다 고유 키를 만든다UUID(사실상 충돌하지 않는 랜덤 식별자 — 128비트 중 122비트가 난수다)를 생성해 Idempotency-Key 헤더에 담아 보낸다. 재시도할 때는 같은 키를 다시 보낸다.
  2. 서버는 처음 본 키면 처리하고, 키와 함께 응답을 저장한다Stripe는 첫 요청의 상태 코드와 응답 본문을 통째로 저장한다 — 성공이든 실패든.
  3. 이미 본 키면 처리하지 않고 저장해 둔 응답을 재생한다클라이언트는 몇 번을 재시도해도 항상 같은 응답을 받고, 결제는 한 번만 일어난다. Stripe는 24시간이 지난 키를 정리한다.

❌ 나쁜 예 — 재시도가 이중 결제가 되는 뷰

class PaymentView(APIView):
    def post(self, request):
        # 타임아웃 후 재시도가 오면 Payment가 하나 더 생긴다
        payment = Payment.objects.create(
            user=request.user,
            amount=request.data["amount"],
        )
        charge_card(payment)
        return Response({"id": payment.id})

✅ 좋은 예 — 멱등성 키 + DB 유니크 제약

class Payment(models.Model):
    # unique=True가 최후의 방어선: 동시 요청이 겹쳐도 DB가 중복을 거부한다
    idempotency_key = models.CharField(max_length=255, unique=True)
    ...

class PaymentView(APIView):
    def post(self, request):
        key = request.headers["Idempotency-Key"]  # 클라이언트가 생성한 UUID
        payment, created = Payment.objects.get_or_create(
            idempotency_key=key,
            defaults={"user": request.user,
                      "amount": request.data["amount"]},
        )
        if created:
            charge_card(payment)          # 첫 요청만 실제 결제
        return Response({"id": payment.id})  # 재시도도 같은 응답
✅ 실무 감각

핵심은 애플리케이션 코드가 아니라 DB 제약이 중복을 막게 하는 것이다. "먼저 조회해서 없으면 만들기"는 결국 SELECT 후 INSERT 두 단계라서, 두 요청이 동시에 조회를 통과하는 레이스 컨디션(경쟁 상태 — 동시 실행의 타이밍에 따라 결과가 달라지는 상황)이 남는다. unique=True가 있으면 그 순간 한쪽이 IntegrityError로 튕기는데, Django의 get_or_create는 이 예외를 잡아 기존 행을 다시 조회해 돌려주는 것까지 알아서 해 준다(단, 위 코드처럼 유니크 필드가 defaults가 아닌 조회 조건 쪽에 있어야 한다). 유니크 제약 없는 멱등성 키는 방어선이 아니라 장식이다.

⚠️ 이 코드에도 틈은 있다

행을 만든 직후, charge_card 직전에 서버가 죽으면? 이후의 재시도는 전부 created=False가 되어 결제 없이 성공 응답을 돌려받는다 — 이중 결제만큼 위험한 "영구 미결제" 상태다. 또 첫 요청이 아직 결제 진행 중일 때 같은 키의 재시도가 도착해도 미완료 작업에 성공처럼 응답하게 된다(Stripe는 이 경우 409로 "처리 중"을 알린다). 실전에서는 status 필드를 pending으로 만들어 두고 결제 성공 시에만 charged로 바꾸는 식으로 상태를 추적한다. "기록과 부수효과 사이의 틈"이라는 이 문제의 정체는 레시피 ②의 경고 박스에서 정면으로 다룬다.

📎 어디까지 저장하나

위 예제는 단순화를 위해 생성된 행을 돌려주지만, Stripe처럼 응답 전체(상태 코드+본문)를 키와 함께 저장하는 편이 더 정확하다. 첫 요청이 검증 오류(400)였다면 재시도도 똑같이 400을 받아야 "같은 요청에는 같은 답"이라는 계약이 유지되기 때문이다. 키는 요청 본문과 함께 저장하고, 같은 키에 다른 본문이 오면 오류로 거절(IETF 초안 권고는 422)하는 것까지 해야 완성이다.

07레시피 ② 백그라운드 워커 — Celery·SQS

큐는 태생이 at-least-once다

메시지 큐(작업을 넣어두면 워커가 꺼내 처리하는 대기열)를 쓰는 순간 전달 보장 문제는 남의 일이 아니게 된다. AWS SQS 문서는 표준 큐(기본형 — 순서 보장과 중복 제거를 제공하는 FIFO 큐라는 다른 종류도 있다)에 대해 명시적으로 말한다: at-least-once delivery — 드물지만 같은 메시지가 두 번 이상 배달될 수 있으니, 컨슈머 코드가 중복 처리에 안전하도록(=멱등하도록) 설계하라. 워커가 메시지를 집으면 일정 시간(visibility timeout) 동안 다른 워커에게 안 보이게 숨겨질 뿐, 그 시간 안에 처리 완료(삭제)를 못 하면 메시지는 다시 나타나 다른 워커에게 배달된다.

Celery(셀러리 — 파이썬 진영의 대표 작업 큐 프레임워크. 태스크를 큐에 넣으면 웹 요청 밖의 별도 워커 프로세스가 꺼내 실행한다)에는 이 선택이 acks_late 옵션으로 그대로 노출되어 있다. ack(수신 확인 — 큐에게 "이 메시지 처리했으니 지워도 돼"라고 알리는 신호)를 언제 보내느냐의 문제다.

설정ack 시점워커가 도중에 죽으면
acks_late=False (기본값)작업 시작 전메시지는 이미 지워짐 → 작업 유실 (at-most-once 쪽)
acks_late=True작업 완료 후메시지 재배달 → 중복 실행 (at-least-once 쪽)

기본값이 False인 데에도 이유는 있다 — 실행할 때마다 죽는 태스크가 무한 재배달되며 워커를 계속 쓰러뜨리는 것을 막는 보수적인 선택이다.

⚠️ 핵심 통찰: 옵션이 보장을 바꾼다

유실이 싫어서 acks_late=True를 켜는 순간, 여러분은 at-least-once를 선택한 것이고 그 태스크는 반드시 멱등해야 한다는 계약서에 서명한 것이다. 태스크를 멱등하게 만들지 않고 acks_late만 켜면, 유실 버그를 중복 버그로 바꿔치기했을 뿐이다.

❌ 나쁜 예 — 재배달되면 DM이 두 번 나간다

@app.task(acks_late=True)
def send_dm(user_id, message):
    # visibility timeout 초과, 워커 재시작… 재배달 경로는 많다
    api.send_direct_message(user_id, message)

✅ 좋은 예 — 처리 기록 테이블로 중복을 걸러낸다

# 큐에 넣는 쪽 — 발행 시점에 고유 ID를 만들어 메시지에 실어 보낸다
send_dm.delay(user_id, message, dispatch_id=str(uuid4()))

# 소비하는 쪽 — 재배달돼도 같은 dispatch_id가 함께 실려 온다
@app.task(acks_late=True)
def send_dm(user_id, message, dispatch_id):
    # dispatch_id 컬럼에는 unique 제약이 걸려 있다
    try:
        DmDispatch.objects.create(dispatch_id=dispatch_id)
    except IntegrityError:
        return  # 이미 처리한 메시지의 재배달 → 조용히 무시
    api.send_direct_message(user_id, message)
⚠️ 완벽하지 않다 — 기록과 부수효과 사이의 틈

위 코드에도 틈은 있다. 기록을 먼저 남기면 "기록 직후, 발송 직전"에 죽었을 때 재배달이 걸러져 DM이 영영 안 나간다(유실). 기록을 나중에 남기면 "발송 직후, 기록 직전"에 죽었을 때 두 번 나간다(중복). 외부 API 호출은 우리 DB 트랜잭션에 묶을 수 없어서 이 틈을 완전히 없앨 수는 없고, 어느 쪽 실패가 덜 아픈지 골라야 한다. 근본 해법은 외부 API 자체가 멱등성 키를 지원하는 것 — 그러면 레시피 ①의 구조가 API 건너편까지 이어진다. 결제 API들이 멱등성 키를 지원하는 이유가 바로 이것이다.

✅ 실무 감각

정기 배치(celery beat 등)도 같은 원리다. "매일 새벽 크레딧 정산" 태스크가 장애로 두 번 돌면? UPDATE credits SET balance = balance - used(비멱등)가 아니라, 정산 결과를 (날짜, 워크스페이스) 유니크 키로 기록하고 이미 있으면 건너뛰는 구조로 만들어 두면 재실행이 무섭지 않다. "이 태스크, 지금 한 번 더 돌려도 괜찮은가?"에 Yes라고 답할 수 있는 태스크가 좋은 태스크다.

08멱등하게 만드는 4가지 패턴

비멱등한 코드를 발견했을 때 꺼내 쓰는 도구 상자

  1. 패턴 1 — 애초에 멱등한 연산으로 표현한다"증가시켜라"(balance += 100) 대신 "이 값으로 만들어라"(plan = 'premium'). 상대 변경(delta)은 비멱등, 절대값 대입은 멱등이다. 요구사항을 절대값으로 다시 쓸 수 있는지부터 살핀다.
  2. 패턴 2 — 멱등성 키 + 결과 저장연산 자체를 멱등하게 못 만들면(결제·발송처럼 실행 자체가 부수효과일 때), 요청마다 고유 키를 붙이고 처리 기록을 남겨 재실행을 걸러낸다. 레시피 ①·②가 이 패턴이다.
  3. 패턴 3 — 조건부 업데이트"현재 상태가 X일 때만 Y로 바꿔라"를 쿼리에 넣는다. 두 번째 실행은 조건 불일치로 0건 갱신 — 자연스럽게 멱등해진다. 상태 머신(정해진 상태들 사이를 정해진 규칙으로만 이동하는 모델 — pending → paid → shipped)이 있는 도메인에서 특히 강력하다.
  4. 패턴 4 — 유니크 제약을 최후의 방어선으로패턴 1~3이 코드 실수·레이스로 뚫려도 DB가 마지막에 막아준다 — 레시피 ①의 unique=True가 바로 이 패턴이다.

SQL로 보는 패턴 1 · 3 · 4

-- 패턴 1: 절대값 대입 (몇 번 실행해도 같은 상태)
UPDATE users SET plan = 'premium' WHERE id = 42;

-- 패턴 3: 조건부 업데이트 (두 번째 실행은 0 rows)
UPDATE orders SET status = 'paid'
 WHERE id = 42 AND status = 'pending';

-- 패턴 4: 유니크 제약 + UPSERT (중복 삽입을 DB가 무시)
INSERT INTO credits (order_id, amount) VALUES (42, 100)
    ON CONFLICT (order_id) DO NOTHING;
📎 용어: UPSERT

UPSERT = UPDATE + INSERT의 합성어. "없으면 넣고, 있으면 갱신(또는 무시)"을 DB가 원자적으로 처리하는 구문. PostgreSQL에서는 INSERT ... ON CONFLICT로 쓴다. 조회와 삽입을 코드에서 두 단계로 하면 그 사이에 다른 요청이 끼어들 수 있지만, UPSERT는 그 틈이 없다.

⚠️ 조건부 업데이트의 함정: 갱신 0건 ≠ 성공

패턴 3에서 0건 갱신은 "이미 처리됨"일 수도, "그런 주문이 없음"일 수도 있다. 후속 동작(영수증 발송 등)이 걸려 있다면 cursor.rowcount를 확인하고 0일 때 현재 상태를 조회해 분기해야 한다. 멱등성은 "조용히 두 번 하지 않기"이지 "결과 확인 생략하기"가 아니다.

09한 장 요약 치트시트

💬 "한 번만 실행될 것이라는 가정은 비싸다" — 왜?

네트워크에서는 "응답 없음"이 "처리 안 됨"을 뜻하지 않기 때문이다. 두 장군 문제가 증명하듯 "정확히 한 번 전달"은 수학적으로 불가능하다. 그래서 고를 수 있는 것은 at-most-once(재시도 안 함, 유실 감수 — 로그·지표)와 at-least-once(ack까지 재시도, 중복 감수 — 업무 데이터의 기본값)뿐이고, exactly-once는 at-least-once 전달 위에 멱등한 처리를 얹어 만들어내는 효과 기준의 보장이다 (Kafka EOS도 이 구조다).

기억할 것내용
멱등성 정의1번 하든 N번 하든 결과 상태가 같다 — f(f(x)) = f(x). 멱등해야 재시도가 안전하다
HTTP 메서드GET·PUT·DELETE는 멱등, POST는 아님 (RFC 9110). POST 재시도에는 멱등성 키
원격 호출의 결과성공 / 실패 / 모름 — 셋이다
멱등성 키클라이언트가 UUID 생성 → 서버는 첫 응답을 저장, 같은 키엔 재생 (Stripe 방식, IETF 표준화 중)
Celery acks_lateFalse(기본) = 죽으면 유실 / True = 죽으면 중복 → 켰다면 태스크를 멱등하게
SQS 표준 큐at-least-once가 명세다. 중복 배달은 버그가 아니라 계약 — 컨슈머가 걸러야 한다
4가지 패턴① 절대값 대입 ② 멱등성 키+기록 ③ 조건부 UPDATE ④ 유니크 제약(최후의 방어선)
설계 질문새 API·태스크를 만들 때마다: "이거 지금 한 번 더 실행돼도 괜찮은가?"
