00새벽 3시, Too many open files

고장은 늘 이 문장으로 시작한다

어느 날 새벽, 잘 돌던 서비스가 갑자기 응답하지 않는다. 로그를 열면 이런 게 쏟아진다.

OSError: [Errno 24] Too many open files
# nginx 쪽에서는 이렇게 보인다
accept4() failed (24: Too many open files)

이상한 점이 있다. 우리 코드는 파일을 열지 않는다. 로그는 표준 출력으로만 나가고, 저장은 전부 S3다. 그런데 왜 "열린 파일이 너무 많다"고 할까?

답은 이 문장 안에 있다. 리눅스가 말하는 "파일"은 우리가 생각하는 파일이 아니다. 지금 이 순간 그 프로세스가 붙들고 있던 것은 HTTP 커넥션 소켓 수천 개였고, 커널 입장에서 그것은 /var/log/app.log와 완전히 같은 종류의 물건이었다. S3에 올리는 그 순간에도 마찬가지다 — HTTPS 커넥션 하나가 소켓 하나이고, 소켓 하나가 곧 "열린 파일" 하나다. "파일을 안 연다"와 "이 자원을 안 쓴다"는 전혀 다른 말이었다.

이 문서가 답하는 것

① 왜 소켓도 · 파이프도 · 심지어 프로세스도 "파일"인가 ② 그 정체인 작은 정수가 커널 안에서 무엇을 가리키는가 ③ 그래서 2>&1은 왜 그렇게 생겼고, ulimit -n은 왜 하필 1024인가 ④ 그리고 이 전부가 왜 "운영체제가 리소스를 추상화 하는 방식"의 교과서적 사례인가. 다 읽으면 Errno 24를 봤을 때 어디를 볼지 손이 먼저 움직인다.

01파일 디스크립터란 무엇인가

놀랍도록 시시한 정답부터

파일 디스크립터(file descriptor, 줄여서 fd)는 0, 1, 2, 3… 으로 세는 작은 음이 아닌 정수다. 그게 전부다. 마법도, 구조체도, 포인터도 아니다.

Python으로 확인해 보면 시시할 정도로 그냥 숫자다.

import socket

f = open("/tmp/a.txt", "w")
print(f.fileno())        # 3

s = socket.socket()
print(s.fileno())        # 4  ← 소켓도 같은 번호 체계를 쓴다
📎 용어: 소켓(socket)

소켓 = 네트워크로 데이터를 주고받기 위한 통로. HTTP 요청 하나를 보낸다는 건 상대 서버와 소켓 하나를 여는 일이고, 그 소켓은 fd 하나를 차지한다. 파일처럼 read · write · close가 그대로 통한다 — 이 문서 전체가 왜 그런지에 대한 이야기다.

이 정수는 프로세스마다 따로 매겨진다. 커널은 프로세스마다 배열 하나를 들고 있고, fd는 그 배열의 인덱스다. 내 프로세스의 3번과 옆 프로세스의 3번은 아무 관계가 없다. 반대로 같은 프로세스 안의 스레드끼리는 이 배열을 공유한다 — 스레드 A가 연 fd를 스레드 B가 그대로 쓸 수 있고, 뒤에 볼 사고도 여기서 난다.

📎 용어: 시스템 콜(system call)

시스템 콜 = 사용자 프로그램이 커널에게 일을 시키는 유일한 창구. 파일 읽기·네트워크 전송처럼 하드웨어가 필요한 일은 프로그램이 직접 못 하고 반드시 커널에 부탁해야 한다. open() · read() · write() · close()가 대표적이다.

0번, 1번, 2번은 예약석이다

번호이름Python에서
0표준 입력 (stdin)sys.stdin
1표준 출력 (stdout)sys.stdout
2표준 에러 (stderr)sys.stderr

이 셋은 부모 프로세스에게서 물려받는다. 터미널에서 프로그램을 띄우면 셋 다 터미널을 가리키고, 그래서 print()가 화면에 뜬다. 물려받는 것이므로 부모(쉘)가 미리 바꿔치기할 수 있다 — 그게 04절에서 볼 리다이렉션이다.

⚠️ POSIX가 못 박은 것은 "번호"지 "열려 있음"이 아니다

표준이 정한 것은 stdin·stdout·stderr가 각각 0 · 1 · 2번을 쓴다는 번호 배정이다. "모든 프로세스가 이 셋을 열린 채로 시작한다"는 보장이 아니다. 부모가 닫아 버리고 프로그램을 띄우면 정말로 닫힌 채 시작하고, 그러면 첫 open()이 0번을 받는다.

$ python3 -c 'f=open("/tmp/a.txt","w"); print(f.fileno())' 0<&-
0   # 0<&- 는 "stdin 을 닫고 실행하라"는 뜻

실무에서 마주칠 일은 드물지만, 왜 3이 나오는지를 "규칙"으로 이해했는지 "외운 값"으로 이해했는지가 여기서 갈린다.

📎 용어: POSIX

POSIX = 유닉스 계열 운영체제가 지켜야 할 인터페이스 표준(IEEE 1003). 리눅스 · macOS · BSD가 이걸 따르기 때문에, 여기서 설명하는 내용은 대부분 세 곳 모두에서 똑같이 동작한다. (윈도우는 다른 길을 갔다 — HANDLE 이라는 별도 체계를 쓴다.)

⚠️ 위 예제의 3은 값이 아니라 규칙이다

스크립트로 돌리면 3이지만, pytest 안에서는 5가 나온다 — pytest가 출력을 가로채려고 임시 파일을 미리 열어 3·4를 차지하고 있기 때문이다. 외울 것은 3이 아니라 "현재 비어 있는 가장 작은 번호"라는 규칙이다.

02왜 하필 "정수"였나

1974년의 설계 결정이 지금 우리 코드를 결정한다

1974년 Communications of the ACM에 실린 Dennis Ritchie와 Ken Thompson의 UNIX 논문에는 이런 취지의 정의가 나온다 — open이 돌려주는 값을 "파일 디스크립터"라 부르며, 이후 read · write 호출에서 그 파일을 가리키는 데 쓰는 작은 정수다. (직접 인용이 아니라 요지 정리다.)

진짜 발명은 그다음이었다. 유닉스는 특수 파일(special file)이라는 개념을 도입해서, 터미널 · 디스크 · 프린터 같은 장치도 파일시스템 안에 이름을 갖게 했다. 그 결과가 이것이다.

장치마다 다른 API 파일 디스크립터라는 단일 창구 ───────────────── ────────────────────────── read_from_tape() ┌──────────────┐ read_from_disk() ──▶ │ read(fd, …) │ read_from_terminal() │ write(fd,…) │ read_from_printer() │ close(fd) │ …장치가 늘 때마다 API 추가 └──────────────┘ fd 가 무엇을 가리키든 동일

이게 왜 대단한가. wc -l이라는 프로그램은 "줄 수를 센다"는 일만 안다. 그 입력이 디스크의 파일인지, 다른 프로그램의 출력인지, 키보드인지 알 필요가 없다. 그냥 fd에서 read()할 뿐이다. 파이프(|)로 아무 프로그램이나 이어 붙일 수 있는 유닉스 철학은, 이 추상화가 없으면 성립하지 않는다.

⚠️ 흔한 오해: "유닉스는 모든 것이 파일이다"

자주 인용되지만 정확하지 않다. TCP 소켓은 파일시스템에 이름이 없고, 소켓과 파이프는 lseek()(읽는 위치를 옮기는 시스템 콜)도 안 된다 — 흘러가 버린 데이터로 되돌아갈 방법이 없기 때문이다. 더 정확한 표현은 "모든 것이 파일 디스크립터를 가질 수 있다"이다. 통일된 것은 저장 방식이 아니라 손잡이다.

(예외도 있다. 유닉스 도메인 소켓 — 같은 머신 안 프로세스끼리 쓰는 소켓 — 은 파일시스템에 이름이 있다. /var/run/docker.sock이 그것이다.)

fd 가 걸어온 길

지금 모르는 단어가 있어도 괜찮다. 05절과 08절에서 하나씩 푼다.

  1. 1974fd 의 탄생Ritchie · Thompson 의 UNIX 논문. open 이 돌려주는 작은 정수. 특수 파일로 장치까지 같은 read · write 로 다룬다.
  2. 1983BSD 소켓4.2BSD 가 네트워크를 fd 위에 올린다. 파일시스템에 이름이 없는 것도 fd 가 될 수 있게 된 순간 — "파일"이 아니라 "디스크립터"가 본질임이 드러난다.
  3. 1999 · 2002fd 를 수만 개 다루는 시대C10K 문제 제기와 그 답인 kqueue · epoll. 08절에서 본다.
  4. 2014Python 3.4 / PEP 446파이썬이 만드는 fd 가 기본적으로 자식 프로세스에 상속되지 않도록 바뀐다. fd 누수가 보안 문제라는 인식의 결과.
  5. 2019pidfdLinux 5.3. 이제 프로세스조차 fd 로 가리킨다.

03세 겹 테이블 — 번호표는 파일이 아니다

이 문서에서 하나만 가져간다면 이 절이다

fd가 "배열의 인덱스"라면, 그 배열의 칸에는 무엇이 들어 있을까. 여기서부터가 진짜 구조다. 커널은 세 겹으로 나눠 들고 있다.

① fd 테이블 ② 열린 파일 서술자 ③ inode (프로세스마다 하나) (offset · 플래그) (파일 실체, 이름 아님) ┌─────────────┐ │ 0 ──────────┼───┐ │ 1 ──────────┼───┼──▶ ┌──────────────────┐ │ 2 ──────────┼───┘ │ offset : 4096 │ ┌──────────────┐ │ 3 ──────────┼──────▶ │ flags : O_WRONLY│ ───▶ │ inode 12345 │ └─────────────┘ └──────────────────┘ ┌─▶│ 크기·권한· │ 프로세스 A │ │ 데이터 블록 │ │ └──────────────┘ ┌─────────────┐ ┌──────────────────┐ │ ▲ │ 3 ──────────┼──────▶ │ offset : 0 │ ───┘ │ └─────────────┘ │ flags : O_RDONLY│ /var/log/app.log 프로세스 B └──────────────────┘ (이름은 밖에서 가리킬 뿐)
  • ① fd 테이블 — 프로세스마다 하나. "3번 칸 = 저기" 정도의 포인터 배열이다. 여기에만 FD_CLOEXEC(05절에 나온다) 같은 디스크립터 자체의 속성이 붙는다.
  • ② 열린 파일 서술자 — 지금 어디까지 읽었는지(offset)와 열 때 준 플래그를 들고 있다. 커널 전역 테이블에 있다. 플래그에는 O_APPEND(항상 끝에 쓰기), O_NONBLOCK(데이터가 없으면 기다리지 말고 즉시 돌아오기) 같은 것들이 들어간다 — 이건 번호가 아니라 서술자의 성질이라, 같은 서술자를 가리키는 번호가 여럿이면 전부에게 한꺼번에 적용된다.
  • ③ inode — 파일의 실체. 크기 · 권한 · 실제 데이터 블록 위치. 파일 하나당 하나다. 이름은 여기 없다 — 경로는 밖에서 inode를 가리키는 꼬리표일 뿐이라, 이름이 둘이어도(하드 링크) inode는 하나다.
⚠️ 이름이 함정이다

영어로 fd는 file descriptor, ②는 open file description — 한 글자 차이인데 완전히 다른 것이다. 이 문서에서는 헷갈리지 않도록 fd는 "번호", ②는 "서술자"로만 부른다. 막히면 이것만 떠올리면 된다 — 번호는 프로세스 안에만 있고, 서술자는 커널에 있다.

⚠️ 핵심 통찰

fd 를 복사한다는 것은 ①의 칸을 복사하는 것이지, ②나 ③을 복사하는 게 아니다. 그래서 복사된 두 fd 는 같은 offset 을 공유한다. 반대로 같은 파일을 open() 두 번 하면 ②가 두 개 생기므로 offset 은 따로 논다 — ③은 여전히 하나다. 여기서 갈라지는 두 갈래가 뒤에 나올 리다이렉션 · 상속 · 누수를 전부 설명한다.

직접 확인해 보자

📎 관용구: lseek(fd, 0, SEEK_CUR)

lseek(fd, 이동량, 기준점) = 서술자의 offset을 옮기는 시스템 콜. 옮긴 뒤의 위치를 돌려주므로, 이동량 0 · 기준점 "현재 위치"로 부르면 "움직이지 말고 지금 위치만 알려 줘"가 된다. ②를 직접 들여다보는 유일한 방법이라 아래 예제에서 계속 쓴다.

① 두 번 open — 서술자가 둘, offset 도 따로

import os
a = open("/tmp/x", "rb")
b = open("/tmp/x", "rb")   # 같은 파일, 다른 서술자

os.read(a.fileno(), 10)      # raw fd 로 10바이트
print(os.lseek(a.fileno(), 0, os.SEEK_CUR),
      os.lseek(b.fileno(), 0, os.SEEK_CUR))   # 10 0  ← 서로 영향 없음
⚠️ 왜 a.read(10) 이 아니라 os.read() 인가

파이썬의 파일 객체는 버퍼드다 — a.read(10)을 부르면 커널에서는 10바이트가 아니라 4096바이트를 통째로 미리 읽어 온다. 그래서 a.tell()은 10을 보여주지만(버퍼 잔량을 빼서 보정한 유저 공간 값), 커널의 실제 offset은 4096이다.

a.read(10)
print(a.tell())                              # 10   ← 파이썬이 보여주는 값
print(os.lseek(a.fileno(), 0, os.SEEK_CUR))  # 4096 ← ②의 진짜 값

②를 이야기하는 자리에서 tell()을 쓰면 ②가 아닌 것을 보여주게 된다. 번호와 서술자를 섞어 쓰는 코드가 위험한 이유가 여기 압축돼 있다 — 라이브러리가 버퍼에 들고 있는 것과 커널이 아는 것이 다르다.

② dup — 번호는 둘, 서술자는 하나, offset 은 공유

a = open("/tmp/x", "rb")
fd2 = os.dup(a.fileno())     # 번호표만 한 장 더 뽑는다
os.read(a.fileno(), 10)

print(os.lseek(fd2, 0, os.SEEK_CUR))  # 10 ← 건드리지도 않은 fd2 가 움직였다
🏨 비유 — 클로크룸을 한 겹 늘려서

번호표(①) 뒤에는 접수대에 붙은 접수 전표(②)가 있다. 전표에는 "이 손님이 어디까지 꺼내 갔는지, 맡길 때 조건이 무엇이었는지"가 적혀 있다. 그리고 옷걸이에 걸린 실제 코트(③)가 있다.

dup() = 같은 전표를 가리키는 번호표를 한 장 더 뽑는다 → 전표가 하나이므로 위치도 하나. 두 번 open() = 같은 코트 한 벌에 대해 전표를 새로 한 장 더 쓴다 → 전표가 둘이라 위치는 따로, 코트는 여전히 한 벌.

✅ 실무 감각 — 여러 워커가 같은 로그 파일에 쓸 때

gunicorn 워커 4개가 같은 로그 파일에 쓰는데 왜 서로를 안 뭉갤까. 답은 offset 공유가 아니라 O_APPEND다. 이 플래그는 "파일 끝으로 이동"과 "쓰기"를 커널이 원자적으로 묶어 주므로, 서술자를 공유하든(fork로 물려받음) 각자 열든 둘 다 안전하다.

이게 중요한 이유는 gunicorn의 기본 설정(preload_app = False)에서는 Django 앱이 fork 이후 각 워커에서 로드되기 때문이다. 즉 로그 파일은 "워커마다 따로 open()"되는 쪽에 해당한다. 그런데도 멀쩡한 건 logging.FileHandler의 기본이 mode='a'(= O_APPEND)이기 때문이다.

그래서 내가 할 일 — 로그나 감사 기록을 직접 여는 코드를 짤 때 'w'가 아니라 'a'인지 확인하는 것. 멀티 워커에서 'w'는 조용히 서로의 기록을 깎아 먹는다. offset 공유는 O_APPEND 없이 열었을 때만 의미가 있고, 로그 용도로는 애초에 그렇게 열지 않는다.

04번호 배정과 바꿔치기

리다이렉션과 파이프는 같은 도구 하나로 만들어진다

POSIX는 open()이 어떤 번호를 줄지까지 못 박아 뒀다. 그 프로세스에서 현재 쓰이지 않는 번호 중 가장 작은 것이다. 구현 재량이 아니라 규약이다.

f1 = open("/tmp/a", "w")
print(f1.fileno())   # 3   ← 0,1,2 다음으로 가장 작은 빈 번호
f1.close()

f2 = open("/tmp/b", "w")
print(f2.fileno())   # 3   ← 방금 비워진 번호가 즉시 재사용된다
⚠️ 번호 재사용이 만드는 버그

닫힌 번호가 즉시 재사용된다는 것은, 이미 닫은 fd 번호를 어딘가에 들고 있다가 나중에 쓰면 전혀 엉뚱한 대상을 건드린다는 뜻이다. 01절에서 본 대로 fd 테이블은 스레드끼리 공유하므로 멀티스레드에서 특히 위험하다 — 스레드 A가 3번을 닫는 순간 스레드 B가 연 소켓이 3번을 받고, A의 뒤늦은 write(3, …)가 그 소켓으로 나간다. 로그 한 줄이 남의 HTTP 응답에 섞여 나가는 식이다. Python에서는 raw fd 번호 대신 파일 객체 · 소켓 객체를 넘기는 것으로 대부분 피할 수 있다.

리다이렉션의 진짜 축은 "예약석 + 바꿔치기"다

리다이렉션이 성립하는 이유는 방금 본 "가장 작은 빈 번호" 규칙이 아니다. 진짜 축은 0 · 1 · 2 예약석 규약이다. 프로그램은 자기 출력이 어디로 가는지 확인하지 않고 무조건 1번에 쓴다. 그러니 프로그램을 띄우기 직전에 1번 칸의 내용만 바꿔치기하면, 프로그램은 아무것도 모른 채 파일에 쓴다.

그 바꿔치기 도구가 dup2()다. dup2(oldfd, newfd)는 "newfd 번 칸이 oldfd 와 같은 서술자를 가리키게 하라. 이미 열려 있으면 조용히 닫고 덮어써라"이고, 이 닫고-덮어쓰기가 원자적이다.

📎 용어: 원자적(atomic)

원자적 = 중간 상태가 남의 눈에 보이지 않는다. Django의 transaction.atomic과 같은 뜻이다. close(1)과 dup(fd)를 따로 부르면 그 찰나에 다른 스레드가 파일을 열어 1번을 채 갈 수 있다 — 그러면 내 출력이 남의 파일로 간다. dup2는 그 틈 자체를 없앤다.

# 쉘이 python app.py > out.log 를 실행할 때 하는 일
fd = os.open("out.log", os.O_WRONLY | os.O_CREAT | os.O_TRUNC, 0o666)
os.dup2(fd, 1)      # 1번(stdout) 칸이 out.log 를 가리키게 한다
os.close(fd)         # 원본 번호는 이제 필요 없다
# 이제 exec 로 python 을 띄운다. python 은 아무것도 모른 채 1번에 쓴다.
⚠️ os.open 의 mode 를 빠뜨리면 실행 권한이 붙는다

os.open의 mode 기본값은 0o777이라, 생략하면 umask 0022 환경에서 0755짜리 로그 파일이 만들어진다. 쉘은 0o666으로 열어 0644를 만든다. 쉘 동작을 재현하는 코드라면 쉘과 같은 값을 줘야 한다.

여기서 유명한 함정이 나온다. 쉘은 리다이렉션을 왼쪽에서 오른쪽 순서로 처리한다.

❌ cmd 2>&1 > out.log

stderr 는 터미널에 남는다

  • 1) 2>&1 — 이 시점의 1번은 아직 터미널. 2번을 터미널에 붙인다
  • 2) > out.log — 1번만 파일로 옮긴다
  • 2번은 여전히 터미널을 가리킨 채다

✅ cmd > out.log 2>&1

둘 다 파일로 간다

  • 1) > out.log — 1번을 파일로
  • 2) 2>&1 — 2번을 "지금의 1번"에 붙인다 = 파일
  • 이때 둘은 서술자를 공유하므로 offset 도 하나 — 섞여도 서로 덮어쓰지 않는다
✅ > /dev/null 2>&1 의 나머지 반쪽

/dev/null은 02절에서 말한 특수 파일의 대표다 — 쓰면 전부 버리고, 읽으면 즉시 끝나는 장치다. 파일시스템에 이름이 있으니 그냥 open()할 수 있고, 그 순간 fd 하나가 된다. 그래서 > /dev/null 2>&1은 "1번을 버리는 장치에 붙이고, 2번도 같은 곳에 붙여라"가 된다. 출력을 없애는 특별한 문법이 아니라 그냥 리다이렉션이다. 같은 계열로 /dev/urandom(읽으면 난수), /dev/stdin(0번을 파일처럼 부를 수 있는 이름)이 있다.

파이프도 같은 도구로 만들어진다

00절에서 "왜 파이프도 파일인가"를 묻고 시작했다. 답은 여기서 나온다.

pipe()는 fd 두 개를 한꺼번에 만든다 — 읽는 쪽과 쓰는 쪽. 둘은 커널 안의 버퍼로 이어져 있고, 디스크에도 파일시스템에도 아무 흔적이 없다. 그런데 read · write · close가 그대로 통한다.

r, w = os.pipe()        # 예: (3, 4) — 번호 두 개
os.write(w, b"hello")
print(os.read(r, 5))    # b'hello'

쉘이 ls | wc -l을 실행할 때 하는 일이 바로 이 두 절의 조합이다.

쉘: r, w = pipe() │ ├─ fork ──▶ ls : dup2(w, 1) ─ 1번(stdout)을 파이프 쓰는 쪽에 붙임 │ close(r), close(w) ─ 원본 번호는 반납 │ exec("ls") ─ ls 는 그냥 1번에 쓴다 │ └─ fork ──▶ wc -l : dup2(r, 0) ─ 0번(stdin)을 파이프 읽는 쪽에 붙임 close(r), close(w) exec("wc") ─ wc 는 그냥 0번을 읽는다 ls 도 wc 도 "파이프"라는 것을 모른다. 아는 것은 0번과 1번뿐이다.

이것이 02절에서 말한 "wc -l은 입력이 무엇인지 알 필요가 없다"의 실물이다. 두 프로그램 어느 쪽도 파이프용으로 고쳐 쓰지 않았다 — 번호 칸만 바꿔치기했을 뿐이다.

⚠️ 그래서 BrokenPipeError 가 난다

python app.py | head -3에서 head는 세 줄만 읽고 끝나면서 자기 쪽 fd를 닫는다. 읽는 쪽이 전부 닫힌 파이프에 쓰면 커널이 EPIPE를 돌려주고, 파이썬은 이걸 BrokenPipeError로 올린다. 버그가 아니라 "받는 사람이 갔다"는 정상 신호다. 파이프의 양쪽 끝이 각각 fd라서 생기는 현상이라, 파일에 쓸 때는 절대 안 난다.

05fork · exec 과 상속

gunicorn 워커가 리슨 소켓을 공유하는 원리

📎 용어: fork 와 exec

fork() = 지금 프로세스를 통째로 복제해 자식을 만든다. exec() = 지금 프로세스의 내용물을 다른 프로그램으로 갈아끼운다. 유닉스에서 새 프로그램을 실행한다는 건 이 둘의 조합이다 — 먼저 나를 복제하고, 복제본을 원하는 프로그램으로 덮어쓴다.

📎 용어: 리슨 소켓과 accept()

서버가 포트를 여는 일은 세 단계다. socket() = 통신용 fd를 하나 만든다 → bind(:8000) = 그 fd에 "8000번 포트"라는 주소를 붙인다 → listen() = "이제 접속을 받겠다"고 선언한다. 여기까지 fd는 하나이고, 이걸 리슨 소켓이라 부른다.

리슨 소켓은 데이터를 주고받지 않는다. 손님이 오면 커널이 대기 줄에 세워 두고, 서버가 accept()를 부를 때마다 손님 한 명당 새 fd를 하나씩 만들어 준다. 그래서 동시 접속 1,000개는 fd 1,001개다 — 리슨 소켓 1 + 접속 1,000.

fork()하면 fd 테이블(①)이 통째로 복사된다. 번호도 그대로, 가리키는 곳도 그대로다. 즉 부모와 자식은 같은 서술자(②)를 공유한다.

이게 prefork 방식 웹서버의 전부다. prefork는 요청을 받기 전에 워커 프로세스를 미리 fork해 두는 방식으로, gunicorn의 기본 sync 워커가 이것이다. 마스터가 리슨 소켓을 하나 만든 뒤 워커를 fork()하면 모든 워커가 같은 리슨 소켓을 물려받는다. 워커들이 각자 accept()를 호출하면 커널이 대기 줄에서 하나씩 꺼내 나눠 준다. 워커 간 통신도, 별도 분배기도 필요 없다.

gunicorn master │ socket() → bind(:8000) → listen() ⇒ fd 5 (리슨 소켓) │ ├── fork() ──▶ worker 1 fd 5 ─┐ ├── fork() ──▶ worker 2 fd 5 ─┼──▶ 같은 서술자 = 같은 대기 줄 └── fork() ──▶ worker 3 fd 5 ─┘ 각 워커가 accept() → 커널이 분배 accept() 마다 새 fd 하나씩 생김

exec 은 다르다 — close-on-exec

exec()는 기본적으로 fd를 그대로 유지한다(프로그램만 바뀌지 fd 테이블은 남는다). 그래서 04절의 리다이렉션이 통한다 — 쉘이 1번을 바꿔 놓고 exec 하면 새 프로그램이 그 상태를 물려받는다.

그런데 이 "유지"가 대부분의 경우엔 사고다. DB 커넥션 소켓이나 비밀 키 파일이 exec한 자식에게 딸려 가면 곤란하다. 그래서 fd마다 FD_CLOEXEC(close-on-exec) 플래그가 있다 — 켜져 있으면 exec 순간 커널이 그 fd를 닫는다. 03절 그림에서 이 플래그가 ①에만 붙는다고 했던 이유가 여기 있다. "이 번호표를 새 프로그램에 넘길 것인가"는 번호표의 속성이지 코트의 속성이 아니다.

✅ Python 은 이미 안전한 쪽으로 바꿔 놨다

Python 3.4 (PEP 446)부터 파이썬이 만드는 fd는 기본적으로 상속되지 않는다(close-on-exec이 켜진 채로 만들어진다). 그전에는 subprocess로 자식을 띄우면 부모의 소켓·파일이 줄줄이 새어 나가서, 부모를 재시작해도 자식이 포트를 붙들고 있어 Address already in use가 나는 고전적인 사고가 있었다. 지금은 명시적으로 물려주고 싶을 때만 os.set_inheritable(fd, True)를 쓴다.

06한계 — EMFILE 과 ENFILE

이하 리눅스 · systemd 기준이다 (macOS 차이는 절 끝에)

fd는 배열의 인덱스다. 배열은 무한하지 않다. 그래서 두 종류의 벽이 있다.

🔴 EMFILE (errno 24)

프로세스 한도 초과

  • Python: OSError: [Errno 24] Too many open files
  • 한도: ulimit -n = RLIMIT_NOFILE
  • 거의 모든 실무 사고가 이쪽이다

🟠 ENFILE (errno 23)

시스템 전체 한도 초과

  • 메시지: File table overflow
  • 한도: /proc/sys/fs/file-max
  • 드물다. 보면 호스트 전체가 이미 아프다

내 한도 확인하기

# 지금 쉘의 프로세스 한도 (soft / hard)
ulimit -Sn ; ulimit -Hn

# 돌고 있는 프로세스의 실제 한도와 현재 사용량 (리눅스)
grep 'open files' /proc/$PID/limits
ls /proc/$PID/fd | wc -l

# 시스템 전체 — 할당됨 / 0 / 최대
cat /proc/sys/fs/file-nr
📎 용어: soft limit 과 hard limit

soft = 지금 실제로 적용되는 값. hard = 프로세스가 스스로 soft를 올릴 수 있는 천장. 권한 없는 프로세스도 soft를 hard까지는 자유롭게 올릴 수 있고, hard 자체를 올리려면 root 권한(정확히는 CAP_SYS_RESOURCE)이 필요하다.

⚠️ 한도는 "개수"가 아니라 "번호"다

대부분이 ulimit -n을 "동시에 몇 개까지 열 수 있나"로 읽지만, man 페이지의 정의는 다르다 — "이 프로세스가 열 수 있는 파일 디스크립터 번호의 최댓값보다 1 큰 값"이다. 개수가 아니라 번호의 상한이다.

확인해 보면 명확하다. 한도를 64로 낮춘 뒤, 파일은 몇 개 안 열었는데 번호만 큰 곳으로 점프시켜 보면 거부된다.

resource.setrlimit(resource.RLIMIT_NOFILE, (64, hard))
os.dup2(f.fileno(), 63)    # OK
os.dup2(f.fileno(), 64)    # EBADF ← 열린 개수와 무관하게 거부

즉 soft 1024 = "fd 번호는 1023까지"다. 이 사실이 다음 이야기의 열쇠다.

왜 아직도 1024인가

systemd 240 이후 리눅스 서비스의 기본값은 soft 1024 · hard 524288이다. 하드는 50만 개를 허용하면서 소프트만 1024로 묶어 둔 게 이상해 보인다. 이유는 30년 전 API 하나 때문이다.

select()는 "이 fd들 중에 읽을 게 생긴 놈이 있으면 깨워 줘"라고 커널에 묻는 API다. 비동기 서버의 조상이고 지금은 epoll로 대체됐다(08절). 문제는 감시할 목록을 받는 자료구조 fd_set이다 — 이건 길이 1024짜리 비트 배열이고, fd 번호를 그대로 배열 인덱스로 쓴다. 3번 fd를 감시하려면 3번째 비트를 켜는 식이다. 파이썬으로 치면 bitmap[fd] = 1인데 리스트 길이가 1024로 고정된 셈이다.

// C 로 실제 크기를 재 보면
printf("%zu bytes = %zu bits", sizeof(fd_set), sizeof(fd_set)*8);
// 128 bytes = 1024 bits   ← FD_SETSIZE 와 정확히 일치

그래서 1500번 fd를 넘기면 감시가 되는 게 아니라 배열 밖 메모리를 덮어쓴다. 파이썬이라면 IndexError가 났을 자리에서, C는 조용히 남의 메모리를 망가뜨린다. 리눅스 man 페이지는 이렇게 못 박아 뒀다 — "select()는 FD_SETSIZE(1024) 미만의 fd 번호만 감시할 수 있고, 이 제한은 바뀌지 않는다."

⚠️ 여기서 인과가 이어진다

한도는 개수가 아니라 번호의 상한이다. 그러므로 soft 1024는 곧 "fd 번호는 1023까지"이고, 이것이 select()의 FD_SETSIZE 1024와 정확히 맞물린다. 소프트 한도 1024는 아직도 select()를 쓰는 옛 프로그램이 조용히 메모리를 깨뜨리지 않도록 막아 주는 안전벨트인 것이다. 그러면서 하드를 524288로 크게 열어 둔 이유는, 현대적인 프로그램은 시작할 때 스스로 소프트를 하드까지 올리면 되기 때문이다. "기본은 안전하게, 원하면 스스로 풀어라"가 이 두 숫자의 뜻이다.

✅ 실무 감각 — 우리 스택에서 어디를 만지나
  • gunicorn · Django — gunicorn은 스스로 한도를 올리지 않는다. 밖에서 넣어 줘야 한다. systemd라면 유닛 파일에 LimitNOFILE=65535, ECS라면 task definition의 ulimits에 nofile 항목. 값은 (요청당 fd 수) × (워커당 동시 요청 수) + 여유로 잡는다. 동기 워커는 워커당 동시 요청이 1이라 보통 수백이면 충분하고, 문제는 거의 항상 비동기 워커 · 누수 · 컨테이너 하드 리밋 쪽이다.
  • nginx — worker_rlimit_nofile을 worker_connections의 최소 2배로 잡는다. 리버스 프록시(요청을 받아 뒤쪽 서버로 넘기는 중계 서버) 모드에서는 요청 하나가 클라이언트 소켓 + 업스트림 소켓 = 2개를 동시에 쓰기 때문이다. 여기에 로그 파일 · 임시 파일 몫을 더한다.
  • 컨테이너 — 실제 적용값은 앱 설정과 런타임(systemd · Docker · ECS)의 하드 리밋 중 낮은 쪽이다. 앱 설정만 올려 놓고 안 먹는 사고가 여기서 난다. 컨테이너 안에서 ulimit -n이 호스트 값을 보여주는 경우도 있으니, 반드시 돌고 있는 프로세스의 /proc/$PID/limits로 확인한다.
⚠️ macOS 는 이 이야기가 통하지 않는다

맥에서 ulimit -Hn을 치면 unlimited가 나온다. hard가 사실상 무한이라 "스스로 hard까지 올린다"는 코드가 성공은 하지만 의미가 없다. 실제 상한은 sysctl kern.maxfilesperproc이 쥐고 있다. 이 절의 숫자들은 리눅스 · systemd 환경 이야기이고, 우리 서비스가 도는 곳도 그쪽이다.

CLOSE_WAIT — 소켓 누수의 지문

소켓이 쌓이는 경우, 어느 쪽이 잘못했는지를 상태 하나로 구분할 수 있다. TCP 연결을 끊을 때는 양쪽이 각자 "나는 다 보냈다"를 알린다. CLOSE_WAIT는 상대는 알렸는데 우리가 아직 안 알린 상태 — 즉 우리 코드가 close()를 안 부르고 있다는 뜻이다.

# 리눅스
ss -tanp state close-wait | head
ss -tan state close-wait | wc -l

# macOS 에는 ss 가 없다
netstat -an | grep -c CLOSE_WAIT
⚠️ 이 숫자가 계속 늘면 한도를 올려도 소용없다

CLOSE_WAIT는 우리가 닫아 주기 전까지 스스로 사라지지 않는다. 타임아웃도 없다. 그래서 이 상태가 단조 증가하면 100% 코드 문제이고, 한도를 올리는 것은 사고를 미루는 것일 뿐이다. 전형적인 원인은 응답 객체·커넥션을 어딘가에 쌓아 두거나, 예외 경로에서 close()를 건너뛰는 코드다.

헷갈리기 쉬운 TIME_WAIT는 정반대다 — 우리가 먼저 끊은 뒤 뒤늦게 도착할 패킷을 대비해 커널이 붙들고 있는 정상 상태이고, 스스로 사라진다. 리눅스에서는 이 시간이 60초로 커널에 박혀 있어 sysctl 로 바꿀 수 없다(흔히 이걸 줄인다고 만지는 tcp_fin_timeout 은 다른 상태를 다룬다). 요약하면 — CLOSE_WAIT 는 우리 탓이고 저절로 안 없어진다. TIME_WAIT 는 정상이고 저절로 없어진다.

파이썬에서 나는 전형적인 누수

여기서 진짜 누수와 커넥션 낭비를 구분해야 한다. 둘 다 고쳐야 하지만 증상이 다르다.

❌ 진짜 누수 — 응답 객체를 계속 붙들고 있다

self.responses = []
for url in urls:
    r = requests.get(url, stream=True)
    self.responses.append(r)     # 참조가 살아 있으니 소켓이 안 닫힌다
# 30개 보관 → 열린 소켓 61개. 캐시·인스턴스 속성·전역 리스트가 전형적인 범인.

✅ with 로 확실히 닫는다

for url in urls:
    with requests.get(url, stream=True) as r:
        save(r.raw)                # 30회 반복 후에도 소켓 1개
⚠️ 흔한 과장: "응답을 안 닫으면 fd 가 샌다"

정확하지 않다. r을 매번 다시 대입하는 루프라면 CPython에서는 직전 응답의 참조가 0이 되면서 소켓이 즉시 닫힌다 — 30회를 돌려도 소켓은 늘지 않는다. 진짜 대가는 fd가 아니라 커넥션이 풀로 반환되지 않는 것이다. keep-alive가 깨져서 매 요청마다 TCP 핸드셰이크를 새로 한다. fd가 실제로 새려면 참조를 붙들고 있어야 한다(위 ❌ 예제).

⚠️ "CPython 은 알아서 닫아 주던데요"

CPython은 객체를 가리키는 참조가 몇 개인지 세다가(참조 카운팅) 0이 되는 순간 즉시 정리한다. 그래서 data = open(path).read()도 대체로 바로 닫힌다. 하지만 이건 파이썬 언어의 규칙이 아니라 CPython이라는 구현의 사정이다. 객체들이 서로를 가리켜 참조 수가 0이 되지 않으면(순환 참조) 정리 시점이 가비지 컬렉터에게 넘어가 한참 뒤로 밀리고, PyPy처럼 참조 카운팅을 쓰지 않는 구현에서는 아예 언제 닫힐지 모른다. with는 이 모든 경우에 즉시 닫는 유일한 방법이다.

✅ 누수를 눈에 보이게 만들기

파이썬은 fd가 닫히지 않은 채 회수되면 ResourceWarning: unclosed …을 낸다. 기본적으로 숨겨져 있어서 아무도 못 본다. 켜 두면 어느 줄에서 열었는지 traceback이 함께 나와 범인을 바로 찾는다.

python -X dev -m pytest              # 개발 모드 — 경고를 표시한다
pytest -W always::ResourceWarning    # pytest 요약에 띄운다

다만 이걸로 테스트가 실패하지는 않는다. ResourceWarning은 객체가 회수될 때(소멸자 안에서) 나기 때문에, -W error로 에러 취급해도 파이썬이 Exception ignored in:만 찍고 넘어간다. 실제로 CI를 실패시키려면 테스트 전후로 fd 개수를 재는 fixture를 두는 편이 확실하다.

def count_fds():
    return len(os.listdir(f"/proc/{os.getpid()}/fd"))
📎 우리 스택에서 fd 를 쓰는 것들

Django 요청 하나가 처리되는 동안 열려 있는 것들 — 클라이언트 소켓 1, PostgreSQL 커넥션 소켓 1, Redis 소켓, 외부 API 호출 소켓, 로그 파일, 업로드 임시 파일. 워커당 이 합계 × 동시 요청 수가 그 프로세스의 fd 사용량이고, 06절에서 한도를 정할 때 쓴 그 값이다.

08추상화의 확장 — epoll · pidfd

파일이 아닌 것들이 계속 fd 가 되어 온 이유

fd가 좋은 추상화였다는 증거는, 리눅스가 새 기능을 추가할 때마다 그것을 fd로 만들었다는 데 있다.

APIfd 로 표현한 것덕분에 가능해진 것
eventfd단순 알림 카운터스레드 간 깨우기를 read로
timerfd타이머 만료타이머를 다른 fd 들과 똑같이 감시
signalfd시그널 수신시그널 핸들러 대신 정상 흐름에서 처리

pidfd프로세스 그 자체엉뚱한 프로세스를 죽이는 사고 없이 지목

왜 굳이 fd로 만들까. 이미 존재하는 도구를 전부 물려받기 때문이다. fd가 되는 순간 epoll로 감시할 수 있고, close()로 정리되며, fork 상속 규칙과 한도 회계가 그대로 적용된다. 새 개념 하나를 기존 우주에 편입시키는 비용이 거의 0이다.

✅ pidfd 가 푼 문제 — 30년 묵은 경합

전통적으로 프로세스는 PID(정수)로 가리켰다. 그런데 프로세스가 죽으면 PID는 재사용된다. 그래서 kill(pid, SIGKILL)은 원리적으로 위험하다 — 내가 PID를 확인한 시점과 신호를 보내는 시점 사이에 그 프로세스가 죽고 다른 프로세스가 같은 번호를 받았다면, 엉뚱한 것을 죽인다. 배포 스크립트가 남의 프로세스를 죽이는 사고가 이렇게 난다. pidfd(Linux 5.3)는 프로세스를 fd로 잡아 둔다. fd는 번호가 아니라 그 프로세스 실체를 붙들기 때문에, 대상이 이미 죽었어도 다른 프로세스로 바뀌어 있지 않다.

04절에서 본 "닫힌 fd 번호를 나중에 쓰면 엉뚱한 것을 건드린다"와 정확히 같은 문제다. 번호는 재사용되고, 손잡이는 재사용되지 않는다.

epoll — 추상화가 자기 자신에게 적용될 때

06절에서 select()가 fd 번호 1023까지만 감시할 수 있다는 것을 봤다. 문제는 하나 더 있다. select()는 호출할 때마다 관심 목록 전체를 커널에 다시 넘기고 전체를 훑는다. 준비된 fd가 하나뿐이어도 1만 개를 확인하므로, 접속이 늘수록 서버가 느려진다.

epoll(Linux 2.5.44, 2002)과 kqueue(FreeBSD, 2000-07)의 해법은 관심 목록을 커널에 한 번만 등록해 두는 것이다. 이후에는 "준비된 것만 줘"라고 물으면 준비된 개수에 비례하는 일만 한다. fd 번호 상한도 없다.

select() epoll ──────── ───── 매 호출마다 전체 fd 목록 전달 epoll_create() ⇒ epoll fd 하나 전체를 훑음 epoll_ctl(ADD) ⇒ 관심 목록은 커널에 상주 비용 ∝ 전체 접속 수 epoll_wait() ⇒ 준비된 것만 돌려받음 fd 번호 1023 까지만 비용 ∝ 준비된 접속 수

여기에는 전제가 하나 붙는다. 감시 대상 fd는 O_NONBLOCK으로 열려 있어야 한다. "준비됐다"는 통보를 받고 read()했는데 그 사이 데이터가 사라졌을 때, 블로킹 모드면 그 자리에서 이벤트 루프 전체가 멈춘다 — 커넥션 하나가 서버 전부를 세우는 것이다. 03절에서 본 대로 O_NONBLOCK은 서술자(②)에 붙는 플래그다.

여기서 이 문서 전체를 관통하는 장면이 나온다. epoll_create()가 돌려주는 것도 fd다. "fd들을 감시하는 장치" 자체가 또 하나의 fd이고, 그래서 epoll 인스턴스를 다른 epoll로 감시할 수도 있다. 추상화가 자기 자신에게 적용되는 것 — 좋은 추상화의 표식이다.

✅ 우리가 매일 그 위에 서 있다

Python의 asyncio는 리눅스에서 epoll을 쓴다(selectors 모듈이 플랫폼에 맞는 최선을 고른다). nginx도, uvicorn도, Redis도 마찬가지다. "비동기 서버가 커넥션 수만 개를 감당한다"는 말의 실체는 fd 수만 개를 커널에 등록해 두고 준비된 것만 받아 간다는 뜻이다. 그리고 그러려면 06절의 한도를 반드시 올려 둬야 한다 — 이 두 가지는 세트다.

09한 장 요약 치트시트

💬 "운영체제가 리소스를 추상화 하는 방식"

커널은 "무엇인가"를 지우고 "어떻게 다루는가"만 남긴다. 파일 · 소켓 · 파이프 · 타이머 · 프로세스는 내부 구현이 전혀 다르지만, 사용자 프로그램에게는 전부 작은 정수 하나로 나온다. 그 정수에는 read · write · close를 할 수 있고, 그게 전부라는 사실이 곧 힘이다 — 프로그램이 상대의 정체를 몰라도 되니 파이프로 아무거나 이어 붙일 수 있고, 커널은 새 개념을 fd로 만들기만 하면 기존 도구 전부를 공짜로 물려줄 수 있다. 대신 정수는 유한하고 명시적으로 반납해야 하며, 그 대가가 Too many open files다.
