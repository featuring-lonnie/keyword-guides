왜 모든 시스템은 로그를 먼저 쓰는가

00커밋 성공 0.1초 뒤, 전원이 뽑혔다

"성공"이라는 응답은 정확히 무엇을 약속하는가

Django에서 이런 코드를 짰다고 하자.

with transaction.atomic():
    Order.objects.filter(pk=order_id).update(status="PAID")
# ← 이 줄을 지나는 순간 COMMIT이 끝났다
return Response({"ok": True})

transaction.atomic() 블록을 빠져나오면 PostgreSQL은 COMMIT을 처리하고 성공을 돌려준다. 그 직후 서버실 차단기가 내려간다. 다시 부팅했을 때 그 주문은 PAID일까?

답은 "그렇다"이다. 그런데 이상하다. 커밋 시점에 실제 테이블 데이터 파일은 아직 디스크에 안 써졌을 가능성이 매우 높기 때문이다. 어떤 경우엔 몇 분 뒤에야 써진다. 그런데도 데이터는 살아남는다.

그 사이의 간극을 메우는 것이 WAL(Write-Ahead Log, 선행 기입 로그)이다. 그리고 이 아이디어는 DB에만 있는 게 아니라, Kafka·이벤트 소싱·Redis·RocksDB·심지어 Git까지 관통한다.

다 읽으면 synchronous_commit, appendfsync, Kafka 파티션, 이벤트 소싱이 전부 같은 아이디어의 변주로 보이기 시작한다.

01제자리 수정이 위험한 이유

디스크는 당신이 기대하는 만큼 원자적이지 않다

WAL이 없는 세상을 상상해 보자. DB가 UPDATE를 받으면 해당 데이터가 들어있는 디스크 위치를 찾아가 그 자리를 새 값으로 덮어쓴다. 이것을 제자리 수정(in-place update)이라고 한다. 직관적이고, 그래서 위험하다.

📎 용어: 페이지(page)

페이지 = DB가 디스크와 데이터를 주고받는 최소 단위 블록. PostgreSQL의 기본 페이지 크기는 8KB다. 행 하나만 바꿔도 DB는 그 행이 들어있는 8KB 페이지 전체를 읽고, 고치고, 다시 쓴다.

문제는 8KB 페이지 하나를 쓰는 일이 하나의 원자적 동작이 아니라는 것이다. 디스크는 그보다 작은 섹터(저장장치가 한 번에 기록하는 최소 단위, 보통 512B~4KB) 단위로 기록하고, 그 사이 어디서든 전원이 끊길 수 있다. 결과는 앞부분은 새 값, 뒷부분은 옛 값인 반쪽짜리 페이지다.

📎 용어: 찢어진 쓰기(torn write / torn page)

페이지 하나가 디스크에 부분적으로만 기록된 상태. 새 값도 옛 값도 아닌, 어느 쪽으로도 해석할 수 없는 쓰레기가 된다. 복구가 불가능한 이유는 "원래 뭐였는지"와 "뭐가 되려 했는지"를 둘 다 잃었기 때문이다.

제자리 수정 중 전원 차단 ───────────────────────────────────────────── 8KB 페이지 (주문 #1042 포함) 쓰기 전: [ 기존값 | 기존값 | 기존값 | 기존값 ] 쓰는 중: [ 새 값 | 새 값 | 💥 전원 차단 쓰기 후: [ 새 값 | 새 값 | 기존값 | 기존값 ] ← 찢어진 페이지 ↑ 여긴 옛날 데이터 → 체크섬 불일치, 해석 불가 → 되돌릴 수도, 밀어붙일 수도 없음

여기에 더 큰 문제가 겹친다. 트랜잭션 하나가 여러 페이지를 건드리는 경우다. 계좌 이체는 출금 행과 입금 행이 서로 다른 페이지에 있다. 출금 페이지만 써지고 입금 페이지를 쓰기 전에 죽으면, 돈이 증발한다. 개별 페이지가 멀쩡해도 전체로 보면 일관성이 깨진 상태다.

제자리 수정의 진짜 문제는 "쓰다가 죽는 것"이 아니다. 죽고 난 뒤에 무슨 일이 있었는지 알아낼 방법이 없다는 것이다. 원본을 덮어쓰는 순간 과거가 사라지고, 작업이 끝나지 않았으므로 미래도 없다. 복구는 정보의 문제이지 운의 문제가 아니다.

02WAL 프로토콜 — 로그가 먼저다

규칙은 단 하나, 순서

해법은 놀랄 만큼 단순하다. 데이터 파일을 건드리기 전에, 무엇을 할 것인지를 별도의 로그 파일에 먼저 기록하고 그 로그가 디스크에 확실히 안착한 것을 확인한다. 그게 전부다. 이것이 WAL(Write-Ahead Logging) 프로토콜이다.

📎 용어: WAL 레코드

WAL에 들어가는 것은 SQL 문장이 아니라 물리적 변경 기록에 가깝다. "파일 X의 블록 Y, 오프셋 Z(블록 시작점부터 몇 번째 바이트인지)의 값을 A에서 B로 바꿨다" 같은 형태. 덕분에 "이 변경이 이미 반영됐는지"를 페이지에 적힌 번호와 비교하는 것만으로 판정할 수 있고(04절), 그래서 몇 번을 재실행해도 안전하다. 참고로 멱등(idempotent) = 여러 번 실행해도 결과가 한 번 실행한 것과 같은 성질.

단, 이 형태만으로는 01절의 찢어진 페이지를 고칠 수 없다 — "바꿀 자리" 자체가 썩었기 때문이다. 그 보완책은 06절에서 다룬다.

WAL 프로토콜의 순서 ───────────────────────────────────────────────────────── 1. 메모리 버퍼의 페이지를 수정 (아직 디스크 X) 2. 변경 내용을 WAL 레코드로 만들어 append 3. COMMIT 요청 4. WAL을 fsync() ────────────▶ 💾 디스크 안착 ✅ 5. 클라이언트에게 "성공" 응답 ← 여기가 내구성 경계선 ... (나중에, 백그라운드로) 6. 수정된 페이지를 데이터 파일에 기록 💾 7. 체크포인트: "6번까지 끝났다"고 표시 💥 4번 이후 어디서 죽어도 → WAL에 다 있으므로 재실행(REDO) 가능

여기서 4번과 5번의 순서가 모든 것을 결정한다.

📎 용어: fsync()

파일에 write()를 해도 데이터는 보통 OS의 페이지 캐시(메모리)에만 있다. 전원이 나가면 사라진다. fsync()는 "이 파일의 내용을 물리 저장장치까지 확실히 밀어 넣고, 끝날 때까지 기다려라"라고 OS에 요구하는 시스템 콜이다. 느리지만, 이게 없으면 내구성도 없다.

📎 용어: 원자성과 내구성 (ACID의 A와 D)

원자성(Atomicity) = 한 트랜잭션의 변경은 전부 반영되거나 전부 없던 일이 되거나, 둘 중 하나여야 한다. 내구성(Durability) = 한 번 "커밋 성공"이라고 대답한 변경은 이후 크래시가 나도 살아남아야 한다. WAL이 지키려는 것이 정확히 이 둘이고, 아래에서 볼 두 규칙이 각각 하나씩을 담당한다.

⚠️ 핵심 통찰 — 이 문서에서 하나만 기억한다면

커밋 성공 = "데이터 파일에 반영됨"이 아니다. 커밋 성공 = "의도가 로그에 안전하게 기록됨"이다. 실제 데이터 파일 반영은 수 초~수 분 뒤에 백그라운드로 일어난다. 그 사이에 죽어도 괜찮은 이유는, 로그만 있으면 죽은 지점부터 다시 진행할 수 있기 때문이다.

WAL이 지키는 두 가지 규칙

"로그를 먼저 쓴다"는 말은 사실 두 개의 규칙으로 나뉜다. 둘 다 필요하다.

⚙️ REDO 규칙

커밋을 알리기 전에, 그 트랜잭션의 모든 변경 로그가 fsync되어 있어야 한다.

  • 지키면: 커밋했다고 말한 것은 크래시 후 반드시 되살릴 수 있다
  • 어기면: "성공" 응답을 준 주문이 사라진다 (내구성 위반)

🔍 UNDO 규칙

아직 커밋 안 된 변경이 담긴 페이지를 디스크에 쓰기 전에, 그 변경의 로그가 먼저 fsync되어 있어야 한다.

  • 지키면: 미완료 트랜잭션이 디스크에 새어나가도 되돌릴 수 있다
  • 어기면: 롤백해야 할 변경이 디스크에 영구히 남는다 (원자성 위반)

DB는 메모리가 부족하면 커밋되지 않은 트랜잭션의 페이지도 디스크로 밀어낼 수 있다. UNDO 규칙은 그 상황을 위한 안전장치다. 이 둘을 합치면 "디스크에 있는 데이터 파일은 언제나 WAL로 설명 가능한 상태"라는 불변식이 성립한다.

03두 번 쓰는데 왜 더 빠른가

WAL은 안전장치이면서 동시에 성능 최적화다

여기서 대부분의 주니어가 걸린다. WAL은 같은 변경을 두 번 쓴다(로그에 한 번, 데이터 파일에 한 번). 그런데 실제로는 WAL을 쓰는 쪽이 더 빠르다. PostgreSQL 7.1의 릴리스 노트도 WAL 도입을 안정성 개선인 동시에 성능 개선으로 소개했다. 왜일까?

먼저 전제를 정리하자. 총 쓰기량은 확실히 늘어난다. 하지만 커밋이 기다리는 쓰기는 WAL 하나뿐이고, 데이터 파일 쓰기는 응답을 보낸 뒤로 밀려난다. 늘어난 것은 총량이고, 줄어든 것은 응답 지연이다.

① 랜덤 쓰기가 순차 쓰기로 바뀐다

한 트랜잭션이 건드리는 데이터 페이지들은 디스크 여기저기에 흩어져 있다. 이걸 커밋마다 직접 쓰면 랜덤 쓰기다. 반면 WAL은 파일 끝에 이어 붙이기만 하는 순차 쓰기(append-only)다. HDD 시절에는 헤드가 움직이지 않아 압도적으로 빨랐다. SSD·NVMe에서도 마찬가지인데, SSD는 제자리 덮어쓰기가 안 돼서 지운 뒤 다시 써야 하고 그래서 내부적으로 조각을 정리하는 작업(가비지 컬렉션 — 언어 런타임의 메모리 GC와는 다른 것이다)이 돌아간다. 순차 쓰기는 정리할 조각을 애초에 덜 만든다.

② fsync 한 번에 여러 트랜잭션을 태운다 (그룹 커밋)

fsync()는 비싸고, 비용의 대부분이 호출 횟수에 붙는 고정비다. 10개의 트랜잭션이 각자 fsync하면 10번이지만, 아주 짧게 기다렸다가 한 번의 fsync로 10개를 함께 내려보내면 1번이다. 흩어진 데이터 페이지들은 이렇게 묶을 수 없지만, 하나의 순차 로그 파일이라면 가능하다. 이것이 그룹 커밋(group commit)이다.

⚠️ 흔한 오해

"SSD니까 fsync는 공짜에 가깝다" — 실제로는 전원 손실 보호(PLP) 커패시터가 있는 엔터프라이즈 SSD와 없는 컨슈머 SSD의 fsync 지연이 수백 배까지 벌어진다. 한 실측(16KB 쓰기 후 fsync)에서는 PLP가 있는 엔터프라이즈 SSD가 1.6µs·12.4µs, 없는 컨슈머 SSD가 891µs·2974µs였다. PLP가 있으면 드라이브가 내부 캐시를 안전하다고 보고 즉시 응답할 수 있지만, 없으면 실제로 낸드(SSD의 실제 저장 소자)까지 밀어 넣어야 하기 때문이다. 로컬 개발 노트북에서 잘 나오던 TPS(초당 트랜잭션 수)가 운영에서 안 나오는 원인이 여기일 수 있다.

③ 데이터 파일 쓰기를 미루고 합칠 수 있다

같은 페이지를 100번 수정해도, 메모리에서 100번 고친 뒤 디스크에는 한 번만 쓰면 된다. WAL이 없으면 커밋할 때마다 써야 하지만, WAL이 있으면 "언제 써도 안전"하므로 미뤘다가 몰아서 쓸 수 있다. 인기 있는 행일수록 이득이 커진다.

📎 용어: 체크포인트(checkpoint)

"이 시점까지의 모든 변경이 데이터 파일에 반영 완료"라고 못 박는 작업. DB는 주기적으로 메모리에 쌓인 수정 페이지들을 디스크에 몰아 쓰고 체크포인트 기록을 남긴다. 이게 있어야 복구할 때 WAL을 처음부터 다 읽지 않고 마지막 체크포인트 이후만 읽으면 되고, 그 이전 WAL 파일은 지워도 된다. 체크포인트가 뜸하면 복구가 느려지고, 잦으면 평소 I/O가 늘어나는 트레이드오프가 있다.

04크래시 복구는 어떻게 일어나는가

ARIES — 1992년에 정리된, 지금도 쓰이는 교과서

WAL 프로토콜 자체는 1970~80년대 데이터베이스 연구에서 이미 존재했다. 그것을 실용적인 완결된 복구 알고리즘으로 정리해 사실상의 표준으로 만든 것이 1992년 논문 ARIES다.

  1. 1992ARIES 논문 발표C. Mohan, Don Haderle, Bruce Lindsay, Hamid Pirahesh, Peter Schwarz (IBM). ACM Transactions on Database Systems Vol. 17, No. 1. "Algorithm for Recovery and Isolation Exploiting Semantics"의 약자. IBM DB2 등에 구현되었다.
  2. 2001PostgreSQL 7.1에 WAL 도입4월 13일 릴리스. 그 전까지 PostgreSQL은 크래시 시 일관성을 보장할 수 없었고, 쓰기 도중 크래시가 나면 테이블·인덱스 페이지가 손상될 수 있었다. (첫 릴리스에서는 UNDO가 시간 부족으로 미구현이었다.)

ARIES의 복구는 크래시 후 재기동할 때 세 번의 패스로 진행된다. Analysis가 마지막 체크포인트 지점에서 시작하고, 나머지 두 패스의 시작점은 Analysis가 계산해 준다.

📎 용어: LSN (Log Sequence Number)

WAL 레코드마다 붙는 단조 증가하는 위치 번호. PostgreSQL에서는 WAL 파일 전체를 하나의 긴 바이트 스트림으로 보고 그 안의 바이트 오프셋을 LSN으로 쓴다. 각 데이터 페이지에도 "이 페이지에 마지막으로 반영된 LSN"이 기록되어 있어서, 복구 시 어떤 로그를 다시 적용해야 하고 어떤 것은 이미 반영됐는지를 비교만으로 판단할 수 있다. 복제 지연을 측정할 때 쓰는 그 LSN이 바로 이것이다.

  1. 1단계 — 분석(Analysis)체크포인트 이후의 WAL을 훑어서 "크래시 순간에 진행 중이던 트랜잭션은 누구였고, 어떤 페이지들이 아직 데이터 파일에 반영 안 됐는지" 목록을 만든다. 아직 아무것도 고치지 않는다. 이 과정에서 Redo를 어디서부터 시작할지(RedoLSN)도 함께 정하는데, 기준이 "아직 데이터 파일에 안 내려간 가장 오래된 페이지"라서 체크포인트보다 앞선 지점이 되는 게 보통이다.
  2. 2단계 — 재실행(Redo)로그에 있는 변경을 순서대로 전부 다시 적용한다. 커밋된 것뿐 아니라 커밋 안 된 것까지 재현한다. 페이지의 LSN과 로그의 LSN을 비교해 이미 반영된 것은 건너뛴다. 이 단계가 끝나면 DB는 크래시 직전의 상태를 정확히 복원한 셈이 된다.
  3. 3단계 — 취소(Undo)그제서야, 크래시 시점에 커밋되지 않았던 트랜잭션들을 거꾸로 되감아 취소한다. 이 취소 작업 자체도 WAL에 기록된다(그래서 복구 도중에 또 죽어도 안전하다).
✅ 왜 커밋 안 된 것까지 다시 실행하는가

ARIES의 이 방식을 "역사 반복(repeating history)"이라 부르며, 이것이 ARIES를 다른 WAL 기반 기법들과 구별짓는 지점이다. 직관적으로는 "어차피 취소할 건데 왜 다시 해?" 싶다. 이유는 단순함이 곧 정확성이기 때문이다. 일단 크래시 직전 상태를 그대로 복원해 놓으면, 그 다음의 취소 작업은 평상시 롤백과 똑같은 코드로 처리할 수 있다. "복구 중에만 쓰이는 특별한 경로"를 만들지 않는 것 — 거의 실행되지 않는 코드가 가장 버그가 많은 코드라는 점을 생각하면, 대단히 실용적인 설계다.

복구 3패스 ────────────────────────────────────────────────────────────── WAL: ───────┬───────────┬──────────────────────┬──💥크래시 RedoLSN 체크포인트 ① Analysis ├──────▶ 훑어보기 ──────┤ 무엇이 미완료인가? (RedoLSN도 여기서 계산) ② Redo ├──────────────────▶ 전부 재적용 ──┤ 크래시 직전 상태 복원 ③ Undo ◀── 되감기 ───┤ 미커밋만 취소 RedoLSN = 아직 데이터 파일에 안 내려간 가장 오래된 페이지 지점 → 보통 체크포인트보다 앞선다 결과: 커밋된 것은 100% 살아있고, 미커밋은 100% 사라진다 → 원자성(A) + 내구성(D) 동시 달성

05내구성은 스위치가 아니라 다이얼

모든 DB가 같은 손잡이를 제공한다

fsync는 비싸다. 그래서 거의 모든 시스템이 "얼마나 안전할 것인가"를 설정으로 조절하게 해준다. 이름만 다를 뿐 손잡이의 정체는 똑같다: 커밋 응답과 fsync 사이를 얼마나 벌릴 것인가. 아래 표의 "flush"는 02절의 fsync()와 같은 뜻이다 — 저장장치까지 실제로 밀어 넣는 그 동작.

시스템설정의미 · 최악의 손실
PostgreSQL synchronous_commit = on (기본) 커밋 응답 전에 WAL을 fsync. 손실 0
PostgreSQL synchronous_commit = off 기다리지 않고 즉시 응답. WAL writer가 나중에 flush → 최대 3 × wal_writer_delay(기본 200ms → 약 600ms) 분량의 커밋이 사라질 수 있다
MySQL / InnoDB innodb_flush_log_at_trx_commit = 1 (기본) 트랜잭션마다 redo 로그 flush. 완전한 ACID
MySQL / InnoDB = 2 커밋마다 로그 파일에 쓰되 flush는 1초에 한 번 → OS 크래시·정전 시 최대 1초 손실
MySQL / InnoDB = 0 커밋 시 아무것도 안 함, 1초 주기로만 처리 → 서버 프로세스만 죽어도 최대 1초 손실
Redis (AOF) appendfsync always 쓰기 배치마다 fsync하고 나서 응답. 가장 안전하지만 지연이 크게 늘어난다
Redis (AOF) appendfsync everysec (기본) 백그라운드 스레드가 1초 주기로 fsync → 최대 1초 손실
Redis (AOF) appendfsync no OS에 완전히 위임 (리눅스는 통상 30초 주기로 flush)
✅ 실무 감각 — PostgreSQL에서 절대 헷갈리면 안 되는 두 파라미터

synchronous_commit = off는 안전한 절충이다. 최근 커밋 몇 개가 사라질 수는 있지만, 사라지는 트랜잭션은 깨끗하게 롤백된 것과 동일한 상태가 되고 DB는 일관성을 유지한다. 반면 fsync = off는 완전히 다른 이야기다. DB 자체가 복구 불능으로 깨질 수 있다. synchronous_commit은 fsync를 얼마나 기다릴지를 조절하지만 fsync = off는 fsync를 아예 하지 않는다. 02절의 순서 규약 자체가 무너져 데이터 파일이 WAL보다 먼저 디스크에 닿는 일이 가능해지고, 그러면 복구가 기준으로 삼을 로그가 없어 데이터 파일이 해석 불가능한 상태로 남는다. 운영에서 이 두 개를 같은 급으로 취급하면 안 된다.

세션 단위로 켜고 끌 수도 있다. 예를 들어 감사 로그 대량 적재 같은 배치 작업만 SET LOCAL synchronous_commit = off로 돌리고, 결제 트랜잭션은 기본값을 유지하는 식이다.

⚠️ 주의 — 다이얼을 돌리기 전에

"1초 손실 허용"이 괜찮은지는 비즈니스가 정하는 것이지 성능 그래프가 정하는 게 아니다. 조회수 집계라면 1초쯤 날아가도 된다. 결제·정산·크레딧 차감이라면 안 된다. 게다가 손실은 "1초어치 데이터"가 아니라 "클라이언트에게 성공이라고 이미 대답해버린 1초어치 요청"이다. 사용자는 성공 화면을 봤는데 데이터가 없는 상황이 된다.

06pg_wal에서 실제로 벌어지는 일

우리 스택에서 만나게 되는 WAL

PostgreSQL의 WAL은 데이터 디렉터리 아래 pg_wal/에 세그먼트 파일 형태로 쌓인다. 세그먼트 하나는 보통 16MB다(initdb --wal-segsize로 변경 가능).

-- 지금 WAL이 어디까지 찼는지 (LSN)
SELECT pg_current_wal_lsn();

-- pg_wal 디렉터리 총 사용량
SELECT pg_size_pretty(sum(size)) FROM pg_ls_waldir();

-- 복제 슬롯이 붙잡고 있는 WAL 양 (디스크 폭탄 감시용)
-- wal_status가 lost면 이미 필요한 WAL이 지워져 그 슬롯은 복구 불능이다
SELECT slot_name, active, wal_status,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
FROM pg_replication_slots
ORDER BY pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) DESC;

full_page_writes — 찢어진 페이지에 대한 방어

01절의 찢어진 페이지 문제를 기억하는가. WAL 레코드가 "블록 Y의 오프셋 Z를 바꿔라"라고만 적혀 있으면, 정작 그 블록 자체가 찢어져 있을 때 복구할 수 없다. 고칠 기준점이 썩었기 때문이다.

PostgreSQL은 full_page_writes(기본 on)로 이를 막는다. 체크포인트 이후 어떤 페이지를 처음 수정할 때는, 변경분이 아니라 그 페이지 전체 이미지를 WAL에 통째로 기록한다. 복구 시에는 이 온전한 이미지로 페이지를 통째로 덮어쓴 뒤, 그 위에 이후 변경들을 적용한다. 찢어진 페이지가 있어도 무관하다.

✅ 실무 감각 — 체크포인트 직후 WAL이 폭증하는 이유

체크포인트가 끝나면 모든 페이지가 "이번 체크포인트 이후 첫 수정" 상태가 된다. 그래서 체크포인트 직후에는 8KB 전체 이미지가 대량으로 WAL에 실려 순간적으로 WAL 생성량이 치솟는다. 체크포인트를 너무 자주 돌리면 이 전체 페이지 기록이 반복되면서 WAL 양과 I/O가 함께 늘어난다. "체크포인트를 자주 하면 안전하겠지"라는 직관이 오히려 부하를 키우는 지점이다.

복제 슬롯 — 실전에서 가장 자주 터지는 WAL 사고

WAL은 복구에만 쓰이는 게 아니라 복제(replication)의 원본이기도 하다. 복제 = 원본 서버의 WAL을 다른 서버로 보내 그대로 재생시켜 똑같은 사본을 유지하는 것이고, 그 사본 서버를 스탠바이 또는 리플리카라고 부른다(같은 말이다). 스탠바이뿐 아니라 CDC(Change Data Capture — WAL을 읽어 변경을 외부 시스템으로 흘려보내는 것. Debezium 등) 도구도 같은 WAL을 따라간다. 이때 PostgreSQL은 복제 슬롯으로 "이 소비자가 아직 여기까지밖에 못 읽었다"를 기억하고, 그 지점 이후의 WAL을 절대 지우지 않는다.

⚠️ 핵심 함정 — 죽은 복제 슬롯은 시한폭탄

소비자가 죽었거나 스탠바이를 그냥 내려버렸는데 슬롯을 지우지 않으면, PostgreSQL은 그 소비자를 영원히 기다리며 WAL을 무한정 쌓는다. max_slot_wal_keep_size의 기본값은 -1(무제한)이라, 비활성 슬롯 하나가 디스크 전체를 채워 DB를 멈춰 세울 수 있다. 그리고 이건 다른 WAL 보존 설정들을 전부 무시한다.

대응: pg_replication_slots의 active = false이면서 보존량이 큰 슬롯을 모니터링·알람 대상으로 두고(WAL 볼륨의 70~75%에서 알람), max_slot_wal_keep_size에 상한을 둔다. PostgreSQL 18 이상이라면 idle_replication_slot_timeout(기본 0 = 비활성, 예: 48h)으로 방치된 슬롯을 자동 무효화할 수 있다 — 17 이하에는 이 파라미터가 없으므로 상한 설정과 모니터링이 유일한 방어선이다.

Django 개발자가 실제로 체감하는 지점

  • transaction.atomic() 블록의 크기 — 블록이 길수록 그 트랜잭션이 잡은 잠금(다른 트랜잭션이 같은 행을 건드리지 못하게 막는 표시)이 오래 유지되고, 미커밋 상태가 길어지면 그 사이의 WAL도 정리할 수 없다. 외부 API 호출을 atomic 블록 안에 넣지 않는 이유 중 하나다.
  • 대량 bulk_update — 건드리는 페이지가 많을수록 WAL 생성량이 커진다. 대량 배치가 도는 시간대에 복제 지연(LSN 차이)이 벌어지는 것은 정상적인 인과다.
  • 읽기 전용 복제본의 지연 — 마스터에 쓰고 곧바로 리플리카에서 읽으면 없을 수 있다. 리플리카는 WAL을 받아 재생하는 중이고, 커밋 시점과 재생 완료 시점 사이에는 필연적으로 시차가 있기 때문이다. "방금 저장했는데 목록에 안 보여요" 류의 버그가 여기서 나온다.

07로그가 원본이 되는 순간 — Kafka·이벤트 소싱·Git

Kafka·이벤트 소싱·Git이 여기서 만난다

지금까지 WAL은 "데이터 파일을 지키기 위한 보조 장치"였다. 그런데 누군가 이런 생각을 한다. 로그만 있으면 데이터 파일을 언제든 다시 만들 수 있다면, 진짜 원본은 로그 아닌가?

이 관점 전환이 현대 데이터 아키텍처의 상당 부분을 낳았다. 순서대로 따라가 보자.

  1. 복제 — 로그를 남에게 보내기WAL을 다른 서버에 보내 그대로 재생하면 똑같은 DB가 하나 더 생긴다. 로그가 재실행 가능하다는 성질을 그대로 활용한 것뿐이다.
  2. CDC — 로그를 다른 종류의 저장소에 보내기재생 대상이 꼭 같은 DB일 필요는 없다. WAL을 읽어 Elasticsearch 색인이나 데이터 웨어하우스를 갱신할 수 있다. CDC(Change Data Capture) = 변경 이력을 로그에서 뽑아 하류 시스템에 전파하는 것. Debezium이 하는 일이다.
  3. Kafka — 로그 자체가 제품이 되기그렇다면 로그를 DB 안에 가둘 필요도 없다. Kafka는 처음부터 분산 커밋 로그로 설계되었다. 토픽의 각 파티션이 하나의 논리적 로그이고, 물리적으로는 세그먼트 파일들의 집합이다. 프로듀서가 메시지를 보내면 브로커는 마지막 세그먼트 파일에 이어 붙이기만 한다. 각 메시지의 오프셋은 DB의 LSN과 정확히 같은 역할을 한다.
  4. 이벤트 소싱 — 애플리케이션 상태를 로그로 표현하기마지막 단계. 주문 테이블에 현재 상태를 저장하는 대신, OrderPlaced → PaymentCaptured → OrderShipped 이벤트를 append-only로 쌓고, 현재 상태는 이벤트들을 처음부터 순서대로 하나씩 누적 적용해(fold) 계산한다. 매번 전부 읽지 않도록 중간 결과를 스냅숏으로 저장해 두는 것이 보통이다. Greg Young이 널리 알린 접근이다.
📎 왜 이벤트 소싱이 "정보를 더 많이 담는가"

Greg Young의 논지를 요약하면 이렇다. 상태만 저장하면 "왜 그렇게 됐는가"를 잃는다. 잔액이 0원인 것은 알아도, 그게 전액 인출 때문인지 세 번의 결제 때문인지 알 수 없다. 의도를 온전히 담은 로그는 정보를 잃지 않으므로, 나중에 생긴 질문에도 과거 데이터로 답할 수 있다. 이건 WAL이 "무엇을 하려 했는가"를 기록해 복구를 가능하게 한 것과 정확히 같은 원리다.

📒 비유 (보조 설명)

회계 장부는 숫자를 지우고 고치지 않는다. 잘못 적었으면 취소 전표를 새로 추가한다. 그래서 잔액은 언제나 전표를 처음부터 더한 결과이고, 감사(audit)가 가능하다. append-only 로그가 데이터의 원본이 되는 시스템이 정확히 이 모양이다.

우리도 매일 쓰는 WAL 사고방식 — 트랜잭셔널 아웃박스

이 사고방식은 DB 내부에만 있는 게 아니다. "DB에 저장하고 그다음 외부 시스템에 알린다"는 흔한 코드는 이중 쓰기(dual write) 문제를 안고 있다.

❌ 나쁜 예 — 두 시스템에 각각 쓰기

with transaction.atomic():
    order = Order.objects.create(...)

# 💥 여기서 프로세스가 죽거나 Kafka가 죽으면?
#    주문은 DB에 있는데 알림은 영원히 안 나간다.
#    순서를 바꿔도 대칭적으로 반대 문제가 생긴다.
kafka_producer.send("orders", order.to_dict())

✅ 좋은 예 — 의도를 같은 트랜잭션 안에 먼저 기록

with transaction.atomic():
    order = Order.objects.create(...)
    # 같은 DB 트랜잭션 = 주문과 발행 의도가 함께 커밋되거나 함께 롤백
    OutboxEvent.objects.create(
        topic="orders",
        payload=order.to_dict(),
        status="PENDING",
    )

# 별도 워커가 PENDING을 읽어 발행하고 SENT로 표시.
# 실패하면 재시도한다 → 최소 1회 전달이 보장된다.
# (소비자 쪽은 중복 수신에 대비해 멱등하게 처리해야 한다)

OutboxEvent 테이블이 하는 일이 바로 WAL이다. 다만 계층이 DB 내부에서 애플리케이션으로 올라왔을 뿐이다.

여기까지가 로그를 원본으로 승격시킨 계열이다. 마지막으로, 같은 목표에 정반대 수단으로 도달한 사례를 보자 — Slack 코멘트가 가장 먼저 언급한 Git이다.

Git — 같은 목표, 다른 수단

Slack 코멘트가 Git의 commit log를 나란히 놓은 것은 정확한 직관이다. 다만 Git은 WAL 프로토콜을 쓰지 않는다. 목표는 같지만 수단이 다르므로, 여기는 정확히 구분하는 편이 낫다.

Git의 요소정체WAL과의 관계
커밋 히스토리 불변 객체들의 append-only DAG(방향 비순환 그래프 — 각 커밋이 부모를 가리키기만 하고 되돌아오지 않는 구조). 새 커밋은 기존 객체를 수정하지 않고 추가한다. --amend조차 새 커밋을 만들고 참조만 옮기는 것이다 append-only + 불변이라는 성질을 공유. 단, "먼저 로그 → 나중에 데이터"의 2단계 구조는 아니다. Git에는 애초에 덮어쓸 "데이터 파일"이 없다
reflog
.git/logs/HEAD		 브랜치 끝과 HEAD가 언제 어디를 가리켰는지를 시간순으로 append하는 로컬 저널 Git에서 WAL에 가장 가까운 것. reset --hard로 날린 커밋을 되찾을 수 있는 이유가 이 저널이다
.git/index.lock O_CREAT|O_EXCL(파일이 없을 때만 만들고 이미 있으면 실패 — 즉 "먼저 만든 쪽이 이긴다")로 잠금 파일을 만들고, 새 내용을 거기에 쓴 뒤, 원자적 rename으로 제자리에 밀어넣는다 WAL이 아니라 원자적 교체 계열. 목적은 동일하다 — 독자가 반쪽 상태를 절대 보지 않게 하는 것
⚠️ 흔한 오해

"append-only면 다 WAL이다" — 아니다. WAL의 정의는 append-only가 아니라 순서 규약이다: 제자리 수정될 데이터가 따로 있고, 그 수정 전에 로그가 디스크에 도달해야 한다. Git은 제자리 수정 자체를 하지 않는 방식(불변 객체 + 원자적 참조 교체)으로 같은 목표에 도달한다. Kafka와 이벤트 소싱도 마찬가지로 "로그가 곧 데이터"인 쪽이지 WAL 프로토콜은 아니다. 공유하는 것은 구현이 아니라 통찰이다.

08같은 패턴 도감 — RocksDB·Redis·SQLite

이름은 다르지만 골격은 같다

RocksDB / LSM 트리 — 가장 교과서적인 형태

LSM 트리(쓰기를 제자리에 고치지 않고 메모리에 모았다가 디스크에 새 파일로 통째로 내려보내는 구조) 기반인 RocksDB에서, 쓰기는 먼저 메모리의 멤테이블(MemTable)에 들어가고 일정 크기가 되면 정렬된 불변 파일(SSTable)로 디스크에 내려간다. 그런데 멤테이블은 메모리라 크래시 나면 사라진다. 그래서 멤테이블에 넣기 직전에 WAL에 먼저 append한다. WAL이 존재하는 이유는 여기서 정확히 하나다: 디스크로 내려가기 전에 죽었을 때 메모리 상태를 재구성하는 것. 내려가고 나면 해당 WAL은 버려도 된다.

Redis AOF — 명령 자체를 로그로

Redis의 AOF(Append Only File)는 수행한 쓰기 명령을 그대로 파일 끝에 이어 붙인다. 재기동하면 그 명령들을 다시 실행해 메모리 상태를 복원한다(7.0부터는 스냅숏 base 파일 + 증분 파일 구조라 전체를 명령으로만 재생하지는 않는다). WAL의 REDO를 명령 수준에서 하는 셈이다.

다만 순서가 반대다 — Redis는 명령을 실행한 뒤 AOF에 기록하므로, 엄밀히는 "선행 기입"이 아니다. 그렇다고 이 순서 차이만으로 내구성이 깨지는 것은 아니다. appendfsync always는 실행 후 기록하되 응답을 보내기 전에 fsync한다. everysec에서 최대 1초가 날아가는 이유는 순서가 아니라 fsync 주기를 1초로 벌려 놓았기 때문이다.

SQLite — 방향을 뒤집은 사례

📄 롤백 저널 (기존 방식)

바뀔 페이지의 옛 값을 별도 파일에 복사해두고, 본 파일은 제자리 수정.

  • 롤백 = 저널에서 옛 값을 되돌려 씀
  • 읽기와 쓰기가 서로를 막는다
  • 약 100MB를 넘는 큰 트랜잭션에서 더 빨랐다 — 단 3.11.0(2016-02-15)부터 WAL 모드도 큰 트랜잭션을 동등하게 처리하므로 지금은 해당하지 않는다

📝 WAL 모드 (3.7.0, 2010)

본 파일은 그대로 두고, 새 값을 별도 WAL 파일에 append.

  • 본 파일을 건드리지 않으므로 읽는 쪽은 쓰는 동안에도 그대로 읽는다 (그 반대도 마찬가지)
  • 디스크 I/O가 순차적이고 fsync 호출이 훨씬 적다
  • 대부분의 시나리오에서 유의미하게 빠르다

"제자리를 덮어쓰지 않는다"는 목표는 같고, 수단이 정확히 대칭이다.

09한 장 요약 치트시트

WAL이란

데이터를 고치기 전에, 무엇을 고칠 것인지를 로그에 먼저 안전하게 적어두는 순서 규약. 커밋 성공 응답이 보증하는 것은 "데이터 파일에 반영됨"이 아니라 "로그가 디스크에 도달함"이다. 실제 반영은 나중에 백그라운드로 일어나며, 그래도 안전한 이유는 로그만 있으면 죽은 지점부터 다시 진행(REDO)하거나 되돌릴(UNDO) 수 있기 때문이다. 덤으로, 흩어진 랜덤 쓰기가 하나의 순차 쓰기로 바뀌고 여러 커밋이 fsync 한 번을 나눠 쓰게 되므로 더 안전하면서 동시에 더 빠르다.

Git · Kafka · 이벤트 소싱까지 이어지는 이유

"변경 이력이 남아 있으면 상태는 언제든 다시 만들 수 있다"는 통찰 하나가 계층을 옮겨 다니는 것이다. 그 이력을 복구용으로만 쓰면 DB의 WAL이고, 남에게 보내면 복제와 CDC이며, 이력 자체를 제품으로 만들면 Kafka이고, 애플리케이션의 진실로 삼으면 이벤트 소싱이다. Git은 여기에 "애초에 덮어쓰지 않는다"는 또 다른 답을 보탠다. 구현은 다르되 적은 원칙은 같다: 과거를 지우지 마라.

기억할 것내용
REDO 규칙커밋 응답 전에 그 트랜잭션의 로그가 디스크에 있어야 한다 (내구성)
UNDO 규칙미커밋 페이지를 디스크에 쓰기 전에 그 로그가 디스크에 있어야 한다 (원자성)
복구 3패스Analysis(파악) → Redo(전부 재적용, 미커밋 포함) → Undo(미커밋만 취소). ARIES, 1992
fsync내구성의 실제 경계선. PLP 있는 엔터프라이즈 SSD는 µs급, 없는 컨슈머 SSD는 ms급 — 수백 배 차이
체크포인트"여기까지 데이터 파일 반영 완료" 표시. 복구 시작점이자 옛 WAL 삭제 기준
내구성 다이얼PG synchronous_commit / InnoDB innodb_flush_log_at_trx_commit / Redis appendfsync — 전부 같은 손잡이
⚠️ 절대 혼동 금지synchronous_commit=off는 최근 커밋 손실(DB는 일관됨). fsync=off는 DB 파손
full_page_writes체크포인트 후 첫 수정 시 페이지 전체 이미지를 WAL에 기록 → 찢어진 페이지 방어
⚠️ 운영 시한폭탄비활성 복제 슬롯. max_slot_wal_keep_size 기본 -1(무제한) → 디스크 풀로 DB 정지
로그가 원본인 시스템Kafka = 파티션이 로그·오프셋이 LSN / 이벤트 소싱 = 상태를 저장하지 않고 이벤트를 fold해 계산
애플리케이션 응용트랜잭셔널 아웃박스 — 외부 발행 의도를 같은 트랜잭션에 먼저 기록하고 워커가 완수
Git의 위치WAL 프로토콜은 아님. 불변 객체 + 원자적 rename + reflog(append-only 저널)로 같은 목표 달성
