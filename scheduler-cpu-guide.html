00코어는 한 번에 하나

CPU 코어 하나는 한 순간에 단 하나의 명령만 실행합니다. 이게 출발점입니다. 그런데 여러분의 노트북은 브라우저·음악·에디터를 "동시에" 돌리고, 서버 한 대는 수백 명의 요청을 "동시에" 받습니다. 코어는 하나인데 어떻게?

답은 아주 빠르게 번갈아 가며 하는 것입니다. 브라우저 조금, 음악 조금, 에디터 조금... 사람 눈엔 동시처럼 보일 만큼 빠르게 전환합니다. 이 "누구를 다음에, 얼마나 실행할지" 결정하는 운영체제의 두뇌가 스케줄러(scheduler)입니다.

이 문서가 답하는 것

① 스케줄러가 어떻게 하나의 코어로 여러 일을 굴리는가 ② 그 "번갈아 하기"에 드는 숨은 비용은 무엇인가 ③ 그래서 왜 "동시성·비동기는 공짜가 아니다"인가. 이 셋을 이해하면 worker 수를 왜 그렇게 잡는지, async 코드에서 무엇을 하면 안 되는지가 보입니다.

01CPU와 스케줄러란

운영체제(OS)에는 실행되길 기다리는 작업이 잔뜩 있습니다. OS는 이들에게 코어를 아주 짧은 시간씩 돌아가며 빌려줍니다. 이 짧은 시간 조각을 타임 슬라이스(time slice) 또는 퀀텀이라고 부릅니다. 고전적으로는 수십 ms(예: 50ms) 수준입니다.

코어 하나의 1초를 잘게 쪼개서 나눠 씀 (시분할, time-sharing) 시간 → │▓▓▓ A ▓▓▓│░░ B ░░│▓ C ▓│▓▓▓ A ▓▓▓│░░ B ░░│ ... └─ 5ms ──┴─4ms─┴─3ms┴─ 5ms ──┴─4ms─┘ 사람 눈엔 A·B·C가 "동시에" 도는 것처럼 보인다. 실제로는 한 순간엔 언제나 하나만 돈다.

스케줄러가 하는 일은 두 가지 질문에 답하는 것입니다. "다음에 누구를 실행할까?"(순서)와 "얼마나 오래 실행하게 둘까?"(시간). 이 결정을 초당 수천 번씩 내립니다.

🎧 비유

스케줄러는 클럽 DJ입니다. 손님(작업)은 많고 무대(코어)는 하나. DJ는 한 곡을 짧게 틀고 다음 곡으로, 또 다음 곡으로 빠르게 넘깁니다. 잘 넘기면 모두가 자기 노래를 듣는 것처럼 느끼지만, 곡을 바꾸는 순간순간마다 아주 짧은 정지가 있습니다. 그 정지가 이 문서의 핵심 주제입니다.

02프로세스 vs 스레드

스케줄러가 굴리는 "작업"의 단위를 알아야 합니다. 딱 두 가지만 기억하세요.

📦 프로세스 (Process)

실행 중인 프로그램 한 벌. 자기만의 독립된 메모리 공간을 가집니다.

  • 서로 메모리를 공유하지 않음 → 격리·안전
  • 예: 크롬 탭 하나, gunicorn worker 하나
  • 전환 비용이 비쌈(메모리 주소공간까지 교체)

🧵 스레드 (Thread)

프로세스 안의 실행 흐름. 같은 프로세스의 메모리를 공유합니다.

  • 메모리 공유 → 통신 빠름, 대신 경합·버그 위험
  • 한 프로세스 안에 여러 스레드 가능
  • 전환 비용이 상대적으로 쌈(주소공간 그대로)

스케줄러는 보통 스레드 단위로 코어를 나눠줍니다(리눅스는 스레드도 프로세스도 같은 "태스크"로 다룹니다). 핵심 차이: 프로세스끼리는 남남이라 전환이 비싸고, 같은 프로세스의 스레드끼리는 전환이 덜 비쌉니다. 왜 비싼지는 바로 다음 장에서.

03컨텍스트 스위칭 — 비용의 정체

"공짜가 아니다"의 실체가 바로 여기 있습니다.

코어가 작업 A를 멈추고 작업 B로 넘어가려면, A가 어디까지 했는지를 전부 저장하고 B가 저장해둔 상태를 전부 복원해야 합니다. 레지스터 값, 프로그램 카운터(다음에 실행할 위치) 등 이 "실행 상태 한 벌"을 컨텍스트(context)라 하고, 저장↔복원 과정을 컨텍스트 스위칭(context switching)이라 합니다.

작업 A 실행 중 ──▶ [A의 상태 저장] ──▶ [B의 상태 복원] ──▶ 작업 B 실행 └───────── 이 구간엔 아무 일도 안 함 ─────────┘ = 순수한 오버헤드(낭비)

이 전환 구간 동안 CPU는 실제 일(여러분의 코드)을 하나도 안 합니다. 그냥 짐을 쌌다 풀 뿐입니다. 얼마나 걸릴까요? 실측치를 보면:

~1–2µs
같은 프로세스 내 스레드 전환 (레지스터만 교체)
+10–50µs
프로세스 전환 시 추가 (주소공간 교체 = TLB 플러시)
수백 µs
캐시가 식으면(cache pollution) 실질 비용은 여기까지

마지막 항목이 진짜 무섭습니다. B로 넘어가면 방금 A가 데워놓은 CPU 캐시가 쓸모없어집니다(cache pollution). B는 차가운 캐시에서 다시 시작해야 하고, 메모리를 많이 쓰는 작업이면 이 "캐시 다시 데우기" 비용이 수백 µs까지 갑니다. 전환 한 번의 직접 비용(1µs)보다 간접 비용이 훨씬 큰 겁니다.

📎 용어: TLB 플러시

TLB는 "가상주소 → 실제 메모리주소" 변환을 캐싱해두는 작은 표입니다. 프로세스가 바뀌면 이 표가 무효가 되어 비웁니다(플러시). 그래서 프로세스 전환이 스레드 전환보다 훨씬 비쌉니다. 지금은 "프로세스 전환 = 추가 세금" 정도로만 기억하면 됩니다.

⚠️ 핵심 통찰

1µs가 별거냐 싶죠. 하지만 스케줄러가 초당 수천~수만 번 전환하고, 여기에 캐시 비용까지 곱해지면 CPU 시간의 상당 부분이 "일"이 아니라 "짐 싸기"에 쓰입니다. 전환이 너무 잦으면 이걸 스래싱(thrashing)이라 부르고, 일보다 전환이 더 바빠지는 상태입니다.

04다음 차례는 누구? (스케줄링)

대기 중인 작업이 여럿일 때 누구를 먼저 줄까요? 대표적인 방식 몇 가지만 감을 잡아둡시다.

방식규칙문제
FCFS (선착순)먼저 온 순서대로앞의 무거운 작업이 뒤를 다 막음(호위 효과)
라운드 로빈모두에게 똑같은 시간 조각을 돌아가며공평하지만 우선순위 구분이 없음
우선순위급한 작업 먼저낮은 우선순위가 영영 못 도는 기아(starvation)
리눅스 CFS"가장 덜 실행된" 작업에게 다음 차례를 (완전 공정)현대 리눅스의 기본. 균형이 좋음

리눅스의 CFS(Completely Fair Scheduler)는 감만 잡으면 됩니다. "목표 지연 시간"(기본 대략 20ms) 안에 대기 중인 모든 작업이 최소 한 번은 돌게 하되, N개가 경쟁하면 각자 1/N씩 나눠 갖습니다. 작업이 많아질수록 각자의 몫이 얇아지죠.

선점형(preemptive)이 핵심

현대 OS는 선점형입니다. 작업이 자발적으로 CPU를 내놓길 기다리지 않고, 타임 슬라이스가 끝나면 OS가 강제로 빼앗아 다음 작업에게 넘깁니다. 덕분에 한 작업이 무한 루프를 돌아도 시스템 전체가 멈추지 않습니다. (선점 = "차례를 강제로 뺏는다"는 뜻.)

💡 왜 알아야 하나

작업 수 N이 늘면 ① 각자 CPU 몫이 1/N로 줄고 ② 그만큼 전환(§03)이 잦아집니다. "worker/스레드를 무작정 늘리면 오히려 느려진다"는 말의 뿌리가 바로 이 두 가지입니다.

05동시성 ≠ 병렬성

주니어가 가장 많이 헷갈리는 지점. 여기만 확실히 하고 갑시다.

🔀 동시성 (Concurrency)

여러 일을 번갈아 가며 다뤄 "동시에 진행되는 것처럼" 보이게 하는 것.

  • 코어 1개로도 가능 (빠른 전환)
  • 구조/설계의 문제 — "여러 일을 다루는 법"
  • 예: 요리사 1명이 3개 냄비를 번갈아 저음

⚡ 병렬성 (Parallelism)

여러 일을 진짜 물리적으로 같은 순간에 실행하는 것.

  • 코어가 여러 개여야 가능
  • 실행/하드웨어의 문제 — "정말 동시에 하는 것"
  • 예: 요리사 3명이 각자 냄비 하나씩

정리하면: 동시성은 "번갈아", 병렬성은 "진짜 동시에". 코어가 1개면 아무리 스레드를 많이 만들어도 병렬이 아니라 동시성(전환)일 뿐입니다. 스케줄러는 동시성을 만드는 장치이고, 진짜 병렬은 코어 개수만큼만 가능합니다.

✅ 실무 감각

코어가 8개면 진짜 병렬은 최대 8개. 스레드를 800개 만들어도 동시에 도는 건 8개뿐이고, 나머지 792개는 순서를 기다리며 전환 비용만 늘립니다. "스레드 = 성능"이 아닌 이유입니다.

06동기/블로킹 vs 비동기

여기서 "비동기가 왜 나왔나"가 풀립니다. 작업은 크게 두 종류입니다.

🧮 CPU-bound (계산 위주)

CPU를 계속 굴리는 일. 이미지 처리, 정렬, 암호화, 큰 반복문.

  • 병목 = CPU 계산력
  • 코어 수만큼만 빨라짐

⏳ I/O-bound (대기 위주)

뭔가를 기다리는 일. DB 응답, API 호출, 파일 읽기, 네트워크.

  • 병목 = 남을 기다리는 시간
  • 기다리는 동안 CPU는 논다

웹 서버 일의 대부분은 I/O-bound입니다. DB에 쿼리를 던지고 응답을 기다리는 그 수십 ms 동안, CPU는 손 놓고 놉니다. 이게 블로킹(blocking)입니다 — "응답 올 때까지 이 자리에서 멈춰 기다림".

❌ 블로킹 — 기다리는 동안 이 스레드는 아무것도 못 함

# API 3개를 순서대로 호출. 각 100ms 걸린다면 총 300ms.
a = requests.get(url_a)   # 100ms 동안 멈춰서 기다림 (CPU 놀고 있음)
b = requests.get(url_b)   # 또 100ms 멈춤
c = requests.get(url_c)   # 또 100ms 멈춤 → 합계 300ms

비동기(async)/논블로킹의 아이디어: "기다리는 동안 멈춰 있지 말고, 그 시간에 다른 일을 하자." 요청을 던져놓고 응답을 기다리는 대신 다음 일로 넘어갔다가, 응답이 준비되면 그때 돌아와 처리합니다.

✅ 논블로킹 — 셋을 동시에 띄우고 함께 기다림

# 3개를 한꺼번에 던져놓고 같이 기다림 → 총 ~100ms (제일 느린 것 기준)
a, b, c = await asyncio.gather(
    fetch(url_a), fetch(url_b), fetch(url_c),
)
# 기다리는(await) 동안 CPU는 다른 요청을 처리한다. 놀지 않는다.
✅ 한 줄 정리

비동기가 빠른 건 계산을 빨리 해서가 아니라, "기다리는 시간"을 낭비하지 않아서입니다. 그래서 async는 I/O-bound에 강하고, CPU-bound에는 별 도움이 안 됩니다(기다리는 시간이 없으니까).

07스레드를 무한정 늘리면?

"동시에 많이 처리하고 싶으니 스레드를 1만 개 만들자" — 여기서 공짜가 아니다가 청구서로 돌아옵니다.

비용 1: 메모리

스레드마다 자기 스택 메모리가 필요합니다. 리눅스 기본값은 스레드당 8MiB(가상 메모리). 스레드 1만 개면 가상 메모리로 80GiB가 예약됩니다(실제 물리 사용은 훨씬 적지만, 공짜는 아닙니다).

비용 2: 전환 폭증

코어는 8개인데 스레드가 1만 개면, 스케줄러는 이 1만 개를 8개 코어에 번갈아 태우느라 컨텍스트 스위칭(§03)을 폭발적으로 일으킵니다. 어느 순간부터는 일보다 전환이 더 바빠지고(스래싱), 스레드를 늘릴수록 처리량이 오히려 줄어듭니다.

처리량 │ ┌──── 최적점 (코어 수 근처) │ ╱ ╲ │ ╱ ╲╲___ 전환 비용이 이득을 잡아먹음 │ ╱ ╲╲╲___ │╱ ╲╲╲___ └────────────────────────────▶ 스레드 수 더 많은 스레드 = 항상 더 빠름 ❌ (거짓)

그래서 현실의 해법은 "스레드를 무한정" 대신 정해진 개수만 재사용하는 것입니다.

  • 스레드 풀(thread pool) — 스레드를 N개만 미리 만들어 두고 작업을 큐에 넣어 돌려 씀. 매번 만들고 없애는 비용도 아낌.
  • 이벤트 루프(event loop) — Node.js·Python asyncio의 방식. 스레드 1개가 수천 개의 I/O 대기를 관리. 기다리는 동안 다른 걸 처리(§06)하므로 스레드가 거의 필요 없음.
  • worker 프로세스 — gunicorn/uvicorn이 코어 수에 맞춰(보통 2×코어+1) 프로세스를 띄우는 것도 같은 논리.
🐍 Python 특이사항: GIL

CPython에는 GIL(Global Interpreter Lock)이 있어, 한 프로세스 안에서는 한 순간에 한 스레드만 파이썬 바이트코드를 실행합니다. 그래서 Python 스레드는 CPU-bound엔 병렬 효과가 거의 없고(GIL이 막음), I/O-bound엔 유효합니다(기다리는 동안 GIL을 놓음). Python에서 CPU 작업을 병렬화하려면 스레드가 아니라 멀티프로세스(또는 Celery 같은 워커)를 씁니다. 이게 Django에서 무거운 계산을 Celery로 빼는 이유 중 하나입니다.

여기까지 오면 아래 규칙들이 "왜"인지 이해됩니다.

상황이렇게, 왜냐하면

이벤트 루프는 스레드 1개로 굴러갑니다. 그 한 스레드 안에서 블로킹 호출(예: 동기 requests.get(), time.sleep(), 무거운 CPU 계산)을 하면, 그 순간 전체 이벤트 루프가 멈춰 다른 모든 요청이 함께 얼어붙습니다. async 코드에선 반드시 async 버전(await asyncio.sleep(), async HTTP 클라이언트)을 쓰거나, 무거운 작업은 별도 스레드/프로세스로 넘겨야 합니다.

✅ 판단 한 줄

"이 작업은 기다리는 일인가, 계산하는 일인가?" 먼저 물어보세요. 기다리는 일이면 async, 계산하는 일이면 멀티프로세스. 이 한 질문이 동시성 설계의 90%입니다.

09숨은 비용 하나 더: 순서가 사라진다

스케줄러가 만드는 비용이 하나 더 있습니다. 성능이 아니라 예측 가능성의 비용입니다.

선점형 스케줄러는 각 스레드를 언제 멈추고 언제 재개할지 그때그때 다르게 정합니다. 코어의 미세한 속도 차, 다른 작업의 부하에 따라 스레드가 끝나는 순서가 실행마다 달라집니다. 그래서:

스레드 A, B, C가 각자 결과를 리스트에 append 한다면... 실행 1회차: [A, C, B] ← 끝난 순서대로 실행 2회차: [B, A, C] ← 이번엔 다르게 끝남 실행 3회차: [A, B, C] → 같은 입력인데 결과 순서가 매번 다름 = 비결정적

같은 입력인데 실행마다 결과가 달라지는 것을 비결정적(non-deterministic)이라고 합니다. 테스트가 어쩔 땐 통과하고 어쩔 땐 실패하는 플래키(flaky) 테스트, "내 컴퓨터에선 됐는데" 버그의 단골 원인이죠.

그래서 병렬 작업의 결과를 모을 때는, 끝나는 순서에 의존하지 말고 다 모은 뒤 명시적인 기준으로 정렬해야 합니다(점수 같은 기준이 동점이면 id 같은 고유 키로 순서를 확정). 동시성이 성능을 주는 대신 "순서의 보장"을 가져갑니다. 이것도 공짜가 아닌 비용의 하나입니다.

10한 장 요약 치트시트

스케줄러(CPU)

코어 하나는 한 번에 하나. 스케줄러가 작업들에게 코어를 짧은 시간씩(타임 슬라이스) 번갈아 빌려줘 "동시에 도는 것처럼" 보이게 한다(동시성). 진짜 동시 실행(병렬성)은 코어 개수만큼만 가능하다.

공짜가 아니다

작업을 바꿀 때마다 컨텍스트 스위칭(상태 저장·복원 ~1µs + 캐시 식음 수백µs)이 든다. 스레드를 무작정 늘리면 전환 비용이 이득을 잡아먹어 오히려 느려진다. 그래서 스레드 풀·이벤트 루프·코어 수 기반 worker를 쓴다.
