00왜 이 둘을 같이 배우나

겉보기엔 상관없어 보이는 두 주제입니다. 하지만 실무에서는 거의 항상 붙어 다닙니다.

CQRS는 "읽기(조회)와 쓰기(변경)를 서로 다른 모델로 다루자"는 설계 패턴입니다. 그런데 읽기 전용 모델을 따로 만들면, 그 데이터가 매번 똑같은 순서와 값으로 만들어진다는 보장이 필요합니다. 오늘 조회하면 A가 1등인데 내일 같은 데이터로 조회하면 B가 1등이면 아무도 그 시스템을 못 믿으니까요.

여기서 결정론적 알고리즘이 등장합니다. 같은 입력이면 항상 같은 출력. 랭킹, 집계, 리스트 정렬처럼 "읽기 모델"을 만드는 로직은 반드시 결정론적이어야 합니다.

한 문장 요약

CQRS는 읽기와 쓰기를 나누는 구조, 결정론은 그 읽기 결과가 흔들리지 않게 하는 성질. 좋은 조회 시스템은 둘 다 필요합니다.

01먼저 알아야 할 것: CQS

CQRS를 이해하려면 그 뿌리인 CQS부터.

CQS(Command Query Separation)는 1980년대 Bertrand Meyer가 제안한 아주 단순한 규칙입니다. 함수(메서드)를 딱 두 종류로 나누라는 것.

⚙️ Command (명령)

상태를 바꾸는 동작. 무언가를 쓰고, 저장하고, 지웁니다.

  • 조회 가능한 데이터를 돌려주지 않는 게 원칙 (실무선 새 id·성공여부 정도는 반환)
  • 예: createOrder(), cancel()
  • "뭔가를 한다"

🔍 Query (조회)

상태를 읽기만 하는 동작. 아무것도 바꾸지 않습니다.

  • 값을 돌려주는 게 목적
  • 예: getOrder(), totalPrice()
  • "뭔가를 물어본다"
🍽️ 비유

식당에서 주문(Command)은 주방에 뭔가를 시키는 행위고, 메뉴판 보기(Query)는 그냥 확인만 하는 행위입니다. 메뉴판을 봤다고 냉장고 재료가 줄어들면 안 되죠. 조회는 부작용(side effect)이 없어야 합니다.

핵심 규칙: "질문을 하면서 동시에 답을 바꾸지 마라(Asking a question should not change the answer)." CQRS는 이 아이디어를 함수 수준이 아니라 시스템/모델 수준으로 끌어올린 것입니다.

02CQRS란 무엇인가

CQRS(Command Query Responsibility Segregation)는 "정보를 바꿀 때 쓰는 모델과 읽을 때 쓰는 모델을 아예 분리하자"는 패턴입니다. 이 용어는 Greg Young이 만들었고, Martin Fowler가 널리 알렸습니다. 요지는 "정보를 업데이트할 때 쓰는 모델과, 읽을 때 쓰는 모델을 서로 다르게 둘 수 있다"는 것입니다. (아래 인용은 모두 원문 그대로가 아니라 요지를 우리말로 옮긴 것입니다.)

보통의 CRUD 앱은 하나의 모델(예: Order 엔티티)로 쓰기도 하고 읽기도 합니다. CQRS는 이걸 둘로 쪼갭니다.

일반 CRUD (한 모델이 다 함) ┌──────────┐ ┌──────────────┐ ┌────────┐ │ 클라이언트 │ ──> │ Order 모델 │ ──> │ DB │ │ │ <── │ (읽기+쓰기 겸용) │ <── │ │ └──────────┘ └──────────────┘ └────────┘ CQRS (읽기/쓰기 모델 분리) ┌─────────────────┐ 쓰기 ──> │ Write 모델 │ ──┐ │ (검증·비즈니스로직) │ │ └─────────────────┘ ▼ ┌──────────┐ ┌────────┐ │ 클라이언트 │ │ DB │ └──────────┘ └────────┘ ┌─────────────────┐ ▲ 읽기 <── │ Read 모델 │ ──┘ │ (검증 없음, DTO만) │ └─────────────────┘

Write 모델은 명령을 받아 유효성 검증과 비즈니스 규칙을 실행합니다. Read 모델은 비즈니스 로직이나 검증이 없고, 화면에 딱 맞는 형태(DTO)를 그냥 돌려줍니다. Microsoft 문서 표현으로는 "읽기 모델은 뷰에 쓸 DTO를 반환하며 검증 스택이 없다".

📎 용어: DTO

DTO(Data Transfer Object) = 화면·API에 필요한 필드만 담아 나르는 단순한 데이터 묶음입니다. ORM 모델처럼 DB에 붙어 있거나 비즈니스 메서드를 갖지 않고, 값만 실어 나릅니다. 그래서 읽기 쪽을 화면 모양대로 자유롭게 만들 수 있는 겁니다.

흔한 오해

CQRS는 "DB를 두 개 쓰는 것"이 아닙니다. 가장 가벼운 CQRS는 DB 하나에서 코드 구조만 읽기/쓰기로 나눕니다. 별도 DB, 이벤트 소싱, 메시지 큐는 전부 선택 사항이고 더 무거운 단계입니다. 이 오해 때문에 많은 팀이 CQRS를 과하게 도입합니다.

03CQRS가 실제로 푸는 문제

"멋있어서" 쓰는 게 아닙니다. 아래 통증이 실제로 있을 때만 값을 합니다.

1. 읽기와 쓰기의 요구가 서로 싸운다

쓰기 쪽은 정규화된 깔끔한 테이블을 원하는데, 화면은 여러 테이블을 5개씩 조인한 복잡한 결과를 원합니다. 하나의 모델로 둘 다 만족시키려다 보면 쿼리가 괴물이 됩니다. 읽기 모델을 따로 두면 화면에 맞게 미리 가공(비정규화)해둘 수 있습니다.

정규화 = 중복 없이 여러 테이블로 잘게 쪼갠 것(쓰기·수정에 안전). 비정규화 = 조회 속도를 위해 일부러 미리 합치거나 복제해둔 것(읽기에 빠름). 쓰기는 정규화를 좋아하고, 화면은 비정규화를 좋아합니다. 이 둘의 충돌이 CQRS의 출발점입니다.

2. 읽기가 쓰기보다 압도적으로 많다

많은 서비스는 읽기가 쓰기보다 훨씬 많습니다(종종 수십~수백 배). Microsoft 문서도 "읽기 수가 쓰기 수보다 많을 때 CQRS가 특히 유리하다"고 말합니다. 이럴 때 읽기 모델만 읽기 전용 복제본(replica)을 여러 대 늘려 트래픽을 분산하고, 쓰기 모델은 적은 인스턴스로 정합성을 지킬 수 있습니다.

3. 팀이 서로 밟는다

한 팀은 복잡한 주문 비즈니스 로직(쓰기)을, 다른 팀은 대시보드/리스트 화면(읽기)을 만듭니다. 모델을 나누면 독립적으로 일할 수 있습니다.

4. 감사 로그 / 과거 상태 복원이 필요하다

"이 주문이 어떤 경로로 지금 상태가 됐지?"를 추적해야 하는 도메인. 이건 CQRS와 자주 짝을 이루는 이벤트 소싱의 영역입니다.

📎 용어: 이벤트 소싱

이벤트 소싱(Event Sourcing) = 현재 상태만 저장하는 대신, "무슨 일이 일어났는지"를 변경 이벤트로 순서대로 전부 기록해두고, 그 기록을 재생해서 상태를 재구성하는 방식입니다. CQRS와 자주 함께 쓰이지만 둘은 서로 독립적인 별개 패턴입니다. CQRS를 쓴다고 이벤트 소싱을 꼭 써야 하는 건 아닙니다.

✅ 실무 감각

원본 데이터(쓰기)와, 그걸 미리 계산해둔 조회용 테이블(읽기)을 나누는 순간 이미 CQRS를 하고 있는 겁니다. 랭킹·대시보드처럼 "복잡하게 집계해서 보여주기만" 하는 화면이 대표적인 무대입니다.

04CQRS의 3단계 (가벼운 것부터)

CQRS는 스위치가 아니라 다이얼입니다. 필요한 만큼만 돌리세요.

  1. 1단계 — 같은 DB, 코드만 분리 같은 데이터베이스를 쓰되 쓰기 경로와 읽기 경로를 나눕니다. 단순히 클래스 두 개로 쪼개는 게 아니라, 읽기 쪽이 쓰기 모델과 다른 자기만의 모델(화면용 DTO)을 갖는 것이 CQRS의 최소 조건입니다. (쓰기·읽기가 똑같은 엔티티를 그대로 반환하면 그건 아직 CQRS가 아니라 그냥 서비스 계층 분리입니다.) 리스크가 거의 없고, 여기서 얻는 이득이 대부분입니다.
  2. 2단계 — 별도의 읽기 전용 모델/테이블 같은 DB 안에서 조회용으로 미리 가공한 테이블(예: order_summary, ranking_snapshot)을 둡니다. 원본을 조회용 모양으로 가공해 이 테이블을 채우는 과정을 프로젝션(projection)이라고 부릅니다(이 문서의 핵심 개념 — §12에서 다시 나옵니다). 이 단계에선 보통 쓰기와 같은 트랜잭션 안에서 동기(synchronous)로 갱신하므로 데이터가 항상 최신입니다(강한 일관성). 화면 쿼리는 단순해지고 빨라집니다.
  3. 3단계 — 물리적으로 분리된 저장소 + 이벤트 쓰기 DB와 읽기 DB를 아예 다른 저장소로 둡니다(예: 쓰기는 PostgreSQL, 읽기는 Elasticsearch/Redis). 여기서는 쓰기가 이벤트를 발행하면 읽기 저장소가 비동기(asynchronous)로 나중에 그걸 구독해 갱신합니다. 갱신이 즉시가 아니라 "나중에"이기 때문에 최종 일관성 문제(§06)를 떠안습니다. 가장 강력하지만 가장 복잡합니다.
⚠️ 주니어가 가장 많이 하는 실수

블로그에서 3단계(이벤트 소싱 + Kafka + 별도 DB)를 보고 "이게 CQRS구나" 하고 첫 프로젝트부터 도입합니다. 그리고 최종 일관성 버그, 동기화 지옥, 디버깅 난이도에 파묻힙니다. 1단계부터 시작하고, 통증이 실제로 생길 때만 다음 단계로.

05코드로 보는 CQRS

1단계 CQRS를 파이썬(Django 스타일)으로 보겠습니다. 핵심은 "쓰기 경로"와 "읽기 경로"가 서로 다른 진입점을 갖는다는 것.

Before — 하나의 서비스가 다 함 (CRUD)

class OrderService:
    def create_order(self, user, items):     # 쓰기
        # 검증 + 저장 + ...
        return Order.objects.create(...)

    def get_dashboard(self, user):          # 읽기
        # 같은 Order 모델을 5중 조인해서 화면용으로 가공...
        return Order.objects.filter(...).select_related(...)  # 점점 괴물이 됨

After — 명령과 조회를 분리 (1단계 CQRS)

# ===== 쓰기(Command) 경로: 검증·비즈니스 로직이 여기 산다 =====
class CreateOrderCommand:
    user_id: int
    items: list

class OrderCommandHandler:
    def handle(self, cmd: CreateOrderCommand) -> int:
        self._validate(cmd)                # 재고, 권한, 금액 검증
        order = Order.objects.create(...)  # 정규화된 원본 저장
        return order.id                     # 명령은 id 정도만 반환


# ===== 읽기(Query) 경로: 검증 없음, 화면용 DTO만 =====
class DashboardDTO:              # 화면에 딱 맞는 모양
    total_orders: int
    recent: list

class OrderQueryService:
    def get_dashboard(self, user_id: int) -> DashboardDTO:
        # 읽기 전용. 조회에 최적화된 쿼리/뷰를 자유롭게 사용
        row = read_dashboard_view(user_id)   # 미리 가공된 뷰/테이블
        return DashboardDTO(total_orders=row.cnt, recent=row.items)
✅ 여기서 얻는 것

쓰기 쪽은 "정확함"에만 집중하고, 읽기 쪽은 "빠르고 화면에 맞음"에만 집중합니다. 둘의 요구가 더 이상 한 클래스 안에서 충돌하지 않습니다. DB는 여전히 하나입니다.

📎 "명령은 값을 반환 안 한다"고 하지 않았나?

§01의 엄격한 CQS 규칙은 "조회 가능한 도메인 데이터를 명령이 반환하지 마라"는 뜻입니다. 위 handle()이 order.id를 돌려주는 것처럼, 실무의 명령은 보통 최소한의 확인값(새로 만든 id, 성공/실패) 정도는 반환합니다. 이건 규칙 위반이 아니라 널리 쓰이는 현실적 완화입니다.

2단계 맛보기 — 쓰기와 같은 트랜잭션에서 읽기 테이블 동기 갱신

class OrderCommandHandler:
    @transaction.atomic              # 원본 저장과 읽기 테이블 갱신을 한 트랜잭션으로
    def handle(self, cmd) -> int:
        order = Order.objects.create(...)        # ① 정규화된 원본(쓰기 모델)
        rebuild_order_summary(order.user_id)     # ② 조회용 테이블을 즉시 갱신 = 프로젝션
        return order.id
# 같은 트랜잭션이라 읽기 테이블이 항상 최신 → 강한 일관성 (아직 최종 일관성 문제 없음)

06최종 일관성(Eventual Consistency)의 함정

3단계(별도 읽기 저장소)로 가면 반드시 만나는 주제입니다. 앞 §04에서 봤듯 3단계는 읽기 저장소를 비동기로 나중에 갱신합니다. 그래서 쓰기 DB에 데이터가 저장된 순간과, 읽기 DB에 반영되는 순간 사이에 시간차가 생깁니다. (2단계처럼 같은 트랜잭션에서 동기로 갱신하면 이 문제가 없습니다.)

사용자가 글 작성 ──> [쓰기 DB 저장 완료] ✅ │ │ 이벤트 발행 → 읽기 DB 반영 (몇 ms ~ 몇 초) ▼ 사용자가 새로고침 ──> [읽기 DB] ❓ 아직 내 글이 안 보임!

이게 "eventual consistency"입니다. 결국엔 일치하지만, 그 순간엔 읽기 데이터가 오래된(stale) 상태일 수 있습니다. Microsoft 문서도 "읽기 데이터가 최신 변경을 즉시 반영하지 못해 오래된 데이터가 나올 수 있다"고 명시합니다.

실무에서 겪는 증상

"방금 저장했는데 목록에 안 떠요" 버그의 상당수가 이겁니다. 대응책: 쓰기 직후엔 낙관적 업데이트(서버 반영을 기다리지 않고, 방금 입력한 내용을 화면에 먼저 그려주는 것)로 보여주기. 또는 정말 즉시 일관성이 필요한 화면이면 3단계 대신 2단계(동기 갱신)를 쓰거나, 아예 CQRS를 쓰지 않기.

07언제 쓰고, 언제 쓰지 말까

Martin Fowler의 조언은 단호합니다. 요지는 대부분의 시스템은 그냥 CRUD로 남는 게 맞고, CQRS는 위험한 복잡성을 더한다는 것. 그리고 시스템 전체가 아니라 특정 기능 영역 하나에만 적용하라고 합니다.

✅ 쓰기 좋은 경우🚫 쓰지 말아야 할 경우
읽기가 쓰기보다 압도적으로 많음 단순한 CRUD 앱 (게시판, 관리자 페이지)
화면용 조회가 매우 복잡함 (랭킹, 대시보드, 피드) 읽기/쓰기 모델이 거의 똑같이 생김
읽기와 쓰기를 따로 확장해야 함 즉시 일관성이 필수인 화면 (잔액, 재고 카운트)
비즈니스 규칙이 복잡하고 자주 바뀜 팀이 작고 도메인이 단순함
감사 로그 / 과거 상태 복원이 필요함 "멋있어 보여서" — 이건 이유가 아닙니다
기억할 규칙

CQRS는 전부 아니면 전무가 아닙니다. 앱의 한 부분(예: 랭킹 화면)에만 적용하고 나머지는 평범한 CRUD로 두는 게 정상이고 건강한 설계입니다.

08결정론적 알고리즘이란

결정론적(deterministic) 알고리즘은 같은 입력이면 항상 같은 출력을 내는 알고리즘입니다. 실행할 때마다, 어느 서버에서 돌리든, 오늘이든 내일이든 결과가 똑같습니다. 무작위성이나 외부 상태에 의존하지 않고, 정해진 단계를 그대로 따릅니다.

✅ 결정론적

  • sort([3,1,2]) → 항상 [1,2,3]
  • 같은 입력 → 같은 출력, 100% 재현
  • 테스트 가능, 캐시 가능, 디버깅 쉬움

🎲 비결정론적

  • shuffle(list) → 매번 다름
  • now(), random()에 의존
  • "내 컴퓨터에선 됐는데" 버그의 원천
🎰 비유

결정론적 알고리즘은 계산기입니다. 2 + 2는 언제 눌러도 4. 비결정론적 알고리즘은 슬롯머신입니다. 같은 레버를 당겨도 결과가 다르죠. 백엔드 로직 대부분은 계산기여야 하고, 슬롯머신이면 안 됩니다.

09왜 결정론이 중요한가

1. 테스트가 가능해진다

결정론적이면 assert rank(data) == expected가 항상 통과합니다. 비결정론적이면 테스트가 어쩔 땐 통과하고 어쩔 땐 실패하는 플래키(flaky) 테스트가 됩니다. 팀 전체의 신뢰를 갉아먹는 주범입니다.

2. 캐싱이 안전해진다

같은 입력이 같은 출력을 낸다면, 결과를 캐시에 저장했다가 재사용해도 안전합니다. 비결정론적이면 캐시된 값이 틀린 값일 수 있습니다.

3. 재현과 디버깅이 가능해진다

버그가 났을 때 "같은 입력을 다시 넣으면 같은 버그가 재현된다"는 건 엄청난 자산입니다. 비결정론적 버그는 재현이 안 돼서 고치기가 지옥입니다.

4. 분산 환경에서 여러 노드가 같은 결과에 도달한다

여러 서버가 같은 데이터를 각자 정렬했는데 결과가 다르면 페이지네이션이 깨지고, 리더보드 순위가 서버마다 다르게 보입니다. 결정론은 여러 노드가 같은 입력에서 같은 상태에 수렴하게 하는 전제 조건입니다(복제 상태 머신의 기반). 참고로 이건 Raft·Paxos 같은 "합의(consensus)" 알고리즘 그 자체는 아니고, 그것이 동작하기 위한 바탕입니다.

✅ 대표 무대: 랭킹

리더보드, 검색 결과, 추천 피드, 콘텐츠 순위 — 전부 "같은 데이터면 같은 순위"가 생명입니다. 여기서 결정론이 깨지면 사용자가 새로고침할 때마다 순위가 춤을 춥니다.

10비결정성은 어디서 오나

대부분의 비결정성은 "실수로 흘려보낸" 것입니다. 범인 목록:

원인예시해결 방향
⏰ 현재 시각datetime.now()를 로직에 섞음시각을 입력으로 주입(inject)
🎲 난수random(), uuid4()시드(seed) 고정 / 밖에서 주입 (uuid4는 시드 불가 → id를 주입하거나 uuid5)
🗺️ 집합 순회 순서set 순서 (Python dict는 3.7+ 삽입순서라 안전)순회 전에 명시적으로 정렬
⚡ 동시성 / 병렬스레드가 끝나는 순서가 매번 다름결과를 모은 뒤 결정론적으로 정렬
🔢 부동소수점 순서a+b+c의 덧셈 순서 차이합산 순서 고정, 정수/decimal 사용
🌐 외부 I/OAPI 응답 순서, DB의 ORDER BY 없는 조회항상 명시적 정렬, 응답 정규화
🤝 정렬 동점(tie)점수가 같은 두 항목의 순서가 들쭉날쭉고유 키로 타이브레이커 추가 ⭐
⚠️ 가장 흔한 함정: ORDER BY의 동점

SQL에서 ORDER BY score DESC만 쓰면, 점수가 같은 행들의 순서는 DB가 마음대로 정합니다. 오늘과 내일이 다를 수 있고, 페이지네이션이 깨집니다. 검색 결과에서 이런 경고가 반복해서 나옵니다: "재현성이 중요하면 ORDER BY에 고유한 타이브레이커 컬럼을 반드시 넣어라."

11결정론적으로 만드는 법

핵심 기법 1 — 안정 정렬 + 타이브레이커

안정 정렬(stable sort)은 값이 같은 항목들의 원래 순서를 유지하는 정렬입니다. 하지만 원래 순서 자체가 안 정해져 있으면 소용없습니다. 그래서 타이브레이커(tie-breaker), 즉 동점일 때 순서를 가르는 고유한 2차 기준을 추가합니다.

❌ 나쁜 예 — 동점 순서가 입력에 끌려감

# Python sorted는 안정 정렬이라, "같은 입력"이면 매번 결과가 같다.
# 문제는 입력 users의 순서가 보장되지 않을 때: 점수가 같은 항목의
# 최종 순서가 입력 순서에 따라 흔들린다 (안정 정렬은 정해지지 않은 순서를 지켜줄 뿐).
ranked = sorted(users, key=lambda u: u.score, reverse=True)

✅ 좋은 예 — 고유 키로 동점을 확정

# 1차: 점수 내림차순, 2차: id 오름차순(고유하므로 순서가 100% 확정)
ranked = sorted(
    users,
    key=lambda u: (-u.score, u.id)   # 튜플: 앞 기준이 같으면 뒤 기준으로
)
# 이제 같은 users 리스트면 언제 어디서 돌려도 결과가 동일 ✅

✅ SQL에서도 동일 원칙

-- ❌ 동점 시 순서 불확정
SELECT * FROM ranking ORDER BY score DESC;

-- ✅ 고유 컬럼(id)을 타이브레이커로 → 완전 결정론적
SELECT * FROM ranking ORDER BY score DESC, id ASC;
✅ 황금 규칙

정렬 기준의 마지막엔 항상 "고유한" 컬럼을 넣어라. id, created_at + id, uuid 등. 그러면 동점이 생겨도 순서가 단 하나로 확정됩니다.

핵심 기법 2 — 비결정성을 "밖으로" 밀어내기

시간과 난수를 로직 안에서 부르지 말고, 바깥에서 입력으로 넣어주세요. 이걸 "결정론적 코어, 비결정론적 껍질(functional core, imperative shell)"이라고 부릅니다.

❌ 함수 안에서 now()를 부름 → 테스트 불가

def is_expired(token):
    return token.expires_at < datetime.now()   # 매 실행마다 기준이 바뀜

✅ 시각을 인자로 주입 → 100% 결정론적, 테스트 쉬움

def is_expired(token, now):        # 시각을 밖에서 받음
    return token.expires_at < now

# 테스트에서 특정 시각을 고정해 넣을 수 있음
assert is_expired(tok, now=datetime(2026, 1, 1)) == True

핵심 기법 3 — 순회 전에 정렬

순서가 중요한 곳에서 set을 순회하기 전에는 명시적으로 정렬하세요. (Python dict는 삽입 순서를 보장하므로, 결정적으로 채웠다면 그대로 순회해도 안전합니다. 위험한 건 set, 그리고 비결정적 소스로 채운 컬렉션입니다.) 병렬 작업의 결과를 모을 때도 마지막에 결정론적으로 정렬해 합칩니다.

# ❌ set 순회 순서에 의존 (프로세스마다 달라질 수 있음)
for item in my_set: ...

# ✅ 명시적 정렬 후 순회
for item in sorted(my_set): ...
참고: 의도적 비결정성

모든 비결정성이 나쁜 건 아닙니다. 셔플, A/B 테스트 배정, 암호학적 난수는 일부러 무작위여야 합니다. 핵심은 "무작위가 필요한 곳에만 두고, 나머지는 전부 결정론적으로" 통제하는 것입니다.

12두 개념이 만나는 지점

이제 처음의 질문으로 돌아갑니다. CQRS와 결정론은 왜 짝일까요?

CQRS의 읽기 모델은 원본 데이터를 가공해서 만든 "미리 계산된 뷰"입니다. 랭킹 스냅샷, 대시보드 집계, 검색 인덱스 같은 것들이죠. 이 뷰를 만드는 과정을 프로젝션(projection)이라고 부릅니다.

[쓰기 모델: 원본 이벤트/데이터] │ │ 프로젝션(집계·정렬·가공) ← 이 로직이 반드시 결정론적! ▼ [읽기 모델: 랭킹 스냅샷 / 대시보드 / 검색 인덱스]

이 프로젝션이 결정론적이지 않으면 CQRS 전체가 무너집니다. 왜냐하면:

  • 읽기 모델을 다시 만들어야 할 때(버그 수정, 스키마 변경으로 재생성) 같은 원본에서 같은 결과가 나와야 합니다. 안 그러면 순위가 갑자기 바뀝니다.
  • 여러 인스턴스가 각자 프로젝션을 돌릴 때 결과가 일치해야 합니다.
  • 동점 처리(타이브레이커)가 없으면 재생성할 때마다 리더보드 순위가 요동칩니다.
✅ 실무 한 줄

"CQRS로 읽기 전용 랭킹 테이블을 만든다"면, 그 랭킹을 계산하는 정렬에는 반드시 고유 키 타이브레이커가 들어가야 합니다. 이 둘은 세트입니다. 집계는 멱등(idempotent)하게, 정렬은 결정론적으로.

멱등 = 같은 집계를 여러 번 돌려도 한 번 돌린 것과 결과가 같음(중복 반영 안 됨) → 재생성·재시도가 안전. 결정론 = 같은 입력이면 항상 같은 출력. 둘은 다른 성질이지만, 읽기 모델을 안전하게 다시 만들려면 둘 다 필요합니다.

13한 장 요약 치트시트

CQRS

읽기 모델과 쓰기 모델을 분리하는 패턴. 쓰기는 검증·비즈니스 로직, 읽기는 화면용 DTO. DB를 나누는 게 아니라 책임을 나누는 것. 1단계(코드만 분리)부터 시작하고, 통증이 생길 때만 다음 단계로. 대부분의 앱은 CRUD로 충분하다.

결정론적 알고리즘

같은 입력 → 항상 같은 출력. 테스트·캐싱·재현·분산 수렴의 전제. 비결정성의 주범은 시간·난수·set 순서·동시성·정렬 동점. 해법: 시간/난수는 밖에서 주입하고, 정렬 마지막엔 항상 고유 키 타이브레이커를 넣어라.

상황이렇게
단순 CRUD 앱CQRS 쓰지 마라
복잡한 랭킹/대시보드 화면읽기 모델 분리(CQRS) + 결정론적 정렬
ORDER BY 쓸 때마지막에 고유 컬럼(id) 추가
로직에서 시간/난수 필요인자로 주입해서 결정론 유지
테스트가 가끔 실패(flaky)숨은 비결정성부터 의심
