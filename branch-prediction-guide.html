Branch Prediction
같은 if 문이 왜 여덟 배 느려질까

0부터 255까지의 정수 3만 개를 두고 "128 이상이면 더한다"는 루프를 돌립니다. 값도, 코드도, 더하는 횟수도 같습니다. 그런데 배열을 미리 정렬해 두기만 하면 이 문서를 쓴 맥에서 약 8배 빨라졌습니다. CPU는 if 문의 무엇을 보고 이렇게 다르게 움직일까요?

💬 "같은 if문인데 데이터의 순서에 따라 실행 속도가 달라질 수 있습니다."

☕ 읽는 데 ~36분 🧭 우선한 것 · 버린 것 · 생긴 개념 🔬 C · Python · numpy 로 직접 재 봄

목차

  1. 값도 코드도 같은데 순서만 다르다
  2. if 문은 CPU에게 갈림길이다
  3. 선택 ① 명령을 겹쳐서 실행한다
  4. 선택 ② 기다리지 않고 찍고 달린다
  5. 선택 ③ 지나간 결과로 다음을 맞힌다
  6. 직접 재 보기 — 순서가 바꾸는 것
  7. 선택 ④ 분기를 아예 없앤다
  8. Python 에서는 — 어디서 중요해지나
  9. 한 장 요약 치트시트

00값도 코드도 같은데 순서만 다르다

유명한 질문 하나를 이 문서의 맥에서 다시 돌려 본다

2012년 Stack Overflow 에 이런 질문이 올라왔습니다. C++ 로 0~255 사이의 난수 32,768개를 만들고, 128 이상인 값만 더하는 루프를 10만 번 돌렸더니 11.54초가 걸렸습니다. 그런데 루프 전에 배열을 정렬하는 한 줄만 넣으면 1.93초, 약 6배 빨라졌다는 것입니다. 더하는 값의 집합은 똑같고, 덧셈은 순서와 상관없이 같은 답을 냅니다.

같은 실험을 C 로 옮겨 이 문서를 쓴 맥(Apple M4 Pro, Apple clang 17)에서 돌려 봤습니다. 배열 크기는 원래 질문과 같은 32,768개이고, 2만 바퀴를 돌렸습니다. 컴파일 옵션은 -O2 입니다. -O0 · -O1 · -O2 는 컴파일러가 코드를 얼마나 적극적으로 고쳐 빠르게 만들지 정하는 옵션으로, -O0 은 거의 고치지 않고 숫자가 클수록 많이 바꿉니다.

for (int r = 0; r < 20000; ++r)
    for (int i = 0; i < 32768; ++i)
        if (data[i] >= 128)        // 이 if 하나가 주인공
            sum += data[i];

실측 — Apple M4 Pro · Apple clang 17 · -O2 · 분기를 남긴 빌드 (3회 반복, 발췌)

sorted     0.155 ~ 0.159s
unsorted   1.27 ~ 1.32s     # 약 8배

분기(branch)는 if 처럼 조건에 따라 다음에 실행할 명령이 갈리는 지점입니다. 기계어에서 어떻게 생겼는지는 01장에서 봅니다. "분기를 남긴 빌드"는 컴파일러가 이 if 를 다른 모양으로 바꾸지 못하게 막은 빌드라는 뜻입니다. 왜 막아야 했는지는 06장에서 봅니다.

짧은 답부터 하겠습니다. CPU는 if 의 답이 나오기 전에 그다음 일을 미리 시작합니다. 어느 쪽 일을 미리 할지는 이 if 가 지금까지 어떻게 갈렸는지를 보고 추측합니다. 정렬된 배열에서는 "아까와 같은 쪽"이라는 추측이 거의 항상 맞습니다. 섞인 배열에서는 반쯤 틀립니다. 틀릴 때마다 미리 해 둔 일을 버리고 다시 시작하는 비용이 쌓여 8배가 됩니다.

이 문서가 답하는 것

① CPU는 왜 답을 기다리지 않고 추측하나 ② 무엇을 근거로 추측하고, 언제 못 맞히나 ③ 컴파일러가 분기를 없애면 무엇이 달라지나 ④ Python 코드에서는 이 효과가 얼마나, 어디서 보이나. 다 읽으면 "if 문의 비용은 개수가 아니라 예측 가능성에 달렸다"는 말을 메커니즘까지 설명할 수 있습니다.

01if 문은 CPU에게 갈림길이다

기계어로 내려가면 if 는 "비교"와 "조건부 점프"가 된다

📎 용어: 기계어 명령 · 레지스터 · 클럭 사이클

기계어 명령은 CPU가 직접 실행하는 가장 작은 일 단위입니다. "메모리에서 값을 읽어라", "두 값을 비교해라", "저 주소로 점프해라" 같은 것들입니다. 레지스터는 CPU 안에 있는 아주 작은 저장칸입니다. 계산은 메모리가 아니라 레지스터에 올린 값으로 하고, 아래 코드의 w12, x0 같은 이름이 레지스터입니다. 클럭 사이클은 CPU가 한 박자 일하는 시간 단위입니다. 4GHz CPU는 1초에 40억 박자를 치므로 한 사이클은 0.25ns(나노초, 10억 분의 1초)입니다.

위 C 코드를 컴파일러가 if 를 바꾸지 못하게 한 줄을 넣고 -O2 로 컴파일하면, 안쪽 루프의 if 부분은 이렇게 됩니다. ARM64(애플 M 칩이 쓰는 명령 체계)의 기계어이고, 주석은 덧붙인 것입니다.

Apple clang 17 -O2 출력 (발췌, 분기를 남긴 빌드)

ldr   w12, [x0, x11]     ; data[i] 를 읽는다
cmp   w12, #128          ; 128 과 비교한다
b.lt  LBB0_3             ; 작으면 더하기를 건너뛴다   ← 분기
ldrsw x12, [x0, x11]     ; (점프하지 않았으면) 같은 값을 64비트로 읽어
add   x8, x8, x12        ; sum 에 더한다
📎 용어: 분기 (branch)

분기는 조건에 따라 다음에 실행할 명령의 주소가 달라지는 명령입니다. 위의 b.lt 처럼 조건이 맞아 다른 주소로 점프한다(taken), 조건이 안 맞아 바로 아랫줄로 그대로 간다(not taken)고 말합니다. LBB0_3 은 점프할 곳의 주소에 컴파일러가 붙인 이름입니다. 루프의 "다시 처음으로" 도 분기입니다. 그래서 이 루프는 한 바퀴에 분기를 적어도 두 번 만납니다.

여기서 문제가 하나 생깁니다. b.lt 다음에 실행할 명령이 ldrsw 인지 LBB0_3 인지는 바로 앞의 cmp 결과를 봐야 압니다. 그런데 CPU는 그 결과가 나오기 한참 전부터 다음 명령을 가져와야 하는 구조로 되어 있습니다. 왜 그런 구조가 됐는지가 다음 장의 이야기입니다.

02선택 ① 명령을 겹쳐서 실행한다

파이프라인 — 처리량을 위해 "다음 명령을 미리 가져오는" 구조가 생겼다

명령 하나를 실행하는 과정은 여러 단계로 나뉩니다. 교과서에 나오는 고전적인 RISC CPU(명령을 단순하고 크기가 고른 것으로 맞춘 CPU 설계)는 다섯 단계를 씁니다. 메모리에서 명령을 가져오고(IF), 무슨 명령인지 해석하고(ID), 계산하고(EX), 필요하면 메모리에 접근하고(MEM), 결과를 레지스터에 기록합니다(WB).

단계를 하나씩 차례로 밟으면 명령 하나에 다섯 사이클이 걸리고, 그동안 다른 단계의 회로는 놉니다. 그래서 공장 컨베이어 벨트처럼 단계를 겹칩니다. 명령 1이 해석 단계로 넘어가면 그 빈 가져오기 단계에서는 명령 2를 가져옵니다. 이렇게 겹친 구조를 파이프라인이라고 합니다. 벨트가 꽉 차면 매 사이클 명령이 하나씩 끝납니다. 명령 하나가 끝나는 데 걸리는 시간은 그대로지만, 같은 시간에 끝나는 명령 수인 처리량이 늘어납니다.

사이클 → 1 2 3 4 5 6 7 명령 1 IF ID EX MEM WB 명령 2 IF ID EX MEM WB 명령 3 IF ID EX MEM WB ↑ 5번 사이클에는 다섯 단계가 모두 일하고 있다 (명령 1 기록 · 명령 2 메모리 · 명령 3 계산 · …)
🧺 비유

빨래 세 바구니를 세탁기 → 건조기 → 개기 순으로 처리한다고 해 봅시다. 첫 바구니를 다 개고 나서 둘째 바구니를 세탁기에 넣는 사람은 없습니다. 첫 바구니가 건조기에 들어가는 순간 세탁기는 비니, 둘째 바구니를 넣습니다. 한 바구니가 끝나는 시간은 그대로지만, 같은 시간에 끝나는 바구니 수가 늘어납니다.

오늘날 CPU의 파이프라인은 이 그림보다 훨씬 깊고 넓습니다. 명령을 가져와서 실행 단계에 닿기까지 10~20단계쯤 거치고, 한 사이클에 명령을 여러 개씩 가져옵니다. 한 사이클의 길이는 가장 느린 단계에 맞춰야 하므로, 단계를 잘게 나눠 깊게 만들수록 사이클을 짧게, 곧 클럭을 높게 할 수 있습니다. 넓다는 것은 명령 여러 개를 나란히 처리한다는 뜻이고, 그만큼 한 박자에 끝나는 일이 많아집니다.

✅ 우선한 것

처리량

  • 단계마다 다른 명령이 동시에 일한다
  • 이상적으로는 매 사이클 명령이 하나(이상) 끝난다

🗑️ 버린 것

"다음 명령이 무엇인지 안 뒤에 가져온다"는 순서

  • 가져오기 단계는 지금 계산 중인 명령보다 여러 칸 앞서 있어야 한다
  • 분기의 답은 계산 단계에서야 나오므로, 그 전까지 무엇을 가져올지 모르는 구간이 생긴다

가장 단순한 대응은 답이 나올 때까지 가져오기를 멈추는 것입니다. 그러면 파이프라인에 빈칸이 생기는데, 이 빈칸을 거품(bubble, stall)이라고 부릅니다.

사이클 → 1 2 3 4 5 6 cmp IF ID EX b.lt IF ID EX ← 4번 사이클에야 갈 곳이 정해진다 다음 명령 ·· ·· IF ID ← 그때까지 가져올 수 없다 (거품)

단계가 다섯 개면 거품이 두어 칸이지만, 가져오기에서 계산까지 10~20단계인 CPU라면 분기마다 그만큼 멈춥니다. 위 루프는 명령 대여섯 개마다 분기를 두 번 만나므로, 매번 멈추면 파이프라인을 깊게 만든 이득이 거의 사라집니다.

이 선택에서 생긴 개념: 파이프라인 단계, 분기 때문에 다음 명령을 정할 수 없는 상황인 제어 해저드(control hazard), 그리고 그 앞에서 멈춘 빈칸인 거품.

03선택 ② 기다리지 않고 찍고 달린다

분기 예측과 투기적 실행 — 맞히면 공짜, 틀리면 통째로 버린다

멈추지 않으려면 답이 나오기 전에 한쪽을 골라 계속 가져오면 됩니다. CPU는 분기를 만나면 "이번엔 점프할 것이다" 혹은 "그대로 갈 것이다"를 추측하고, 그 길의 명령을 가져와 해석하고 계산까지 해 둡니다. 이 추측을 분기 예측(branch prediction)이라고 하고, 답이 확정되기 전에 미리 실행하는 것을 투기적 실행(speculative execution)이라고 합니다.

미리 계산한 결과는 임시 상태로 둡니다. 레지스터나 메모리에 확정해 쓰지 않습니다. 분기의 답이 나왔을 때 추측이 맞았으면 임시 결과를 그대로 확정하고, 잃은 시간은 없습니다. 틀렸으면 분기 뒤로 들어온 명령을 모두 버리고 맞는 주소에서 다시 가져오기 시작합니다. 이것을 파이프라인을 비운다(flush)고 합니다. 이때 잃는 시간은 대략 가져오기에서 계산까지의 단계 수, 요즘 CPU에서 10~20사이클입니다. 이 문서의 맥에서 어림한 값은 05장 끝에 있습니다.

🚗 비유

갈림길이 많은 길을 달리는데, 내비게이션이 갈림길을 지나고 몇 초 뒤에야 "왼쪽이었습니다"라고 알려 준다고 해 봅시다. 갈림길마다 차를 세우고 안내를 기다리면 너무 느리니, 운전자는 감으로 한쪽을 골라 계속 달립니다. 맞았으면 그대로 갑니다. 틀렸으면 갈림길까지 되돌아와 다른 길로 들어가야 합니다. 되돌아오는 거리가 파이프라인 깊이이고, 감이 얼마나 자주 맞느냐가 전체 속도를 정합니다.

✅ 우선한 것

맞히는 동안 파이프라인이 쉬지 않기

  • 분기의 답을 기다리는 거품이 사라진다
  • 추측이 맞으면 분기는 거의 공짜다

🗑️ 버린 것

"코드가 같으면 시간도 같다"는 성질

  • 같은 기계어라도 추측이 맞는 비율, 곧 데이터에 따라 시간이 달라진다

이 선택에서 생긴 개념: 분기 예측, 투기적 실행, 그리고 틀렸을 때의 비용인 분기 미예측 페널티(branch misprediction penalty).

⚠️ 핵심 통찰

분기의 비용은 분기가 몇 개냐가 아니라 얼마나 잘 맞혀지느냐에 달렸습니다. 늘 같은 쪽으로 가는 분기는 조건을 확인하는 비용 말고는 거의 들지 않고, 동전 던지기 같은 분기는 두 번에 한 번 파이프라인을 비웁니다. 관통 질문의 "데이터 순서"는 바로 이 맞히기 쉬움을 바꿉니다.

04선택 ③ 지나간 결과로 다음을 맞힌다

고정 규칙 → 분기마다 기억 → 패턴까지 기억

찍고 달리기로 했다면 이제 무엇을 근거로 찍을지가 문제입니다. 근거는 점점 풍부해졌습니다.

고정 규칙 — 코드 모양만 보고 찍는다

가장 싼 방법은 정해진 규칙으로 찍는 것입니다. 대표적인 규칙은 "뒤로 가는 분기는 점프한다고, 앞으로 가는 분기는 그대로 간다고 찍는다"입니다. 루프 끝의 "다시 처음으로"는 뒤로 가는 분기이고 거의 항상 점프하니 잘 맞습니다. 이것을 정적 예측이라고 합니다. 하지만 이 규칙은 데이터를 보지 않습니다. 위의 b.lt 는 앞으로 가는 분기라서 늘 "그대로 간다"로 찍히고, 실제로 점프하는 128 미만 원소에서는 모두 틀립니다.

분기마다 최근 경향을 기억한다 — 2비트 카운터

다음 단계는 분기 명령마다 지난 결과를 기억하는 동적 예측입니다. 가장 단순한 것은 직전 결과 하나를 기억했다가 그대로 다시 찍는 방식입니다. 그런데 이 방식은 루프 끝의 분기에서 두 번 틀립니다. 루프를 빠져나갈 때 한 번 틀리고, 그 "빠져나감"을 기억한 채 다음에 루프를 다시 돌 때 첫 바퀴에서 또 틀립니다. 2비트 포화 카운터는 여기에 관성을 붙였습니다. 상태 네 개를 두고, 점프하면 오른쪽으로, 그대로 가면 왼쪽으로 한 칸씩 움직입니다. 양 끝에서는 더 가지 않고 멈춥니다(포화). 그래서 예측이 바뀌려면 두 번 연속 반대로 가야 하고, 한 번 빠져나간 정도로는 예측이 그대로라 두 번째 실수가 없습니다.

강하게 약하게 약하게 강하게 그대로 감 ⇄ 그대로 감 ⇄ 점프함 ⇄ 점프함 (00) (01) (10) (11) └─── 이 둘이면 "그대로 감" ───┘└───── 이 둘이면 "점프함" ─────┘ 점프했다 → 오른쪽 한 칸 그대로 갔다 → 왼쪽 한 칸 양 끝에선 멈춤

이것만으로도 정렬된 배열은 거의 다 맞습니다. 정렬된 배열의 if 결과는 앞쪽 절반이 모두 "128 미만", 뒤쪽 절반이 모두 "128 이상"입니다. 카운터가 틀리는 곳은 128을 넘는 경계와, 다음 바퀴를 위해 배열 처음으로 돌아가는 곳 정도입니다. 32,768번 중 몇 번입니다. 섞인 배열에서는 다음 원소가 128 이상일 확률이 매번 반반이라 카운터가 어느 상태에 있든 절반을 틀립니다.

최근 결과의 패턴까지 기억한다 — 분기 이력

2비트 카운터는 "번갈아 간다", "세 번에 한 번 점프한다" 같은 규칙적인 패턴을 못 맞힙니다. 그래서 분기의 최근 결과 몇 개를 비트열로 기억하고(분기 이력), 이력 패턴마다 카운터를 따로 두는 방식이 나왔습니다. "최근이 점프 · 그대로였으면 다음은 점프" 같은 규칙을 배울 수 있게 된 것입니다. 여러 분기의 결과를 한 이력으로 묶어 분기 사이의 관계까지 쓰는 방식, 신경망의 일종인 퍼셉트론으로 찍는 방식도 나왔고, 오늘날 CPU는 아주 긴 이력을 씁니다.

요즘 예측기가 얼마나 기억하는지 보여 주는 측정이 있습니다. 성능 연구자 Daniel Lemire 는 난수로 만든 같은 분기 결과를 여러 번 반복해 보여 주면서, 몇 개까지 완벽하게 외우는지 쟀습니다. 그 결과 Apple M4 는 약 1만 개, AMD Zen 5 는 약 3만 개였습니다. 패턴이 아무리 무작위처럼 보여도 같은 순서로 다시 나오면 예측기에게는 외울 수 있는 규칙입니다.

✅ 우선한 것

규칙이 있는 데이터는 거의 다 맞히기

  • 한쪽으로 쏠린 분기, 정렬된 데이터, 반복되는 패턴은 미예측이 드물다

🗑️ 버린 것

단순한 회로

  • 분기마다, 이력 패턴마다 카운터를 둘 표가 필요하고, 표가 클수록 칩 면적과 전력을 더 쓴다

이 선택에서 생긴 개념: 2비트 포화 카운터, 분기 이력, 그리고 예측기가 패턴을 "배운다"는 관점.

그래도 한계는 남습니다. 결과에 규칙이 아예 없으면 어떤 예측기도 절반을 틀립니다. 이 한계를 피하는 길이 06장의 네 번째 선택입니다. 그 전에 지금까지의 설명이 실제 숫자와 맞는지 재 봅니다.

05직접 재 보기 — 순서가 바꾸는 것

같은 코드, 같은 크기, 배치만 바꾼 배열

00장의 루프(분기를 남긴 -O2 빌드)에 배치만 다른 배열을 넣어 봤습니다. 모든 배열은 32,768개이고 2만 바퀴를 돕니다. 각 조건은 한 번 먼저 돌려 둔(예열) 뒤에 쟀습니다. "주기 N" 은 난수로 만든 길이 N 짜리 결과 패턴을 배열 끝까지 되풀이한 것이고, "128 이상 확률 p" 는 각 원소가 확률 p 로 128 이상이 되게 만든 것입니다.

한 번 틀릴 때 잃는 시간

예측기가 거의 못 외우는 100만 개 행으로 03장의 비용을 어림해 봅니다. 원소당 시간은 섞인 배열이 약 2.5ns, 정렬이 0.24ns 로 약 2.3ns 차이입니다. 섞인 배열은 두 번에 한 번꼴로 틀린다고 가정하면(이 맥에서는 미예측 횟수를 직접 세지 못했습니다), 한 번 틀릴 때 약 4~5ns 를 잃는 셈입니다. 클럭을 약 4.5GHz 로 잡으면 스무 사이클 안팎으로, 03장의 10~20사이클 범위 위쪽 끝입니다. 늘어난 시간에 분기 말고 다른 손실도 섞여 있을 수 있으니, 넉넉하게 잡힌 어림으로 읽으면 됩니다.

앞 표의 90% 행도 이 값과 맞습니다. 비교 6억 5천만 번 중 10%가 틀리고 한 번에 4~5ns 를 잃는다면 약 0.3초가 늘어나야 하는데, 실제로 정렬 대비 약 0.35초가 늘었습니다. 같은 계산을 70%·50% 행에 하면 실측보다 크게 나옵니다. 첫 표는 32,768개라 예측기가 섞인 패턴의 일부를 외운 상태이고, 틀리는 비율이 높은 행일수록 외워서 줄어드는 몫도 큰 것으로 보입니다.

06선택 ④ 분기를 아예 없앤다

조건부 선택과 벡터화 — 예측할 것이 없으면 틀릴 것도 없다

예측이 안 되는 분기라면 분기를 없애는 방법도 있습니다. 같은 C 소스를 최적화 수준만 바꿔 컴파일해 보면 컴파일러가 실제로 그렇게 합니다.

Apple clang 17 -O1 출력 (발췌) — 점프 대신 고르기

ldr   w12, [x0, x11]      ; data[i] 를 읽는다
cmp   w12, #127
csel  w12, w12, wzr, gt   ; 127보다 크면 그 값, 아니면 0 을 고른다
add   x8, x8, x12         ; 무조건 더한다 (0 이면 더해도 그대로)

csel(x86 에서는 cmov)은 조건에 따라 두 값 중 하나를 고르는 명령입니다. 점프가 아니라서 다음 명령의 주소는 늘 같고, 예측할 것이 없습니다. C 로 쓰면 sum += (data[i] >= 128) ? data[i] : 0; 과 같습니다. 이렇게 점프 대신 값을 고르는 명령을 조건부 선택(conditional select)이라 하고, 컴파일러가 if 를 이런 모양으로 바꾸는 변환을 if-conversion, 이렇게 짠 코드를 branchless 코드라고 부릅니다.

-O2 에서는 한 걸음 더 갑니다. 128비트 레지스터에 값 4개를 한꺼번에 담아 한 명령으로 비교합니다. 비교 결과로 "참이면 비트가 전부 1, 거짓이면 전부 0"인 마스크를 만들고, 값과 AND 하면 128 이상인 값만 남고 나머지는 0이 됩니다. 그것을 한꺼번에 더합니다. 여러 데이터를 명령 하나로 처리하는 이 방식을 SIMD, 루프를 이렇게 바꾸는 것을 벡터화라고 합니다.

Apple clang 17 -O2 출력 (발췌) — 4개씩 비교하고 마스크로 거른다

ldp     q17, q18, [x12, #-32]   ; 값 8개를 레지스터 두 개에 읽는다
cmgt.4s v21, v17, v0            ; 4개를 한 번에 127 과 비교 → 마스크
and.16b v17, v17, v21           ; 마스크로 거른다 (아니면 0)
uaddw.2d v2, v2, v17            ; 누적한다
; … 같은 패턴이 반복되고, 분기는 루프 끝의 "다시 처음으로" 하나뿐

실측 — 같은 소스, 최적화 수준별 (32,768개 × 2만 바퀴, 3회 반복)

빌드정렬 / 섞임if 의 모양
-O00.39s / 0.73 ~ 0.78s (약 2배)분기 그대로, 원소마다 메모리를 여러 번 오간다
-O10.15s / 0.15scsel 로 바뀜

분기가 사라지자 정렬 여부가 시간에 아무 영향도 주지 않았습니다. 그래서 00장 실험에서는 if 안에 아래 한 줄을 넣어 컴파일러가 if 를 바꾸지 못하게 막았습니다. 아무 일도 하지 않는 빈 어셈블리지만, 컴파일러는 이 줄을 "건드리지 말 것"으로 다루므로 if 를 계산으로 바꾸지 못합니다.

if (data[i] >= 128) { __asm__ volatile(""); sum += data[i]; }

-O0 의 차이가 2배에 그친 것도 볼 만합니다. 최적화를 끄면 변수를 매번 메모리에 썼다가 다시 읽으므로 원소 하나에 드는 다른 일이 많습니다. 분기에서 잃는 시간이 같은 자릿수여도, 나머지 일이 크면 전체에서 차지하는 비율이 작아집니다.

✅ 우선한 것

데이터와 상관없이 일정한 속도

  • 예측할 분기가 없으니 미예측도 없다
  • SIMD 까지 가면 분기를 잘 맞히던 정렬 배열보다도 빠르다(이 속도 이득은 분기를 없앤 덕이 아니라 4개씩 동시에 처리한 덕이다)

🗑️ 버린 것

필요한 쪽만 계산하는 경제성

  • 버릴 쪽까지 늘 계산한다. 한쪽이 무거우면 손해다
  • 잘 맞혀지는 분기라면 이득이 없거나 오히려 느려진다
  • 어느 모양이 될지는 컴파일러가 정한다

이 선택에서 생긴 개념: 조건부 선택(cmov / csel), branchless 코드, SIMD 와 벡터화.

⚠️ 흔한 오해 — "branchless 가 항상 빠르다"

조건부 선택은 양쪽 값을 다 준비한 뒤 고르므로, 분기가 잘 맞혀질 때는 이길 이유가 없습니다. 고성능 컴퓨팅 교재 Algorithmica 의 실험에서는 분기가 약 75% 넘게 예측되면 분기 코드가 이겼고, 컴파일러도 비슷한 기준을 써서 cmov 사용 여부를 정한다고 설명합니다. 이 문서의 실측에서는 csel 버전(0.151s)과 정렬 배열의 분기 버전(0.156s)이 거의 같았습니다.

07Python 에서는 — 어디서 중요해지나

효과는 남아 있지만, 원소마다 하는 다른 일에 묻힌다

같은 실험을 Python 3.12 로 해 봤습니다. Python 의 if 는 바이트코드(인터프리터가 하나씩 읽어 실행하는 중간 명령)로 컴파일됩니다. 3.11부터 CPython 은 자주 도는 바이트코드를 자료형에 맞춘 전용 명령으로 바꿔 두고, dis 에 adaptive=True 를 주면 바뀐 모습이 보입니다. 그래서 루프를 여러 번 돌린 뒤에 봤습니다. 이름 끝에 _INT 처럼 자료형이 붙은 것이 바뀐 전용 명령입니다. 이름 오른쪽 숫자는 명령의 인자이고, (to N) 은 점프할 위치입니다. 여기서 볼 것은 POP_JUMP_IF_TRUE 한 줄입니다.

python 3.12 · dis.dis(loop, adaptive=True) (발췌)

FOR_ITER_LIST        13 (to 40)
STORE_FAST__LOAD_FAST  2 (x)
LOAD_FAST__LOAD_CONST  2 (x)
LOAD_CONST            2 (128)
COMPARE_OP_INT       92 (>=)
POP_JUMP_IF_TRUE      1 (to 28)   # ← if 가 바이트코드의 분기가 된다
JUMP_BACKWARD         9 (to 10)
LOAD_FAST__LOAD_FAST  1 (total)   # 28: 참이면 여기로
...

바이트코드의 분기는 인터프리터의 C 코드 안에서 다시 진짜 분기가 됩니다. CPython 3.12 소스에서 POP_JUMP_IF_TRUE 는 if (Py_IsTrue(cond)) { JUMPBY(oparg); }(발췌) 로 구현돼 있습니다. 이 C 의 if 는 데이터를 그대로 따라 갈리므로, 섞인 배열에서는 CPU의 예측기가 C 실험과 같은 어려움을 만납니다. 3.13부터는 이 if 가 곱셈으로 바뀌었지만, 다음에 실행할 바이트코드가 이 결과에 따라 갈리므로 그 바이트코드를 처리하는 C 코드로 가는 점프는 여전히 데이터를 따라 갈립니다.

실측 — Python 3.12.12 · 0~255 정수 32,768개 · 한 번 훑는 시간 (순서를 바꿔 2회 측정, ms = 1천 분의 1초 · µs = 100만 분의 1초)

방식정렬 / 섞임차이
for + if0.39 ~ 0.41ms / 0.48 ~ 0.51ms약 1.25배
sum(x for x in d if x >= 128)0.42 ~ 0.44ms / 0.51 ~ 0.54ms약 1.2배
numpy a[a >= 128].sum()13 ~ 14µs / 55 ~ 59µs약 4배
numpy np.where(a >= 128, a, 0).sum()15 ~ 16µs / 15 ~ 16µs차이 없음

순수 Python 루프에서도 차이는 있지만 25% 안팎입니다. 원소당 시간으로 바꾸면 정렬일 때 약 12ns, 섞였을 때 약 15ns 입니다. 늘어난 3ns 는 C 에서 본 미예측 비용과 같은 자릿수이지만, 인터프리터가 원소마다 하는 다른 일, 곧 리스트에서 객체를 꺼내고 바이트코드를 하나씩 해석하고 비교 결과 객체를 다루는 일이 12ns 나 되니 비율이 작아집니다. 06장의 -O0 와 같은 구조입니다.

numpy 는 반복을 C 로 돌리므로 차이가 다시 커집니다. 불리언 마스크로 고르는 a[a >= 128] 은 섞인 배열에서 약 4배 느렸습니다. 다만 이 4배를 분기 예측 하나로 설명하면 틀립니다. numpy 는 마스크에서 False 구간을 건너뛰고 True 가 이어진 구간을 찾아, True 구간마다 복사 함수를 한 번씩 부릅니다. 마스크를 미리 만들어 두고 고르는 부분만 재면 이렇습니다.

실측 — numpy 2.4.0 · 32,768개 · a[mask] 만 측정

마스크True 구간 (True · False 합친 구간)시간
정렬1 (2)약 9µs
짧은 주기 패턴 (예측 쉬움)약 8천 (약 1만 6천)약 35µs
섞임 (예측 어려움)약 8천 (약 1만 6천)약 53µs

구간 수가 큰 몫을 하고, 구간 수가 같을 때는 구간 경계를 맞히기 어려운 쪽이 그 위에 미예측 비용을 더 냅니다. 반면 np.where 는 양쪽 값을 모두 계산해 고르는 방식이라 배치와 상관없이 같은 시간이 걸렸습니다. 06장의 조건부 선택을 라이브러리 수준에서 고른 셈입니다.

⚠️ 함정 — 빠르게 하려고 정렬하지 말 것

첫째, 정렬 자체가 한 번 훑는 것보다 비쌉니다. Stack Overflow 질문 본문에도 나중에 편집자가 덧붙인 문장으로 이 점이 적혀 있습니다. 둘째, Python 에서는 정렬이 오히려 느리게 만들 수 있습니다. 0~100만 사이 정수 200만 개로 같은 루프를 돌리니 섞인 리스트는 원소당 약 15ns, 정렬한 리스트는 약 41~44ns였습니다.

리스트에는 정수 객체의 주소가 들어 있어서, 정렬하면 메모리에 만들어진 순서와 다른 순서로 객체를 찾아가게 됩니다. 그러면 CPU 캐시(최근 읽은 메모리와 그 근처를 CPU 가까이에 복사해 두는 작은 고속 메모리)를 계속 놓칩니다. 분기 예측이 아니라 메모리 배치에서 오는 비용입니다.

✅ 실무 감각 — Django 서비스에서 이게 보이는 곳

요청 하나를 처리하는 시간은 대부분 DB·네트워크를 기다리는 ms 단위이고, 분기 미예측은 한 번에 ns 단위입니다. 뷰 코드의 if 몇 개를 걱정할 일은 아닙니다. 이 효과가 보이는 곳은 수십만~수백만 원소를 도는 반복이 C 로 내려가는 곳입니다. numpy·pandas 필터, 정렬·압축·파싱 같은 C 확장, 그리고 DB 엔진이 수많은 행에 조건을 거는 필터 루프가 그렇습니다. DB 연구에서도 메모리 안의 행에 조건을 거는 알고리즘의 성능이 분기 미예측에 크게 좌우된다는 결과가 있습니다.

  1. 1단계 — 순수 Python 루프라면if 순서보다 루프 자체가 비쌉니다. 반복이 무겁다면 numpy 같은 C 수준 연산으로 옮기는 것이 먼저입니다.
  2. 2단계 — numpy 로 옮겼다면마스크 인덱싱과 np.where 가 데이터 배치에 따라 다르게 반응할 수 있습니다. 실제 데이터로 둘 다 재 봅니다.

08한 장 요약 치트시트

같은 if 인데 왜 순서에 따라 속도가 다를까

CPU는 if 의 답을 기다리지 않고 지나간 결과의 패턴으로 추측해 앞서 달리기 때문이다. 파이프라인을 쉬지 않게 하려고 투기적으로 실행하는데, 추측이 틀리면 미리 한 일을 버리고 파이프라인을 다시 채운다. 정렬된 데이터처럼 결과에 규칙이 있으면 예측기가 거의 다 맞히고, 무작위면 절반을 틀린다. 그래서 같은 값, 같은 코드라도 순서가 실행 시간을 바꾼다. 컴파일러가 분기를 조건부 선택이나 SIMD 로 바꿔 없애면 순서는 더 이상 상관없다.

선택우선한 것 / 버린 것생긴 개념
① 명령을 겹친다처리량 / 다음 명령을 안 뒤에 가져오는 순서파이프라인, 제어 해저드, 거품
② 찍고 달린다파이프라인을 쉬지 않게 하기 / 코드가 같으면 시간도 같다는 성질분기 예측, 투기적 실행, 미예측 페널티
③ 지나간 결과로 맞힌다규칙 있는 데이터의 적중률 / 단순한 회로(이력 표의 면적 · 전력)2비트 카운터, 분기 이력, 패턴 학습
④ 분기를 없앤다데이터와 무관한 일정한 속도 / 필요한 쪽만 계산하는 경제성cmov · csel, branchless, SIMD

분기의 비용개수가 아니라 예측 가능성. 늘 같은 쪽이면 거의 공짜고, 정렬이 빠른 것도 값이 아니라 if 결과에 규칙이 생겨서다
