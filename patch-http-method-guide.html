HTTP 메서드는 왜 다섯 개뿐일까

GET · POST · PUT · PATCH · DELETE. 우리는 이 다섯 개를 마치 알파벳처럼 세트로 외운다. 그런데 이 목록은 누가 정했고, 왜 하필 다섯 개일까? 실제 등록된 HTTP 메서드는 40개가 넘고, 그중 PATCH는 웹이 태어난 지 19년이나 지나서야 합류한 늦둥이다.

💬 "왜 GET, POST, PUT, PATCH, DELETE밖에 없나요? HTTP Method는 고정된 목록이 아님. PATCH가 추가된 것도 비교적 최근임."

☕ 읽는 데 ~30분 🕰️ 1991 GET → 2026 QUERY 🐍 Django·DRF 실무로 연결

00이름만 바꿨는데 전화번호가 사라졌다

가장 흔한 첫 만남

회원 프로필 수정 화면을 만든다. 유저가 이름만 고쳤다. 프론트엔드는 착실하게 바뀐 것만 보낸다.

❌ 나쁜 예 — 부분만 담아 보낸 PUT

PUT /api/v1/users/42
Content-Type: application/json

{"name": "김민수"}

그리고 배포 다음 날, 고객센터로 문의가 들어온다. "전화번호랑 이메일이 왜 다 지워졌죠?"

서버가 버그를 낸 게 아니다. 스펙대로 동작한 것이다. PUT의 본문은 "이 리소스가 앞으로 이런 모습이어야 한다"는 완성된 새 상태다. phone이 본문에 없다는 말은 "전화번호를 안 보냈다"가 아니라 "전화번호가 없는 상태로 만들어라"에 가깝다.

여기서 자연스러운 질문이 나온다. 그럼 "일부만 바꿔라"는 어떻게 말하지? 바로 그 자리를 메우려고 2010년에 뒤늦게 합류한 메서드가 PATCH다. 그런데 이 이야기를 제대로 하려면 그 앞의 더 큰 오해부터 풀어야 한다 — 애초에 HTTP 메서드는 다섯 개가 아니다.

⚠️ "그런데 우리 DRF에선 안 지워지던데요?"

맞다. DRF ModelViewSet의 PUT은 required=True 필드가 빠지면 400을 내고, required=False 필드가 빠지면 validated_data에 그 키가 없어서 기존 값을 그대로 둔다. 즉 DRF는 PUT을 스펙보다 관대하게, 사실상 PATCH처럼 처리한다. 위 사고는 프레임워크가 막아주지 않는 곳에서 난다 — 직접 put()을 구현했거나, 외부 서비스의 PUT API를 호출하거나, 요청 본문을 모델에 그대로 덮어쓸 때다. "PUT의 빠진 필드는 지워지는 게 맞다"를 원칙으로 삼되, 내 프레임워크가 실제로 어떻게 처리하는지는 따로 확인해야 한다.

이 문서가 답하는 것

① 왜 우리 눈에는 메서드가 다섯 개로만 보이는가 ② PUT과 PATCH는 정확히 무엇이 다른가 ③ PATCH를 실제로 안전하게 구현하려면 무엇을 지켜야 하는가. 다 읽으면 "PATCH 쓰면 되죠?"에서 "이 API의 PATCH는 어떤 지시서 포맷을 받고, 멱등한가?"로 질문이 바뀐다.

01메서드는 '목록'이 아니라 '레지스트리'다

HTTP 명세는 메서드를 닫힌 목록으로 못 박은 적이 한 번도 없다. 프로토콜 문법상 요청의 첫 단어는 그냥 토큰(공백·특수문자가 없는 문자열)이면 된다. GET이든 PROPFIND든 BREW든 전송 계층에서는 똑같이 유효하다.

대신 IETF(Internet Engineering Task Force — 인터넷 표준을 논의하고 RFC 문서로 확정하는 국제 기구)는 "누구나 아무 단어나 쓰면 서로 못 알아듣는다"는 문제를 레지스트리로 풀었다. 표준의 내용을 정하는 곳이 IETF, 그렇게 정해진 이름들을 명부로 관리하는 곳이 IANA다. 메서드 이름과 그 의미를 IANA(인터넷 번호 할당 기관)가 관리하는 공개 명부에 등록하게 한 것이다.

📎 용어: IANA 레지스트리

IANA는 포트 번호, 미디어 타입(application/json처럼 Content-Type 헤더에 들어가는 "본문의 형식" 이름), HTTP 상태 코드처럼 전 세계가 같은 의미로 써야 하는 이름들의 공식 명부를 관리하는 조직이다. "HTTP Method Registry"는 그중 메서드 담당 명부이고, 새 메서드는 보통 RFC 문서로 의미를 정의한 뒤 여기에 한 줄로 등록된다.

지금 그 명부에는 40개의 메서드가 등록돼 있다. 우리가 아는 다섯 개는 그중 일부일 뿐이다.

⚠️ 핵심 통찰

메서드가 다섯 개로 보이는 건 HTTP의 제약이 아니라 우리가 사는 생태계의 제약이다. 왜 하필 그 다섯 개인지, 서로 맞물린 네 가지 이유를 다음 절에서 하나씩 본다.

02GET 하나에서 40개까지 — 그리고 왜 5개만 보이나

메서드 목록은 계속 자랐고, 심지어 줄어든 적도 있다

  1. 1991HTTP/0.9 — 메서드는 GET 하나요청 한 줄이 전부였다. 헤더도, 상태 코드도, 다른 메서드도 없었다.
  2. 1996RFC 1945 (HTTP/1.0) — GET · HEAD · POST본문에서 정식으로 정의한 건 이 셋. PUT · DELETE · LINK · UNLINK는 "추가로 쓰이기도 하는 것들"로 부록에 언급되는 데 그쳤다. 이 넷 중 다음 판에서 본문으로 올라가는 건 PUT · DELETE 둘뿐이다.
  3. 1997RFC 2068 (HTTP/1.1) — OPTIONS · TRACE 신설, PUT · DELETE 승격규범 본문이 정의한 건 일곱 개 — CONNECT는 아직 없다. 그리고 PATCH · LINK · UNLINK가 부록 §19.6에 실린다. PATCH의 첫 등장이다. 이 부록은 "존재는 알되 다른 구현에 있으리라 믿지는 말라"고 못 박은 자리다.
  4. 1999RFC 2616 — CONNECT 추가, PATCH · LINK · UNLINK 삭제명세가 삭제 사유를 직접 적었다 — "정의는 됐으나 널리 구현되지 않았다". 메서드 목록은 늘기만 하는 게 아니라 줄기도 한다. 그 사례가 바로 PATCH 자신이다.
  5. 1999~2007WebDAV 계열 — 수십 개가 한꺼번에웹을 읽기 전용 문서 저장소가 아니라 공유 파일 서버처럼 쓰려는 시도. PROPFIND · MKCOL · COPY · MOVE · LOCK 등이 이때 RFC로 정의됐다(IANA 레지스트리 자체는 2014년에 신설되며 이들을 소급 수록했다).
  6. 2010RFC 5789 — PATCH 등장L. Dusseault, J. Snell. 1997년 부록에서 잘려나간 지 13년 만의 복귀다. 이번엔 부록이 아니라 자기 이름을 단 독립 RFC로.
  7. 2013RFC 6902 JSON Patch · Rails 4PATCH의 본문 포맷이 표준화되고, Rails 4가 update 라우트의 기본 동사를 PUT에서 PATCH로 바꾸면서 널리 퍼졌다.
  8. 2014RFC 7396 — JSON Merge Patch"바뀐 필드만 담은 JSON"이라는, 우리가 실제로 가장 많이 쓰는 그 방식이 표준이 됐다.
  9. 2022RFC 9110 (HTTP Semantics) — 핵심 8개 재정의GET · HEAD · POST · PUT · DELETE · CONNECT · OPTIONS · TRACE. 1999년에 정리된 여덟 개가 그대로다.
  10. 2026RFC 10008 — QUERYJ. Reschke, J. Snell, M. Bishop. 목록은 지금 이 순간에도 자라고 있다.
⚠️ 흔한 오해

"PATCH는 REST 5대 메서드 중 하나" — 실제로는 핵심 명세의 규범 본문에 한 번도 들어가 본 적이 없는 확장 메서드다. RFC 9110이 정의하는 8개에도, 그 전신인 RFC 2616의 8개에도 PATCH는 없다. 그뿐 아니라 1997년 부록에 실렸던 PATCH는 1999년에 "널리 구현되지 않았다"는 이유로 잘려나갔다. 지금 우리가 쓰는 PATCH는 그로부터 11년 뒤 독립 RFC로 다시 제안돼 살아남은 두 번째 시도다. 표준이 된다는 게 한 번에 끝나는 일이 아니라는 뜻이기도 하다.

그래서 왜 우리 눈엔 다섯 개만 보이나

등록된 40개 중 다섯 개만 일상에 남은 데는 서로 맞물린 이유가 있다.

  1. 브라우저 폼이 두 개만 보낸다HTML <form>의 method 속성은 GET과 POST만 받는다. method="DELETE"라고 써도 브라우저는 알아듣지 못하고 GET으로 처리한다. 그래서 오래된 웹 프레임워크들은 _method=PATCH 같은 숨은 필드를 POST에 실어 보내는 우회책(method override)을 쓴다. 서버 앞단의 미들웨어가 POST 요청에서 그 필드(또는 X-HTTP-Method-Override 헤더)를 발견하면 요청의 메서드를 PATCH로 바꿔치기한 뒤 라우터에 넘긴다 — 네트워크에는 POST로 나가고, 애플리케이션 코드에는 PATCH로 도착하는 셈이다.
  2. 중간 장비가 모르는 메서드를 막는다브라우저와 애플리케이션 서버 사이에는 대개 중계 장비가 여러 겹 있다. 요청을 대신 받아 뒤쪽 서버로 넘겨주는 리버스 프록시(nginx가 대표적), 그 길목에서 공격성 요청을 걸러내는 WAF(웹 애플리케이션 방화벽), 회사 방화벽 같은 것들이다. 이 중 일부는 "아는 메서드만 통과"라는 화이트리스트로 동작해서, 잘 알려지지 않은 메서드는 애플리케이션 서버에 닿기 전에 중간에서 잘린다.
  3. CRUD 교육이 4대 1로 맞춰 가르친다Create · Read · Update · Delete를 POST · GET · PUT/PATCH · DELETE에 짝지어 외우는 게 표준 커리큘럼이다. 이 틀에 안 들어가는 메서드는 배울 계기가 없다.
  4. WebDAV 계열은 용도가 좁았다PROPFIND · MKCOL 같은 메서드는 "웹을 네트워크 드라이브처럼" 쓰는 시나리오용이다. 그 시나리오 자체가 주류가 되지 못했다.

03PUT vs PATCH — 새 사진 vs 수정 지시서

RFC 5789가 PATCH를 도입하며 설명한 차이는 한 문장으로 요약된다. PUT의 본문은 리소스의 수정된 버전 그 자체이고, PATCH의 본문은 현재 리소스를 어떻게 고칠지 적은 지시문의 집합이다. 뒤에 나오는 멱등성·Content-Type·원자성·상태 코드는 전부 이 한 줄에서 파생된 결과일 뿐이니, 헷갈릴 때마다 여기로 돌아오면 된다.

📄 PUT — 교체

"이 리소스는 앞으로 이 모습이다"

  • 본문 = 완성된 새 상태
  • 빠진 필드 = "그 값은 없음"
  • 같은 요청을 100번 보내도 결과 동일
  • 본문 타입: application/json 등 리소스 표현

📝 PATCH — 지시

"현재 상태에서 이렇게 바꿔라"

  • 본문 = 변경 지시서
  • 안 적힌 필드 = "건드리지 마라"
  • 지시 내용에 따라 반복하면 결과가 달라질 수 있음
  • 본문 타입: application/merge-patch+json 등 패치 포맷

✅ 좋은 예 — 이름만 바꾸는 PATCH

PATCH /api/v1/users/42
Content-Type: application/merge-patch+json

{"name": "김민수"}       ← phone·email은 언급이 없으므로 그대로 유지된다

✅ 같은 결과를 PUT으로 하려면 — 전부 다 보내야 한다

PUT /api/v1/users/42
Content-Type: application/json

{
  "name": "김민수",
  "phone": "010-1111-2222",   ← 안 바꾸더라도 반드시 실어야 한다
  "email": "minsu@example.com"
}
🏨 비유

호텔 예약을 바꾼다고 하자. PUT은 예약 카드를 새로 써서 통째로 갈아 끼우는 것이다. 새 카드에 조식란을 안 적었다면 조식은 사라진다. PATCH는 "체크아웃만 하루 미뤄주세요"라는 메모 한 장이다. 나머지 항목은 건드리지 않는다. 다만 이 메모를 실수로 두 번 보내면 이틀이 밀린다. 그래서 실무에서는 메모를 "하루 미뤄주세요"가 아니라 "체크아웃을 8월 3일로 해주세요"라고 쓴다 — 같은 메모가 열 번 도착해도 결과가 같다. 왜 이 차이가 중요한지가 다음 절의 주제다.

04PATCH는 멱등이 아니다

IANA 레지스트리에 Safe: No, Idempotent: No 로 등록돼 있는 이유

📎 용어: 안전(safe)과 멱등(idempotent)

안전한 메서드는 서버 상태를 바꾸지 않는, 읽기 전용 의미를 가진 메서드다(GET · HEAD · OPTIONS · TRACE). 멱등한 메서드는 상태를 바꾸긴 하지만 같은 요청을 두 번 이상 보내도 한 번 보낸 것과 결과가 같은 메서드다(PUT·DELETE 그리고 안전한 메서드 전부). 멱등성은 "응답이 같다"가 아니라 "서버에 남는 상태가 같다"는 뜻이다.

멱등성이 중요한 건 재시도 때문이다. 클라이언트가 요청을 보냈는데 응답이 오기 전에 네트워크가 끊겼다고 하자. 서버가 처리를 마쳤는지 클라이언트는 알 방법이 없다. 이때 메서드가 멱등하다면 그냥 다시 보내면 된다. 멱등하지 않다면, 재시도는 두 번 실행의 위험을 진다.

재시도는 내가 코드를 안 짜도 이미 일어나고 있다. 유저가 버튼을 두 번 누르고, 모바일 앱의 HTTP 라이브러리가 타임아웃 시 자동으로 다시 보내고, 프론트엔드 데이터 라이브러리가 실패한 요청을 백오프로 재시도하고, Celery 같은 작업 큐가 실패한 태스크를 재실행한다. 그래서 "이 엔드포인트를 두 번 보내면 어떻게 되나"는 선택 과목이 아니라 모든 상태 변경 엔드포인트가 답해야 하는 질문이다.

PATCH가 멱등하지 않은 이유는 지시서에 '상대적인 변경'을 적을 수 있기 때문이다. 배열 끝에 값을 덧붙이는 JSON Patch 연산을 보자.

📎 잠깐 — PATCH 본문에는 표준 문법이 두 가지 있다

하나는 Merge Patch(application/merge-patch+json) — 바꿀 필드만 담은 평범한 JSON이고, 앞 절 예제가 이것이다. 다른 하나는 JSON Patch(application/json-patch+json) — {"op": "연산", "path": "위치", "value": 값} 객체를 순서대로 나열한 배열이다. 멱등성이 깨지는 장면은 JSON Patch에서 가장 선명하므로 여기서 먼저 쓴다. 두 포맷의 전체 비교는 바로 다음 절에 있다.

⚠️ 멱등하지 않은 PATCH — 두 번 보내면 두 번 붙는다

PATCH /api/v1/users/42
Content-Type: application/json-patch+json

[{"op": "add", "path": "/tags/-", "value": "vip"}]
                          ↑ "-" 는 "배열의 끝에 추가"라는 뜻

# 1회: tags = ["신규", "vip"]
# 2회: tags = ["신규", "vip", "vip"]   ← 상태가 달라졌다

✅ 멱등한 PATCH — 절대값을 지정하면 몇 번을 보내도 같다

PATCH /api/v1/users/42
Content-Type: application/merge-patch+json

{"grade": "vip"}

# 1회: grade = "vip"
# 2회: grade = "vip"   ← 동일
✅ 실무 감각

명세가 "PATCH는 멱등하지 않다"고 말하는 건 "멱등할 수 없다"가 아니라 "멱등하다고 가정하지 마라"는 뜻이다. 절대값만 담는 Merge Patch 방식으로 API를 설계하면 실질적으로 멱등해진다.

05지시서의 언어 — Merge Patch vs JSON Patch

PATCH의 Content-Type은 '리소스의 타입'이 아니라 '지시서의 문법'이다

PUT에서 Content-Type: application/json은 "본문이 JSON으로 표현된 리소스"라는 뜻이다. PATCH에서는 의미가 다르다. 본문은 리소스가 아니라 지시서이므로, Content-Type은 그 지시서를 어떤 문법으로 읽어야 하는지를 가리킨다. 표준화된 문법이 둘 있다.

JSON Merge Patch (RFC 7396)

바뀔 필드만 담은 JSON을 그대로 보낸다. 우리가 실무에서 "PATCH 쓴다"고 할 때 대부분 이것이다.

Content-Type: application/merge-patch+json

{
  "name": "김민수",
  "phone": null        ← null 은 "이 키를 삭제하라"는 뜻
}
⚠️ Merge Patch의 구조적 한계

null에 "삭제"라는 의미를 부여했기 때문에, 어떤 필드의 값을 실제 null로 설정하는 것은 Merge Patch로 표현할 수 없다. "삭제"와 "null로 설정"을 구분해야 하는 도메인이라면 이 포맷은 애초에 맞지 않는다. 또 배열은 부분 수정이 불가능하고 통째로 교체된다 — 태그 하나를 추가하려 해도 전체 배열을 다시 보내야 한다.

JSON Patch (RFC 6902)

연산을 순서대로 나열한 배열을 보낸다. add·remove·replace·move·copy·test 여섯 가지가 있고, 위치는 JSON Pointer(/tags/0 같은 경로 문법)로 지정한다.

Content-Type: application/json-patch+json

[
  {"op": "test",    "path": "/grade",  "value": "basic"},
  {"op": "replace", "path": "/grade",  "value": "vip"},
  {"op": "remove",  "path": "/tags/0"}
]
# test 가 실패하면 전체가 적용되지 않는다 — 지시서 안에 조건을 넣을 수 있다
항목JSON Merge PatchJSON Patch
표준RFC 7396 (2014)RFC 6902 (2013)

본문 모양바뀐 필드만 담은 JSON 객체연산 객체의 배열
삭제 표현값을 null로{"op":"remove"}
값을 null로 설정불가능가능
배열 부분 수정불가 — 통째로 교체인덱스 단위로 가능
조건부 적용없음test 연산
읽기 쉬움매우 쉬움어려움 (사람이 손으로 쓰기 번거롭다)
✅ 실무 감각

대부분의 사내 API는 Merge Patch로 충분하다. 필드 단위 수정이 전부이고, 프론트엔드가 만들기도 쉽다. JSON Patch가 값을 하는 건 배열 순서를 다루거나(할 일 목록 재정렬), 읽은 뒤 남이 안 건드렸을 때만 적용되게 하고 싶거나(test 연산으로 "지금 값이 basic일 때만 vip로 바꿔라"를 지시서 안에 넣을 수 있다 — 이 전략을 낙관적 동시성 제어라 하고 07절에서 자세히 본다), 변경 이력을 그대로 기록·재생해야 할 때다. 반대로 단순 CRUD에 JSON Patch를 쓰면 클라이언트와 서버 양쪽에 불필요한 복잡도만 얹힌다.

⚠️ 자주 하는 실수

Merge Patch 문법으로 본문을 보내면서 Content-Type만 application/json으로 두는 경우가 압도적으로 많다. 엄밀히는 어떤 문법의 지시서인지 서버가 알 수 없는 상태다. 실무에서는 대개 그냥 동작하지만(서버가 Merge Patch로 가정하므로), 외부에 공개하는 API라면 정확한 미디어 타입을 쓰거나 문서에 명시해야 한다.

06서버가 지켜야 할 계약 — 원자성과 상태 코드

RFC 5789는 PATCH를 구현하는 서버에 강한 의무 하나를 부과한다.

⚠️ 원자성은 선택이 아니라 의무

서버는 지시서 전체를 원자적으로 적용해야 하며, 부분적으로만 반영된 상태를 절대 외부에 노출해서는 안 된다. 지시서 전체를 적용할 수 없다면 아무것도 적용하지 않아야 한다. 지시가 다섯 개인데 셋째에서 실패했다면, 앞의 둘도 되돌려야 한다.

📎 용어: 원자성(atomicity)

여러 단계로 이뤄진 작업이 "전부 성공" 아니면 "전부 실패" 둘 중 하나로만 끝나는 성질. 중간 상태가 관측되지 않는다는 뜻이기도 하다. 데이터베이스에서 트랜잭션(여러 SQL을 한 덩어리로 묶어, 도중에 실패하면 이미 실행된 것까지 전부 취소 — 이 취소를 롤백이라 한다 — 해 시작 전 상태로 되돌리는 장치)이 보장하는 바로 그 성질이다.

✅ Django에서 원자성 확보 — 트랜잭션으로 감싼다

from django.db import transaction

class UserViewSet(ModelViewSet):
    @transaction.atomic          # 예외가 나면 이 안의 모든 변경이 롤백된다
    def partial_update(self, request, *args, **kwargs):
        return super().partial_update(request, *args, **kwargs)

먼저 settings.DATABASES[...]["ATOMIC_REQUESTS"]를 확인한다. True면 모든 요청이 이미 트랜잭션 안이라 이 데코레이터는 필요 없다. 꺼져 있거나 값이 없으면(기본값은 False) 위처럼 명시적으로 감싼다.

성공은 어떤 코드로 알릴 것인가

200과 204 둘 다 유효하다. 갱신 결과를 클라이언트가 다시 그려야 하면 200 + 갱신된 리소스 표현을, 클라이언트가 이미 결과를 아는 단순 수정이면 204 No Content를 쓴다. 어느 쪽이든 응답에 갱신된 ETag를 같이 실어야 클라이언트가 곧바로 다음 수정을 걸 수 있다 — 왜 그런지는 다음 절에서 본다.

실패를 어떤 코드로 알릴 것인가

"지시서를 못 읽겠다", "읽었는데 지금 상태에 적용할 수 없다", "포맷 자체를 지원하지 않는다"는 서로 다른 실패다. RFC 5789가 권하는 구분은 다음과 같다.

상태 코드언제 쓰는가
400 Bad Request지시서 자체가 깨졌다 — JSON 파싱 실패, op 누락 등
409 Conflict지시서는 유효하나 현재 리소스 상태에 적용할 수 없다 — 없는 경로를 remove 하려는 경우 등
412 Precondition FailedIf-Match 같은 조건부 헤더가 맞지 않았다 (다음 절 참고)
415 Unsupported Media Type서버가 모르는 패치 포맷이다 — JSON Patch만 받는데 merge-patch+json이 왔다
422 Unprocessable Content문법도 맞고 적용도 가능하지만 비즈니스 규칙 위반이다 — 이미 정산된 캠페인의 예산 수정 등
⚠️ DRF는 기본으로 400만 낸다

위 표는 "이렇게 구분해서 내라"는 지시인데, DRF에서 serializers.ValidationError는 전부 400으로 나간다(파서 미스매치만 415가 자동). 409 · 412 · 422는 직접 예외 클래스를 만들어야 한다. 이때 중요한 건 코드 숫자보다 에러 코드 문자열이다 — 프론트엔드가 메시지 문구를 비교하는 대신 코드로 분기해야, 나중에 문구를 바꿔도 화면이 안 깨진다. 구분이 필요한 실패마다 전용 예외를 하나씩 만드는 게 실무 규칙이다.

✅ 실무 감각 — Accept-Patch

명세는 PATCH를 지원하는 리소스의 OPTIONS 응답에 Accept-Patch: application/merge-patch+json 헤더를 넣어야 한다(SHOULD)고 정한다. 415를 반환할 때도 마찬가지다 — 클라이언트가 뭘 보내야 하는지 알게 된다. 대부분의 사내 API는 문서로 대신하지만, 적어도 415와 함께 주는 습관은 들일 만하다.

07동시 수정 — ETag와 If-Match

부분 수정은 안전해 보이지만, 오히려 충돌을 눈에 안 띄게 만든다

PATCH는 "내가 건드린 필드만 바꾸니까 남과 안 부딪힌다"는 인상을 준다. 서로 다른 필드를 고친다면 실제로 그렇다. 문제는 같은 필드를 동시에 고칠 때다.

lost update — 두 사람이 같은 필드를 동시에 고칠 때 [A] [서버] [B] ───────────────────────────────────────────────────── GET ───────────▶ grade = "basic" grade = "basic" ◀─────── GET A와 B 모두 "basic"을 읽은 상태로 각자 화면을 띄웠다 PATCH grade=vip ─▶ grade = "vip" grade = "gold" ◀─────── PATCH grade=gold ▲ A가 쓴 "vip"는 흔적도 없이 사라졌다 B는 A의 변경을 본 적조차 없다
📎 용어: ETag

ETag는 서버가 리소스의 현재 버전에 붙여주는 지문(fingerprint)이다. 내용이 바뀌면 값도 바뀐다. 보통 콘텐츠 해시나 updated_at 타임스탬프로 만든다. 클라이언트는 이 값을 If-Match 헤더에 되돌려 보내 "내가 읽었을 때 그 버전 그대로일 때만 적용해라"라고 조건을 걸 수 있다.

✅ 좋은 예 — 읽을 때 받은 지문을 쓸 때 되돌려 보낸다

# 1) 읽기 — 서버가 현재 버전의 지문을 준다
GET /api/v1/users/42
  → 200 OK
    ETag: "v7-9f2c1a"

# 2) 수정 — 그 지문일 때만 적용하라고 조건을 건다
PATCH /api/v1/users/42
  If-Match: "v7-9f2c1a"
  Content-Type: application/merge-patch+json

  {"grade": "vip"}

  → 200 OK
    ETag: "v8-3b7e02"    # 갱신된 새 지문 — 다음 수정은 이 값으로 If-Match
  → 412 Precondition Failed   # 누군가 먼저 바꿈 → 다시 읽고 재시도
✅ 실무 감각

응답에 갱신된 ETag를 반드시 다시 실어야 한다. 안 그러면 클라이언트는 방금 자기가 바꾼 리소스의 새 지문을 몰라, 연속으로 수정할 때마다 GET을 한 번 더 해야 한다.

이 방식을 낙관적 동시성 제어라 부른다 — 미리 잠그지 않고, 충돌이 났을 때만 거부하는 전략이다. 행을 미리 잠그는 SELECT ... FOR UPDATE와 달리 잠금 시간이 0이라 처리량이 높다. 협업 편집 화면이나 여러 담당자가 같은 캠페인을 만지는 어드민처럼 동시 편집이 실제로 일어나는 화면이라면, PATCH 도입과 함께 검토할 가치가 있다. 단순 개인 설정 페이지에는 과하다.

08Django·DRF 실무 — partial=True 와 '미전송 vs null'

Django REST Framework에서 ModelViewSet은 PUT을 update()에, PATCH를 partial_update()에 연결한다. 둘의 차이는 딱 한 곳, 시리얼라이저에 넘기는 partial 플래그다.

# DRF 내부 동작을 단순화하면 이렇다
serializer = self.get_serializer(instance, data=request.data, partial=partial)
#                                                        ↑ PUT은 False, PATCH는 True
📎 partial=True가 실제로 하는 일

partial=True는 필수 필드 검증을 건너뛰게 만든다. required=True인 필드가 요청 본문에 없어도 검증이 통과하고, validated_data에는 실제로 보내온 키만 담긴다. 즉 "안 보낸 필드"는 아예 validated_data에 존재하지 않는다 — None으로 채워지는 게 아니다. 이 구분이 다음 함정의 핵심이다.

함정 ①: .get()은 '안 보냄'과 'null'을 구분하지 못한다

❌ 나쁜 예 — 안 보낸 필드가 조용히 지워진다

def patch(self, request, pk):
    user = User.objects.get(pk=pk)
    user.name = request.data.get("name")     # 키가 없으면 None → 이름이 날아간다
    user.phone = request.data.get("phone")   # 00절의 그 버그가 PATCH 이름표를 달고 재현된다
    user.save()

✅ 좋은 예 — 키의 '존재 여부'로 판단한다

def patch(self, request, pk):
    user = User.objects.get(pk=pk)
    changed = [f for f in ("name", "phone") if f in request.data]
    # 키의 존재로 판단 — null 을 명시적으로 보낸 경우는 반영된다
    for field in changed:
        setattr(user, field, request.data[field])
    user.save(update_fields=changed)   # 실제로 바뀐 컬럼만 UPDATE 문에 담긴다

DRF의 partial_update()를 그대로 쓰면 이 처리를 시리얼라이저가 대신해 준다. 직접 patch()를 구현할 때만 조심하면 된다.

⚠️ Merge Patch의 null 규칙과 Django 모델의 충돌

Merge Patch 표준에서 null은 "키를 삭제하라"는 뜻이지만, Django 모델의 null=True 컬럼에서는 "값을 NULL로 저장하라"가 자연스러운 해석이다. 대부분의 API는 후자로 구현한다 — 틀린 건 아니지만 표준과는 다른 해석이므로, 외부 공개 API라면 문서에 어느 쪽인지 반드시 적어야 한다.

함정 ②: 상대적 변경은 PATCH여도 멱등하지 않다

# 조회수 증가를 PATCH 엔드포인트로 노출한다면
Post.objects.filter(pk=pk).update(view_count=F("view_count") + 1)
# F() 는 DB 레벨에서 "현재값 + 1"을 계산해 경합을 막아준다.
# 하지만 "현재값 기준 상대 변경"이므로, 요청이 두 번 도달하면 2가 오른다.
# 재시도 가능한 클라이언트를 상대한다면 요청 식별자로 중복을 걸러야 한다.
⚠️ DRF에 merge-patch+json을 그대로 보내면 415가 난다

05절에서 "정확한 미디어 타입을 쓰라"고 했지만, 여기엔 함정이 하나 있다. DRF의 기본 파서 JSONParser는 media_type = "application/json"이라, 프론트에서 Content-Type: application/merge-patch+json으로 보내면 뷰에 닿기도 전에 415가 떨어진다. 둘 중 하나를 고른다.

① 사내 API라면 그냥 application/json을 쓰고, "이 엔드포인트의 PATCH 본문은 Merge Patch 규칙을 따른다"를 API 문서에 적는다 — 대부분 이걸로 충분하다. ② 외부 공개 API라 미디어 타입을 정확히 쓰고 싶다면 파서를 하나 더 붙인다.

class MergePatchJSONParser(JSONParser):
    media_type = "application/merge-patch+json"

class UserViewSet(ModelViewSet):
    parser_classes = [JSONParser, MergePatchJSONParser]
✅ 우리 스택으로 정리하면

① 부분 수정 엔드포인트는 PATCH + partial_update로 두고, ② 지시서는 절대값만 담는 Merge Patch 스타일로 제한하고, ③ @transaction.atomic으로 감싸 원자성을 지키고, ④ 동시 편집이 실제로 일어나는 리소스에만 If-Match를 얹는다. 이 네 가지면 실무의 90%는 덮인다.

09새 메서드는 어떻게 태어나는가 — QUERY 사례

PATCH가 2010년에 합류했듯, 2026년에도 새 메서드가 들어왔다

"HTTP 메서드는 고정된 목록이 아니다"라는 말의 가장 좋은 증거는 지금 막 일어난 일이다. 검색 API를 만들어 본 사람이라면 익숙할 딜레마에서 출발한다.

  1. GET으로 하자니 조건이 URL에 안 들어간다필터가 20개짜리 검색이면 쿼리 스트링이 수 KB가 된다. 게다가 HTTP 명세는 GET 요청의 본문에 일반적으로 정의된 의미가 없다고 못 박아 두었다. 명세가 의미를 정의하지 않았다는 건 구현체가 그 본문을 어떻게 다뤄도 규격 위반이 아니라는 뜻이다. 실제로 상당수의 프록시·CDN·HTTP 클라이언트 라이브러리는 GET의 본문을 그냥 떼어 버리거나 아예 전송하지 않는다 — 내 서버가 읽을 줄 알아도 본문이 도착하지 않는다.
  2. POST로 하자니 캐시도 재시도도 못 한다POST는 안전하지도 멱등하지도 않다고 선언돼 있다. 그래서 프록시와 CDN(전 세계에 분산된 캐시 서버망 — 같은 응답을 매번 원 서버까지 가지 않고 가까운 곳에서 돌려준다)은 응답을 캐시하지 않고, 클라이언트는 타임아웃 시 자동 재시도를 못 한다. 실제로는 그냥 읽기 작업일 뿐인데도.
  3. 그래서 새 메서드를 만든다본문을 실을 수 있고, 안전하며 멱등한 메서드. 이것이 QUERY다. 2026년 RFC 10008로 표준이 됐다(J. Reschke, J. Snell, M. Bishop).
QUERY /api/v1/contents
Content-Type: application/json
Accept: application/json

{
  "categories": ["뷰티", "홈리빙"],
  "follower_range": [10000, 500000],
  "period": {"start": "2026-07-01", "end": "2026-08-01"}
}
# 본문을 쓰지만 읽기 전용이고 멱등하다 → 캐시·재시도 모두 안전
📎 URL이 같은데 본문이 다르면 캐시가 어떻게 구분하나

바로 떠오르는 질문이고, RFC 10008이 실제로 푸는 문제가 이것이다. HTTP 캐시는 보통 URL을 키로 쓰는데, 이 명세는 QUERY 요청의 캐시 키가 요청 본문을 반드시 포함해야 한다(MUST)고 못 박는다. 그래서 같은 주소라도 조건이 다르면 다른 항목으로 저장된다. POST에는 이런 규칙이 아예 없어서 캐시가 손댈 여지 자체가 없었다는 게 차이다.

메서드 하나가 표준이 되는 경로

PATCH와 QUERY는 똑같은 길을 걸었다.

실무에서 반복되는 불편 │ ▼ IETF 워킹그룹에서 문제 제기 · 인터넷 드래프트 작성 │ (draft-ietf-httpbis-... 로 여러 판을 거치며 다듬는다) ▼ RFC 발행 — 의미·안전성·멱등성·오류 처리를 문서로 확정 │ PATCH → RFC 5789 (2010) │ QUERY → RFC 10008 (2026) ▼ IANA HTTP Method Registry 에 한 줄 등록 │ 이름 / Safe / Idempotent / 참조 RFC ▼ 서버·프레임워크·프록시가 구현 ── 여기까지 와야 실제로 쓸 수 있다 │ PATCH 는 이 마지막 단계에 몇 년이 더 걸렸다
⚠️ 표준이 됐다고 바로 쓸 수 있는 건 아니다

메서드는 양쪽 끝과 그 사이 모두가 알아야 동작한다. 클라이언트, 로드밸런서, 리버스 프록시, WAF, 웹 서버, 애플리케이션 프레임워크 — 하나라도 모르는 메서드를 거부하면 요청은 서버에 닿지 않는다. PATCH가 2010년 표준화 이후에도 한동안 POST + _method=PATCH로 쓰인 1차 원인은 브라우저 폼의 GET/POST 제약(02절)이고, 중간 장비의 화이트리스트는 그 위에 얹힌 두 번째 관문이다.

📎 용어: 로드밸런서

02절에서 본 리버스 프록시·WAF에 더해 로드밸런서(같은 역할을 하는 서버 여러 대에 요청을 나눠 보내는 장비)도 같은 길목에 선다. 관문이 많을수록 새 메서드가 끝까지 도달하기 어려워진다.

10한 장 요약 치트시트

왜 다섯 개밖에 없나요?

다섯 개밖에 없는 게 아니라, 다섯 개만 모두가 이해한다. HTTP는 메서드를 닫힌 목록이 아니라 IANA 레지스트리로 관리하고, 거기엔 지금 40개가 등록돼 있다. 우리 눈에 다섯 개만 보이는 건 브라우저 폼(GET·POST만 지원), CRUD 중심 교육, 중간 장비의 화이트리스트가 만든 생태계의 교집합이다.

PATCH가 최근이라는 게 무슨 뜻인가요?

PATCH는 핵심 명세의 규범 본문에 한 번도 들어간 적 없는 확장 메서드이고, 심지어 한 번 잘려나갔다 돌아왔다. 1997년 RFC 2068 부록에 처음 실렸다가 1999년 "널리 구현되지 않았다"는 이유로 삭제됐고, 2010년 독립 RFC 5789로 다시 제안돼 이번엔 살아남았다. 2022년 최신 핵심 명세(RFC 9110)의 8개에도 여전히 없다. 그래도 모두가 쓰는 건, 새 메서드를 계속 받아들이도록 설계된 레지스트리 방식이 의도대로 작동했다는 증거다. 2026년 QUERY가 같은 길을 따라 들어왔다.

기억할 것내용
한 줄 원리PUT의 본문은 새 상태, PATCH의 본문은 변경 지시서
PUT에 일부만 보내면빠진 필드는 "값 없음"이 된다 — 데이터가 지워질 수 있다

지시서 문법 2종merge-patch+json(쉽고 흔함) / json-patch+json(배열·조건부에 강함)
Merge Patch의 null표준상 "키 삭제". 값을 진짜 null로 두는 건 표현 불가 — 구현 시 문서화 필수
서버의 의무원자성 — 전부 적용하거나 전부 적용하지 않는다
성공 응답200(갱신된 표현) 또는 204. 어느 쪽이든 갱신된 ETag를 같이 실는다
실패 코드400 문법 / 409 상태 충돌 / 412 조건 불일치 / 415 모르는 포맷 / 422 규칙 위반
